# 规则优先级与冲突处理规范

## 规范定位与适用范围

统一规则来源、性质、作用域、继承、裁决、例外及冲突处理。

本规范是规则来源、性质、适用范围、优先关系、例外及冲突裁决的唯一主定义。项目修改、读取、实施及交付流程遵循 [AI 修改与交付规范](AgentWorkflow.md)。

本节统一规定 Agent 如何识别适用规则、判断约束强度、处理用户决策与项目规范的关系、协调不同作用域及专项规范、保护已有实现，以及处理规则例外和实际冲突。采用五类规则、分层继承、职责归口、多维裁决及增量治理的方式。在外部强制条件及实际技术可行范围内，由用户决定项目规范及重要业务、架构与技术事项，Agent 负责主动调查、分析、提出推荐及在明确授权范围内实施。规则裁决不构成额外的开发阶段、运行时框架或自动修改授权。

## 适用范围与基本原则

1. **全部有效且适用的规则共同生效。** 本节适用于用户级、项目级、领域级、目录级及特定对象或文件的规范，也适用于通用规范、专项规范、已确认的业务及技术契约、当前任务要求与例外。新增设计、项目调查、实施、静态审查、交付及规范维护均应按实际相关范围判断适用关系。
2. **规则性质、来源、适用范围及授权分别判断。** 不以文件层级、某一关键词、读取顺序或规则的严格程度作为唯一裁决依据。能够共同满足的规则应共同执行，不将正常补充、细化、技术选型和合法兼容视为真实冲突。
3. **保护已确定的硬性架构、业务及授权边界。** Agent 不得因实现便利、个人偏好、性能优化、设计模式、历史代码或局部规范而自行解除约束。用户明确调整项目规则或批准例外时，按其真实决策及有效范围处理，不改变其他仍然适用的约束。
4. **规则裁决以实际证据为依据。** 应读取与当前任务相关的真实规范、用户确认及项目实现，区分有效规则、默认方案、实际技术契约、历史实现、已批准例外和待核实信息。不得将源码现状、注释、示例、其他 Agent 的说法或未确认的讨论建议直接当作正式规范变更依据。
5. 本节统一解释规范之间的协作和冲突处理，不代替各专项规范的技术定义、授权条件及实际业务契约，不因建立规则优先级而降低原有要求、批量整改历史代码或新增项目运行机制。具体任务实施、工具权限及验证权限仍遵守[AI 修改与交付规范](AgentWorkflow.md)。
6. 本节规定规范的逻辑作用域及语义适用方式，不预设 Agent 工具对 AGENTS.md、AGENTS.override.md 或其他文档的实际自动发现、加载、替代及上下文行为。具体规范文档结构、读取机制及维护方式另按用户确认的文档体系确定，不在本节擅自建立规则文件、索引、读取工具或管理框架。

## 规则类型及约束强度

1. **按完整语义划分五类规则。** 同一条款可以同时具有不同性质的子要求，应按各自实际适用条件判断，不机械对整条规则赋予单一强度，也不因本节分类降低已经确定的约束。

| 规则类型 | 含义 | 默认执行方式 | 典型事项 |
|---|---|---|---|
| 硬性约束（Mandatory Rule） | 明确必须遵守的职责、行为、技术或过程边界 | 在实际适用范围内必须遵守，Agent 不得自行突破；项目内部规则的调整或例外须有明确用户决策 | Manager 与 System 单向依赖、权威状态所有权、纯处理边界、必要中文注释、禁止主动编译及运行验证、真实交付 |
| 授权约束（Authorization Rule） | 对特定变更或操作设定明确实施授权条件 | 满足对应授权条件后方可实施，普通任务许可或工具权限不替代专项授权 | 项目文件修改、公共接口及框架改造、UI 交互、额外校验、自动绑定、Git 状态变更 |
| 默认规则（Default Rule） | 缺少其他有效专用约定或合法选型条件时采用的统一方案 | 应采用默认方案；存在有效专用约定、适用既有契约或规则明确允许的选型条件时按其处理 | 新建 EventSystem 默认同步分发、ConfigManager + ConfigSystem 默认架构、基础处理实现默认静态、配置及代码默认目录 |
| 推荐原则（Design Principle） | 指导技术判断的优先倾向及设计依据 | 主动考虑并按实际职责、价值及约束选择，重要取舍纳入相应方案说明 | 组合优先、细粒度职责拆分、积极考虑设计模式、数据驱动、低分配设计 |
| 参考示例（Reference Example） | 辅助理解规则、选型及职责关系的示意 | 根据真实需求使用，不独立产生类型、目录、业务规则及运行机制的实施义务 | 候选目录树、职责数据流、示例类型、算法及代码片段 |

2. **硬性约束必须在其适用条件内执行。** 用户拥有项目内部规则的最终决策权，但 Agent 不得以普通任务授权、低成本实现或其他规则的推荐方式自行放宽硬性约束。条件性要求只在条件成立时执行，例如 Odin Required 只用于真正必需的引用，不因使用“必须”而扩大适用对象。外部强制条件不属于用户可以单方面解除的项目规则。
3. **授权约束不是无条件禁止。** 已满足对应规则的明确授权条件时，可以在批准范围内实施，不属于违反规则或另行建立规则例外。改变授权条件本身、扩大操作范围或跳过既有授权程序，则必须具有相应明确的规则调整或例外决策。具体修改及操作授权由[AI 修改与交付规范](AgentWorkflow.md)和有关专项规范定义。
4. **默认规则具有实际执行约束，不等同于可任意忽略的建议。** 缺少其他有效依据时采用统一默认方案，不仅因个人偏好、代码规模、实现便利或抽象数量而偏离。默认规则已规定其他适用条件的，按条件作出合法选择；例如基础处理实现存在明确多态或独立执行状态需求时可采用普通实例。超出既有合法选型条件或已确认方案的变化仍按实际影响说明及确认，保留各专项明确规定的偏离确认要求。
5. **推荐原则允许有依据的技术取舍。** 必须考虑某项技术或设计问题，不等同于必须采用某种技术实现。例如主动识别适用设计模式属于过程要求，积极采用有设计价值的模式属于设计倾向，不要求每项功能机械套用模式。推荐原则不得推翻硬性约束、明确默认规则、现有稳定契约及已批准方案；重要技术决策遵守[技术实现方案设计与评估规范](../Design/TechnicalDesign.md)。
6. **参考示例不独立产生实施义务。** 不得为配齐示例调用链、目录、类型、字段、参数、事件、状态或算法而虚构需求或擅自实施。示例所解释的正式规则仍具有原有约束力；表格和代码块不自动属于非强制参考，例如明确规定的命名格式、职责及发布权限表和 Odin 父子分组要求继续生效。
7. 规范用语应尽量统一，结合上下文、适用条件及实际语义判断约束性质：

| 常见表述 | 语义参考 |
|---|---|
| 必须、不得、禁止 | 在明确适用条件内表达强制要求或禁止事项 |
| 经确认后、未经授权不得 | 表达实施授权条件 |
| 默认采用、默认使用 | 缺少有效专用约定及其他合法选型条件时执行 |
| 优先采用、优先考虑 | 按具体条款表达默认选择或设计倾向，不仅凭关键词定性 |
| 推荐、建议、鼓励 | 技术设计及选择指导 |
| 可以、允许 | 在实际适用条件及其他规则允许的范围内具有选择权限 |
| 按需、根据实际职责 | 根据真实需求、职责、契约及证据判断 |
| 示例、参考 | 辅助理解规则，不自行增加实施要求 |

8. **重要位置按需标记，不机械逐条贴标签。** 对容易误解的硬性约束、专项授权、默认方案和例外可明确标记性质及适用条件。无需将现有全部条款逐条添加五类标签，不以标签替代完整语义判断，不因未标记而减弱已确定的规则。新增或维护规范时优先保持清晰、稳定且一致的表述。

## 规则来源与有效范围

1. **区分外部强制条件与用户制定的项目规范。** 实际平台及工具权限、适用的安全要求、C# 语言及 Unity 和第三方接口的真实技术条件、适用的许可证等外部义务，是方案可行及合法实施的前提。项目规则、局部文档或用户确认不能使不具备的技术能力成立，也不能解除外部强制条件。存在限制时应说明并提供实际可行的替代方案。
2. 项目内部规则的有效性取决于真实来源、明确适用范围及用户决策依据，不由文件名、标题、存放路径或工具读取顺序单独决定。当前用户的明确要求、已经确认的设计及实施方案、正式项目规范、有效局部约定、项目稳定技术契约分别按其性质作为判断依据。
3. 规则逻辑作用域默认按以下五个层级理解，允许在同一文档内表达不同作用域，不要求每个层级都有独立文件：

| 逻辑作用域 | 主要职责及适用范围 |
|---|---|
| 用户级 | 对用户多个项目适用的共同开发偏好、协作及通用架构规则 |
| 项目级 | 当前项目的实际技术环境、框架、架构及项目专用约定 |
| 领域级 | 指定公共框架、业务领域或其他具有独立职责的功能范围 |
| 子目录级 | 领域内部或其他明确局部范围的专用约定 |
| 特定对象或文件 | 指定类型、组件、对象、资源、文件、生成或适配实现的特殊契约 |

4. 规则作用域与约束强度是独立维度。每个作用域均可包含硬性约束、授权约束、默认规则、推荐原则及参考示例；下层规则更加具体，不自动拥有解除上层硬性约束或授权条件的权限。实际适用关系遵循本节“上层规范与局部规范”。
5. 对跨多个项目、领域、目录或职责的任务，应分别识别各部分实际适用规范及共同协作契约，不将某一局部规则推广到其他范围。调用其他领域的合法能力时遵守其公开契约，不因此自动继承被调用领域的全部内部代码组织及风格规则。
6. **不能确认的规则不得假定为不存在、已满足或已失效。** 适用规范不可读取、来源或生效条件不明、授权依据不足时，应说明实际调查范围和不确定性；关键规则无法确认且影响实施时，暂停无法确定合规性的部分，按本节冲突处理原则提供可行的独立分析或已授权工作。

## 统一规则优先级及裁决原则

1. **采用多维裁决型规则模型，而非无条件的单一覆盖排序。** 判断当前任务及具体决策时，应结合以下顺序核对相关约束、有效决策、项目契约和技术选型。表中顺序表示判断路径及各项作用，不表示前一项可以无条件废止后一项，也不表示低位规则可以随意忽略。

| 判断顺序 | 判断对象 | 实际裁决语义 |
|---|---|---|
| 01 | 外部强制条件及实际技术可行性 | 确认方案是否具有合法、真实的技术及操作前提 |
| 02 | 明确用户决策 | 确定已经确认的业务需求、技术选择、规则变更、适用例外及具体实施授权 |
| 03 | 有效硬性约束与授权约束 | 确认仍须保持的架构、职责、状态所有权、业务契约及各项授权条件 |
| 04 | 有效项目及局部专用约定 | 在不突破其他有效约束的前提下，采用适用的具体规则和明确技术约定 |
| 05 | 已有稳定实现及技术契约 | 合法复用既有框架、接口、配置、目录、调用及维护约定，保护存量，不扩大历史违规 |
| 06 | 通用默认规则 | 缺少适用专用约定、稳定契约或规则已允许的其他选型条件时执行 |
| 07 | 推荐原则与参考示例 | 在有效约束及默认规则允许的范围内指导实际设计和选择 |

2. 用户明确决策可以正常覆盖默认规则及推荐原则；与项目硬性约束或授权规则发生冲突时，应确认其是否明确决定调整对应规则或批准例外，不将普通需求、问题修复或方案偏好解释为隐式覆盖。外部强制条件始终按实际限制处理。
3. **同一事项优先采用有效且更具体的专用约定。** 具体规则应具有明确适用范围及有效依据，且与其他仍然生效的约束共同成立。已有稳定技术实现优先于新建默认技术方案及参考示例，不自动优先于硬性职责、依赖、状态、授权及已经明确替代其契约的用户决策。
4. **各项适用硬性及授权约束应同时满足。** 规范职责归口用于解释特定决策的主要定义，不能替代其他专业规范的适用条件；不得只选择有利于当前实现的条款。存在多个合法技术选择时按已确定的默认及推荐倾向、项目真实需求和技术设计规范评估。
5. 不默认以最新读取、最近修改、文件最长、条款靠后、目录最深、描述最详细、最严格或实现最容易等作为冲突裁决依据。明确的替代、修订、废止或例外声明，仅在其真实生效及适用范围内决定原规则的有效性。不能依据现有规则确定结论时按本节冲突报告机制处理。
6. 规则裁决与实施授权分别检查。即使已经能够确定应适用的规则、合法技术方案或有效例外，项目写入、公共能力改造、UI、校验、资源、外部操作和实际验证仍遵守各自授权及权限约束，不通过裁决结果自动取得实施许可。

## 用户要求与规则约束

1. **用户拥有其项目规范、业务及重要设计的最高决策权。** 在外部强制条件、实际技术能力及操作权限允许的范围内，用户可以确定、调整或废止项目规范、架构原则、业务规则、技术偏好及适用例外。Agent 应主动说明实际问题及候选方案，不擅自以自身偏好代替用户决定。
2. 应根据真实上下文区分以下用户要求的语义。同一指令可以同时明确多项内容，不因语义不同而强制分拆消息或重复请示：

| 用户要求类型 | 核心含义及授权边界 |
|---|---|
| 业务需求 | 确定需要实现的功能、行为及目标，不自动决定全部技术手段 |
| 技术实现要求 | 确定具体实现偏好或技术方案，不自动解除其他职责及授权约束 |
| 项目专用约定 | 确定指定项目或局部范围的稳定规则或技术契约，不自动适用于其他项目 |
| 实施授权 | 允许执行已经明确且可审查的具体修改或操作，不自动成为长期规则变更 |
| 规则例外 | 允许特定约束在明确范围及条件内偏离，不扩展到其他规则及任务 |
| 规范变更 | 正式调整、替代或废止指定长期规则，不自动取得规范文件写入及已有项目迁移授权 |

3. 用户明确指定的合法配置形式、文件位置、技术方案及其他专用约定，优先于通用默认规则和推荐原则；按对应专业规范保持其技术及职责边界。用户没有明确指定的技术细节，由 Agent 按有效规则及实际情况主动设计并推荐，不将普通局部决策全部交由用户。
4. **普通用户要求不自动解除硬性约束。** 当前要求与既有硬性规则发生实际冲突时，应指出相应规则、冲突原因、影响及符合原有规则的候选方案。用户确实需要偏离时，须明确规则调整或例外的意图及范围，并按具体实施方案取得确认。用户已了解冲突及影响并明确批准对应规则决策及实施方案时，不重复请示相同事项。
5. **规则决策与实施授权分别确定。** 认可技术设计、确定长期架构、批准规则例外或讨论规范变更，不自动授权写入项目、修改规范文件、重构历史实现、迁移资源、安装依赖或执行其他操作。多项已明确的相关规则决策、实施及专项授权可以纳入同一方案统一确认，不新增独立审批阶段。
6. 新的明确用户决策仅在实际替代范围内优先于旧决策。必须核对决策对象、适用范围、实际变更意图和成立条件；不得根据消息时间、一次授权、宽泛表达或临时实现推断其他长期规则已经失效。任务恢复或项目条件变化时，核对原有决策及例外是否仍适用。
7. **保持 Agent 的正常技术自主性。** 变量命名、私有方法、普通集合及不改变已确认方案的局部细节由 Agent 在规则允许范围内决定。重要模式、算法、核心契约及设计取舍纳入修改前方案；未确定的业务规则、附加限制、UI 变化、公共影响、硬性约束偏离及长期规范调整由用户明确决策，按既有授权程序实施。
8. 不得将用户的项目规则决策权理解为能够改变客观事实、解除外部限制或虚构实际能力。技术上无法实现、工具不可用或关键前提无法核实时，应如实说明限制及候选方案，不执行无依据的方案，不假装规则或技术冲突已经解决。

## 通用规范与专项规范

1. **采用职责归口与专项协作。** 各规范负责明确的规则定义及专业事项；针对具体决策，应优先识别该事项的主要规范，同时识别涉及的协作规范。主要规范负责当前问题的规则主定义及技术边界，协作规范负责其他实际相关的职责、业务、技术和授权约束，不建立专项规范对通用规范的绝对优先关系。

## 上层规范与局部规范

1. **采用分层继承、增量式组织。** 在明确作用域内，下层规范继承上层全部适用规则，并可按真实职责及技术契约补充、细化或合法覆盖。未单独规定的事项继续遵守有效上层规范，不需要局部文件复制全部通用内容。
2. 规则之间的关系应分别判断：继承表示继续遵守上层适用规则；补充表示增加相容的局部要求；细化表示将通用规则落实为具体契约；覆盖表示在明确范围内采用不同规则或方案。继承、补充和细化通常可共同成立；覆盖须判断原规则的约束强度、有效依据及其他适用条件。

| 上层规则性质 | 局部规范的处理方式 |
|---|---|
| 硬性约束 | 不自动允许覆盖；确需偏离时具有明确用户规则调整或例外决策 |
| 授权约束 | 继续满足原有授权条件；调整授权规则本身须具有明确有效决策 |
| 默认规则 | 有效局部专用约定或合法既有契约可以在相应范围内覆盖，保持其他约束及专项确认要求 |
| 推荐原则 | 根据真实局部需求及技术依据选择适合的实现，不推翻硬性及授权约束 |
| 参考示例 | 按真实职责和契约使用，不自动新增义务 |

3. 下层规范可以规定更具体的开发要求或已经确认的业务及技术契约，但不能仅凭目录层级、规则详细程度、文件名或存在某段文字就认定其具有解除上层硬性或授权约束的权限。已明确批准且可核实的局部长期例外，按真实生效范围执行，不重复请示相同决定。
4. **局部规则不自动传播。** 领域、目录、类型及对象的专用约定仅在明确适用范围内生效。相邻目录、其他领域、同后缀类型、公共框架及其他项目不自动采用该约定；跨领域调用仍遵守共同的公开能力、状态及依赖契约。
5. 新增文件时识别目标目录及相关上层规范；修改文件时识别其实际所属范围、维护来源及相关专项规则；移动或重命名文件时同时核对原位置与目标位置的规范及实际契约。任务涉及多个目录时分别调查各自适用规则，不能用单一目录规则代替其他范围的要求；修改共享接口时还应检查实际调用方及协作契约。
6. 子 Agent、自动化、编辑器及其他间接实施方式同样受实际操作对象及目标范围的规范和授权约束。不得通过切换工作目录、委托其他 Agent 或使用工具绕过适用规则。任务恢复或发生并行修改时重新核对受影响的有效规则及例外，不依据过期内容实施。
7. 局部规范优先记录具有独立价值的职责、专用术语、技术契约、特殊开发要求及明确例外。没有独立规则需求的普通职责目录不强制创建 AGENTS.md；不机械复制上层规范，不为形式配齐用户级、项目级、领域级及子目录级文档。
8. 上述为规则语义和适用关系，而非对具体工具加载行为的描述。AGENTS.md、AGENTS.override.md 等规则文件的实际发现、同目录选取、覆盖及读取机制，应依据真实工具能力和后续已确认的规范文档读取规则确定。不能因文件名含 override 就将其解释为对项目硬性约束的无限制豁免，也不能假定所有上层或下层文件已自动进入当前上下文。

分层适用示例（只表达逻辑关系，不要求创建示例文件）：

```text
用户级通用规则
    → 当前项目级规则
        → Combat 领域规则
            → Damage 子目录规则
                → DamageCalculator.cs 的实际适用规则

其他领域的局部规则不自动作用于 DamageCalculator.cs；
跨领域协作时分别遵守对应范围规则和真实公共契约。
```

例如项目选择 Addressables 作为配置资产来源，可覆盖 Resources 的通用默认位置，同时保持配置及资源所有权和合法依赖。CombatConfigProvider 的专用读取约定可以细化 ConfigSystem 的访问方式；若某局部条款要求纯 Calculator 隐式访问全局 ConfigSystem，则须核实是否存在明确批准的职责例外，不能因该规则更具体而自行接受冲突。

## 已有实现与默认规则

1. **采用存量保护与增量治理。** 新增代码、实际受影响的修改及经确认的重构范围应遵守当前有效规则和合法专用约定；已有稳定实现及不属于授权范围的内容继续受到保护。新规范生效不自动获得对已有代码、资源、配置、目录或公共框架的整改及迁移权限。
2. 发现已有实现与规则不同，应依据真实职责、依赖、数据所有权、技术契约、运行证据及实际任务影响区分下列情况。不能仅因与示例不同就认定存在缺陷，也不能以已有实现能够正常运行证明不存在架构违规。

| 差异性质 | 典型情况 | 默认处理 |
|---|---|---|
| 技术实现差异 | 已有字符串事件、协程调度、导表或资源加载框架与新建默认方案不同 | 核实稳定契约并合法复用，不建立平行框架 |
| 命名及组织差异 | 历史 EventBus、已有命名空间、目录或访问组织 | 保护稳定名称及组织契约，不主动批量改名、拆分或迁移 |
| 真实架构冲突 | 已有 System 反向调用 Manager、纯处理层产生未经允许的副作用、重复权威状态 | 说明实际冲突及受影响路径，保护未获授权修改的存量，不在新增开发中扩大违规 |
| 实际功能缺陷 | 能够根据证据确认的错误执行、重复提交、资源泄漏或其他契约缺陷 | 按实际任务影响提出处理方案，区分已确认问题、静态风险及待验证假设 |

3. **已有适用且稳定的技术契约优先于通用默认方案。** 按真实功能及职责识别已有框架、接口、数据格式、资源机制、命名和目录约定，不根据名称推断是否缺少某项能力。例如既有名为 ConfigManager 的普通 C# 配置框架若实际承担合法框架职责，可以沿用其稳定名称和接口；若实际为 Unity 挂载管理器且业务 System 反向依赖该管理器，则属于实际职责冲突。新建类型仍按已确定的职责及命名规范设计。
4. **区分已有代码、实际修改内容与新增代码。** 不涉及任务的代码保留；需要调用的代码核实真实入口及副作用；需要修改的代码在授权范围内落实适用规则、同步维护受影响契约及注释；新增代码遵守全部实际适用的新建规则；经确认的重构按明确目标及迁移方案实施。修改一个方法不自动取得整个文件、领域或框架的规范整改权限。
5. **已有违规不构成新增违规的依据。** 历史实现违反硬性约束时，不因其长期存在、具有相同名称或当前可运行就认定为已批准例外。新增功能不得扩大相关违规、增加禁止依赖或通过中转接口、Utility、兼容层等隐藏实际副作用。已有合法入口不因同一类型其他无关方法存在历史问题而自动失效；调用时按真实调用路径、技术契约、状态影响及依赖关系判断，不将历史违规扩大到本次新增协作。
6. 不影响当前任务的历史违规或缺陷，按实际影响单独报告并保护现有代码；能够在既有授权内完成的必要相关规范化正常实施。实际架构冲突、公共契约变更或缺陷修复需要超出已确认范围时，须说明依据及候选方案并取得相应授权。阻塞当前任务时暂停依赖该问题的部分，不使用未经授权的兼容、兜底、功能禁用或占位实现掩盖阻塞。
7. 可按实际问题性质和整改影响使用以下判断等级，不要求建立额外的技术债务管理系统、评分或独立记录文件：

| 整改判断 | 适用情形 | 处理方式 |
|---|---|---|
| L1：保持兼容 | 合法技术、命名或组织差异 | 复用已有稳定契约 |
| L2：局部规范化 | 当前已确认修改范围内需要完善的实现、注释或组织 | 按真实影响完成相关必要调整，不改变未授权契约 |
| L3：专项整改 | 真实架构冲突、功能缺陷或公共契约问题 | 提出专项处理方案，按实际影响取得确认 |
| L4：架构迁移 | 现有架构或框架不能满足实际需求，需要系统性调整 | 比较技术方案，说明迁移、兼容及影响，取得具体实施授权 |

8. **不默认引入历史兼容层。** 已有稳定实现能够直接满足需求时，不为命名统一、目录形式或隐藏历史实现新增重复入口。确有接口不兼容、第三方适配或经确认的渐进迁移需求时，评估具有独立技术职责的适配或兼容实现，明确真实调用、维护边界、生命周期和临时机制的移除条件，经对应授权实施，不以兼容为由绕过禁止依赖。
9. Agent 应主动识别有实际价值的架构改进和技术债务，按[技术实现方案设计与评估规范](../Design/TechnicalDesign.md)提出可审查方案，区分当前必要改动、可选优化及系统迁移。不因规则更新、历史代码与默认模板不一致或个人技术倾向，自动实施全量整改、改名、迁移、框架替换及资源重建。
10. **规范生效与历史代码迁移分别确定。** 长期规则更新后，后续新增设计及已授权的实际修改遵守其有效范围；已有实现需要迁移时，说明真实范围、目标契约、依赖及调用方、序列化与资源影响、兼容性、风险及候选方案，按原授权机制实施。规范修改本身不等于批准修改任何实际项目代码。

## 临时例外与规则变更

1. **正常选型、授权及存量兼容不属于真正的规则例外。** 按照默认规则已经允许的替代条件采用普通实例，使用用户明确指定的合法配置形式，满足自动绑定或 Git 操作的专项授权条件，以及合法沿用已有 EventBus 技术契约，均属于正常规则执行。偏离规则原本允许范围的行为才需要明确的例外或规则变更决策。
2. 项目内部规则例外必须具有明确用户决策依据，不能由 Agent 自行批准或从普通需求、历史实现、工具许可、文件名及宽泛授权推断。规则例外不解除外部强制条件，也不自动解除其他仍然生效的架构、业务、技术及授权约束。
3. 根据适用范围及持续性区分以下事项，结束条件可以按操作、任务、迁移状态、依赖或契约变化确定，不强制每项例外设定具体到期日期：

| 例外或规则变更类型 | 生效范围 | 结束或替代条件 | 推荐记录位置 |
|---|---|---|---|
| 单次例外 | 一次明确指定的操作 | 操作结束、授权撤销或成立条件失效 | 对应操作方案及实际交付说明 |
| 任务级例外 | 已确认的具体任务及相关实施范围 | 任务结束、取消、方案或成立条件失效 | 当前确认方案及交付说明 |
| 局部长期例外 | 明确项目、领域、目录、类型或其他指定对象 | 被撤销、替代或成立条件失效 | 经授权记录于对应项目或局部规范 |
| 正式规则变更 | 被修改规则的明确适用范围 | 后续正式修订、替代或废止 | 经授权维护对应主定义及相关引用 |

4. **重要例外应具有可核实的语义记录。** 按实际需要在确认方案或对应正式规则中明确下列信息。简单例外可简明合并表达，不为满足格式机械生成独立报告或新增例外管理系统。

| 记录事项 | 说明 |
|---|---|
| 原始规则 | 需要偏离的规范、章节及可定位条款 |
| 例外内容 | 明确允许的偏离行为与不允许的扩大范围 |
| 适用范围 | 对应项目、模块、目录、类型、方法、任务或单次操作 |
| 引入原因 | 真实技术、架构、业务或迁移依据 |
| 实际影响 | 调用、职责、状态、资源、业务、兼容及维护影响 |
| 保留约束 | 仍然生效的其他职责、业务和授权规则 |
| 生效条件 | 用户决定、实际前提及必要实施授权 |
| 结束条件 | 失效、撤销、替代或迁移完成条件；存在清理需求时说明实际责任及方案 |
| 决策依据 | 可核实的用户确认、对应方案或正式规范条款 |

5. **例外不自动传播或延长。** 指定方法的例外不扩展为整个类型，指定类型不扩展为同类其他类型，局部范围不扩展为其他领域或项目，当前任务不扩展至后续任务。一项规则的例外不解除其他规则。规则变更仅替代其明确规定的内容和范围，不默认为全部相关规范失效。
6. 例外失效、撤销或成立条件变化后，不得继续将其作为新增开发依据；后续任务重新核对当前有效规则、实际历史状态及授权。例外失效不自动触发 Git 回滚、删除代码、重建资源、重构或撤销已发生的业务效果。已确认的临时清理及迁移方案可以在有效授权范围内实施；尚未批准或出现新增影响的处理须重新确认，并如实报告遗留问题。
7. **长期例外及正式规则变更应具备后续可读取、可核实的依据。** 不长期依赖 Agent 的记忆、未确认讨论或无法核实的记录。对应规范文件的新增及修改、主定义调整、相关引用同步和历史项目迁移分别按实际授权处理；不因单次或任务级例外而自动修改 AGENTS.md，不强制建立独立 Exceptions.md 等文件。
8. 对 Manager 与 System 单向依赖、单例作用域、状态所有权、纯处理职责、修改前确认、禁止主动编译及运行验证、已有成果保护等重要约束，确需调整时应明确对应规则及真实影响，不能由普通任务、目录规则或技术方案隐式解除。当前既有约束继续有效；本节本身不批准任何具体例外或改变实际操作权限。

## 真实冲突识别与处理

1. **采用分级裁决型冲突处理。** Agent 应主动识别全部相关规则及真实问题，能依据明确适用范围、规则语义、有效专用约定及合法例外解决的，按有效规则处理，不将所有判断机械提交用户。无法明确裁决的真实冲突、规则调整及授权缺失，按实际影响报告并取得决策或补充授权。
2. 区分以下规则问题，不能将所有技术差异都认定为冲突，也不能将真实冲突隐含在普通技术选型中：

| 问题类型 | 判断参考 | 默认处理 |
|---|---|---|
| 表面冲突 | 规则作用对象、适用条件或行为含义不同 | 澄清语义后共同执行 |
| 默认规则差异 | 有效项目或局部约定与通用默认方案不同 | 在合法范围内采用具体约定 |
| 推荐原则取舍 | 多个合法候选设计具有不同价值 | 按技术依据选型，重要取舍纳入方案 |
| 已有实现差异 | 已有合法技术或名称、组织契约不同 | 合法兼容，保护既有实现 |
| 硬性规则冲突 | 需求或方案无法同时满足有效职责或行为约束 | 报告真实冲突并提出替代方案，偏离须明确决策 |
| 授权冲突 | 实施范围、专项操作或行为未获相应授权 | 说明缺失的授权及影响，确认后实施 |
| 同级或独立有效规则冲突 | 对同一对象及条件规定互不兼容的要求 | 核对主定义、有效替代关系及例外；仍无法裁决时提交用户 |
| 技术可行性冲突 | 真实平台、API、工具或依赖条件不能满足方案 | 如实说明限制并评估可行方案，不假定已具备能力 |
| 规则缺失或不明确 | 关键规则不可读取、来源或例外有效性不明 | 明确不确定性，暂停受影响部分，不虚构规则或授权 |

3. 对同一事项的实际冲突，依次核对是否针对相同对象、操作、范围及条件，是否具有不同约束强度及适用前提，是否有明确规则主定义及协作边界，是否存在真实有效的修订、替代或废止声明，是否有仍然生效的用户决策或例外。可确定为旧重复描述时按核实的有效主定义处理并报告不一致；仍存在两个互不兼容的有效要求时不得擅自选择。
4. **不得采用无依据的自动裁决标准。** 不以读取顺序、文件修改时间、目录深度、条款位置、文字篇幅、严格程度、实现便利或 Agent 偏好单独确定规则有效性；不能将下层规范、其他 Agent 修改、现有实现及技术工具权限直接解释为更高优先级。最新明确用户决策按实际替代范围处理，不等同于最新文件总是优先。
5. 规则冲突处理依次开展适用规范识别、规则性质分类、真实冲突判断、有效裁决依据核对、可行方案及权限确认、已授权实施与静态审查、真实交付。该过程按实际任务融入既有七阶段流程，不新增独立审批、技术框架或额外文档交付要求。
6. **采用最小阻塞范围原则。** 冲突无法解决时，暂停依赖该冲突或无法确认合规性的实施部分；已经获得授权、规则明确、能够独立安全完成的工作可以继续。无关历史问题单独报告。若核心授权、必要规则或关键技术前提影响整个任务，则停止所有受影响的实施，明确可完成范围及下一步决策。不为保持进度而新增隐藏依赖、无授权临时行为、占位、静默兜底或虚假成功结果。
7. 冲突解决后应重新检查方案是否仍满足所有有效规则及具体授权，重要技术变化、公共影响、附加行为和例外范围变化按[AI 修改与交付规范](AgentWorkflow.md)补充确认。已经明确解决且没有新增影响的部分不重复确认。不得为消除冲突擅自修改规则文件、删除已有实现、变更 Git 状态或改变验证权限。

## 冲突报告及用户确认

1. **按实际冲突及风险调整沟通深度。** 不要求每次正常选型或规则细化都输出完整规范分析。以下等级仅用于判断报告及确认的详细程度，不引入新的任务分类框架、强制报告文件或固定审批次数。

| 报告等级 | 适用情况 | 默认处理及沟通要求 |
|---|---|---|
| 一级：自主裁决 | 明确合法默认覆盖、技术差异、正常规则细化或允许的选型 | 按实际有效规则处理，重要依据及取舍在方案或交付中简要说明，继续遵守实施授权 |
| 二级：简要确认 | 局部授权不足、具体技术契约需确定或范围存在实际歧义 | 明确具体规则、问题、影响、推荐处理及待确认事项；受影响部分确认后实施 |
| 三级：完整冲突报告 | 硬性架构冲突、独立有效规范矛盾、重大例外或长期规则变更 | 提供真实规则定位、冲突证据、影响、候选方案、推荐、风险、适用范围及用户决策事项 |

2. 无法依据现有规则明确处理的冲突，应按相关情况提供以下内容，使用户能够直接审查及决定，不仅报告“规范冲突”或“无法继续”：

| 报告内容 | 说明要求 |
|---|---|
| 01. 冲突位置及对象 | 实际相关文件、目录、类型、接口、操作及所属职责 |
| 02. 涉及规则及证据 | 规范文件或真实来源、章节及可定位条款、具体约束、适用条件、已确认决定及无法核实的部分 |
| 03. 实际问题及影响 | 冲突为何不能同时满足，受影响的行为、调用方、数据、资源、架构、授权及技术前提 |
| 04. 候选处理方案 | 优先评估保持现有规则的合法方案；需要例外、规则调整或迁移的候选单独说明实际偏离、代价及范围 |
| 05. 推荐及风险 | 明确推荐理由、方案适用条件、技术取舍、未核实信息及需要用户手动验证的事项 |
| 06. 当前实施状态 | 已完成、暂停、尚未实施、不受影响可继续部分，以及保留的已有成果 |
| 07. 待用户决策及授权 | 需要确定的规则选择、例外或长期变更、具体实施范围及专项授权条件 |

3. **候选方案必须真实可行并符合其所声明的约束。** 保持现有规则的合法实现应优先评估；需要改变硬性规则或公共契约的方案应明确标为需要决策的候选，不将其作为现有规则下已经合法的默认方案。没有实际可行的候选时如实说明，不为了格式虚构多个方案或掩盖技术限制。
4. 用户已明确了解并批准具体规则调整、例外、行为变化及实施方案时，无需再次询问已确认的相同内容；缺失的授权或新发现的影响仍须按对应规则说明并确认。对讨论中推荐方案表示认可，不自动构成写入规范文件或项目代码的授权。冲突报告可合并到已有技术评估、修改方案及交付，不增加独立开发阶段。
5. 如用户确认建立长期例外、修改或废止正式规则，应明确主定义、受影响的规范引用及适用范围，在获得对应文档修改授权后同步维护，避免长期存在不一致的规则。规范同步与已有项目迁移分别确认；普通选型、已满足的专项授权以及单次或任务级例外不默认修改长期规范。实际文档组织和维护机制另按用户确认的规范体系执行。

冲突报告简例（仅用于说明报告方式，不批准示例中的任何例外）：若用户要求 DamageCalculator 直接访问 ConfigSystem，应说明其与纯处理层及配置显式传递规范的实际冲突，给出相关条款位置。优先评估由 CombatSystem 获取配置后通过参数或 InputData 显式提供，或由合法所有者装配具有明确有效期的只读配置依赖；确需直接访问时，应将其作为明确改变依赖边界的规则例外候选，说明影响及范围。报告尚未实施的冲突部分和其他独立已授权部分，由用户确认方案，不默认改变配置、架构或其他约束。

## Agent 规则检查与交付要求

1. 项目调查及方案设计过程中，应根据任务相关范围完成规则识别及必要裁决，不要求每次输出完整规则清单或机械读取无关模块的全部文档：
   - 实际相关的用户要求、有效项目及局部规则、对应专项主定义、合法专用约定及当前实施授权。
   - 各条规则的适用对象、范围、约束强度、前置条件及可能的复合语义；相关硬性约束和授权条件是否共同成立。
   - 已有实现、实际技术及业务契约、维护来源、历史差异、已确认缺陷、静态风险及不确定性。
   - 新旧决策之间的实际替代关系、例外的批准依据、生效及结束条件、保留约束和影响范围。
   - 真实冲突是否可依据现有有效规则裁决，是否需要候选方案、用户决定、额外授权或暂停受影响部分。
2. 修改方案应按实际影响说明重要规则选择、真实冲突、候选及推荐、必要例外或规则变更、已有成果保护、拟修改范围与对应专项授权。不把默认覆盖、正常技术选型或已满足授权条件误报为硬性规则例外。无法读取关键规范或确认重要前提时说明实际限制，不以猜测代替调查。
3. 实施前及实施过程中核对实际适用规则、已确认方案、例外条件、文件归属及公共协作契约。跨目录、任务恢复、并行开发或出现方案外影响时重新核对受影响范围。授权内正常实现自主完成，真实新增冲突按最小阻塞范围原则处理，不通过间接工具及子 Agent 绕过规则。
4. 交付前在既有静态审查权限内核对实际改动与有效规范、用户决策、例外及授权是否一致，区分合法存量兼容、实际新增内容、未授权改变、无关历史问题及未完成整改。不通过主动编译、获取编译错误诊断、运行或测试验证规则合规性，验证权限继续遵守[AI 修改与交付规范](AgentWorkflow.md)。
5. **交付应说明实际重要的规则裁决及剩余冲突。** 根据任务规模纳入既有交付结构，说明真实采用的专用规则及重要取舍、已批准例外及其适用范围、规则或规范文档变更及授权依据、历史问题和仍需用户决定的事项、暂停范围及实际完成的独立部分。未读取、未核实、未实施或待验证内容如实标明，不将推断表述为确认结果；不机械输出全部规则及独立冲突报告。
6. 本节的规则裁决、例外和冲突报告均与既有七阶段流程、用户确认、专项变更授权、工具权限及最终交付共同生效。不得以落实规范、减少冲突或完善文档为由自动修改无关文件、重构、安装工具、建立平行框架或引入运行机制。

| 设计维度 | 默认推荐或约束 |
|---|---|
| 规则分类 | 硬性约束、授权约束、默认规则、推荐原则、参考示例；按完整语义判断 |
| 规则用语 | 统一语义，重要位置按需标记，不机械全文加标签 |
| 用户决策 | 项目规则及重要设计的最终决策权，明确新决策在实际替代范围内生效 |
| 实施权限 | 规则决策、例外和具体实施授权分别判断，可在明确方案中统一确认 |
| 裁决模型 | 综合外部条件、用户决策、约束强度、适用范围、规范职责、项目契约及有效例外，不采用无条件覆盖排序 |
| 纵向规则 | 分层继承、局部补充及细化、受控覆盖、明确作用域 |
| 横向规则 | 职责归口、主要规范与协作规范共同生效、主定义唯一及必要引用 |
| 已有实现 | 存量保护、增量遵循、合法稳定契约优先于默认方案、历史违规不扩散 |
| 例外 | 明确原规则、偏离行为、范围、影响、批准依据及有效条件，不自动传播 |
| 例外结束 | 恢复按有效规则开展后续开发，不自动回滚或迁移历史实现 |
| 正常规则选择 | Agent 根据有效规则主动裁决，遵守既有方案及授权 |
| 真实冲突 | 说明规则位置、事实、影响、候选方案及推荐，取得明确决策 |
| 阻塞范围 | 暂停受影响部分，独立且已授权的合法工作可以继续 |
| 规则文件维护 | 长期规则及例外具有可核实记录，文档修改及项目迁移分别授权 |
| 文档组织与读取 | 不预设具体文件拆分及工具自动加载机制，按后续确认的规范文档体系确定 |
