# 规范文档维护与演进规范

## 规范定位与适用范围

本规范负责整个 DevelopmentStandards 规范体系的组织、权威来源、版本管理、规范修改审批、跨电脑部署与同步、已有项目兼容、规则生命周期、审计及长期演进。它维护的是规范体系本身，不替代 RulePriority.md 的规则裁决主定义，也不替代 AgentWorkflow.md 的项目开发与读取流程。

## 规范体系组织与维护职责

1. 通用规范采用独立 GitHub 仓库集中维护，仓库初始名称为 `DevelopmentStandards`，初期建议设为 Private。仓库只保存规范入口、共享专项规范及必要的维护资料，不上传 Codex 认证信息、会话数据、个人配置或无关项目代码。
2. GitHub `main` 是正式通用规范的权威维护来源。本地 Git 工作副本用于编辑、审查及版本管理；Codex Home 中的文件是实际使用的部署副本。未经正式合并的本地变更、开发分支及部署副本修改，不自动成为正式规范。
3. 项目专用规范和局部增量规范由对应项目仓库维护，不将多个项目的业务规则混入通用规范仓库。通用规则、项目事实、项目契约、项目专用规则及明确批准的例外应分别表达。
4. 规范体系采用分层职责式组织：核心入口、共享专项规范、项目专用规范及局部增量规范。规范的横向专业职责与纵向适用作用域分别确定；目录分类不自动产生代码架构层级或规则优先级。
5. 共享专项规范按独立专业职责拆分。具有独立主定义、阅读价值和维护价值时建立独立文档；不按代码类型、文档行数或文件数量机械拆分。相关规则可以集中维护，但每项正式规则必须有明确的主定义及维护责任。
6. 通用规范目录采用 `Standards/`，按 `Governance/`、`Architecture/`、`Code/`、`Design/`、`Runtime/`、`Unity/` 分类。目录及文件名使用英文 PascalCase；正文使用中文并保留必要技术术语；不机械添加数字前缀、版本后缀或重复的 `Standard` 后缀。
7. 项目专用规范较少时可以由项目级 `AGENTS.md` 承载；存在独立维护价值时按需建立 `Standards/Project/`。领域、目录及对象局部规范优先就近存放，只记录必要增量，不复制全部上层规则。未形成实际规则需求的目录不强制创建规范文件。
8. 规范文档采用统一基础结构与专项扩展相结合的方式。正式专项规范应明确文档身份、定位、适用范围、相关规范、核心规则及必要的 Agent 检查要求；不强制机械设置空白章节。
9. YAML Front Matter 的基础字段为 `id`、`title`、`category`、`scope`。文档 ID 使用稳定语义标识，例如 `architecture.core-roles`、`runtime.configuration`、`project.world-game.configuration`。重要规则可按实际引用和维护需要设置稳定语义 ID，不要求所有普通条款逐一编号。`scope: General` 表示规则可跨项目、跨引擎复用，但仍受其语言、框架、职责及明确适用条件限制；General 文档中明确标注的 Unity API、MonoBehaviour、PlayerLoop 或 Unity 场景生命周期实现，只在 Unity 条件成立时适用。`scope: Unity` 表示文档整体仅适用于 Unity 工程及其特定技术环境。`scope` 只表达技术适用范围，不表示规则强度、优先级或无条件必读；实际读取仍按任务性质和五维匹配机制确定。
10. 同一规则只维护一个权威主定义。其他文档可以保留关键约束摘要、适用提醒、条件协作说明及参考示例，但不得独立维护可能不一致的第二份完整定义。文档引用应使用可定位的相对路径；相对路径以包含该引用的文档所在目录为基准。
11. 规范摘要、索引、示例和检查清单不能替代完整规则。规则性质、约束强度、适用条件及授权边界按 `RulePriority.md` 裁决。

## GitHub 仓库治理

1. 正式稳定分支为 `main`。候选修改采用主题分支；重大体系重构使用独立 `refactor/*` 分支；已发布规则的紧急修正可以使用 `hotfix/*` 分支。分支命名用于表达工作目的，不决定规则效力。
2. 主题分支示例：`standards/rule-loading`、`standards/state-commit`、`refactor/standard-structure`、`hotfix/broken-reference`。未经确认的讨论内容不得直接写入 `main`。
3. 规范修改按影响范围决定审查方式。核心架构规则、规则优先级、授权流程、多份规范联动及体系重构优先采用 Pull Request；小幅文本修正可以简化流程，但仍须保留实际差异审查。
4. 一个 Git Commit 应表达一个明确的变更目的。提交说明应能识别规范主题及变更内容；无关规范修改不机械合并为一个提交。
5. Git Commit、Push、Merge、Tag、Release、Fetch、Pull、分支及工作区状态变更均继续遵循用户明确的 Git 操作授权。仓库访问能力或规范修改授权不自动包含 Git 写入授权。
6. GitHub `main` 是正式规范来源；本地工作副本和 Codex Home 不自动成为权威来源。项目内受控副本只有在明确记录其来源及版本时，才作为该项目选定的通用规范版本使用。

## 规范版本管理与发布

1. 整套规范统一版本管理。核心入口及全部共享专项规范共同组成一个完整规范版本，不默认对每份专项文档独立维护版本号。
2. 版本号采用三段式 `Major.Minor.Patch`：
   - Major：改变核心规则、职责契约、授权边界或产生不兼容规则变化。
   - Minor：在保持既有有效契约兼容的前提下，新增专项规范、规则或兼容能力。
   - Patch：修正错别字、排版、失效引用及不改变规则语义的错误。
3. 版本升级依据规则语义、适用范围、约束强度、授权及兼容性影响判断，不以修改行数、文件数量或文档数量决定。仅修改一句话也可能构成 Major；大量排版调整也可能仍是 Patch。
4. 仓库根目录使用 `VERSION` 记录声明的规范体系版本，使用 `CHANGELOG.md` 记录正式变更。`VERSION` 不替代 Git 提交身份；`CHANGELOG.md` 不替代 Git 历史。
5. Git Commit 用于记录每次实际变更；Git Tag 用于标记正式版本对应的准确提交；GitHub Release 按实际分发及说明需要创建。三者不要求一一对应。
6. 首个完整迁移基线拟采用 `v1.0.0`。在原始规则迁移、完整性审计、引用检查及用户确认完成前，不得宣称已在 GitHub 正式发布，不得虚构 Tag、Release 或提交 SHA。
7. 版本元信息不在每份专项规范中重复维护。文档 ID 标识规范身份；体系版本标识一组完整规则；Git Commit 与 Tag 标识实际内容快照。
8. `main` 可以包含已确认合并但尚未创建新 Release 的变更。应区分 main 当前 HEAD、最近稳定发布版本及尚未合并的主题分支。
9. 日常开发默认使用当前有效的本地部署版本，不自动联网跟随 GitHub 最新版本。项目可以按实际需要固定某个正式版本；任务期间默认保持有效规范来源稳定。
10. 规范更新发生在任务期间时，应核对受影响规则、已确认方案及授权。无实质影响时可以继续；改变已确认方案成立条件或授权边界时，按实际影响重新评估并取得确认，不混用不同版本的同名规则。

## 规范修改与审批

1. 规范变更应具有明确的问题来源、修改目标、适用范围及用户决策依据。规范讨论、规则设计确认、文档修改授权、Git 操作授权、版本发布授权及本地部署授权分别判断；已明确授权的操作不机械重复确认。
2. 规范变更按审查深度分为四级：
   - L1 文本维护：错别字、排版、失效链接及不改变规则语义的修正。
   - L2 规则澄清与兼容扩展：补充已有规则解释、适用条件或兼容方案，不改变原有有效契约。
   - L3 规则语义变更：改变约束、适用范围、默认方案、职责或技术契约。
   - L4 规范体系级变更：影响规范组织、治理、读取、部署或维护机制。
3. L1 可以简化方案与审查；L2 说明新增内容及原规则是否保持不变；L3 必须完整说明语义变化及兼容性；L4 必须审查整体结构、跨文档依赖及迁移影响。分级决定维护审查深度，不表示规则优先级，也不直接决定版本号。
4. 规范修改沿用既有七阶段协作流程：问题识别、现有规范调查、规则设计与评估、修改方案设计、用户确认、文档实施与静态审查、变更交付。不得因规范维护任务而绕过用户确认。
5. 修改方案应说明原有规则、拟修改规则、主定义文档、涉及文件、约束性质变化、适用范围、默认方案、授权条件、例外、关联规范、兼容性及明确保持不变的内容。
6. 不得以整理文档、优化表达、减少冗余或迁移文件为由，未经确认改变规则语义、约束强度、适用范围、默认方案、授权条件或有效例外。
7. 正式规则应维护唯一主定义。修改后检查核心入口摘要、专项引用、任务索引、示例、关联协作契约及受影响项目规则。关联文档检查不自动取得修改所有相关文件的授权；超出原方案的实质规则变化应补充说明及确认。
8. 重复内容删除、规则迁移、规则废止及规则移除分别处理。迁移应保持原规则语义及可定位性；废止应说明原因、替代方案、适用范围和存量兼容；移除应有明确用户决策依据。
9. 发现规范问题时可以主动提出修改建议，但不得未经确认直接修改通用规范。重要长期架构决策可以按需使用 ADR 或 GitHub Issues 记录；这些记录不替代正式主定义。
10. 修改完成后执行与实际范围相匹配的静态审查，包括内容完整性、规则语义、职责归属、主定义唯一性、引用、兼容性及授权范围。不得因文档审计自动编译、运行项目或修改项目代码。

## 规范部署与跨电脑同步

1. 默认采用独立规范仓库工作副本与 Codex Home 受控部署副本。GitHub 负责权威维护及版本发布；本地规范仓库负责编辑和版本管理；Codex Home 负责实际读取。默认不将整个 `.codex/` 目录作为 Git 仓库。
2. 默认部署位置为当前实际 `CodexHome/` 下的 `AGENTS.md` 与 `Standards/`。Codex Home 根据实际环境及 `CODEX_HOME` 确定，不硬编码用户名、磁盘路径或固定工作目录。
3. 部署采用文件白名单：`AGENTS.md` 与完整 `Standards/` 为默认受管理内容。`README.md`、`VERSION`、`CHANGELOG.md`、`.git/`、`.github/` 及未来工具目录默认不复制到 Codex Home。不得覆盖 `config.toml`、认证文件、会话数据、Skills、Hooks 配置或其他无关 Codex 文件。
4. 默认单向部署：权威仓库向 Codex Home 分发。Codex Home 中发现的独立修改不自动回写或成为正式规则；应回到规范仓库按正式变更流程处理。
5. 本地部署记录使用 `StandardsDeployment.json`，记录规范仓库地址、选定 ref、实际 Commit SHA、体系版本、部署时间及受管理文件清单。可记录 SHA-256 辅助识别部署后本地修改。部署记录是本地生成文件，不属于通用规范仓库初始文件。
6. 首次安装、更新及回退前检查实际 Codex Home、目标目录、现有 AGENTS.md / AGENTS.override.md、文件差异、本地修改及入口冲突。生成部署差异后再执行已授权操作。
7. 旧版本文件仅在能够确认属于此前部署管理范围、目标版本不再包含且清理已获授权时删除。不得删除未知归属文件、用户独立文件或其他 Codex 数据。
8. 本地文件与目标版本均发生变化时，不静默覆盖或自动合并。应比较上次部署内容、本地内容及目标版本，明确保留、迁移、放弃或冲突解决方案。
9. 部署失败时应停止扩大写入范围，报告部分完成状态；只有文件实际部署并完成核对后才更新部署记录。部署工具可以采用暂存、备份及失败恢复，但不得假定普通多文件复制天然具有事务原子性。
10. 规范回退属于重新部署明确的历史版本，不自动回退 GitHub 历史或项目代码。部署脚本、自动同步、Hooks、符号链接及其他工具按实际需要经确认后引入；不默认每次启动或任务时联网检查及自动更新。
11. 更换电脑时，从 GitHub 获取选定规范版本，核实新电脑的 Codex Home，部署 `AGENTS.md` 与 `Standards/`，核对文件、路径、版本及入口冲突后使用。跨电脑同步不要求每个 Unity 项目重新复制全部通用规范。

## 规范更新与已有项目兼容

1. 规范发布、规范部署、项目版本采用及项目代码迁移属于不同事项，不自动相互产生操作授权。
2. 已有项目默认采用存量保护与增量治理。未涉及代码保持不变；新增代码遵守当前有效规范；本次需要修改的既有代码在已确认范围内遵守适用规则并保护稳定契约；专项整改及整体迁移独立制定方案。
3. 已有历史实现可以作为兼容依据，但不自动成为新增代码的设计依据，不得继续扩大历史违规，也不得仅为符合新版默认类型、目录或框架而建立职责重复的公共实现。
4. 存量治理沿用四种方式：L1 存量兼容、L2 局部规范化、L3 专项整改、L4 整体迁移。专项整改及整体迁移应说明实际问题、文件及调用范围、依赖影响、风险和验证要求，经用户确认后实施。
5. 普通项目默认使用当前有效共享规范；大型、长期维护、稳定交付或多人协作项目可以明确固定正式版本。项目固定版本应可追溯到实际 Tag 或 Commit；不自动解除用户级现行治理及授权约束。
6. 固定版本项目切换版本时，应明确目标版本及兼容性影响。规范更新不自动触发全项目符合性扫描、批量代码整改或项目迁移。
7. 项目专用规则与例外在通用规范更新后应检查实际有效性。新版规范已正式覆盖某项例外时，可以提出取消建议；仍然有效的例外不得未经确认删除或扩大范围。
8. 规范版本回退不自动回退项目代码。项目代码迁移、资源迁移、公共框架改造及其他实际修改均遵循项目本身的授权及存量保护要求。

## 规则生命周期、长期演进与审计

1. 规范采用问题驱动的持续演进方式，不以规则数量或文档数量作为完善程度的依据。新增规则前优先检查已有规则是否已能解决问题，判断问题来自规则缺失、表达不清、读取遗漏、执行保障不足还是实际实现错误。
2. 规则生命周期可采用 Proposed、Active、Deprecated、Removed：候选规则不具有正式效力；正式规则按适用范围执行；废止规则按明确的过渡及存量契约处理；移除规则不再作为正式依据，历史内容由 Git 保留。不得由 Agent 自行判定规则失效。
3. 新增专项规范须具有独立专业职责、规则完整性、单独阅读价值及维护价值；已有规范可以合理承载时不重复新建。未来扩展如 Networking、Persistence、Shader、EditorTools 等仅为候选方向，不预先创建空白文件或目录。
4. 技术规范更新应核实实际 Unity / C# / 包版本、目标平台、现有实现、替代方案、兼容性及迁移成本。新技术出现或旧 API 被弃用不自动构成强制迁移依据。
5. 规则废止应说明原因、适用范围、替代方案、兼容处理及迁移要求。废止不自动产生历史代码迁移义务。无实际价值的历史规则经确认后可以从正式文档移除，完整历史由 Git Tag、Commit 及发布记录保存，不默认建立 Archive 或 Deprecated 目录副本。
6. 规范审计采用局部审计、关联审计及体系审计：单份规范修改后审查其内容与引用；跨文档修改审查职责及语义一致性；重大版本发布、体系重构、重复冲突积累或用户明确要求时进行整体审计。以事件驱动为主，不强制固定审计周期。
7. 整体审计应按实际范围检查规则完整性、语义、职责归属、主定义唯一性、冲突、引用、读取可达性、技术适用性、项目兼容性及维护部署一致性。
8. 审计发现不自动产生修复授权。错别字、失效链接、规则冲突、技术过时、职责过大、项目不兼容及读取问题分别提出相应处理方案，不顺手扩大为项目代码整改。
9. GitHub Issues、讨论记录及 ADR 可按需记录候选问题、设计决策及历史依据；正式生效规则仍以经过确认并纳入有效规范版本的主定义文档为准。
10. 自动化工具优先处理可客观判断的问题，如 Markdown 链接、文档 ID、YAML 元信息、文件清单及部署完整性。规则语义冲突、架构职责、授权和项目兼容性仍需人工及 Agent 结合实际证据审查。不得自动删除重复规则、自动修改正式规范或自动发布部署。

## Agent 检查与交付要求

规范维护任务应按实际范围核对：权威仓库与分支、当前版本、主定义、原有规则及用户决策、关联规范、兼容性、引用和索引、部署差异、授权及实际 Git 操作。交付时说明实际修改文件、规则语义变化、版本建议、关联影响、未解决问题及未执行的 Git / Release / 部署操作。不得虚构已提交、已推送、已发布或已部署的状态。
