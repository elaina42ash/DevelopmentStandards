# AI 修改与交付规范

## 规范定位与适用范围

定义 Agent 的开发流程、授权、项目调查、静态审查、交付及规范读取机制。

本规范是 Agent 项目修改、规范读取、实施授权、静态审查及任务交付流程的主定义。规则来源、性质、适用范围、优先关系及例外由 [规则优先级与冲突处理规范](RulePriority.md)统一裁决。

本节统一约束 Agent 的需求理解、项目调查、技术实现方案设计与评估、修改方案设计、用户确认、代码实施与静态审查以及任务交付。用户负责需求、业务决策及架构与变更方案审批；Agent 负责主动调查、技术设计、具体实现、静态审查及真实交付。在已确认范围内应充分发挥 Agent 的自主开发能力，不逐次请示正常实现细节，也不得自行扩大需求、改变业务行为或破坏已有项目成果。 规则识别、优先关系、例外及冲突裁决贯穿本节七阶段流程，具体遵循[规则优先级与冲突处理规范](RulePriority.md)，不新增独立审批或实施阶段。

## 适用范围与基本原则

1. **先明确任务及授权，再执行项目修改。** 本节适用于脚本、Prefab、场景、资源、配置表、文档、工程设置、生成工具及其他项目文件的新增、修改、移动、重命名和删除，也适用于通过 Unity 编辑器、MCP、命令行、脚本、子 Agent 或其他工具间接实施的项目变更。
2. **任务级授权与专门授权共同生效。** UI 与交互、附加校验与限制、公共基础模块、公开接口、配置、资源、生成产物、序列化和其他专项变更仍须遵守对应专项规范。本节不放宽其具体确认条件，不将普通业务实现授权扩大为其他行为的授权。 用户明确批准规则调整或例外，不自动解除其他专项授权；已满足规则本身授权条件的操作不属于真正的规则例外。
3. **架构先行与任务范围控制并不冲突。** 保持既有职责划分、稳定架构及合理细粒度拆分，在已确认方案内实现完整能力；限制非必要影响，而非机械限制文件、类型、接口、代码行数或调用层级。
4. **以实际项目证据为依据。** 已有稳定代码、工具及运行契约优先复用，不能仅凭名称、通用经验或其他项目的做法推断当前项目的实现。对不可读取、无法确认或存在冲突的事实，明确说明证据范围、假设及待确认事项。
5. 不将规范中的默认方案、示例、检查清单、技术建议或工具可用性视为自动修改授权；也不得借遵守规范擅自批量整改、重构已有项目或生成额外文件。发现实际问题时按本节的计划外问题处理规则报告。
6. 方案、检查及交付的详细程度应与实际任务规模和影响相匹配。不得对简单修改机械输出完整系统设计文档，也不得为追求简短省略关键技术决策、修改边界、用户确认及必要风险说明。

## 任务类型与开发阶段

1. **先区分讨论、调查、设计与实施任务。** 用户要求解释概念、分析问题、审计代码、讨论架构、提供示例或拟定方案时，默认只进行相应分析和交付，不修改实际项目文件。提供供用户审查的示例代码不等同于在项目中实施该代码。
2. 需要实施项目修改的任务，默认按以下七个阶段组织。阶段表示实际职责和授权边界，不要求将每个阶段拆分为独立消息、独立工具调用或单独文档；简单任务可以简洁表达，必要阶段不得省略。

| 阶段 | 名称 | 主要职责及交付 |
|---|---|---|
| 01 | 需求分析 | 明确目标、预期业务行为、任务边界及需用户决定的问题 |
| 02 | 项目调查 | 识别不同作用域及专项适用规范、真实冲突、有效例外、已有架构、代码、调用方、Unity 资源及真实技术契约 |
| 03 | 技术实现方案设计与评估 | 考虑具体实现方式、设计模式、算法、数据结构、职责及技术选型，按照[技术实现方案设计与评估规范](../Design/TechnicalDesign.md)主动研究及比较有实际意义的候选方案，形成明确推荐 |
| 04 | 修改方案设计 | 将推荐技术方案落实为具体职责、类型、文件、调用关系、行为变化及影响范围，说明重要规则裁决及需确认的冲突、例外和授权 |
| 05 | 用户确认 | 取得对应实施方案的明确授权；未确认前不修改项目 |
| 06 | 代码实施与静态审查 | 在授权范围内完成实现，审查实际修改、依赖、契约及适用规范 |
| 07 | 任务交付 | 交付真实完成情况、文件变更、手动操作及验证步骤、静态检查和剩余风险 |

3. **技术设计与具体修改方案是不同职责。** 技术实现方案设计与评估回答“具体能力如何实现更合理”，修改方案设计回答“如何在当前项目中落实该方案”。Agent 不应只寻找能够运行的写法，还应考虑适合实际需求的设计模式、算法、数据结构、扩展性、维护性及性能；存在有实际价值的候选方案时，应说明比较结果及推荐依据。具体技术设计原则、设计模式与架构协作、外部研究及选型评估遵循[技术实现方案设计与评估规范](../Design/TechnicalDesign.md)；本节负责明确其开发阶段、修改授权及实施交付关系，不新增独立审批阶段。
4. 项目调查、技术设计和修改方案设计可以根据证据迭代进行；发现前提不成立或需求存在影响业务行为的歧义时，应在实施前明确。用户未确定的业务规则、限制、UI 行为和公共契约，不得由 Agent 以实现方便为由自行决定。
5. 用户已经审查并明确批准完整方案时，无需重复提交相同方案。恢复已授权任务时，仍应核对当前项目状态、适用规则和授权有效性；存在新增影响或原方案不再成立时，按本节补充确认流程处理。
6. 用户仅要求讨论、审计或提供方案时，可以在相应阶段结束并直接交付分析结果，不机械进入用户确认、文件写入或代码实施阶段。

## 修改授权及有效范围

1. **修改授权以已确认的任务方案为单位，而不是每次文件写入、每个类型或每个方法为单位。** 实施前须说明修改原因、职责归属、拟修改内容、文件范围、行为及影响，并取得用户明确确认。已经确认的方案不需要重复请示。
2. 用户明确要求按已说明的具体方案修改、开始实施或交付实际修改结果，属于相应方案的实施授权。对明确的实施请示回复 OK、同意或确认，按上下文判断为对应方案的授权；对设计方向、架构建议或问题分析表示认可，不自动构成项目文件修改授权。 用户明确的规则决策、单次或任务级例外及长期规范变更应与具体实施授权分别判断，按[规则优先级与冲突处理规范](RulePriority.md)处理；可以纳入同一具体方案确认，不重复请示已明确的事项。
3. 单纯描述需求、询问实现方式、要求审计、要求查看代码或提出意见，不等同于批准尚未说明的实施方案。用户要求“全部按照建议来”“直接修改”等，应以已经说明并可审查的具体方案为授权边界，不得解释为无限制的项目修改权限。
4. **授权范围应能够对应实际任务。** 应明确目标、涉及的业务或技术领域、允许新增或调整的类型及文件、业务及技术契约、相关资源或配置、明确排除的事项以及需要专项确认的变化。无需为正常局部实现的每一条语句、变量、私有成员、构造函数或方法分别申请授权。
5. 已确认的职责、文件和行为范围内，Agent 可以自主完善正常实现细节、补齐相关注释、遵守适用命名和访问权限规则并修正自身实现疏漏。不得借实现细节新增独立业务功能、未确认的业务限制、扩大文件及公共影响范围或改变已批准的技术方案。实际文件范围或关键实现与原方案存在变化时，按“实现过程中的方案调整”处理并在交付时说明。
6. 公共基础模块、跨业务接口及共享能力、全局配置、UI 状态及交互、额外校验、资源和序列化迁移等，仍须按相应专门规范说明其具体变化及影响并取得确认。单次任务可以同时确认多个已经明确说明的相关修改，不要求分散重复请示，也不得用笼统授权代替其具体审批条件。
7. 工具调用审批、系统文件权限、自动执行模式、终端权限或其他技术操作许可，不自动等同于用户对业务设计及项目变更的批准。反之，业务方案的确认也不自动授权 Git 提交、推送、安装依赖、外部系统写入或发布等其他操作。
8. 用户明确要求停止、撤销授权或改变任务目标时，应停止不再获授权的后续操作。已确认方案若因项目变化、依赖变化或新需求而失效，必须重新说明受影响部分并取得确认，不沿用过期授权实施不同方案。

授权判断参考：

| 用户表达或情形 | 默认判断 |
|---|---|
| “这个功能怎么设计”“给我看看方案” | 只进行设计或说明 |
| “给我审计一下” | 只进行调查及审计，不自动修复 |
| “这个架构没问题” | 认可设计方向，不自动授权写入项目 |
| “按照刚才确认的方案修改” | 授权该具体实施方案 |
| “确认，开始实现” | 授权已说明的对应实施方案 |
| 对明确实施请示回复 OK | 按上下文授权该实施方案 |
| 对讨论中的设计建议回复 OK | 不自动视为实施授权 |
| 工具允许执行写入命令 | 仅表示工具操作权限，仍检查项目变更授权 |

## 开发前调查与已有实现识别

1. **先调查实际项目，再设计具体实现。** 在确定修改方案前，应根据目标任务阅读核心入口、相关专项规范及已经明确适用的项目规范，检查现有代码、实际架构、框架及相关依赖，不得直接以其他项目模板生成不符合当前项目的实现。 按[规则优先级与冲突处理规范](RulePriority.md)识别实际目标范围的有效上层及局部规则、相关专项主定义、既有专用约定和例外；关键规则无法确认时不得假定其内容或已合规。
2. 按实际任务执行以下相关调查，不要求每次简单修改都扫描整个项目或输出完整调查报告：

| 调查维度 | 检查内容 |
|---|---|
| 规范调查 | AGENTS.md 及实际适用的用户级、项目、领域、目标目录或特定对象规则，相关专项主定义、规则冲突及有效例外 |
| 架构调查 | 已有 Manager、System、Controller、单例机制、所属领域及公共框架 |
| 代码调查 | 目标文件、现有类型、方法、局部实现及合法可复用能力 |
| 依赖调查 | 实际调用方、输入输出、事件、状态持有者、提交路径及跨 System 协作 |
| Unity 调查 | 相关 Prefab、场景、组件、序列化字段、绑定、资源路径及生成产物 |
| 技术调查 | Unity 版本、目标平台、插件及包、程序集、语言特性和实际 API 契约 |
| 工作区调查 | 当前实际文件内容、版本管理状态、已有用户修改及可能的并行修改 |

3. **不得凭名称推断实际契约。** 例如不能假设 EventSystem 一定具有 Publish<T> 接口、项目一定使用名为 Singleton<T> 的基类，或某个配置一定来自 ScriptableObject。应核对实际类型定义、调用方式、初始化、数据来源及生命周期，第三方和 Unity API 须匹配项目当前版本及已有契约。
4. 项目已有适用单例、事件、配置、日志、资源、对象池、输入、持久化及其他公共能力时，优先复用。不得为符合默认命名、设计模式或个人偏好建立承担相同职责的平行框架；存在真实不足时，先评估扩展已有实现，再提出必要的替代或重构方案。
5. 需要修改现有接口、数据结构或资源引用时，应按实际调用及维护关系追踪相关使用方，不仅检查当前文件。涉及 UnityEvent、动画事件、序列化、反射、第三方插件、字符串资源路径、自动生成或其他动态依赖时，应识别实际可见证据及无法静态确认的部分。
6. 调查过程默认只读，可以阅读源代码、配置文本和已有文档，检查文件与目录、搜索定义及调用、分析用户提供的错误信息及运行结果，使用符合本节约束的 Git 只读命令。不得以调查为由修改项目、自动补引用、安装依赖、生成资源、主动编译或运行项目。
7. 对任务影响较小、能够由既有稳定契约明确判断的细节，可在方案中简要说明；涉及实际缺陷、职责冲突、未知业务规则、不可确认的关键技术前提或公共能力改造时，必须明确报告依据、风险及候选处理方案，不得虚构 API、配置值或实现事实。

## 修改前方案设计及说明

1. **方案须足以供用户审查实际行为及影响。** 在完成必要调查和技术实现方案设计与评估后，向用户说明准备采用的实现、推荐理由及落实方式；重要技术决策应在实施前可审查，不得在完成修改后才首次告知用户。 技术设计说明及有实际价值的候选方案比较按[技术实现方案设计与评估规范](../Design/TechnicalDesign.md)纳入本次修改方案，不强制创建独立技术文档。
2. 修改方案按相关范围包含以下内容，已明确的需求及约定无需反复展开：

| 方案内容 | 说明要求 |
|---|---|
| 需求理解 | 本次目标、预期结果及边界 |
| 当前实现 | 已识别的现有能力、真实问题及依据 |
| 技术方案 | 拟采用的设计模式、算法、数据结构或其他实现机制；按实际任务说明调查依据、重要候选对比、推荐理由、取舍及待验证事项，具体遵循[技术实现方案设计与评估规范](../Design/TechnicalDesign.md) |
| 职责归属 | 相关类型、层级、依赖方向、输入输出及实际职责 |
| 修改清单 | 拟新增、修改、移动、重命名及删除的文件与原因，必要时给出目标路径 |
| 行为变化 | 修改前后业务、UI、执行、结果、异常或其他契约的区别 |
| 影响范围 | 调用方、公共模块、资源、配置、存档、生成及工程影响 |
| 保留内容 | 相关但明确不改变的既有业务、接口、UI 及稳定架构 |
| 手动操作 | 需要用户完成的绑定、挂载、配置、导表、生成或其他操作 |
| 风险及待确认项 | 无法静态确认的依赖、实际限制、重要规则裁决、真实冲突及例外、候选方案与待用户决定的事项；具体遵循[规则优先级与冲突处理规范](RulePriority.md) |

3. 简单修改可以简要说明目标位置、具体原因和行为变化；普通功能应说明相关职责及处理流程、修改清单和影响；完整系统应说明整体职责、数据流、接口及相关生命周期；公共框架、存档、数据库、资源架构、程序集及全局设置等高影响修改，应详细说明真实调用方、兼容性、迁移风险和有意义的候选方案。
4. 用户需要审查具体代码时，应提供足以判断实现方式的代码或差异示例；通常不要求在修改前展示所有最终代码。方案文字、目录树、调用关系图、表格或代码示例均可用于清楚表达方案，不强制采用某一种表现形式或创建独立方案文件。
5. 涉及业务规则、UI、附加限制、公共能力、接口或其他专门授权事项时，按对应章节提供必要的专项说明。不得将重要行为变化隐藏在“优化”“兼容”“增强健壮性”“整理代码”等宽泛描述中。
6. 方案应明确由 Agent 执行的静态检查、需用户手动完成的编译和运行验证，以及有实际意义的验收场景与预期结果。不得把待验证事项描述为已经通过验证；不为提交方案擅自执行验证。

方案简例：新增背包整理功能。以下为说明方案结构的示例，不确立排序规则、整理按钮、存档策略或必须建立的类型。

```text
目标：按用户已确认的排序规则整理背包物品。
技术方案：规则判断与排序算法分离，计算结果由所属系统组织提交。
职责关系：
    InventorySystem
        → InventorySortLogic
            → InventorySortRules
            → InventorySortAlgorithm
        → InventorySortCommitter
拟修改：InventorySystem.cs 的业务入口。
拟新增：对应 Logic、Rules、Algorithm、Committer 等已确认职责文件。
行为范围：调整物品排列顺序，不改变数量、堆叠规则及容量。
不修改：未获授权的 UI、存档结构和其他业务 System。
验证：Agent 静态审查，用户手动验证整理结果及原有业务行为。
```

## 修改范围控制与架构保护

1. **最小化非必要影响，而非最小化代码量、文件数量、类型数量或架构层级。** Agent 应完整实现用户确认的任务和稳定职责边界，不得仅为减少修改文件、缩短调用链或压缩代码而将独立职责合并到 System、绕过 Logic 或 Committer，或者放弃必要的细粒度组织。
2. 已确认的架构先行允许在当前实现较简单时建立稳定职责边界；不得为了填充架构、展示技术能力或预防假设性需求而新增未确认的业务功能、缓存、队列、重试、状态机、全局框架等运行机制。继续遵守[架构设计与职责拆分规范](../Architecture/ArchitecturePrinciples.md)。
3. 目标功能所必需且已经获授权的代码实现、相关调用调整、文件新增、注释补齐及自身实现疏漏修正可以完整进行。与任务无关的重构、命名统一、格式化、接口调整、目录迁移、资源处理或其他修改不默认执行。
4. 必须区分必要技术前置条件与 Agent 自行添加的业务约束。不得以异常处理、参数检查、性能优化、日志、资源管理、设计模式或架构规范为由擅自增加业务拒绝、自动恢复、兜底、UI 状态变化或未确认的运行机制。
5. 保持未要求改变的原有行为，包括业务规则、数值、调用契约、执行时机、事件及状态提交、资源路径、配置来源、UI、序列化引用和项目设置等。若无法在现有契约内完成目标任务，应明确冲突及候选方案，不能悄悄以新的行为取代原有功能。
6. 不得为表面完成任务编造不存在的接口、隐藏缺失依赖、提供虚假成功结果，或以空方法、占位实现、临时默认值、重复兼容实现代替已经承诺的完整功能。确需阶段性交付或占位时，必须有明确授权、范围和后续处理说明，并如实标记未完成能力。
7. 不得为顺便落实规范而修改无关历史代码、配置或文档；规范所要求的相关修改仍应在当前已确认范围内完整实施。发现现有代码违反规范时，按实际影响报告，不自动取得整改授权。 已有稳定实现优先于通用默认方案，但已有违规不构成新增违规依据；存量保护、增量治理及整改边界遵循[规则优先级与冲突处理规范](RulePriority.md)。

## 实现过程中的方案调整

1. **方案实施中发现新问题，先判断是否属于已确认范围。** 已确认职责、文件及行为范围内的普通实现细节、局部修正和必要注释，可以自主处理；涉及新职责、计划外文件、公共接口、业务规则、UI、资源、数据或其他新增影响时，须判断是否需要补充方案及用户确认。
2. 新增或变化超出已确认方案时，应说明新发现的事实、原方案不能覆盖的原因、拟修改内容、具体影响及替代方案，取得补充授权后实施。已批准的其他内容无需重复确认。
3. **计划外问题不阻塞当前任务时，继续独立且安全的已授权工作，并单独报告问题。** 不得顺手修复其他业务的 Bug、擅自重构公共框架或批量更改既有代码风格。
4. 计划外问题确实阻塞当前任务时，停止依赖该问题的修改，说明阻塞原因及实际可完成范围，提出候选方案并等待确认。不以绕过框架、创建平行接口、静默默认值、临时禁用功能或其他未经授权的行为掩盖阻塞；不受影响的已授权工作可以继续。 规则冲突、例外失效或关键规范无法确认时，同样按[规则优先级与冲突处理规范](RulePriority.md)的最小阻塞范围原则处理。
5. 已确认技术方案的关键前提、实现机制、公开行为或依赖关系发生变化时，必须在采用替代方案前重新说明并取得确认，不能仅在交付时告知已擅自更换技术方案。仍处于原授权边界内的正常局部实现细节可以继续完成，并在有实际影响时如实说明。
6. 调查中发现缺少第三方插件、工程能力、配置、资源或必要装配时，应明确缺失项及影响，不自动安装、扫描查找、修改工程设置或补齐绑定。必要运行时检查及诊断继续遵守对应规范。
7. 用户提供新的编译错误、运行异常或其他验证结果后，Agent 应分析证据、定位实际原因并提出修复范围和方案。任何后续修复仍须取得用户确认，不将用户提供错误信息视为直接修改授权，不通过主动编译或编译错误检查自行验证修复结果。

| 实施中发现的情况 | 默认处理 |
|---|---|
| 当前新增代码中的普通实现疏漏 | 在原授权范围内修正 |
| 已确认职责范围内的局部实现细节调整 | 保持原契约，自主处理 |
| 需要计划外文件或公共接口变更 | 报告新增影响，补充确认 |
| 需要改变其他 System、UI 或配置的行为 | 按对应专项授权确认 |
| 无关业务缺陷或技术债务 | 单独报告，不顺手修复 |
| 阻塞当前实现的缺失依赖或架构冲突 | 暂停受影响部分，说明候选方案 |
| 用户提供新的编译或运行错误 | 分析并提出修复方案，确认后修改 |

## 已有代码及用户修改保护

1. **以实际当前文件为基础实施。** 修改前读取目标文件及相关上下文，确认已有实现、用户修改及稳定契约；不得依据过期文本、其他版本的文件、缓存内容或假设性模板直接覆盖当前实现。
2. 仅修改已授权范围及相关必要内容。重写完整文件、删除已有功能或成员、迁移目录、改动序列化字段、批量替换术语、自动格式化整个文件、调整编码或换行风格等，须有实际需要并处于明确确认的范围内。普通局部修改应保留无关方法、有效注释及已有文件风格；被修改的类及方法仍须按代码注释规范补齐相关说明。 注释维护覆盖实际受影响的类型及成员、调用契约、关键流程和设计说明，不自动扩大为全文件或全项目注释整改。
3. 不得仅因未找到直接 C# 调用，就判定现有代码、资源、Prefab、事件或配置可以删除。应检查真实调用、序列化、Inspector、动画、反射、第三方接口、生成及动态路径依赖；无法静态确认的关系应说明风险，删除、移动及重命名继续遵守文件归属和专项授权规范。
4. **保护用户已有成果和未提交修改。** 当前工作区存在已暂存、未暂存、未跟踪的文件或其他尚未提交的变更时，不得为获得干净工作区而恢复、覆盖、清理或删除。目标文件已有修改时，应以实际内容为基础保留其语义，在确认范围内进行局部修改。
5. 应按任务范围检查并区分修改前已有变更、本任务实际变更及实施期间出现的其他来源变更。不要求每次创建提交、备份或新分支。缺少版本管理或无法可靠区分来源时，应说明检查范围及不确定性，不将工作区全部差异报告为本 Agent 所作。
6. 第三方代码、包和生成产物须遵守实际维护来源及对应专门规范；不得通过直接修改生成文件、清理缓存、重建 .meta 或替换插件实现规避既有维护流程。
7. 实施前后均应保护已有序列化和资源契约。需要迁移时按已经批准的具体范围保留 .meta、GUID、已有引用及合法调用；不擅自重建或自动修复无法确认的绑定。

## 多 Agent 协作与并行修改

1. **用户及其他 Agent 的修改受到同等保护。** 不得擅自恢复、清理、移动、删除或覆盖其他任务产生的文件和改动，也不得将其他来源的修改视为本任务自动获得的重构范围。
2. 在实际存在并行开发或工作区可能发生变化时，应在实施前检查目标文件当前内容，在写入和最终交付前根据实际情况重新核对变更。发现相关公共契约、目标文件或依赖被并行修改时，应重新识别实际内容和调用影响，而不是继续依据旧版本执行。 相关规则及例外发生变化时亦应核对其真实生效范围、用户决策及实际影响；不得仅凭其他 Agent 的修改推断规则已经调整或获得额外授权。
3. 并行修改涉及互不冲突的代码区域且可以确认保留双方成果时，可以在原授权范围内基于最新文件继续完成当前任务；同一代码区域、职责边界或稳定契约发生不能安全处理的冲突时，暂停冲突部分，说明差异、影响和候选合并方案，经确认后处理。
4. 不因另一个 Agent 创建了某个文件或类型，就假设它正确、可删除或属于当前任务。需要调用该能力时仍须检查其真实契约；需要修改其他 Agent 的成果时按实际授权和影响范围处理。
5. 不要求为了并行开发统一建立文件锁、任务管理框架、全局 Agent 协作系统或强制新建 Git 分支、Worktree。采用这些机制应遵循项目实际工作流及用户明确授权。
6. 最终交付应区分本任务实际改动、保留的其他来源改动、发现的冲突及未解决部分；只有具有实际证据时才能确认本任务没有覆盖已有成果，不虚构并行状态或修改归属。

## Git 与版本管理操作

1. **Git 只读调查与版本库变更分别授权。** 可以使用不会改变项目文件、暂存区、分支、远端及其他版本管理状态的只读查询理解当前状态和修改范围。实际命令参数、脚本、别名及工具效果应符合只读要求。
2. 修改项目代码的授权不自动包括暂存、提交、推送、同步远端、切换分支、创建 Worktree、合并、回滚或改写历史等操作。须根据用户明确授权的版本管理动作及实际范围执行，不把工具执行许可或默认工作流视为无限制操作授权。

| 操作或命令 | 默认权限及约束 |
|---|---|
| `git status`、`git diff`、`git log`、`git show`、`git blame` 等只读查询 | 允许按任务相关范围使用 |
| `git add`、调整暂存区 | 不默认执行，须有明确授权 |
| `git commit` | 用户明确授权后按实际提交范围执行 |
| `git push`、发布远端分支或标签 | 用户明确授权后按具体目标执行 |
| `git fetch`、`git pull` 等远端同步 | 涉及网络及版本库状态变化，须明确授权 |
| `git merge`、`git rebase`、`git cherry-pick`、`git revert` | 用户明确授权后按实际范围执行 |
| `git stash` 及其应用、删除操作 | 用户明确授权后执行，保护已有工作 |
| 创建、删除、切换分支或 Worktree | 用户明确授权后执行 |
| `git restore`、`git checkout --`、`git reset` 等恢复或覆盖操作 | 不得擅自执行，需确认具体对象和影响 |
| `git reset --hard`、`git clean`、强制推送及其他高风险覆盖或删除操作 | 禁止擅自执行；确有需求时须单独说明实际丢失风险、对象及范围并取得具体授权 |

3. 即使用户已经授权 Git 操作，也不得无依据将无关文件、其他 Agent 或用户未授权的修改纳入暂存、提交、恢复、推送或删除范围。应核对已有暂存内容、目标分支、涉及路径及远端目标；发现范围不清、可能覆盖其他成果时先报告。
4. 不为减少冲突、获取干净工作区、重新开始任务或修复错误而自动 stash、reset、clean、restore、切换分支或覆盖文件；不将回滚当作任务失败或中断的默认行为。需要撤销本任务已经发生的修改时，应说明撤销范围及对当前文件的影响，并取得确认。
5. 不强制每次开发前新建提交、备份文件、分支或 Worktree；沿用项目已明确的版本管理方式，仍需保护用户已有变更和操作授权。项目没有 Git 时，可以通过当前文件及任务相关差异进行静态审查，不擅自初始化版本库。
6. 实际执行过的版本管理状态变更应在交付中说明操作、作用范围及可确认结果；未执行的提交、推送或同步不得报告为已完成。

## 工具使用与操作权限

1. **按实际操作效果，而非工具名称或实现形式判断权限。** 通过命令行、Unity MCP、编辑器脚本、文件写入、自动化、第三方服务或子 Agent 实施的项目修改，与直接手工修改文件具有同样的授权约束。
2. 只读调查可以使用当前可用且不会主动触发编译、编译错误检查、运行验证或未授权变更的工具。若工具会写入工程、改变 Unity 场景或 Inspector、执行生成流程或改变外部状态，应在实施前查明实际作用和影响，不能凭工具名称假定安全。
3. 允许在已确认任务范围内使用工具完成代码及合法资源修改，不要求用户分别确认每个普通编辑命令。工具的实际输入、输出、覆盖范围、外部调用及可能副作用超出授权时，须重新确认相应操作。

| 操作类型 | 默认处理 |
|---|---|
| 阅读源文件、搜索类型和调用方、读取已有配置及资源结构 | 允许符合约束的只读调查 |
| 创建、修改项目脚本或文档 | 先明确方案并确认，在授权内执行 |
| 创建或修改场景对象、组件、Prefab、资产 | 按项目修改、Unity 及 UI 等专项授权执行 |
| 手动修改 Unity 序列化文本 | 说明原因和引用影响，优先使用已有适用编辑器或工具，按确认范围执行 |
| 修改 ProjectSettings、Packages、asmdef 或安装、升级插件 | 说明真实技术需求、项目及平台影响，明确确认后执行 |
| 导表、代码生成及资源处理工具 | 确认真实维护来源、输入输出和清理范围及执行权限 |
| 修改外部数据库结构、数据、服务或云端配置 | 必须取得对应具体外部变更授权 |
| 上传数据、部署、发布、执行 Git 远端写入 | 必须取得对应具体操作授权 |
| 主动编译、编译错误检查、运行或性能验证 | 禁止，具体遵循下方验证权限 |

4. 使用 Unity 编辑器或 MCP 工具时，应分别识别读取场景及组件信息、修改内存中的场景对象、保存场景、应用 Prefab Override、资产导入、编译及运行操作的实际效果。不能因为没有直接修改 .unity 或 .prefab 文件，就将场景对象、引用或 Inspector 的改变视为只读行为。
5. 需要工具安装、包升级、项目设置变更、外部网络数据传输或远端写入时，应明确真实需要、目标、权限及影响，不为完成普通代码任务擅自改变环境。不得将认证凭据或其他敏感信息无依据写入源码、配置、日志或外部服务。
6. 子 Agent、自动化任务及工具脚本均须遵循当前已确认的项目范围和禁止事项。不得通过委托执行或间接工具调用规避修改授权、编译限制、手动绑定或用户已有修改保护。
7. 工具不存在、无法确认其实际行为、执行失败或结果无法核实时，应如实报告限制，选择当前已获授权且符合要求的替代方式，或交付已经完成的独立部分；不虚构工具执行结果、文件内容及修改状态。

## 静态审查及验证权限

1. **Agent 必须在任务交付前完成与实际修改相关的静态文本及代码审查。** 静态审查用于检查已实现代码与用户确认方案、职责边界、实际依赖、命名及注释、序列化、资源生命周期和其他适用规范是否一致，不以运行代码、构建项目或编译诊断为手段。
2. **禁止主动编译、编译错误检查、编译验证及运行验证。** 本限制覆盖调查、开发、修复、实施、静态审查及交付全部阶段，而不只是在完成任务之后。所有项目编译及实际运行验证由用户手动完成；Agent 仅分析用户提供的编译结果、错误信息、运行日志及测量证据，提出方案并在确认后修复。
3. 不得使用 Unity 编辑器、Unity Batch Mode、dotnet build、MSBuild、其他编译命令、Unity Console 的编译错误查询、编译诊断工具或语言服务器等主动执行或获取编译错误诊断；也不得通过名称为检查、验证、测试或其他形式的工具间接执行上述操作。静态阅读代码、查阅定义及调用、检查文本差异等不触发编译或编译错误检查的操作仍然允许。
4. 不得启动 Play Mode、执行自动化测试、运行游戏、主动进行性能测试、采集运行 Profiler 数据及内存快照，或主动打包项目作为验证手段。项目构建、测试、运行、性能测量和功能验收由用户手动执行；Agent 可以提供操作步骤和预期结果并分析用户提供的结果。
5. **保留正常操作引发被动 Unity 编译的既有例外。** 已确认的正常文件写入、资源修改或其他合法开发操作可能由 Unity 自身被动触发自动编译，允许此类非验证目的的附带行为。不得借此主动要求刷新、重新编译或执行构建来获得编译结果，不得继续查询相应编译诊断或主动修复未经用户提供的编译错误。
6. 静态审查可以检查源代码、调用关系、接口及数据契约、文本差异、目录及命名、注释、Odin 父子分组、序列化字段、资源路径、.meta 与 GUID、权威状态和清理路径等实际相关信息。不要求通过编译器、语言服务器诊断、运行测试或额外安装分析工具来完成审查。 注释覆盖、格式、内容一致性及 Region 的静态检查具体遵循[代码注释规范](../Code/Comments.md)，不通过主动编译或编译错误诊断核对注释。
7. 根据当前任务范围处理静态审查发现的自身实现疏漏；超出授权范围的问题须先报告并确认。静态审查不能取代用户运行验收，也不能保证 Unity 导入、序列化、反射、外部服务及平台上的实际行为一定正确。
8. **不得虚构验证结果。** 只报告已经真实执行的检查及其结果；区分静态确认、静态推断、用户提供的实际结果、预期行为及待验证风险。未主动编译或运行时不得声称“已通过编译”“测试全部通过”“功能运行正常”“不存在错误”等未经验证的结论。

## 任务中断与恢复

1. 用户要求停止、当前任务中断、工具失败或上下文发生变化时，停止未获继续授权的操作。不能假定已经写入的文件、Unity 内存状态、外部修改或版本库操作自动撤销。
2. 任务未完整完成时，应如实说明已完成部分、实际写入或未确认的变更、尚未实施部分、当前阻塞及可能影响。能够核实当前状态时应核实；因中断无法确认时明确标记，不宣称整体完成或全部恢复。
3. 用户要求继续原任务时，应先重新阅读目标文件、当前相关规范及实际工作区状态，核对此前已确认的方案和实际完成情况，避免重复新增、重复修改或覆盖中断期间用户及其他 Agent 的成果。 同时核对适用规则、重要规则决策及例外的生效和结束条件，避免沿用已经失效的例外或授权。
4. 原方案仍然成立且任务范围没有变化时，可以继续已确认的剩余部分，不重复请示相同内容；如项目、依赖、业务需求或方案边界已经变化，应对新增影响及冲突提出补充方案并取得确认。
5. 不默认撤销、回滚、清理未完成文件、重置仓库或重建 Unity 资源来恢复任务前状态。需要撤销时，说明本任务实际修改、其他来源变更、目标恢复范围及可能风险，按具体授权处理并保护用户已有成果。
6. 不将任务分批实施或中断视为创建新业务机制、自动补齐占位实现或修改其他文件的授权。最终交付应明确实际完成边界及仍需要用户处理的事项。

## 最终交付规范

1. **交付必须与实际修改及已确认方案一致。** 不仅说明任务是否完成，还应让用户能够确认发生了哪些修改、采用何种核心实现、影响了哪些既有契约，以及下一步需要手动完成什么。尚未实施、部分完成或无法核实的事项应明确标记。
2. 默认采用以下统一交付结构。根据任务规模简化或合并不必要的部分，不要求简单任务输出完整长篇报告；与任务实际相关的关键内容不得遗漏，不能以“其他优化”“顺手修复”等含糊表述隐藏变更。

| 交付内容 | 具体要求 |
|---|---|
| 01. 完成情况 | 已实现目标、已完成及未完成内容、实际阻塞和限制 |
| 02. 文件修改清单 | 本任务实际新增、修改、移动、重命名及删除的文件和用途 |
| 03. 核心实现说明 | 实际采用的技术方案、关键设计模式、算法及数据结构、职责组织、调用关系和数据流；按实际任务说明关键取舍、扩展方式及外部依赖来源 |
| 04. 行为与影响范围 | 实际业务及接口变化、公共框架、配置、资源、UI 和其他相关影响，必要的授权依据、重要规则裁决及例外范围、规范变更及与原方案的差异 |
| 05. 用户手动操作 | Inspector 引用、组件挂载、资源配置、导表、生成和其他前置操作 |
| 06. 用户手动验证 | 具体场景、操作步骤及预期结果，明确这些是待验证事项 |
| 07. 静态审查情况 | 实际执行的检查及结果、未能核实的事项、历史问题、剩余规则冲突、风险和待确认项 |
| 08. 编译与运行状态 | 如实明确未主动编译、检查编译错误、运行项目或执行测试；用户提供的验证结果另行注明 |

3. 文件清单使用真实可定位的项目相对路径，说明新增、修改、移动、重命名及删除的具体文件与实际用途。必要时提供对应类型、方法或行号；移动及重命名同时说明原路径和目标路径。应区分本任务改动与其他来源改动，不要求将所有代码全文重新粘贴到对话，用户明确要求完整代码或文件时按实际请求交付。
4. 对实际改变的公共接口、运行行为、UI 状态、交互、界面结构、校验及附加限制、配置与资源契约、状态提交、异步执行及其他专项变化，应说明变化内容、影响范围及对应授权来源；与原方案存在的差异、实现过程中作出的重要局部决策及其依据也应如实说明。不得宣称无影响而遗漏已知变更。 涉及重要规则选择、局部长期例外、规则调整及尚未解决冲突时，按[规则优先级与冲突处理规范](RulePriority.md)说明实际决策依据、有效范围及受影响的实施状态。
5. **Unity 手动绑定及配置清单为相关任务的必要交付内容。** 按[Unity 项目约束](../Unity/ProjectConstraints.md)列出需要用户手动拖拽、挂载、绑定或配置的所属脚本或对象、字段名、期望类型、建议绑定位置及用途。必要时说明必需或可选语义、相关 Prefab 或场景及配置前置条件。无法静态确认的绑定必须标记为“需要用户手动确认”，不得报告已正确绑定；无新增绑定要求时可以明确说明。
6. 涉及配置表、生成代码及数据、SO、二进制、JSON、Addressables、Prefab、场景、包、项目设置等实际运行依赖时，应说明真实维护来源、用户需要手动执行的生成、导入、配置或迁移步骤，指出相关影响及验证事项。不得把未生成的产物、未配置的引用或未执行的工具动作报告为已完成。
7. **手动验证步骤应具有可操作性。** 根据实际修改提供相关场景、必要前置条件、操作步骤及预期结果，覆盖关键正常路径以及存在实际需求的失败、取消、事件、并发、部分提交、资源清理和原有行为保护等场景。性能相关任务应按既有规范说明需用户测量的条件及指标；不为无关情况机械增加验证步骤。
8. 静态审查只报告实际检查过的范围、发现的问题及处理结果，标明无法静态确认的依赖、序列化、运行和平台风险。必须如实说明剩余问题、技术限制、尚未验证的假设及需要用户决定的事项，不得用完成代码修改代替实际运行验收。
9. 已执行的 Git 及外部系统变更应明确其实际操作和结果；未执行的操作不得宣称已完成。普通代码交付不默认暂存、提交、推送或发布。
10. 项目开发任务交付时应明确实际编译及运行验证状态，例如：“已完成本次授权范围内的代码实现与相关静态审查；未主动编译、检查编译错误或运行验证，需用户在 Unity 中手动完成以下验证。”只有实际完成相关审查时才使用相应完成表述；用户已提供的验证证据应单独如实记录。

## 规范文档读取机制

### 规范来源与路径定位

1. 通用规范的权威维护来源为独立 GitHub 规范仓库；本地 Codex Home 中的 `AGENTS.md` 与 `Standards/` 是实际使用的部署副本。读取时应确认当前任务使用的有效规范来源，不将未同步的 GitHub 内容、开发分支或其他项目副本视为本地已生效规则。
2. 默认通用规范根目录为当前实际 `CodexHome/Standards/`。`CodexHome`、`StandardsRoot` 与 `ProjectRoot` 是逻辑路径名称，不是 Codex 原生环境变量或可直接执行的路径；实际读取前必须根据当前环境核实真实位置及访问权限。
3. Markdown 相对路径以包含该链接的文档所在目录为解析基准。跨用户级规范根目录、项目根目录及局部目录的引用，应明确来源，不得按当前终端工作目录错误解析。
4. 项目专用规范与局部规范采用增量方式补充通用规范。项目事实、项目契约、项目专用规则及明确批准的规则例外分别判断，不因项目文件存在或类型名称相同就替代通用规则主定义。

### 原生加载与目标目录主动发现

1. Codex 原生发现的用户级及项目级指令作为初始入口，不假定原生启动加载已经覆盖当前任务涉及的全部子目录规则或 `Standards/` 中的专项 Markdown。
2. 明确实际调查或修改目标后，应检查项目根目录至目标目录之间的适用规则文件。普通局部规则默认使用 `AGENTS.md`；同目录存在有效 `AGENTS.override.md` 时，按 Codex 原生同目录选择机制将其视为普通 `AGENTS.md` 的替代入口，而非增量合并文件。
3. 目录规则按实际作用域继承、补充及细化。目录更深、文件名含 override 或规则描述更具体，不自动取得解除上层硬性约束或授权条件的权限。局部规则不得无依据传播到相邻目录、其他领域或其他项目。
4. 新增文件时检查计划创建位置及其父目录；修改文件时检查目标文件所属目录及父目录；删除文件时检查原位置；移动或重命名时同时检查原位置与目标位置。跨多个目录的任务应分别检查各自适用规范及共享接口契约。
5. 目标范围尚不明确时，可以进行必要的只读目录调查和文件定位；范围明确后，应在技术方案设计及实施前完成相关规范发现。不得默认遍历并读取整个项目的全部局部规范。

### 专项规范的按需匹配

1. 专项规范采用规则引导的按需读取方式，不默认全量读取全部30份规范，也不得仅凭 Agent 自身经验忽略实际适用规则。
2. 根据以下五个维度综合确定初始阅读集合：
   - 任务性质：新增、修复、重构、架构设计、性能优化、规范维护等。
   - 职责类型：Manager、System、Controller、Logic、Processor、Committer、Formula 等实际职责。
   - 技术机制：事件、状态提交、配置、资源、对象池、日志、异步、并发、持久化、渲染等。
   - 文件及资源类型：C#、Prefab、场景、SO、Excel、JSON、二进制、asmdef、生成代码等。
   - 实际影响与授权：UI、业务限制、公开接口、权威状态、公共框架、序列化及其他专项变更。
3. 核心入口中的文档索引用于定位规范及适用范围；任务索引用于形成初始阅读集合。索引不是封闭清单。调查中发现新职责、技术机制、文件类型或实际影响时，必须补充读取对应规范。
4. 选定的专项规范默认完整读取。仅在任务范围明确、章节定位准确且不会遗漏适用条件、约束、例外及必要关联规则时，允许定向读取相关章节。标题、摘要、关键词命中或孤立条款不等于完成必要读取。
5. 新建公共框架、完整系统设计、重要架构调整、规则冲突及规范维护任务，应完整掌握相关专项规范及必要依赖。读取数量不设固定上限，不为减少上下文而遗漏必要规则。

### 关联规范与递进读取

1. 规范引用分为三类：基础依赖、条件协作及参考关联。基础依赖必须读取或确认已经有效掌握；条件协作在触发条件成立时必须读取；参考关联按真实设计、理解及研究需要读取。
2. 引用分类不改变规范本身的适用性及约束强度。即使某份规范被列为参考关联，只要它根据当前任务实际适用，仍必须读取。
3. 读取专项规范后，识别其基础依赖和条件协作关系，按任务实际情况递进展开。条件尚未明确且可能影响技术选型时，应在方案确认前提前掌握相关规则。
4. 不因普通 Markdown 链接存在就无条件递归读取全部文档。根据文档 ID、实际来源、有效版本及已掌握的阅读范围去重；已有效掌握的规则可在当前任务内复用。
5. 遇到循环引用时，终止重复展开路径，但不得因此跳过尚未掌握的必要规则。基础依赖之间形成循环时应检查职责归属；条件协作或参考关联存在双向引用不自动构成错误。
6. 不设置固定递归深度或文档数量上限。当当前任务的必要规则及实际适用依赖均已掌握时，结束本轮递进读取。

### 动态补读与上下文恢复

1. 规范读取贯穿任务生命周期。已有效掌握且来源、内容及适用条件未变化的规则可以复用，不机械重复读取。
2. 新增职责、技术机制、文件操作范围、业务影响、专项授权事项或跨领域协作时，应补充读取对应规范。补读不构成新增实施授权；超出已确认方案仍须按授权规则补充确认。
3. 规范读取状态至少区分：未读取、部分读取、有效掌握、待补充、有效性待核对及读取受阻。记录状态用于定位和恢复，不得凭状态标签虚构实际读取或理解结果。
4. 规范文件、来源、版本或实际内容发生变化时，重新评估对当前任务的影响。任务期间默认保持有效规范来源稳定，不混用未经核实的不同版本。
5. 发生上下文压缩、关键规则缺失或任务中断恢复时，重新核对核心治理、目标范围规范、实际项目状态、已确认方案、完成情况及剩余授权。无需重读全部规范，只恢复当前任务实际需要但无法继续确认的规则。
6. 子 Agent 必须获得自身任务适用的有效规范、项目契约、局部规则及授权范围。主 Agent 的读取结果只有在实际内容、来源及适用范围已明确传递时才可复用；不得假定其他 Agent 的阅读自动成为自身上下文。

### 读取检查、失败处理与执行保障

1. 有效读取应确认来源有效、阅读范围完整、规则语义及适用条件明确、版本时效有效，并且影响实施的冲突已处理。仅知道文件存在、查看索引或摘要、搜索关键词，不视为完成必要读取。
2. 在重要技术决策、实施修改前及静态审查时，核对当前适用规范是否已有效掌握。规范读取检查与实际规范符合性检查分别处理；已读取不代表代码已经符合规则。
3. 读取失败应区分定位失败、文件缺失、访问失败、内容不完整、来源或版本异常及规则冲突。优先通过允许的只读调查恢复实际规则，不虚构内容、不擅自创建替代规范、不扩大文件权限、不自动同步 GitHub。
4. 必要规范无法有效掌握时，不得实施受该规范约束的修改；已授权且不受影响的独立工作可以继续。按最小阻塞范围处理，并说明实际调查范围及未解决问题。
5. 当前默认采用行为规范约束与流程检查，不强制引入 Hooks、读取追踪程序、依赖数据库或自定义加载器。工具级保障仅在存在实际问题、明确方案及授权后引入；自动化不得替代语义判断、用户授权或静态审查。
6. 不强制输出完整规范读取报告。对重要规则依据、读取失败、规则冲突、有效例外、规范版本变化及实际违规情况进行必要披露。
