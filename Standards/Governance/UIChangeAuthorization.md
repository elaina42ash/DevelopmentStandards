# UI 与交互变更授权规范

## 规范定位与适用范围

定义 UI 状态、交互方式及界面结构变更的独立授权边界。

本规范是对应专业事项的规则主定义文档。规则适用范围、约束性质、优先关系及例外统一遵循 [规则优先级与冲突处理规范](RulePriority.md)；项目修改、读取、实施及交付遵循 [AI 修改与交付规范](AgentWorkflow.md)。

## UI 与交互变更授权规则

1. UI 状态、交互方式和界面结构的变更，必须基于用户明确要求，或基于 Agent 提出并经用户确认的具体方案。Agent 可以主动提出建议，但不得将建议直接实施为修改。已经明确确认的内容，在授权范围内无需重复确认。 本节为 UI 及交互变更授权的主定义，满足对应专项授权属于正常规则执行；其他规范的技术选择或局部约定不自动解除本节授权条件。

2. 用户确认业务功能、算法、数据处理、接口调整或问题修复，不代表同时授权改变相关 UI。不得以“属于同一业务模块”“实现时顺便处理”“优化体验”“增强健壮性”或“防止误操作”为由，自行扩大 UI 修改范围。

3. 未经上述授权，不得新增、删除或改变控件状态控制逻辑，包括按钮启用或禁用、置灰、显示或隐藏、交互锁定及自动恢复。此限制同时覆盖直接修改控件，以及通过父对象、CanvasGroup、遮罩、射线拦截或组件开关等方式间接影响交互。

4. 未经上述授权，不得新增按钮、面板、弹窗、提示文字、Loading、遮罩、占位界面或替代控件；不得删除、销毁、替换或重建现有 UI，也不得擅自改变现有界面的层级、布局、对象名称、组件和引用绑定。此规则同时适用于脚本、Prefab、场景、编辑器工具和运行时创建逻辑。

5. 加载中、请求中、数据未就绪、条件不满足、引用缺失或操作失败，本身不构成改变 UI 状态或创建 UI 的授权。必要的业务校验和错误处理仍应按项目规范执行，其必要性与授权边界必须遵守[校验与附加限制授权规范](ValidationAuthorization.md)；如果 Agent 认为还需要禁用控件、锁定页面或增加提示，必须另行说明具体方案并取得确认。 异步业务的执行状态、并发控制及取消策略不自动构成 UI 交互变更授权，具体业务约束见[异步业务与状态一致性规范](../Runtime/StateConsistency.md)。

6. Agent 主动建议 UI 变更时，必须在修改前说明涉及的界面和控件、当前行为、修改后的行为、触发及恢复条件、修改原因和影响范围。用户确认后只能实施该具体方案；新增的交互行为或结构调整仍须再次确认。

7. 本规范不要求删除或重写现有 UI 状态逻辑。已确认任务所需的正常数据显示、内容刷新，以及沿用既有机制的列表条目创建、复用和回收，可以在已确认范围内执行；不得借此新增交互规则或重建现有界面。 列表池化、虚拟化、减少刷新及其他表现性能优化不自动授权改变排序、布局、交互或已有显示契约。

8. 交付时，若实际改变了 UI 状态控制、交互方式或界面对象，必须简要列出变更内容及其对应的用户要求或已确认方案，不得将其隐藏在“其他优化”或“顺手修复”中。
