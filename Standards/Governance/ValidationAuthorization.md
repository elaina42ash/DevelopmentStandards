# 校验与附加限制授权规范

## 规范定位与适用范围

定义校验依据、附加限制、拦截、自动修正及兜底行为的授权边界。

本规范是对应专业事项的规则主定义文档。规则适用范围、约束性质、优先关系及例外统一遵循 [规则优先级与冲突处理规范](RulePriority.md)；项目修改、读取、实施及交付遵循 [AI 修改与交付规范](AgentWorkflow.md)。

## 校验与附加限制授权规则

1. **校验必须有依据。** 阻断执行的条件必须来自用户明确要求、已确认方案，或可验证的实际运行依赖；不得自行创造业务规则或配置契约。
2. **摆放习惯不等于运行契约。** 不得仅根据当前对象名称、父子层级、路径、排列顺序、场景或 Prefab 归属，增加强制校验。确有技术依赖时，必须说明具体依赖。
3. **额外限制必须先获授权。** 为防止误操作、增强健壮性或规范配置而新增的限制、拦截、自动修正、恢复、重试或兜底行为，必须由用户明确要求，或先提出具体方案并取得确认。 新增请求拒绝、排队、取消旧请求、去重、合并、超时、重试及其他会改变业务行为的并发处理策略，同样必须具有明确需求、既有契约或经确认的方案。 配置校验、自动修正、缺失兜底、自动覆盖及加载重试等额外行为，同样须具有明确依据并遵守[配置数据管理规范](../Runtime/Configuration.md)。 对象池容量、查询缓冲区容量、缓存失效、调度预算及其他资源限制不得被擅自转化为业务拒绝、结果截断或玩法限制，具体遵循[性能与内存管理规范](../Runtime/Performance.md)、[对象池规范](../Runtime/ObjectPooling.md)、[资源管理规范](../Runtime/ResourceManagement.md)。 不得因局部或专项规范表述更加严格就擅自增加业务限制；规则真实冲突及例外遵循[规则优先级与冲突处理规范](RulePriority.md)，本节校验依据及授权条件继续有效。
4. **报错本身也不能成为借口。** 不得因为“只是增加错误日志、警告或提前返回”，就擅自把原本允许的配置判定为错误，或拒绝执行原有功能。
5. **保留必要错误检查。** 已确认功能必需的空引用检查、参数有效性检查及真实 API 前置条件，仍按现有规范处理；不得借此扩大为额外的层级、权限或交互限制。
6. **确认必须针对具体行为。** 请示时说明限制条件、依据、触发后果和影响范围。用户确认后可在该范围内实施，无需重复确认；不得扩大授权。
7. **交付时说明新增限制及授权来源。** 本规范不自动授权删除或重写项目已有校验，发现问题仍应先说明修改方案。
