# 代码注释规范

## 规范定位与适用范围

定义中文注释、XML 文档、关键步骤编号、Region、Inspector 及技术说明。

本规范是对应专业事项的规则主定义文档。规则适用范围、约束性质、优先关系及例外统一遵循 [规则优先级与冲突处理规范](../Governance/RulePriority.md)；项目修改、读取、实施及交付遵循 [AI 修改与交付规范](../Governance/AgentWorkflow.md)。

本规范统一规定项目自研代码的中文注释、类型和成员文档、方法内关键步骤及关键调用说明、`#region` 职责区域、技术设计意图和注释维护要求。默认采用完整语义注释型：注释既服务于人工阅读，也服务于后续 Agent 理解架构职责、真实调用契约、技术选型及维护边界。完整注释不等于逐行翻译代码，不以注释数量或篇幅代替信息质量。


## 相关规范

### 条件协作
- [代码命名规范](Naming.md)：注释需要说明类型、成员及职责命名语义时适用。
- [类的访问权限与公开接口规范](AccessControl.md)：注释涉及公开能力、调用方、访问范围及稳定契约时适用。

## 适用范围与基本原则

1. **新增或修改代码时，必须提供完整、准确的中文注释。** 按本节明确的适用范围组织区域划分、类型说明、字段及其他成员说明、方法注释、方法内关键步骤和关键调用说明。类及方法的注释不因其代码量较少、当前只有一个调用方或仅委托其他能力而省略。
2. **采用完整语义注释，而非逐行重复代码。** 注释应说明职责、用途、设计意图、业务或技术语义、关键流程及调用约束。已有清晰命名仍须遵守本节规定的声明级注释要求；局部变量及普通语句不机械逐行添加注释。
3. 注释以中文为主，类型名、方法名、字段名、API、设计模式、算法、协议标识及其他技术术语按实际契约保留必要的英文。保持注释术语与项目实际业务、命名、配置和技术实现一致，不擅自翻译稳定的外部标识或修改代码名称。
4. **注释必须以实际代码、已确认的业务需求及技术契约为依据。** 区分实际行为、必要约束、设计意图及尚待验证的事项，不虚构功能、规则、调用权限、性能结论或已经完成的验证。不能借添加注释自行新增业务限制、前置条件、失败处理或其他运行行为。
5. 注释详细程度按职责重要性、行为契约、技术复杂度和实际维护风险确定，不规定固定字数、行数或注释占比。简单类型、纯公式和局部方法可以简明说明；重要业务入口、公共框架、异步处理和关键技术实现应保留充分的设计及调用说明。
6. 本节用于项目自研的新建代码及已授权修改的相关代码，不改变第三方及生成代码的实际维护契约，不构成自动批量补注释、重排成员、改名、重构、扩大任务范围或引入工具的授权。具体变更和已有成果保护遵循[AI 修改与交付规范](../Governance/AgentWorkflow.md)。 完整注释的强制要求、默认组织、按需说明及示例应按实际语义区分，已有稳定及第三方、生成契约的适用范围和实际冲突遵循[规则优先级与冲突处理规范](../Governance/RulePriority.md)；不减弱实际受影响代码的注释要求。

## 注释覆盖范围与格式

1. **类型和方法统一采用 XML 文档注释。** 类、接口、结构体、枚举类型、委托类型、构造函数及各访问级别的方法均须具有相应中文 XML 注释。方法注释不因 public、internal、protected、private、static、abstract、virtual 或 override 等访问及实现形式而降低覆盖要求。
2. 字段、常量和枚举成员统一使用中文行注释 `//`，默认写在对应声明之前；带 Attribute 的字段可写在其相关 Attribute 之前，使注释与实际成员的声明关系清楚，不将字段统一改用 XML 注释。
3. 属性及事件使用中文 XML 注释，明确读取、写入、订阅、通知等实际契约。普通属性访问器和事件访问器由所属属性或事件的文档承接，访问器中的非显然行为按实际需要使用方法内注释，不要求为每个 get、set、add、remove 机械重复完整文档。
4. 构造函数、Unity 生命周期入口、事件响应方法、接口实现、重写方法等同样遵守方法注释规范。局部函数、Lambda、匿名方法及其他不适合独立 XML 文档的局部实现，使用合法的中文行注释表达必要的局部语义及调用关系；不为注释形式改变原有实现结构。
5. 方法内部关键流程采用中文编号注释 `// 1.`、`// 2.` 等，关键调用及非显然局部实现应具有相应说明。编号注释已经完整说明关键调用目的时，无需重复添加另一条含义相同的注释。

| 代码对象 | 默认注释形式 | 覆盖要求 |
|---|---|---|
| Class / Interface / Struct / Enum / Delegate 类型 | `///` XML | 必须说明职责及适用契约 |
| 构造函数、方法 | `///` XML | 必须，包含 private 方法及 Unity 生命周期入口 |
| Property / Event | `///` XML | 必须说明实际访问、通知及使用契约 |
| 字段、常量 | `//` | 必须说明数据、依赖或固定程序语义 |
| 枚举成员 | `//` | 必须说明具体枚举值的业务或技术含义 |
| 局部变量、局部函数及匿名行为 | `//` | 按实际需要解释非显然语义 |
| 方法内关键流程 | `// 1.`、`// 2.` 等 | 必须按实际关键步骤组织 |
| 公共框架、生命周期及副作用相关关键调用 | `//` 或对应编号注释 | 必须说明调用目的及必要约束 |
| 职责区域 | `#region` / `#endregion` | 按实际职责及本节区域适用条件组织 |

上述格式用于项目手写代码及已确认范围内的相关修改。XML 文档不能替代方法内部的关键流程说明，Inspector 显示文本不能替代源码注释。

## XML 注释规范

1. **XML 注释使用 `///`，基础内容以 `summary`、实际存在的 `param`、`returns` 及 `typeparam` 等合法标签表达。** `summary` 应说明类型或成员真正承担的职责和用途，不只翻译名称。参数名、泛型参数名及引用成员必须与实际声明保持一致。
2. 具有参数的方法、构造函数、委托等，应分别说明各实际参数的含义、必要单位、有效范围或所有权等相关语义；具有返回值的声明应说明返回值及真实结果语义。无参数不添加空 `param`，void 方法及构造函数不添加 `returns`，无泛型参数不添加空 `typeparam`。
3. 重要设计意图、架构关系、设计模式、调用约束、生命周期、异常与取消、资源所有权及其他补充契约，优先使用 `remarks` 或适合的 XML 标签表达。不为形式要求每个简单声明机械增加所有标签或固定格式的长篇说明。
4. 实现接口或重写已有成员，且其实际行为与已有完整文档契约一致时，可以使用 `<inheritdoc/>` 继承有效的 XML 文档。存在具体实现差异、附加的技术条件或重要设计说明时，应明确补充对应文档，不以继承标记掩盖实际差异，也不继承明显错误或缺失的说明。
5. `exception` 只用于说明按真实契约可能向调用方传播且需要调用方了解的异常，不将普通业务失败、合法空值或取消一律描述为程序异常。异常文档不授权新增 `throw`、改变异常传播或追加校验，继续遵守[Unity 日志与异常处理规范](../Runtime/Logging.md)。
6. XML 内容须与 C# 文档注释语法相容，标签闭合、参数名称准确，必要时使用 XML 转义或适用的引用、代码标签。通过静态文本及代码审查核对，不为生成文档或发现注释错误主动编译、执行编译错误检查或安装文档工具。

| XML 标签 | 用途及要求 |
|---|---|
| `<summary>` | 类型或成员的职责、用途及主要语义 |
| `<param name="...">` | 每个实际参数的含义及必要约束 |
| `<returns>` | 非 void 方法及委托的返回值、结果及必要有效期 |
| `<typeparam name="...">` | 实际泛型参数的含义及相关约束 |
| `<remarks>` | 重要设计意图、架构关系、模式角色及补充行为契约 |
| `<exception cref="...">` | 实际可能传播且调用方需要了解的异常契约 |
| `<see cref="..."/>` / `<paramref name="..."/>` | 引用真实类型、成员或参数 |
| `<inheritdoc/>` | 继承真实适用的接口或基类文档 |
| `<example>` | 有实际理解价值的调用或使用示例 |
| `<value>` | 必要时补充属性的值语义 |

## 类型职责与架构说明

1. **类型注释首先说明“该类型是谁、属于哪个领域、负责什么”。** 对业务对象、职责类型、数据结构、接口、枚举及委托分别表达其身份、能力契约、数据用途或调用语义，不将技术形式或名称翻译当作完整职责说明。
2. 具有重要架构定位、独立处理职责或稳定能力契约的类型，应在 `summary` 及必要 `remarks` 中明确实际所属领域及所有者、职责范围、上下层协作、主要输入输出、权威状态及副作用边界、生命周期或重要调用限制。按真实职责选择相关内容，不机械复制相关架构专项规范中的全部条款。
3. **重要技术设计应具有可定位的源码说明。** 对采用的重要设计模式、算法、抽象、关键数据结构及不宜被随意简化的稳定委托边界，应说明实际采用原因、当前类型的角色及扩展或协作方式。具体技术设计遵循[技术实现方案设计与评估规范](../Design/TechnicalDesign.md)。
4. 简单 Formula、Operation、数据类型或局部能力同样须有准确的类型注释，可以通过简明 `summary` 完成；不为充实注释虚构复杂架构、模式角色、未来功能或不存在的依赖。
5. 接口注释侧重共同能力及调用契约，实现类型侧重实际职责与具体实现特点；数据结构注释侧重数据语义、所有权、读写权限及有效范围。不能只靠接口名称或类注释保证实际架构权限和不可变性。

| 职责类型 | 类型注释重点 |
|---|---|
| Manager | 管理范围、单例作用域、管理状态、合法协调及观察职责 |
| System | 所属业务或框架、统一入口、用例组织、状态所有权及合法内部协作 |
| Controller | 所属场景、协调范围、入口及实际生命周期 |
| Module | 所属对象、独立能力、装配、执行及清理职责 |
| Initializer / Factory | 装配范围、初始化或创建契约、真实所有者及生命周期 |
| Processor | 工作单元、处理生命周期、委托提交及最终结果交付 |
| Logic | 纯业务流程、显式输入输出及无外部副作用边界 |
| Resolver | 明确解析问题、组织的能力及结果语义 |
| Rules / Calculator / Evaluator / Selector 等 | 实际判断、计算、评估或选择职责及输入输出契约 |
| Operation / Formula / Algorithm | 具体处理语义、公式或算法、适用条件及执行状态 |
| Committer | 提交范围、目标状态持有者、必要步骤及真实完成条件 |
| Provider / Registry | 数据来源、查询或注册契约、实际所有者及有效范围 |
| RuntimeData / Snapshot / Config 等 | 数据用途、状态或配置权威性、读取写入语义及有效范围 |
| Service / DataStorage / Adapter | 实际技术能力、持久化或适配契约、依赖及资源责任 |

类型文档示例（仅展示已明确采用策略模式时的注释结构，不代表必须新增下列类型或策略）：

```csharp
/// <summary>
/// 组织技能目标的解析过程，并返回符合既定选择契约的解析结果。
/// </summary>
/// <remarks>
/// 架构定位：技能系统内部的纯业务解析能力。
/// 设计模式：策略模式，通过 ISkillTargetSelector 隔离具体选择实现，
/// 使不同选择方式能够按照统一契约独立扩展及替换。
/// 职责边界：只处理显式提供的候选目标、参数及合法选择能力；
/// 不自行读取全局状态，不执行伤害、状态提交或表现操作。
/// </remarks>
```

以上为类型声明前的文档片段。实际职责、选择规则及装配方式须与对应实现一致，不以示例注释代替实际代码。

## 字段、属性及数据注释

1. **字段及常量须使用中文行注释说明真实语义。** 普通字段说明存储内容及用途；常量说明其固定程序、数学或协议语义及必要依据。不只写“变量”“数量”“配置”等不能区分实际含义的说明。
2. 重要数据、状态、集合和依赖字段应按实际需要说明所属对象或业务、数据来源、权威性、单位、读写责任、Key 含义、有效范围及清理责任。避免将派生数据、显示状态、缓存或实时只读视图错误描述为权威状态或稳定快照。
3. 枚举成员必须说明相应业务或技术含义；具有外部协议、存档、组合标志或明确数值契约时说明相关意义，不因添加注释而改变枚举成员名称、数值或序列化方式。
4. **属性及其他正式数据访问能力须明确实际值语义。** 对读取、受控写入、返回引用、集合或 Snapshot 的属性，应说明实际数据来源、可修改性、所有权及有效范围。不得将 get-only、readonly、只读接口或私有 setter 误描述为对整个引用对象的不可变保证。
5. 局部变量按实际需要注释。重点解释非显然的数学量、单位转换、特殊索引、临时缓冲区、跨步骤中间数据及特殊技术约束，不机械为简单循环变量和语义明确的普通局部变量逐一添加注释。

| 数据或字段类别 | 说明重点 |
|---|---|
| 常量 | 固定程序语义、数学关系、协议标识或数值依据 |
| 配置字段 | 设计用途、单位、表示范围、默认含义及生效条件（按实际契约） |
| 运行时状态 | 所属对象、权威性、合法更新者及有效范围 |
| 集合及索引 | 元素语义、Key 含义、维护时机及数据来源 |
| 依赖字段 | 提供的能力、装配来源、实例及有效范围 |
| 缓存字段 | 原始来源、有效期、失效条件及维护责任 |
| 异步字段 | 所属任务、等待或取消语义及清理责任 |
| 资源字段 | 加载、取得、借用、所有权、有效期及释放责任 |

字段及属性注释参考（仅为格式示例，按实际状态契约使用）：

```csharp
// 当前角色的权威生命值，由合法状态提交入口按约定更新。
private float currentHealth;

/// <summary>获取角色当前有效的生命值。</summary>
public float CurrentHealth => currentHealth;

// 目标选择能力，由所属装配入口显式提供。
private readonly ISkillTargetSelector targetSelector;

// 本次有效范围内的任务索引，Key 为任务 ID。
private readonly Dictionary<int, Mission> missionById;
```

上述为若干独立成员的注释示例，不规定这些成员必须位于同一类型，也不代表完整声明及初始化代码。

## 方法及调用契约注释

1. **所有正式方法（包括 private 方法）使用 XML 注释。** 说明方法用途、每个实际参数的含义、返回值或结果语义及必要调用约束；不因方法只有一行代码、仅被本类型调用或属于 Unity 生命周期入口而省略方法文档。
2. 构造函数应说明实际创建或装配用途、所需依赖及必要所有权契约；泛型方法说明实际泛型参数。委托类型应说明参数、返回值及真实执行语义。事件声明说明发生的事实、通知范围及必要订阅和生命周期约束，不将指令误作事实事件。
3. 具有稳定公开或内部协作契约的成员，应按实际需要说明合法调用方、真实前置条件、状态影响、完成边界、失败与取消语义及返回数据所有权，具体遵循[类的访问权限与公开接口规范](AccessControl.md)。仅供类型内部的简单方法，可以使用足以说明其用途和实际参数、结果的简明文档。
4. 涉及业务执行、查询、状态提交、事件、异步、持久化、网络、资源或其他外部操作时，应说明调用方需要了解的真实行为，包括实际发生的副作用、执行及返回时机、数据有效性、所有权及失败结果。不得将纯计算完成、提交完成、事件分发完成、异步执行完成和前台表现完成混为一谈。
5. 注释中的前置条件和限制必须具有明确依据。不得以补充方法文档为由新增范围限制、非必要空值规则、默认值、异常、自动恢复、重试或阻断条件；需要改变真实行为时，仍按原有授权及专项规范实施。
6. 使用 `remarks` 说明不易从签名和 `summary` 理解的重要契约，避免对所有简单方法复制同样的架构说明。需要变更参数、返回类型、执行行为或公开契约时，应同步更新实际受到影响的文档，不能以注释修改代替接口变更授权。

| 方法文档内容 | 说明要求 |
|---|---|
| 用途、参数及返回值 | 基础要求，按实际声明完整说明 |
| 合法调用范围及前置条件 | 有实际架构或技术约束时说明 |
| 状态影响及副作用 | 存在状态写入、事件、网络、存储或其他外部行为时说明 |
| 执行时机及顺序 | 存在生命周期、调用阶段或明确顺序依赖时说明 |
| 完成、失败、取消及异常 | 按真实业务、异步和异常契约说明 |
| 数据及资源所有权 | 涉及返回引用、借用、有效期、释放等契约时说明 |
| 设计意图及扩展方式 | 存在重要算法、模式、稳定抽象或特殊实现时说明 |

纯计算方法示例（仅说明注释形式，不确立暴击规则及数值）：

```csharp
/// <summary>根据显式提供的攻击力和倍率计算暴击伤害。</summary>
/// <param name="attack">本次计算使用的攻击力。</param>
/// <param name="multiplier">本次暴击使用的伤害倍率。</param>
/// <returns>计算得到的暴击伤害。</returns>
/// <remarks>仅执行纯数值计算，不自行取得配置或提交角色状态。</remarks>
public static float Calculate(float attack, float multiplier)
{
    return attack * multiplier;
}
```

## 方法内部编号注释

1. **方法内部关键流程必须使用中文编号注释。** 默认使用 `// 1. ...`、`// 2. ...`、`// 3. ...`，分别说明具有明确语义的处理步骤及其目的。每个方法的主流程独立从 1 开始编号，按实际代码组织顺序表达，不使用跨方法连续编号。
2. 编号粒度以业务或技术逻辑步骤为单位，而不是 C# 代码行数。一项步骤可包含局部变量准备、必要判断、一次或多次调用及中间结果组织；不得将普通赋值、声明、调用、返回等语法行为逐行翻译为没有新信息的编号注释。
3. 条件分支、循环、提前返回、异常处理及清理路径应在所属步骤中说明其实际语义和必要条件。复杂局部流程可以在对应编号步骤内使用普通中文行注释补充说明，不为形式强制建立多层编号或将所有互斥分支写成固定顺序执行的步骤。
4. 单行公式、简单 Getter 或只包含直接且语义清晰的局部操作的方法，如果没有需要独立解释的关键流程，可以由准确的声明级注释说明，不机械添加“计算”“返回结果”等重复步骤。具有重要框架调用、状态提交或实际副作用的单步方法，仍应明确该关键调用的目的。
5. 修改处理顺序、分支条件或关键步骤时，必须同步更新实际受影响的编号及说明，保证编号与当前流程相符。注释不构成改变执行顺序、合并职责、拆分方法或新增处理步骤的授权。

不推荐将编号当作语法翻译：

```csharp
// 1. 声明变量。
float baseDamage;
// 2. 计算数值。
baseDamage = attack * skillMultiplier;
// 3. 返回结果。
return baseDamage;
```

推荐按独立处理语义组织（假设两步计算均已确认）：

```csharp
// 1. 根据攻击力和技能倍率确定基础伤害。
float baseDamage = BaseDamageFormula.Calculate(attack, skillMultiplier);

// 2. 在基础伤害上应用本次已确定的暴击倍率。
return CriticalDamageFormula.Calculate(baseDamage, criticalMultiplier);
```

## 关键调用及副作用说明

1. **调用公共框架方法、生命周期方法或可能产生副作用的方法时，必须在调用处说明调用目的。** 包括具有实际业务意义的 System 调用、状态提交、事件发布及订阅、资源加载和释放、对象创建及回收、持久化、网络、生命周期装配及清理等。按实际需要进一步说明调用条件、顺序、结果及所有权。
2. 关键调用注释应说明本次为何调用对应能力、传递的关键数据或使用的结果语义，而不是只写“调用方法”“执行保存”“调用 System”。通过编号注释已经表达相应目的及约束时，不再重复添加内容相同的普通行注释。
3. 对需要按明确顺序执行的步骤、可预期失败、提前退出、取消、重入、异常传播和资源清理，应按真实代码说明关键处理意图，不能将实际尚未发生的结果描述为成功，也不能把等待取消等同于已撤销的业务操作。
4. 纯处理层的调用说明应表达显式输入、处理职责及返回结果；提交和其他副作用的说明位于实际承担对应职责的实现中。不借注释赋予纯处理层额外权限，不用注释替代状态保护、事件契约、合法调用方向或必要的真实实现。
5. 普通语言语法、简单属性读取、语义明确且无重要技术约束的局部调用，不需要机械增加额外注释；本条不降低公共框架、生命周期及副作用相关关键调用的既有说明要求。

| 关键调用类别 | 说明重点 |
|---|---|
| System、公共框架及内部稳定能力 | 使用哪项真实契约、为何调用及结果如何用于当前职责 |
| 状态提交 | 已确定的业务结论、提交目标、实际结果及必要完成边界 |
| 事件 | 已成立的事实、通知目的、订阅归属及必要生效范围 |
| 资源与对象池 | 取得或归还目的、所有权及合法释放时机 |
| 生命周期及异步 | 装配、注册、清理、等待、取消或释放的真实目的 |
| 存储、网络及外部接口 | 执行目的、重要副作用及需要处理的真实结果 |

例如，在已明确的同步处理流程中，可以采用以下关键调用注释（仅表示调用位置的说明，不代表固定提交顺序或省略实际业务条件检查的授权）：

```csharp
// 1. 根据已准备的业务输入确定处理结果。
var result = progressLogic.Calculate(inputData);

// 2. 按既定契约将满足提交条件的业务结果应用到任务状态。
var commitResult = progressCommitter.Commit(result);
```

## Region 区域划分

1. **`#region` 按实际职责组织，区域名称采用清楚的中文语义。** 对具有多个成员类别、独立业务操作或生命周期阶段的常规类型，应按职责划分区域，使类型结构、成员定位及代码折叠更易理解，不以代码行数作为唯一判断依据。
2. 统一采用 `#region 区域名称` 和匹配的 `#endregion`。区域用于组织和表达代码，不改变访问权限、生命周期、依赖方向及实际执行顺序。不要把 Region 当作独立类型、架构层级或运行时机制。
3. 新建常规多成员类型默认按声明成员、构造与生命周期、业务或技术能力、事件响应及内部实现的逻辑顺序组织；区域内依照实际职责进一步归类，不只按 public、private 等访问修饰符划分。已有稳定区域顺序及名称优先沿用，确需调整时按当前任务范围处理。
4. **不机械配齐固定区域模板。** 只为实际存在且需要归类的成员建立区域，不生成空区域。对于仅有一个简单公式、单一明确操作或无需额外归类的极小类型，可以不设置 Region，但仍须具备本节要求的类型和成员注释。具有独立业务入口或多个职责区域的类型不得以当前逻辑较少为由省略有意义的区域划分。
5. 默认采用清晰的平级区域，不为形式进行多层嵌套；确有独立子职责时可以合理组织嵌套区域。Region 中的业务或技术名称应与所属类型的实际语义一致，例如“注册监听”“触发事件”“任务查询”“伤害计算”。
6. 修改旧代码时，更新与本次实际修改相关的 Region 及其说明；保留无关成员位置、已有稳定结构和实际声明顺序。不得为统一 Region 风格擅自重排整个类型、改变字段初始化顺序、移动成员至其他类型或批量格式化文件。

| 默认组织顺序参考 | 区域名称参考 | 实际内容 |
|---|---|---|
| 01 | 常量 | 固定程序参数及标识 |
| 02 | Inspector引用 / 配置参数 | 显式绑定引用及可配置字段 |
| 03 | 字段 | 状态、依赖及其他成员字段，可按具体职责命名 |
| 04 | 属性 | 读取及其他正式访问契约 |
| 05 | 事件 | 事件及通知契约声明 |
| 06 | 构造函数 | 类型创建及合法依赖装配 |
| 07 | Unity生命周期 / 初始化与释放 | 对应生命周期、初始化及清理入口 |
| 08 | 具体业务或技术职责 | 例如任务查询、任务进度处理、伤害计算、注册监听 |
| 09 | 事件响应 | 实际监听和局部响应方法 |
| 10 | 内部实现 / 内部类型 | 局部处理及所属内部类型；已有“内部工具”等稳定区域可沿用 |

以上为缺少专用约定时的默认组织参考，不要求所有类型都建立相同名称、数量或顺序的区域。例如 EventSystem 可以采用“常量、字段、初始化、注册监听、触发事件、移除监听、内部实现”；DamageCalculator 可以采用“计算依赖、构造函数、伤害计算”。具体区域与类型职责及实际成员对应，不为填充区域新增字段、方法或类型。

## Inspector 与 Unity 专项注释

1. **源码注释与 Inspector 说明分别保留。** 暴露在 Inspector 的字段应具有中文 `//` 源码注释，同时按[Odin Inspector 分组规范](../Unity/OdinInspector.md)提供中文 `LabelText`、完整 `Tooltip`、合法父子分组及确有需要的 `Required` 等 Attribute。Tooltip 不替代源码注释，源码注释也不替代 Inspector 操作说明。
2. 源码注释重点说明字段的技术及业务用途、依赖归属和实际使用契约；LabelText 说明编辑器中的字段名称；Tooltip 按实际需要说明应绑定的对象、用途、单位、默认含义及生效条件。三者应保持语义一致，不机械复制同一长段文字。
3. 必需引用、可选引用、运行时注入和正常资源加载须分别描述。只说明真实的绑定及配置要求，不在 Tooltip、Required 或其他提示中自行设定未经确认的范围、层级、名称、限制或业务拒绝条件。Odin 校验及运行时检查继续遵守其专门规范。
4. Unity 生命周期方法、事件响应、对象池租用和归还、异步取消及清理等方法使用 XML 注释，并在必要关键步骤说明实际行为、有效期及资源责任。不要只写“Unity 自带方法”“启用时调用”，应说明该类型为何在相应时机执行对应操作。
5. 手动绑定、加载、初始化、配置生效、订阅及资源清理等注释应与项目实际契约一致，不将未知绑定状态描述为已经配置，不因补注释增加自动查找、自动绑定或其他未经授权的逻辑。交付时仍按[AI 修改与交付规范](../Governance/AgentWorkflow.md)和[Unity 项目约束](../Unity/ProjectConstraints.md)提供需要用户手动操作的清单。

Inspector 字段注释示例（仅展示三种说明形式及真实单位的关系，实际分组、引用校验和字段契约按所属项目确定）：

```csharp
// 角色基础移动速度，供移动能力计算实际位移。
[SerializeField]
[LabelText("基础移动速度")]
[Tooltip("角色每秒的基础移动距离，单位为米/秒。")]
private float moveSpeed;
```

## 技术设计与实现说明

1. **重要技术实现应在合适的代码位置保留设计意图。** 按[技术实现方案设计与评估规范](../Design/TechnicalDesign.md)实际采用的设计模式、算法、数据结构、抽象边界、继承与组合及第三方适配，需结合职责和重要性在类型、方法或关键实现处说明其解决的问题、采用原因、重要契约及维护时需要保留的行为。
2. 设计模式注释应说明真实模式名称、参与类型的具体角色及协作方式。对已确定的稳定委托层、单一实现的策略契约及其他架构先行设计，可说明其独立职责及可替换边界，不因代码简单将其错误描述为冗余，也不虚构未来策略、注册机制或其他功能。
3. 算法及公式注释应说明实际原理、输入输出、必要成立条件、单位、关键步骤及业务结果语义；复杂度、精度、随机分布、顺序和稳定性等按真实实现说明。不因注释规定某算法就擅自改变已确认的业务规则或实际数值。
4. 重要数据结构应说明实际选择原因、核心访问模式、索引维护及数据所有权；性能优化说明实际优化目标、理论依据、运行代价和行为保护要求。理论复杂度、静态推断、设计目标和用户提供的实际测量结果须分别表达，不虚构实测提升、GC 或帧时间数据。
5. 对非显然的技术处理、平台或版本差异、特殊执行顺序、资源所有权、异步一致性及第三方接口适配，应说明实际适用条件及必要保留原因。注释不替代真实技术契约核实，不把临时推测描述为必须遵守的永久约束。
6. 借鉴外部方案、复用部分源码或引入第三方实现时，按实际采用方式在适当位置保留真实来源、必要版本或提交信息、版权及许可证要求，遵守既有维护契约。不将未经确认的来源、阅读范围或许可证写入注释，也不以中文注释要求删除第三方原始声明。
7. 代码注释保留对本地实现理解和维护有价值的稳定设计信息，不要求复制整份技术比较报告、全部 AGENTS.md 条款或历史讨论。技术决策、候选对比及实际研究依据仍按技术设计和 AI 交付规范提供；源码中的设计说明应与实际方案一致。

| 技术内容 | 注释重点 |
|---|---|
| 设计模式 | 真实模式、采用原因、参与类型的角色及协作契约 |
| 算法 / 数学公式 | 原理、实际输入输出、成立条件、单位及必要复杂度分析 |
| 数据结构 | 访问模式、选择依据、索引维护、状态及有效期 |
| 抽象、继承与组合 | 共同契约、独立变化方向及实际装配关系 |
| 性能优化 | 目标、理论或静态依据、代价及需要保持的业务语义 |
| 特殊技术处理 | 真实技术依赖、执行顺序或不可随意改变的原因 |
| 外部实现 | 真实来源、适配内容、必要版本、版权及许可证义务 |

例如采用空间哈希执行范围查询时，可以说明索引的目的在于缩小候选范围，仍需执行最终精确距离判断；实际查询成本取决于访问网格数量及候选数量，同时具有索引维护和内存开销。这是设计及理论说明，不代表已取得 Unity 实测性能收益，也不规定具体游戏的范围判断规则。

## 注释维护及已有代码保护

1. **代码变化时同步维护相关注释。** 修改已有逻辑时，不得只修改代码而不补齐被修改的类、字段、方法及其他受影响成员的规范注释。同步检查类型职责、方法参数、返回值、真实行为契约、关键调用、编号步骤、设计意图和必要的区域划分。
2. 修改旧方法时，应完整补齐该方法的 XML 文档及内部相关说明，并核对所属类型的职责注释。修改字段、属性、事件、接口或技术实现时，应维护实际受影响的数据或协作说明。不能只更新某一行注释而保留与本次实现明显冲突的相关文档。
3. **相关注释维护不等于全文件或全项目注释整改。** 在已授权范围内补齐实际受影响的注释；与当前修改无关的历史方法、字段、类型、文件和稳定 Region 保持原有内容，不默认批量格式化、重排或补写。发现无关缺失、过时说明或职责问题时，可按实际影响报告；独立注释整改任务须取得相应确认。
4. 注释与实际代码或确认方案存在不一致时，应基于真实证据识别正确语义，在已授权范围内修正相关说明。若代码行为与用户确认的业务契约冲突，应报告冲突并按授权处理，不自行选择修改业务或用注释掩盖缺陷。
5. 第三方、生成代码及具有专用文档契约的框架文件保留其真实维护来源、有效注释、版权、许可证及外部协议说明；项目自研的适配代码遵守本节。需要修改生成注释时，应按实际维护工具、模板或 Schema 及授权范围处理，不直接批量改写产物。
6. 可以使用具有明确含义的 TODO、FIXME 等维护标记，以中文说明实际未完成事项、已知问题或必要后续处理条件；不为假设需求堆积无依据的待办，不以占位代码或待办注释代替当前已经承诺的完整功能。尚未完成的内容须在交付中如实说明。
7. 不默认通过长段注释掉的废弃代码保存历史版本；已有保留的旧代码、有效设计记录及迁移说明受修改授权保护，不擅自删除。确有临时保留或兼容迁移需求时，按真实任务及版本管理契约处理。
8. 注释应保留有价值的设计原因、技术前提及已确定契约，而不是记录不必要的聊天过程、Agent 身份、无关修改历史或虚构验证结果。不得在注释中无依据保存凭据、敏感信息或私有外部数据。维护注释不授权新增工具、生成独立文档或扩大项目修改范围。

## Agent 注释检查与交付要求

1. **交付前应对实际新增及修改代码进行注释静态审查。** 按当前任务检查类型、方法、构造函数、属性、事件、委托、字段、常量及枚举成员的覆盖与格式，确认注释准确、完整且与实际代码及已确认方案一致。
2. 注释静态审查按实际修改核对以下相关内容，不要求检查无关历史文件或为每个简单任务输出完整清单：
   - 中文注释覆盖、类型职责及重要架构说明是否完整，是否存在只翻译名称或语法的无意义说明。
   - XML 标签、参数及泛型参数名称、返回结果、继承文档和实际调用契约是否准确对应声明。
   - 字段、属性及集合的状态来源、单位、实际所有权、有效范围及 Inspector 说明是否一致。
   - 方法内关键步骤编号、分支、关键框架及副作用调用的目的和执行契约是否与代码一致。
   - Region 是否按实际职责组织、配对正确，是否存在空区域、无必要的重复分组或无关成员重排。
   - 重要设计模式、算法、数据结构、技术选型、真实外部来源及技术约束是否得到必要说明，是否存在虚构性能或验证结论。
   - 被修改类和方法的相关注释是否同步维护，第三方、生成代码、无关历史注释及其他来源修改是否得到保护。
3. 在本次已确认范围内修正实际发现的注释缺失、错误或不一致；超范围问题按[AI 修改与交付规范](../Governance/AgentWorkflow.md)报告，不借注释审查扩大整改范围。仅执行允许的静态文本及代码检查，不主动编译、检查编译错误、运行项目、执行测试或安装注释检查工具。
4. 最终交付按任务实际情况说明相关注释及重要设计说明的维护情况、已检查范围和未能确认事项；不要求逐条粘贴全部注释或创建独立注释审计文档。注释的准确性和静态审查不等于实际功能、编译、性能或运行验证已经通过。

默认注释参考：

| 设计维度 | 默认推荐或约束 |
|---|---|
| 总体倾向 | 完整语义注释型，强调真实信息及设计意图，不逐行翻译代码 |
| 注释语言 | 中文，保留必要英文技术术语及真实标识 |
| 类型及方法 | XML 注释，包括构造函数、private 方法、Unity 生命周期及接口实现 |
| 属性及事件 | XML 注释，表达实际访问、通知及行为契约 |
| 字段、常量及枚举成员 | 中文行注释 `//` |
| 局部变量及局部实现 | 按实际需要说明非显然语义 |
| XML 基础内容 | summary、实际参数、实际返回值及泛型参数；其他标签按需 |
| 类型职责 | 重要类型说明所属领域、架构定位、职责边界及必要模式角色 |
| 方法契约 | 用途、参数、返回值及实际调用约束 |
| 方法内流程 | 按实际关键逻辑步骤中文编号，不逐行编号 |
| 关键调用 | 必须说明调用目的及必要约束，允许由编号注释承接 |
| Region | 中文职责分组，常规多成员类型使用，不机械配齐或要求极小类型完整分区 |
| Inspector | 源码注释、LabelText 和 Tooltip 分别保留，其他 Attribute 按专门规范 |
| 技术实现 | 说明重要设计模式、算法、数据结构及技术选择依据 |
| 注释维护 | 同步补齐实际受影响的类型及成员，保护无关旧代码 |
| 验证及交付 | 静态文本及代码审查，真实说明检查范围，不主动编译及运行验证 |
