# 类的访问权限与公开接口规范

## 规范定位与适用范围

定义 C# 访问权限、封装、公开接口、集合及程序集边界。

本规范是对应专业事项的规则主定义文档。规则适用范围、约束性质、优先关系及例外统一遵循 [规则优先级与冲突处理规范](../Governance/RulePriority.md)；项目修改、读取、实施及交付遵循 [AI 修改与交付规范](../Governance/AgentWorkflow.md)。

本节在既有职责划分、单向依赖、状态归属及提交契约的基础上，明确 C# 类型和成员的访问范围、系统公开能力及稳定调用契约。访问权限用于保护既有架构边界，不是要求减少职责类型数量、合并处理层或建立新的业务框架。

## 适用范围与已有实现保护

1. **统一架构访问边界，尊重已有技术契约。** 本节的职责与依赖约束适用于新增设计和业务开发；访问修饰符、类型组织及程序集划分的默认方案适用于新建代码及经用户确认的相关重构。 已有访问形式的差异与真实架构访问违规应分别判断，按[规则优先级与冲突处理规范](../Governance/RulePriority.md)保护稳定契约，不以历史可访问性作为新增违规调用的依据。
2. 已有项目形成稳定的类型访问范围、公开成员、接口、继承体系、程序集及序列化契约时，应优先沿用其实际实现。不得仅因现有类型使用 public、存在公开字段、未使用 sealed 或未建立 asmdef，就判定其需要重构。
3. 发现已有实现存在实际职责冲突、权威状态泄漏、不合理访问范围或无法满足当前需求的情况时，Agent 必须说明具体问题、实际调用方、影响范围及候选方案，取得用户确认后才能修改。发现问题不构成自动修复或批量收紧权限的授权。
4. **访问权限变更属于调用契约变更。** 涉及已有类型、方法、字段、属性、构造函数、接口或继承关系的访问范围调整时，应检查实际调用、装配、序列化、反射、插件及其他框架契约。涉及公共基础模块、共享接口、程序集或跨业务影响时，遵守 AI 修改与交付规范中的报备与确认要求。
5. 本节不得作为主动新增命名空间、创建程序集、迁移文件、批量增加接口或改变 UI、业务规则及运行行为的依据。已有第三方、生成代码和稳定框架入口仍遵循相应契约。

## 语言访问权限与架构访问权限

1. **语言访问权限决定技术上能否访问，架构访问权限决定职责上是否允许访问。** 两者必须分别判断；C# 编译器允许访问某个类型或成员，不等于当前调用方拥有使用该能力的架构权限。
2. public 不自动等同于跨业务公开入口，internal 不自动等同于所属 System 私有。类型和成员的有效可访问范围，应结合包含类型、实际程序集、继承关系及已有访问契约判断。
3. **技术可访问性不得解除既有依赖约束。** Manager 可以按职责使用 System 的公开能力；System 不得反向依赖 Manager；外部调用方不得绕过所属 System 调用其内部 Processor、Logic、Committer 等能力或直接修改权威业务状态。具体处理类型的合法协作仍按各自专门约定确定。
4. 访问修饰符、接口、委托、事件、静态入口、单例或反射均不得用于变相扩大架构权限。EventSystem 执行订阅者主动注册的通用回调仍遵循既有事件协作约定，不因此被视为反向依赖。
5. **访问边界优先通过职责设计和合适的语言机制表达。** 不得为强制调用关系而擅自增加调用栈检查、运行时调用者身份检查、反射校验或其他与实际业务无关的阻断机制。访问权限不是运行时业务授权或服务端安全校验的替代品。

## C# 访问修饰符使用原则

1. **采用能够满足真实调用契约的最小合理可见性。** 类型的可见性与成员的可见性分别确定；不得为了方便调用而默认将所有类型、字段及方法声明为 public，也不得为了收紧权限而破坏已有明确职责的独立类型及合法协作关系。
2. 新增普通类型及成员时，应明确其访问修饰符，避免依靠不清楚的默认可见性表达架构意图；接口成员、显式接口实现、枚举成员和其他受 C# 语言或框架约束的声明按实际合法语法及既有契约处理。
3. public 用于具有明确调用契约的类型或成员；internal 用于程序集内部的协作能力；private 用于类型内部实现；protected 用于实际存在的继承扩展契约。protected 不用于让无关业务通过继承取得内部实现的访问权限。
4. protected internal 和 private protected 只在确有对应继承及程序集访问需求，并且当前 Unity/C# 版本支持时使用，不作为普通职责类型的默认访问修饰符。
5. 类型的有效可见性应与其构造、公开签名及所使用的数据类型相容。不得为了使签名能够公开而机械提升内部实现类型的访问权限；应先判断公开签名是否泄漏内部实现，再按真实调用契约选择类型和可见性。
6. 类型拆分后允许通过正式成员入口进行合法协作。不得仅为使用 private 将原本具有独立架构职责的类型强制改为嵌套类型、合并到上层或取消其稳定入口。

| 修饰符 | 常见访问范围 | 默认使用场景 |
|---|---|---|
| `public` | 在包含类型可访问的前提下公开访问 | 正式调用契约 |
| `internal` | 同一程序集；显式友元程序集按既有契约处理 | 程序集内部协作 |
| `private` | 所属类型的内部访问范围 | 内部实现细节 |
| `protected` | 所属类型及合法派生类型的访问范围 | 继承扩展契约 |
| `protected internal` | 同程序集或合法派生类型的访问范围 | 特殊框架扩展 |
| `private protected` | 同一程序集内的所属类型及合法派生类型的访问范围 | 受限继承扩展 |

上表用于普通 C# 访问权限判断，不代替 C# 对包含类型、派生访问及特殊声明的具体语法限制。

## 各职责类型的默认访问权限

以下为缺少项目专用约定时的新建类型默认设计。访问范围应由实际职责、所有权、调用者及程序集边界确定，不以职责后缀机械决定所有类型的访问修饰符。

| 职责类型 | 默认类型可见性 | 职责边界 |
|---|---|---|
| Manager | `public` | 项目级公共管理入口，不公开全部内部实现 |
| System | `public` | 统一业务或框架系统公开入口 |
| Controller | `public` | 场景级协调入口，成员按实际调用契约确定 |
| Module | 按实际挂载、装配及调用契约 | 所属对象的能力入口，不因挂载而公开全部成员 |
| View / Presenter / ViewModel / Model | 按已确认的 UI 分层及装配范围 | 保持表现职责及业务状态边界 |
| Initializer | 按装配范围 | 只服务于明确的初始化及装配契约 |
| Factory | `internal` 优先 | 明确的共享创建能力可以公开 |
| Processor | `internal` | 所属系统内部工作单元处理能力 |
| Logic | `internal` | 所属系统内部纯业务流程 |
| Resolver | `internal` | 所属系统内部综合解析 |
| Rule / Rules / RuleSet | `internal` | 所属系统内部规则能力 |
| Calculator / Evaluator | `internal` | 内部计算及评估能力 |
| Matcher / Selector / Mapper / Normalizer | `internal` | 内部具体职责能力 |
| Operation / Formula / Algorithm | `internal` 优先 | 已明确为跨模块公共能力时可以公开 |
| Committer | `internal` | 所属系统内部状态提交能力，不作为普通业务公开入口 |
| Provider / Registry | `internal` 优先 | 按实际访问范围及数据所有权确定 |
| 业务对象 | 按实际身份及使用契约 | 对象身份、读取及受控行为分别确定 |
| RuntimeData | `internal` 优先 | 权威状态持有及受控更新 |
| Request / Result / CommitResult / RequestResult / Snapshot | 按实际传递契约 | 对外业务签名需要使用时可以公开相应契约类型 |
| Event | 按事件订阅及传递范围 | 跨程序集使用时可以公开相应事件契约 |
| Config / SaveData / DisplayData / InputData | 按数据用途、序列化及调用范围 | 不因数据类型可访问而取得权威状态写入权限 |
| Service / DataStorage / Adapter | 按实际技术及共享契约 | 区分内部实现与公共基础能力 |
| Utility | 按实际共享范围 | 明确的公共技术能力可以公开 |

1. 上表中的 internal 表示默认限制内部实现类型的语言可见性，并不代表同一程序集中的任意业务都可以调用。即使因现有框架或合法跨程序集协作需要使用 public，其所属职责和架构调用范围仍须保持明确。
2. 真正独立于某个具体系统内部实现、具有明确共享契约的纯处理或技术能力，可以在合法依赖范围内对外开放，不要求所有公共计算或技术能力都经过 System 转发。不得把某个业务 System 的内部规则、状态提交或私有计算机械提升为全局公共能力。
3. 公开类型所使用的参数、返回值及其他可见契约类型，应与实际公开范围相符。公开 Request、Result 或 Snapshot 不代表其关联的内部 RuntimeData、Logic 或 Committer 也必须公开。
4. 上述默认方案不改变 Manager、System、Controller 的单例与作用域约定，不向其下属类型传递单例要求。已有稳定实现存在不同访问范围时，按本节已有实现保护规则处理。

## System 与 Manager 的公开能力边界

1. **业务 System 是所属业务能力的统一公开入口。** Manager、Controller、其他业务 System 及合法调用方，应通过所属 System 的公开业务能力或已明确的专门契约进行业务查询、请求提交及结果处理。不得仅因为内部类型或成员技术上可访问，就绕过业务入口、处理规则及一致性机制。
2. 公开能力应与实际职责匹配。System 可以提供明确的业务执行、状态查询、可用性判断和快照获取；Manager 可以提供自身管理职责内的公共能力；Controller 可以提供所属场景内的协调入口。不要求不同类型机械配齐相同接口。
3. 注册、注销、装配、初始化、释放、重置及诊断等能力，应按实际所有权与调用范围公开，不自动作为普通业务接口。只有符合生命周期契约的装配方、所有者及其他合法调用方才能使用相应能力。
4. **不默认公开内部实现实例。** 不得通过公开字段、属性、方法返回值、委托或其他方式向无关业务暴露内部 Processor、Logic、Resolver、Committer、可写 RuntimeData、可变 Registry 集合或其他能够绕过稳定业务入口的实现。需要共享某项明确能力时，应以稳定的能力契约表达，而非直接开放整套内部实现。
5. 单例公开访问入口遵循项目既有框架。不得提供可由无关调用方任意替换、清空或创建有效单例实例的入口；单例的创建、初始化、重置和释放仍由既有生命周期约定确定，不为统一访问权限而擅自修改单例基类或构造机制。
6. 查询当前有效业务状态应使用所属 System 的明确查询能力或其他已确认的合法读取契约。通用 Formula、Algorithm、Utility 等具有独立共享职责的能力可以直接调用，不强制为所有公共技术能力设置 System 转发方法。
7. 公开查询、可用性判断与实际业务执行应区分；查询到的可用性不自动保证之后的提交仍然有效。并发、重入及实际提交边界继续遵循[异步业务与状态一致性规范](../Runtime/StateConsistency.md)。

| 接口类别 | 用途及命名示例 |
|---|---|
| 业务执行入口 | 执行明确业务请求，例如 `ClaimReward()` |
| 状态查询 | 获取当前状态，例如 `GetMissionProgress()` |
| 可用性查询 | 查询当前条件，例如 `CanClaimReward()` |
| 快照获取 | 获取约定范围的稳定数据，例如 `GetInventorySnapshot()` |
| 注册及注销 | 显式建立或解除关联，例如 `RegisterCharacter()` |
| 生命周期入口 | 根据所有权执行装配或清理，例如 `Initialize()` |
| 诊断入口 | 获取必要的只读运行信息，例如 `GetSubscriptionCount()` |

上述类别不代表所有成员均应使用 public，也不要求每个 System、Manager 或 Controller 提供全部接口。

## 内部职责类型的协作与访问

1. **internal 类型的正式调用入口默认使用 public，类型内部实现默认使用 private。** 以类型的访问修饰符表达整体可见性，以成员的访问修饰符区分其正式调用契约和内部细节；不要求 internal 类型的所有成员重复声明为 internal。构造函数及其他成员根据实际创建、装配和访问契约确定。
2. public 类型的对外公开契约使用 public，确实只供同程序集内合法调用方使用的协作能力优先采用 internal，类型内部实现使用 private，继承扩展能力按实际契约使用 protected 等修饰符。
3. internal 类型中的 public 成员仍受该类型自身的有效访问范围限制；同一程序集内能够访问该成员的类型，也必须遵守其架构依赖规则。public 成员并不因此变为跨业务公共能力。
4. System 可以按职责直接调用所属内部类型，Processor 继续通过显式提交接口或已有明确提交契约委托 Committer；Logic、Resolver、具体职责能力及基础处理实现层继续遵守其单向依赖及纯处理约束。不得通过改变访问修饰符、抽取接口或公开静态方法来绕过这些限制。
5. 具有明确语义和稳定边界的细粒度独立类型，即使只提供一个方法或当前只有一个调用方，也允许保留正式的调用入口，不要求将其合并到其他类型或以 private 方法替代。

示例：以下仅说明访问修饰符及职责入口的设计，不规定任务进度公式。实际新增代码应遵守代码注释规范中的中文注释要求及其他规范。

```csharp
/// <summary>组织任务进度的纯计算。</summary>
internal sealed class MissionProgressCalculator
{
    #region 进度计算

    /// <summary>根据明确输入计算变化后的任务进度。</summary>
    /// <param name="progress">原任务进度。</param>
    /// <param name="count">本次进度增量。</param>
    /// <returns>计算后的进度。</returns>
    public int Calculate(int progress, int count)
    {
        // 1. 委托类型内部的增量计算实现。
        return CalculateIncrement(progress, count);
    }

    /// <summary>根据给定进度和增量执行局部计算。</summary>
    /// <param name="progress">原任务进度。</param>
    /// <param name="count">本次进度增量。</param>
    /// <returns>按本示例增量公式计算后的进度。</returns>
    private int CalculateIncrement(int progress, int count)
    {
        return progress + count;
    }

    #endregion
}
```

## 字段、属性及权威状态保护

1. **普通字段默认使用 private。** 不因读取便利或 Inspector 展示需求而公开可变字段。具有明确数据传递契约的 DTO、第三方协议、生成代码或其他稳定框架类型，可以按其实际契约使用字段；不将普通字段规则机械套用于这些契约。
2. 仅在确有读取需求或稳定公开契约时提供属性或查询方法。不得为每个私有字段机械创建 public getter、setter 或无明确用途的包装方法。简单读取可以使用只读属性，具有查询条件、明确结果或其他契约语义时可以使用方法。
3. **读取权限与写入权限分离。** 权威状态由业务对象、RuntimeData 或既有权威来源持有，状态修改由所属 System 组织，并由具有合法提交权限的实现通过受控入口更新。可采用 get-only 属性、private set、明确更新方法等方式表达实际边界；不得向 UI 或无关业务开放可任意修改权威状态的字段或 setter。
4. 受控状态更新方法负责按既定契约应用结果，不重新实现完整领域规则。必要的数据有效性检查须有真实运行依赖或已确认的业务契约依据，不得借封装之名额外新增业务限制。
5. 外部调用方不得取得能够任意写入权威状态的对象、集合、引用或能力接口。即使字段为 private、属性为只读或接口名称带有只读语义，也应检查实际返回对象是否仍然暴露不应公开的修改能力。
6. 业务对象可以拥有符合自身职责的公开行为，Manager、Controller、Module 等也可以在各自职责范围内公开相应管理或表现能力。不得将权威业务状态的保护机械扩大为所有对象都不能具有任何公开修改方法。

示例：内部 RuntimeData 提供受控写入契约，仅供符合状态提交规则的调用方使用，不向普通外部业务交付可写实例。

```csharp
/// <summary>承载钱包的当前有效运行时状态。</summary>
internal sealed class WalletRuntimeData
{
    #region 属性

    /// <summary>获取当前金币数量。</summary>
    public int Gold { get; private set; }

    #endregion

    #region 状态更新

    /// <summary>按照已确定的提交契约应用金币结果。</summary>
    /// <param name="newGold">已经确定且满足实际提交条件的金币数量。</param>
    public void ApplyGold(int newGold)
    {
        // 1. 应用由合法提交方确定的状态结果，不重复领域计算。
        Gold = newGold;
    }

    #endregion
}
```

该示例不代表所有状态更新只需一次赋值，也不意味着 internal 或 private set 能够独立保证业务一致性。调用方、实际提交检查与写入须遵守既有状态提交及异步一致性规范。

## 集合、只读访问及数据所有权

1. **区分只读访问、稳定快照及数据不可变性。** get-only 属性、readonly 字段和 IReadOnlyList 等接口能够限制相应访问方式，但不自动使被引用的对象、底层集合或元素不可变，也不保证异步等待期间数据保持不变。
2. 不得直接将可变权威集合以只读接口的形式返回后，就将其视为完全隔离的只读数据。如果底层对象仍可被合法转换回可变类型，或元素自身能够修改权威状态，应按照实际调用契约选择合适的只读包装、只读元素、独立数据、查询方法或其他明确的数据边界。
3. **实时只读视图与 Snapshot 必须具有不同语义。** 实时只读视图可以反映状态后续变化；Snapshot 表达获取时点的稳定状态，不能以对共享可变对象的只读包装代替实际所需的稳定快照。
4. 公开数据应明确返回值的所有权、有效范围、是否可能变化及允许的操作。独立可变副本可以由明确所有者修改，但不得因此影响源权威状态；对象池、临时缓冲区及借用数据遵守其实际有效期。
5. 不要求每次查询都复制集合、深拷贝完整业务对象或创建独立接口。按实际数据语义、读写边界、异步有效期及性能需要选择适用方式，不为形式引入额外分配或复杂数据转换。 复用临时集合、输出缓冲区及池化数据时，仍须保证实际数据所有权、有效期、并发隔离及结果完整性，具体遵循[性能与内存管理规范](../Runtime/Performance.md)、[对象池规范](../Runtime/ObjectPooling.md)、[资源管理规范](../Runtime/ResourceManagement.md)。
6. Provider、Registry、RuntimeData、Snapshot、Event 等类型的具体读取和传递契约，继续遵循其专门规范及[异步业务与状态一致性规范](../Runtime/StateConsistency.md)。

| 访问方式 | 实际语义 |
|---|---|
| 查询方法 | 获取明确的当前状态或查询结果 |
| 只读属性 | 提供约定值或只读访问入口，不代表引用对象不可变 |
| 实时只读集合视图 | 观察当前集合，内容可能随源数据变化 |
| Snapshot | 获取时点的稳定只读状态 |
| 独立数据副本 | 调用方按约定拥有数据，修改不影响源权威状态 |
| 可变原始集合 | 限于具有明确所有权及受控更新权限的内部实现 |

## Inspector 与代码访问权限

1. **Inspector 可见性、Unity 序列化及 C# 代码访问权限分别确定。** 可挂载性、Inspector 配置和运行状态观察需求，不自动要求字段、属性或方法使用 public。
2. 需要通过 Unity Inspector 配置的普通序列化字段，默认采用 `[SerializeField]` 与 private，继续遵守中文 LabelText、完整 Tooltip、Odin 分组及 Required 等既有规范。不得仅为 Inspector 可见而使用 public 可变字段。
3. 公开只读属性、只读查询及 Odin 调试展示可以根据实际职责提供。调试展示不得向无关业务开放可变权威状态或取得另一份权威状态所有权，也不构成新增调试功能的默认授权。
4. 不得为了采用 readonly、const、自动属性或其他访问形式而破坏 Unity 或项目既有序列化、Inspector 引用及配置赋值契约。Unity 原生序列化通常面向符合条件的字段，属性及 readonly 字段不能按普通可序列化字段机械处理；Odin 或第三方序列化按项目实际契约确定。
5. 变更已有字段、属性、类型或访问修饰符之前，应检查序列化字段名称、类型、Prefab、场景、ScriptableObject、UnityEvent 持久绑定、反射和第三方插件的实际依赖，保留 .meta 及 GUID 等既有引用关系。存在迁移需要时，应提出具体方案并取得确认，不擅自重建资源或自动绑定引用。
6. Unity 生命周期入口、事件回调、组件创建及框架要求的可访问性，按照实际 API 及稳定契约确定。不得仅为统一访问修饰符破坏正常 Unity 生命周期、已绑定事件或已有框架行为。

## Interface 的引入及访问范围

1. **Interface 用于表达明确的调用能力或稳定契约，不用于机械配对实现类型。** System 可以继续沿用已确定的单例公开入口，不强制建立 IInventorySystem、IMissionSystem 等接口，也不因存在 Interface 而引入 DI 容器或额外生命周期框架。
2. 存在明确的能力隔离、Unity 实现隔离、实现替换、框架扩展、只读能力、独立验证或稳定协作契约时，可以按实际职责引入 Interface。只有一个实现或当前只有一个调用方，不构成否定稳定接口边界的理由；不为假设性的需求机械创建空洞的同名接口。 抽象、接口、继承与组合的设计依据及技术选型遵循[技术实现方案设计与评估规范](../Design/TechnicalDesign.md)，不因此改变本节访问权限和既有协作边界。
3. Processor 继续通过显式提交接口或项目已有的明确提交契约委托 Committer。System 直接使用所属 Committer 时，不强制新增接口。Module 等其他能力接口继续遵守各自的专门约定。
4. Interface 自身的访问范围应与真实调用方及程序集相符。仅供系统内部协作的接口优先采用 internal，例如 `IMissionProgressCommitter`；具有实际跨程序集公开契约时可以使用 public。接口的参数、返回类型及实现方式须满足实际语言和框架要求。
5. 接口名称遵循 `I` + PascalCase 及既有语义命名；具体 Committer 接口继续遵循 `IMissionProgressCommitter` 与 `MissionProgressCommitter` 等既有命名约定。已有稳定接口不为形式批量改名或拆分。
6. **接口不自动改变调用权限或依赖方向。** 不得通过接口、显式接口实现、回调、委托、适配器或服务定位机制变相使 System 依赖 Manager，或使纯处理层、外部业务绕过状态提交边界。只读接口也不自动使其实现对象不可变。
7. 已有框架确需通过继承、接口或其他契约组织创建及协作时，优先复用。新增共享接口、调整公开接口成员、实现关系或签名，应检查实际调用方和兼容性，按既有授权规则处理。

## sealed、readonly 与 const 使用约定

1. **无明确继承扩展职责的普通 C# 具体实现类型，默认优先采用 sealed。** 例如 Logic、Resolver、Calculator、Evaluator、Committer 及普通 RuntimeData。sealed 限制其他类型继续继承该类，不妨碍该类按契约继承既有基类或实现接口。
2. System、Manager、Controller、Module、业务对象及框架具体类型是否使用 sealed，应根据实际继承、扩展和 Unity 框架契约确定；具有明确派生扩展职责的基类不得机械封闭。静态类无需额外添加 sealed。
3. 不得为了形式对已有类型批量增加 sealed、移除 virtual、abstract 或改变继承关系。确有调整需要时，检查现有派生类型、扩展入口、插件及测试使用契约，并取得用户确认。
4. **在字段声明或构造函数中完成赋值、之后不需要重新赋值的普通 C# 依赖字段，优先采用 readonly。** 需要按生命周期替换、重新装配或由 Unity 序列化赋值的字段，应保留符合实际契约的实现，不强制使用 readonly。不得将 readonly 引用等同于被引用对象的不可变性，也不得借 static readonly 保存纯处理层禁止的全局可变状态。
5. const 用于编译期可确定且确实属于固定程序语义的常量，继续采用代码命名规范规定的 UPPER_SNAKE_CASE 命名。需要运行时初始化的固定引用可按契约使用 readonly；运行时权威状态仍由受控字段或属性承载。
6. 设计配置、策划可调整参数、运行时数据和固定程序常量必须区分。不得仅因当前取值不变，就将伤害倍率、技能冷却或其他实际可配置业务参数硬编码为 const；继续遵循既有配置、常量及禁止魔法数字的规则。 配置引用可以按实际所有权及生命周期采用 readonly，但不得将 readonly 引用等同于配置对象及其内部数据不可变；Inspector 配置继续遵循既有序列化约束，常量及配置选型具体遵循[配置数据管理规范](../Runtime/Configuration.md)。

## 事件与委托的访问权限

1. 明确的 C# 局部事件通知契约，默认优先使用 `event` 而非对外暴露可任意赋值和调用的公共委托字段。事件的订阅范围应按实际调用契约确定。
2. 对于普通字段式 C# event，合法外部调用方可以订阅和解除订阅，但不能直接覆盖整个事件的监听关系或直接触发该事件。事件触发由具有实际发布权限的所属类型组织；存在明确的继承触发契约时，按既有 `OnXxx` 约定提供合法入口。
3. 既有 UnityEvent、回调、框架事件接口及 Inspector 绑定继续遵守其实际技术契约，不为统一事件声明形式而擅自替换或收紧访问。无论使用哪种形式，均不得绕过业务发布权限、状态提交及依赖方向。
4. EventSystem 的 Publish、TriggerEvent 或其他发布接口可以根据框架契约公开，但技术上可以访问发布方法，不代表调用方拥有任意业务事件的发布权限。事件的发布负责人、订阅范围、数据只读性和生命周期继续遵循[EventSystem 与事件协作规范](../Architecture/EventSystem.md)。
5. 不得向无关调用方公开可以覆盖内部监听集合、任意触发内部事件或控制其他所有者订阅关系的可变字段和操作。局部事件的访问保护不替代全局事件框架的既有订阅管理规则。

## 公开接口及稳定调用契约

1. **公开接口包括对合法调用方提供的稳定能力，不仅指 C# interface 类型。** public 方法、属性、事件、构造入口及其他公开成员应具有明确用途与调用范围；internal 类型的正式协作入口也可以形成稳定的内部契约。
2. 公开接口应按实际需要明确输入参数、返回结果、真实前置条件、状态影响、完成时机、失败及取消语义、数据所有权和有效范围。简单同步查询不需要机械建立完整设计文档；涉及异步、共享状态、状态提交或跨系统调用时，应明确与其实际风险相关的契约。 异常触发、传播、结果转换及必要诊断信息的公开契约同时遵守[Unity 日志与异常处理规范](../Runtime/Logging.md)，不将内部异常信息机械暴露给普通调用方。
3. 新增公开能力时，应以业务或技术能力语义命名并提供符合既有中文注释规范的说明，不泄漏无关内部处理步骤、可变状态或具体存储实现。业务条件不满足、未知结果及其他失败表达遵守既有日志、提交及异步一致性规范。 公开契约及内部正式协作成员的 XML 文档应准确表达实际参数、返回值及必要调用边界，具体遵循[代码注释规范](Comments.md)。
4. **接口变更不仅指签名变更。** 可见性、参数与返回类型、执行时机、实际副作用、业务前置条件、重复调用行为、异常传播、等待与取消范围、数据新旧语义及所有权变化，都可能影响已有调用契约，即使方法名称及签名完全不变。
5. 修改已有公共接口或跨职责稳定契约前，必须检查实际调用方及影响，说明变更原因、调用方式、行为差异、兼容性、序列化和迁移风险，并按已有报备与确认规则执行。不得通过新增无依据的兼容层、兜底逻辑或旧新并行接口规避确认。
6. 公开访问范围的扩大或收紧都须有实际需求、职责依据及明确授权。不得为临时消除访问问题、方便测试、缩短调用链或解决编译问题而机械提升可见性，亦不得因规范更新而擅自删除已有稳定公开能力。

行为契约变更示例（并非允许自动实施的修改）：同步提交改为延迟提交；原允许的重复调用改为忙碌拒绝；原在业务提交完成后返回改为等待全部 UI 表现结束；实时查询改为读取历史缓存；纯查询新增状态写入。上述变更即使不改变签名，也应按照实际影响执行报备与确认。

## asmdef 与程序集访问边界

1. **internal 约束程序集范围，不约束目录、命名空间或业务 System 范围。** 普通 Unity 业务代码处于同一 Assembly-CSharp 时，不同目录中的 internal 类型仍可能彼此访问；不得据此认定业务内部实现已实现编译隔离。
2. 项目已有 `.asmdef`、`.asmref` 或其他程序集组织及引用契约时，必须优先沿用，并根据实际编译归属确定可访问范围。程序集访问保护与本文件的架构访问约束应共同生效。
3. 需要独立公共框架、明确编译隔离、程序集依赖治理或其他具有实际依据的模块隔离时，可以提出 asmdef 方案。在正确配置程序集引用且不存在额外访问授权时，internal 可限制其他程序集直接访问内部实现。
4. **不强制每个 System、每个业务目录或每个职责层建立独立 asmdef。** 程序集拆分应依据实际依赖方向、共享契约、平台及编辑器隔离需求确定，不为形式或假设性的访问风险机械增加程序集。
5. 建立或调整程序集前，应识别现有依赖图、实际程序集归属、运行时及 Editor 代码、第三方插件、平台兼容、测试和序列化引用影响，说明方案、成本、风险及迁移范围并取得用户确认。不得擅自增加程序集引用、扩大可见性或建立跨程序集循环依赖。
6. 不同 System 在不同业务用例中按已确定职责互相提供能力，不自动构成架构违规，但独立程序集之间不得形成不被编译系统允许的循环引用。若拆分方案与合法协作关系冲突，应评估保留同程序集、重新组织程序集边界或采用具有明确职责的共享契约等方案，不得仅为解决程序集循环引用而把必要业务调用改成普通事件或破坏已有业务边界。
7. 测试、扩展或其他明确的跨程序集内部访问需求，可以按已确认的项目契约使用友元程序集等机制。不得为临时调用或测试机械开放所有内部类型、自动添加 InternalsVisibleTo 或绕过实际职责边界。
8. **程序集、命名空间、文件目录与业务职责边界是不同概念。** 不要求一一对应；普通游戏业务代码的命名空间使用继续遵循本文件原有约定，不因建立 asmdef 而自动新增或修改命名空间。 具体领域目录、职责目录及 Unity 特殊目录的组织遵循[代码目录组织与文件归属规范](DirectoryStructure.md)，不因目录归属自动新增或调整程序集定义及引用。

| 场景 | 推荐处理 |
|---|---|
| 普通游戏项目 | 沿用现有程序集，使用合理访问修饰符与架构规范共同约束 |
| 已使用 asmdef 的项目 | 保持既有程序集依赖及访问边界 |
| 独立公共框架 | 可以考虑独立程序集，按实际框架契约确定 |
| 需要编译层隔离的业务 | 提出明确的程序集方案，确认后实施 |
| 每个 System 或职责层分别创建 asmdef | 不机械引入 |
| 修改现有程序集、引用或额外内部访问权限 | 必须按既有变更授权规则处理 |

## Agent 开发前检查与默认设计方案

1. 新增类型、设计公开接口或修改已有访问契约前，Agent 应根据实际任务识别：
   - 类型的职责、所有者、实际调用方和合法依赖方向。
   - 当前程序集、已有访问修饰符、框架接口、继承及装配契约。
   - 成员属于对外能力、内部协作、继承扩展还是类型内部实现。
   - 是否暴露权威状态、可变集合、内部处理实例、提交能力或监听管理权限。
   - 数据读取与写入权限、返回对象所有权、只读视图与快照语义，以及相关异步有效期。
   - Unity 序列化、Inspector、Prefab、场景、UnityEvent、反射及第三方插件等实际依赖。
2. 按任务相关范围说明新增或变更的公开能力、内部访问边界及其依据；发现真实冲突或需要调整已有接口、继承及程序集结构时，先报告调用影响和候选方案，经用户确认后实施。不要求无关任务机械输出完整检查报告。
3. 交付时应说明实际发生的公开接口、访问范围、权威状态访问或程序集变更及授权来源，列出需要用户手动确认的调用、序列化及绑定风险。只进行符合既有协作规则的静态文本及代码审查，不得主动编译、检查编译错误或进行运行验证。

| 权威状态写入 | 仅由合法提交方通过受控更新能力执行 |

| 局部事件 | 明确通知契约时优先采用 C# event |
| 公开接口 | 明确实际行为契约，不公开无关内部实现 |
| asmdef | 沿用已有组织；确有隔离需求时按确认方案建立 |
| 命名空间 | 继续遵守原有规范 |
| 已有代码 | 优先保留稳定契约，实际缺陷及冲突经确认处理 |

上述默认方案不构成主动重构授权。访问修饰符用于在语言层面保护既定架构，公开契约用于向合法调用方提供稳定能力，程序集隔离按实际需求选择；不得因技术可访问性而绕过职责分层，也不得以权限收紧为由破坏已有合理的细粒度架构。
