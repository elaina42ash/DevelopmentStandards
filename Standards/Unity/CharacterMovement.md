# Unity 人物控制与移动默认规范

## 规范定位与适用范围

定义人物控制职责、输入消费、时间域、运动后端及相机跟随。

本规范是对应专业事项的规则主定义文档。规则适用范围、约束性质、优先关系及例外统一遵循 [规则优先级与冲突处理规范](../Governance/RulePriority.md)；项目修改、读取、实施及交付遵循 [AI 修改与交付规范](../Governance/AgentWorkflow.md)。

## 适用范围与规则优先级

1. 本规范适用于玩家角色、可控制角色，以及复用相同运动架构的 AI、网络角色或回放角色；同时适用于 2D、3D、第一人称、第三人称、横版和俯视角等表现形式。
2. 用户当前任务中的明确合法要求、有效项目专用约定及已有稳定技术契约，优先于本规范针对人物控制与运动实现给出的通用默认方案。上述优先关系不自动解除实际技术条件、架构职责、业务契约及变更授权。不得为了套用默认方案而替换已经稳定运行的输入系统、状态机、运动器、动画系统、相机系统、网络同步或回放系统。规则适用及真实冲突遵循[规则优先级与冲突处理规范](../Governance/RulePriority.md)，本节规定的偏离说明及确认要求继续有效。
3. 本规范是缺少项目专用约定时的默认方案，不代表所有人物都必须使用 Rigidbody、`FixedUpdate` 或同一种移动实现。
4. 需要偏离本规范时，Agent 必须在修改前说明偏离原因、影响范围、风险和替代方案，并取得用户确认。

## 默认职责分层

1. 人物控制默认拆分为以下职责，具体是否拆成多个组件由项目现有架构决定：
   - 输入提供层：采集并标准化设备、AI、网络或回放输入。
   - 输入消费层：保存当前意图和待处理请求，不直接采集底层输入。
   - 角色决策层：根据输入、角色状态和玩法规则决定行为是否允许执行。
   - 运动执行层：通过当前运动后端更新速度、位置、旋转和碰撞状态。
   - 表现层：驱动 Animator、模型或 Sprite 朝向、音效、特效和 UI。
   - 相机层：在项目既有相机更新阶段跟随人物。
2. 推荐数据流为：`Input Provider -> Character Intent -> Character Logic -> Character Motor -> Character State -> Character Presentation`。
3. 上述职责可以存在于同一个脚本中，但代码边界必须清晰；不得把输入采集、物理运动、动画、相机和 UI 无边界地堆在一个方法或一个巨型控制器中。
4. 同一时刻只能有一个明确的运动权威写入者负责人物主体的最终位置、旋转或主速度；击退、移动平台、Root Motion、冲刺等额外运动必须通过项目已有的组合、优先级或状态机制接入，禁止多个组件相互覆盖同一运动状态。

## 输入消费层约束

1. 人物控制模块不得直接调用具体输入采集 API，包括但不限于：
   - `UnityEngine.Input`、`Input.GetAxis`、`Input.GetKey`、`Input.GetButton`。
   - Unity Input System 的设备轮询、`InputAction` 查找或启用、`PlayerInput` 采集逻辑。
   - Rewired 的 Player 轮询或其他第三方输入采集接口。
2. 输入来源必须由项目现有输入模块提供；人物控制模块只接收抽象后的输入快照、状态或事件。
3. 不得在人物控制模块内部重新实现一套与现有输入模块并行的输入系统，也不得为了完成单个功能临时绕过现有输入接口。
4. 输入提供层可以通过方法、接口、事件或数据快照传递输入；Agent 必须优先沿用项目已有方式，不得未经确认新增新的输入总线、命令框架或输入 DTO 体系。
5. 未确认输入提供层的更新时机和数据契约前，不得假设输入一定来自 `Update`、`FixedUpdate` 或某一种 Input System Update Mode。

## 连续输入与瞬时请求

1. 输入数据必须明确区分“按下”“按住”“释放”和数值状态，禁止使用含义不清的字段同时承担多种语义。
2. 连续输入表示“当前仍然成立的意图”，例如移动方向、观察方向、瞄准方向、持续防御和持续蹲下；默认只保留最新状态。
3. 在两个物理步或模拟 Tick 之间出现 `Left -> Left -> Right` 时，使用 Rigidbody 物理后端的下一次物理步默认读取最新的 `Right`，不得把已经过期的连续方向排队到后续物理步逐条回放。
4. 瞬时请求表示“一次独立操作”，例如跳跃按下、攻击按下、闪避、冲刺、交互和技能释放；请求必须保留到负责该行为的系统明确消费或按既定规则失效。
5. 瞬时请求消费后必须显式清除或递减，避免漏执行、重复执行或跨状态残留。
6. 当同一请求在一个消费周期内最多只需要保留一次时，使用待处理标记即可；只有玩法明确要求保留每一次输入时，才使用计数、时间戳或有界队列。
7. 不得未经需求确认自动加入跳跃缓冲、土狼时间、输入宽限期或请求过期策略；项目已有这些机制时必须沿用其语义。
8. 瞬时请求不等于必须由 `FixedUpdate` 消费：物理跳跃等请求由物理运动阶段消费，菜单、换武器或纯业务行为应由其所属系统在正确的时间域消费。

## 时间域与 Unity 生命周期

1. `Update`、`FixedUpdate` 和 `LateUpdate` 不是一一对应关系；一个渲染帧内可能执行零次、一次或多次 `FixedUpdate`，不得依赖“每次 Update 后必定紧跟一次 FixedUpdate”的假设。
2. 逻辑应放入其所修改状态所属的时间域：
   - 渲染帧意图、普通状态展示和大多数表现更新使用 `Update` 或项目既有动态更新阶段。
   - Unity Rigidbody / Rigidbody2D 物理状态和依赖固定时间步的运动使用 `FixedUpdate` 或项目既有物理 Tick。
   - 依赖人物本帧最终姿态的相机或纯表现修正默认使用 `LateUpdate`，但必须服从 Cinemachine 或项目相机系统的更新配置。
   - Root Motion 使用项目配置的 Animator 更新模式和 `OnAnimatorMove` 等既有入口，不得与另一套位置或速度写入逻辑并行竞争。
3. 角色业务逻辑不应因为名称是“业务逻辑”就全部放入 `FixedUpdate`；应根据它修改的是物理状态、渲染状态、网络 Tick 状态还是普通游戏状态决定执行阶段。
4. 用于决定 Rigidbody 运动的接地、墙体、斜坡和碰撞查询，默认与对应物理运动保持在同一物理时间域；表现层读取其缓存结果，不重复生成另一套相互冲突的判定。
5. 在 `Update` 中自行积分运动时使用 `Time.deltaTime`；在 `FixedUpdate` 中自行积分固定步运动时使用 `Time.fixedDeltaTime`。给 Rigidbody 的速度属性赋“每秒速度”时不得再次乘时间步。
6. Agent 不得未经确认修改 `Time.fixedDeltaTime`、Physics / Physics2D Simulation Mode、Input System Update Mode、Animator Update Mode 或 Cinemachine Update Method；这些是项目级设置，会影响其他系统。 高频更新、集中调度及低分配优化须保持实际输入、运动时间域、物理及表现契约，具体遵循[性能与内存管理规范](../Runtime/Performance.md)、[对象池规范](../Runtime/ObjectPooling.md)、[资源管理规范](../Runtime/ResourceManagement.md)。

## 运动后端识别与选择

1. 新增或修改人物移动前，Agent 必须先识别当前使用的运动后端，不得混用彼此冲突的方案：
   - Dynamic Rigidbody / Rigidbody2D。
   - Kinematic Rigidbody / Rigidbody2D。
   - Unity `CharacterController`。
   - 基于 Cast、Sweep 或重叠查询的自定义运动学控制器。
   - Animator Root Motion。
   - NavMeshAgent、网络权威 Tick、回滚模拟或项目自定义运动框架。
2. 如果项目已有运动后端，必须在该后端内扩展功能，不得仅因个人偏好改成另一种方案。
3. 如果任务是从零设计且需求不足，Agent 必须先说明候选方案的控制精度、物理交互、碰撞处理、网络需求和维护成本，再按用户确认的方案实现。

## Rigidbody / Rigidbody2D 角色

1. 由 Unity 物理系统推进的 Rigidbody 或 Rigidbody2D 角色，默认在输入提供层的既有更新阶段接收输入并缓存，在 `FixedUpdate` 中读取缓存输入并修改物理状态。
2. 下列操作默认属于物理阶段：
   - 修改项目当前 Unity 版本对应的线速度或角速度 API，例如 `linearVelocity`；旧版本项目可能使用 `velocity`。
   - `AddForce`、`AddTorque`、`MovePosition` 和 `MoveRotation`。
   - 物理跳跃、重力、物理加速度、碰撞约束和移动修正。
3. 不得仅把 `linearVelocity` 或 `velocity` 的赋值放入 `Update`，就宣称物理系统已经按渲染帧响应；真正的物理推进、接触和碰撞求解仍由物理模拟时间步决定。
4. 精确操控型人物可以采用明确的目标速度、加速度或速度变化模型；强调质量、惯性和真实受力的角色可以使用力或冲量。不得把“使用 Rigidbody”机械等同于“必须使用 AddForce”，也不得把直接速度控制写成所有人物通用的唯一方案。
5. 跳跃采用直接设置垂直速度、速度变化、冲量还是其他方式，必须服从现有运动模型和玩法手感；不得在没有依据时强制所有角色使用同一种跳跃实现。
6. 写入速度时必须明确各系统拥有的分量或贡献，避免无意覆盖重力、击退、移动平台、Root Motion 或其他系统产生的速度。
7. Rigidbody 插值只用于改善确认存在的渲染抖动，不会提高物理模拟频率，也不会让物理系统响应每一个渲染帧输入；插值还可能带来一个物理步的视觉滞后，启用前必须结合相机跟随和手感进行评估。
8. 不得把 `Transform.position` 或 `Transform.rotation` 作为带 Rigidbody 角色的常规移动通道。出生、传送、复位等例外操作必须明确区分于普通移动，并使用与当前后端一致的处理方式。

## Kinematic Rigidbody / Rigidbody2D 角色

1. Kinematic 表示运动主要由代码控制，不表示 Unity 物理系统改为跟随渲染帧运行。
2. 仍依赖 Unity 物理碰撞和固定模拟时，默认在 `FixedUpdate` 中使用 `MovePosition`、`MoveRotation` 或项目既有 Kinematic Motor。
3. 同一物理步之前多次提交 `MovePosition`、`MoveRotation` 或同类目标时，不得假设每次调用都会分别产生一次完整物理推进；应只在选定的物理 Tick 中提交该 Tick 的最终目标。
4. Kinematic 角色通常不会像 Dynamic Rigidbody 一样自动接受重力、力和碰撞冲量；需要由当前运动器明确处理的行为不得遗漏。
5. 如果项目采用完全自定义的运动学控制器，则应遵循该控制器自己的 Tick、Cast、穿透修正和平台处理规则，而不是同时再让 Rigidbody 作为第二套运动权威。

## Unity CharacterController 与自定义运动学控制器

1. Unity `CharacterController` 不属于普通 Rigidbody 动力学后端；默认可以在 `Update` 或项目既有人物 Tick 中计算本次位移并调用 `CharacterController.Move`。
2. `CharacterController.Move` 接收的是本次调用的位移量，且不会自动施加重力；速度积分、重力、跳跃速度和垂直位移必须由人物运动逻辑明确维护，并按所选 Tick 使用对应的时间步。
3. 自定义 Cast / Sweep 运动学控制器可以运行在 `Update`、固定 Tick 或网络 Tick，但输入、速度积分、碰撞查询、位移修正和状态更新必须处于同一套一致的模拟流程中。
4. 只有当前方案明确为自定义运动学控制器并完整承担碰撞处理时，才允许直接更新 Transform 或自定义位置状态；不得把直接改 Transform 当作绕过现有物理问题的临时方案。
5. 自定义控制器必须考虑项目实际需要的墙体、地面、斜坡、台阶、穿透修正、移动平台和高速移动检测；不得在未处理这些问题时宣称其与标准物理方案等价。
6. 存在网络预测、回滚、录像回放或确定性需求时，应使用明确的自定义模拟 Tick，并将渲染表现与权威模拟状态分离；不得默认绑定渲染帧率。

## 动画、朝向、音效和视觉反馈

1. Animator 参数、模型或 Sprite 朝向、准星、UI、音效和纯视觉特效默认由表现层在渲染帧更新，不应因 Rigidbody 使用固定时间步而全部等待 `FixedUpdate`。
2. 表现层可以同时读取：
   - 输入意图，用于立即反馈方向、瞄准或操作预期。
   - 角色决策状态，用于展示已接受的动作。
   - 运动器状态，用于展示实际速度、接地、上升、下落和碰撞结果。
3. 对需要降低感知延迟的物理操作，允许在输入到达的当前渲染帧播放不改变权威状态的起手动画、音效或预备特效，再由后续物理 Tick 执行实际物理行为。
4. 必须区分“玩家请求了动作”和“动作实际执行成功”：跳跃、命中、落地、受击等确认型表现应由角色状态或物理结果触发，不得仅凭原始按键提前认定成功。
5. Animator 默认按其当前 Update Mode 运行；普通 `Normal` 模式通常由渲染帧更新，`Animate Physics`、Root Motion 或项目自定义 Playable 流程必须遵循现有配置。
6. 不得默认在 `FixedUpdate` 中持续写入 Animator 参数、重复触发 Animator Trigger、音效或一次性特效；确需与物理同步时，应先生成一次状态变化或表现事件，再由表现层消费一次。
7. 必须区分视觉朝向和物理朝向：仅翻转模型、Sprite 或视觉子节点时可在表现层更新；会改变 Rigidbody、Collider、挂点坐标系或物理旋转时，必须由对应运动 Tick 的权威写入者处理。

## 相机跟随

1. 普通脚本相机默认在 `LateUpdate` 读取人物最终显示姿态，以减少人物与相机更新顺序不一致造成的抖动。
2. 使用 Cinemachine、相机插值、网络插值或项目自定义相机框架时，必须遵循其既有更新策略，不得同时新增另一套并行跟随逻辑。
3. 相机跟随物理角色时，应统一 Rigidbody 插值、相机更新模式和跟随目标 Transform 的来源。
4. 相机平滑、Rigidbody 插值和动画过渡解决的是视觉平滑，不等于物理系统响应了每一次渲染帧输入；不得用这些表现手段掩盖人物运动状态被多个系统重复写入的问题。

## Agent 执行人物控制任务的要求

1. 修改前除遵守AI 修改与交付规范中的通用确认流程外，还必须先检查并说明：
   - 现有输入来源和输入消费接口。
   - 当前运动后端和运动权威组件。
   - 连续输入与瞬时请求的保存、消费和清理方式。
   - `Update`、物理 Tick、`LateUpdate`、`OnAnimatorMove` 或网络 Tick 的职责分工。
   - Animator Update Mode、Root Motion、相机框架及网络或回放要求。
   - 将修改的脚本、Prefab、Animator、输入配置、相机或项目设置及其影响范围。
2. Agent 必须明确选择并说明当前任务采用的路径：
   - Rigidbody / Rigidbody2D 物理驱动：缓存输入，物理 Tick 执行运动，渲染帧执行表现。
   - Kinematic Rigidbody + Unity 物理：缓存输入，物理 Tick 提交最终运动目标，渲染帧执行表现。
   - `CharacterController` / 自定义运动学：在选定模拟 Tick 中主动移动并处理碰撞，通常为 `Update`。
   - 自定义固定模拟 Tick：用于网络、回滚、回放或确定性需求，渲染层独立读取或插值。
3. 默认数据流为：`现有输入模块 -> 角色输入快照/事件 -> 角色规则或状态机 -> 唯一运动执行器 -> 角色状态快照 -> 动画/特效/相机`。
4. 未确认输入来源时，不得自行接入 Unity Input API、Input System 或 Rewired；只能保留或对接项目已有输入消费接口。
5. 未确认运动后端时，不得直接生成最终移动实现；必须先从现有代码和组件中识别 Rigidbody、Kinematic、CharacterController、Root Motion 或自定义控制器的实际使用方式。
6. 不得未经确认引入新的状态机、命令队列、事件总线、依赖注入框架、输入框架、完整人物控制框架或相机框架。
7. 使用 Unity API 时必须匹配项目当前 Unity 版本和现有代码风格；不得为了使用新 API 无关地升级或批量改名旧代码。
8. 完成方案或代码后，必须列出：
   - 需要用户手动绑定或配置的引用。
   - 需要用户在 Unity 中手动验证的输入、移动、跳跃、碰撞、动画和相机行为。
   - 采用的运动路径、运动权威写入者、输入字段语义、瞬时请求清理规则和各生命周期职责。
   - 未通过静态代码即可确认的风险或待确认项。
9. Agent 不得自行编译或运行验证；所有验证由用户按 AI 修改与交付规范中的验证权限要求由用户手动完成。
