# 异步业务与状态一致性规范

## 规范定位与适用范围

定义异步、并发、重入、状态有效性、幂等、取消及跨 System 一致性。

本规范是对应专业事项的规则主定义文档。规则适用范围、约束性质、优先关系及例外统一遵循 [规则优先级与冲突处理规范](../Governance/RulePriority.md)；项目修改、读取、实施及交付遵循 [AI 修改与交付规范](../Governance/AgentWorkflow.md)。

本节定义跨项目、跨引擎可复用的业务一致性原则，约束异步、并发及重入场景中的业务组织、状态有效性和实际结果交付。Unity 的 UniTask、协程、主线程及 PlayerLoop 等具体技术实现遵循[Unity 异步与 UniTask 规范](Async.md)；其他引擎遵循对应的异步技术规范及项目契约。使用 UniTask、Task、协程、回调或事件，不自动保证业务状态一致性；本节不改变已经确定的异步技术选型、架构职责及修改授权规则。各项规则按照自身职责共同生效，局部规则及技术选型不得自动引入额外业务限制、并发控制或 UI 变化；适用关系及真实冲突遵循[规则优先级与冲突处理规范](../Governance/RulePriority.md)。

## 适用范围与已有实现保护

1. **统一业务约束，不统一具体技术实现。** 本节适用于存在跨帧等待、外部异步操作、多个工作单元、竞争读写、同步回调重入或多方状态提交等实际需求的业务，以及具有相应问题的 Manager 管理流程；具体执行机制按所属职责和项目实际需求确定。纯同步业务也应遵守与其实际状态冲突及重入风险有关的约束。
2. **优先复用已有机制。** 项目已经具有适用的请求处理框架、命令系统、队列、异步互斥机制、取消契约、版本控制、事务、幂等机制或服务端提交接口时，必须先识别并沿用其稳定实现及业务语义。技术方案不同于本节参考方案，不构成主动重构的理由。
3. **新建机制须有实际依据。** 项目缺少适用能力时，应先明确业务需求、冲突范围、权威来源、预期行为及候选方案；涉及新增公共能力、改变既有执行策略或引入附加限制时，必须说明影响并取得用户确认。不得建立与已有框架重复的平行机制，不得为假设性风险增加未确认的运行行为。
4. 发现既有实现存在真实的一致性缺陷、职责冲突或无法满足当前需求时，必须明确报告具体读写路径、发生条件和影响，提出方案并按授权流程处理，不得将发现问题视为自动修复、批量迁移或重构授权。
5. 本节中的策略、数据字段、结果名称和职责协作示例用于表达设计语义，不要求所有项目引入对应类型或技术。与具体任务无关的同步计算、普通查询及局部操作，不需要为满足规范而增加完整请求生命周期、锁、事务或其他框架结构。

## 异步、并发与重入的语义区别

1. 异步表示操作可能挂起等待并在之后继续执行；并发表示多个操作在一段时间内同时处于处理过程中，允许交错执行；并行表示多个操作在同一时刻实际执行。异步不等同于并行，也不保证不存在状态冲突。
2. **在 Unity 项目中，主线程及单例不等于业务串行；其他引擎按其执行模型判断。** `await`、协程挂起、外部回调以及同步事件或委托引发的再次调用，均可能使其他业务进入尚未完成的操作。即使不使用多线程，也需要根据实际读写路径识别竞争和重入；同一 System 只有一个有效实例，不代表同时只允许处理一个请求。
3. 重入表示一次业务尚未达到其约定完成边界时，同一业务入口再次被调用。重入与异步等待、独立并发可以同时存在；是否允许以及如何处理，必须遵循该业务的实际契约。
4. **优先保持无需异步的处理为同步。** 普通纯业务计算和不需要等待的操作，继续遵循既有同步实现约定；不为了统一形式而引入异步框架、任务队列或跨帧等待。需要跨帧计算时，由符合职责的上层组织调度，处理类型仍保持显式输入、输出和状态隔离。Unity 项目的具体异步 API 遵循[Unity 异步与 UniTask 规范](Async.md)；其他引擎遵循其对应技术契约。

## 业务状态、执行状态与表现状态

| 状态类别 | 含义及示例 | 主要职责归属 |
|---|---|---|
| 权威业务状态 | 当前有效金币、背包物品、任务进度等 | 业务对象、RuntimeData 或既有权威来源，由所属 System 组织受控更新 |
| 请求执行状态 | 待处理、处理中、提交中、已结束、等待确认等 | System、Processor；Committer 可以保存自身提交所需的执行状态 |
| 表现与交互状态 | 页面显隐、加载展示、动画进度及当前交互等 | Manager、Controller、Presenter、View 或明确的局部能力所有者 |

1. 上述状态必须按照各自职责、实际所有权和有效范围管理。不得以执行状态或表现状态代替权威业务状态，也不得以权威业务状态已更新推定所有前台表现已经结束。
2. 业务请求、状态持有者、页面、场景、对象池租用及其他执行资源可以具有不同的生命周期。某一对象被关闭、停用、销毁或回收，不自动决定其他业务是否取消、完成或失效。
3. 执行状态只表达实际处理过程，不得成为另一份独立裁决同一业务事实的权威状态。不得仅为了表示异步状态而默认新增状态机、全局状态标记或 UI 控制逻辑。
4. **一致性处理不构成 UI 变更授权。** 不得将 `isProcessing`、请求排队、异步等待或提交检查自动关联到按钮禁用、置灰、遮罩、Loading、页面锁定及其他未经确认的交互变化；仍须遵守[UI 与交互变更授权规范](../Governance/UIChangeAuthorization.md)及[校验与附加限制授权规范](../Governance/ValidationAuthorization.md)。

## 异步业务的职责归属

| 类型 | 异步业务中的职责 |
|---|---|
| Manager | 自身管理职责范围内的异步流程和管理状态一致性，不接管业务 System |
| System | 确定所属业务的执行策略、权威来源、一致性要求、完成条件及跨 System 协作 |
| Processor | 在已确定的工作单元处理契约内执行调度、处理顺序、生命周期管理及请求结果交付 |
| Provider | 提供与实际处理时机相符的有效状态、只读数据或快照 |
| Logic 及下层纯处理类型 | 根据显式输入确定业务处理结果，不自行组织外部异步执行或提交 |
| Committer | 按提交契约检查结果有效性，组织实际提交及相关步骤，返回真实提交结果 |
| 业务对象 / RuntimeData | 持有所属权威状态并提供受控更新能力 |
| DataStorage | 按存储契约执行持久化读写，保证其负责的写入及数据有效性边界 |
| Service / Adapter | 提供底层网络、文件、平台及外部接口等技术能力，准确表达可确认的执行结果 |
| EventSystem | 按既有事件契约传播已成立事实，不承担通用业务调度和并发控制 |
| Controller / Presenter / View / Module | 按各自职责管理交互、表现或局部执行生命周期，不绕过 System 的业务一致性边界 |

1. **System 负责确定业务执行与一致性契约。** 具体契约来自用户要求、已确认方案或项目现有业务规则；System 不因组织并发而取得擅自改变规则的权限。存在跨 System 业务时，仍由主导 System 组织完整用例。
2. System 可以直接组织同步或异步业务；存在明确的工作单元处理生命周期时，可以引入或复用 Processor。Processor 执行已经确定的处理策略，不自行定义是否允许并发、合并、取消或重试等业务决策，不依赖具体业务 System，并通过显式提交接口委托 Committer 执行实际提交。
3. Provider 可以按既有契约提供所需状态；Logic、Resolver、具体职责能力及基础处理实现层仍遵守纯处理和显式依赖约束。异步组织、外部读写、等待和状态提交不得向纯处理层下沉，不得通过回调、委托或事件变相绕过该边界。
4. Committer 负责满足其提交范围内的一致性契约，不重复执行领域规则、不接管跨 System 用例。待提交的业务结果失效、提交部分完成或实际结果尚未确认时，应如实返回实际情况，由 System 或 Processor 按既定职责组织后续处理。
5. **允许细粒度拆分，不机械新增全局框架。** 在已有明确职责和稳定契约时，可以将请求集合、调度、执行状态或具体互斥能力进一步拆分。单例约束不向这些类型传递。不得仅因使用异步而引入 AsyncManager、ConcurrencyManager、ConcurrencySystem、全局请求队列、事务管理器或其他通用架构；确有公共基础能力需求时仍须报备并取得确认。本节不确立 Scheduler、Executor、Coordinator 等新的通用职责后缀。

## 请求处理与并发策略

应首先识别多个请求是否代表独立操作、是否共享冲突状态、是否要求顺序处理，以及是否允许取消、拒绝或合并。以下是可选择的业务处理策略，不是所有异步业务必须经过的阶段，也不是统一强制的实现方式。

| 策略 | 核心语义 | 适用情形及限制 |
|---|---|---|
| 独立并发处理 | 多个请求分别执行，允许交错 | 相互独立的查询、资源加载或不发生状态冲突的操作；不得破坏共享状态契约 |
| 顺序处理（Queue） | 按已确定顺序逐个处理工作单元 | 必须保留每次操作且顺序影响结果，或需要隔离冲突状态的请求；须明确等待、处理和完成边界 |
| 忙碌时拒绝（Reject） | 有请求执行时按契约拒绝新请求 | 明确要求独占执行的登录、切换或其他业务；拒绝是业务行为，不能擅自增加或静默丢弃 |
| 最新请求优先（Latest Wins） | 只将当前最新有效请求的结果应用到对应目标 | 搜索、预览、筛选等允许旧结果失效的业务；不得丢弃已经产生的独立业务效果，旧操作不一定能够真正取消 |
| 共享执行结果（Single Flight） | 多个语义可共享的请求共用一次实际执行 | 同一有效范围内的相同配置或资源加载；独立消费、奖励等不得因参数相同而错误共享 |
| 批量合并处理（Batch） | 按明确契约组合多个工作单元后处理 | 已确认允许合并的操作；必须保留必要的业务语义、独立效果、事件及请求结果对应关系 |

1. **不得仅因方法是异步方法，就默认增加 `isProcessing` 拦截、队列、拒绝、取消旧请求、共享结果、自动去重或批量合并。** 策略必须有既有契约、明确需求或经确认的方案作为依据。已有策略不得未经确认改变。
2. 需要保留每次独立操作时，不得将多次调用机械判定为重复请求或使用只保留最新结果的策略；请求 A 和请求 B 的参数相同不代表它们属于同一次逻辑操作。
3. 顺序处理必须明确受理时机、有效状态读取时机、处理次序和进入下一工作单元的条件；不得在请求入队时保存一份可能已经失效的权威状态，并将其无条件用于之后的计算。请求表达的原始意图、参数及必要身份应按契约保存。
4. 忙碌时拒绝、等待、过期、取消和其他处理结果必须根据已有请求契约明确交付，不得以静默 `return` 将未执行的请求报告为成功，也不得自行改变后续请求的执行机会。队列在失败、取消及异常后的继续或停止策略应有明确依据，并保证对应工作单元和必要资源得到正确处理。
5. 最新请求优先只表示旧结果不再适用于该目标，不等同于旧执行一定取消或旧业务效果被撤销。共享执行时，应明确共享范围、执行所有者、各等待者的取消与结果交付关系，并遵守所用异步技术对任务多次等待及共享结果的约束；Unity 项目中的 UniTask 多次等待约束遵循[Unity 异步与 UniTask 规范](Async.md)。单个等待者退出不自动取消共享操作。
6. 批量合并应检查合并前后的规则判断、顺序、阶段变化、独立副作用及结果归属是否符合契约。例如进度增量 `+1`、`+3`、`+2` 只有在合并不改变所需的业务效果时，才可以作为一次 `+6` 处理。不得借批处理擅自跳过中间奖励、事件或其他必要步骤。
7. 对于具有稳定请求处理职责的业务，可以提前建立 Processor 等架构边界，即使目前请求较少或仅执行简单处理；但不得为了充实实现而凭空增加上述策略或额外生命周期。

示例：玩家有 100 金币，两个独立购买请求各消耗 80 金币。若两次请求均读取余额 100 后挂起，恢复时又未经一致性保障直接提交，则可能造成超额消费、丢失更新或重复发放。若业务已确定采用顺序处理，并且该机制覆盖所有相关余额写入路径，则第一个请求完成扣款后，第二个请求按最新余额 20 执行原有余额规则；不应凭该示例为所有购买业务自动增加队列或拒绝策略。

## 并发控制的有效作用域

1. **按照实际冲突状态及业务有效范围确定并发控制，而不是按照类型名或单例身份确定。** 必须识别相关操作的读取对象、写入对象、共享资源、共同约束及其他可能修改这些状态的合法入口。
2. 同一个 System 可以管理多个独立的账号、背包、角色、战斗或其他业务对象。不同实例互不冲突时，允许独立处理；不得因 System 采用单例而机械将所有请求放入同一个全局串行范围。
3. 不同业务对象或不同 System 仍可能依赖同一权威状态，例如购买不同商品可能共同消耗同一钱包余额。涉及多个对象或资源的操作，应按照实际一致性契约覆盖全部相关冲突范围；单独保护其中一个对象或一条入口，不能推定整个业务安全。
4. 并发控制只在实际需求所需的范围内组织。可以按项目、System、账号或会话、业务对象、共享资源及单次请求等范围确定；不默认建立按所有对象索引的锁表、作用域容器或复杂调度框架。
5. 需要同时保护多个冲突范围时，应明确获取、等待和释放的关系，避免循环等待、遗漏相关写入路径或因持有保护而等待只能在保护释放后完成的操作。具体技术实现按已有机制或经确认的方案确定。

例如，一个 InventorySystem 可以分别处理多个不共享状态的 Inventory；玩家背包与仓库之间的转移则需要按该次转移的一致性契约考虑两个实际状态持有者。两个不同商店商品的购买可能竞争同一 Wallet，不得仅按商品 ID 判断请求互不冲突。

## 状态读取与提交有效性

1. **业务结果的计算依据必须与实际提交条件相符。** System 或 Processor 应组织与处理时机对应的状态读取，通过显式输入、只读信息或 Snapshot 将所需状态提供给 Logic。需要跨越等待时，应明确数据是实时只读访问还是固定快照，以及其所有权和有效期；不能将指向可变状态的只读接口误认为稳定快照。 存在运行时配置变化时，业务计算所依据的配置及其有效范围同样属于提交有效性的一部分；是否固定当前配置、提交时重新确认或延迟至后续业务生效，遵循实际业务及配置更新契约，不强制引入配置版本号、快照或热更新框架。具体遵循[配置数据管理规范](Configuration.md)。
2. 在读取、计算及提交之间存在异步挂起、事件回调、重入、其他合法写入或权威状态变化时，必须按实际契约保证计算依据在提交时仍然有效，不得无条件将旧状态计算出的结果覆盖新状态。
3. Committer 可以执行提交有效性检查，包括目标身份、有效范围、必要依赖和结果所依据的条件。该检查用于确保提交契约成立，不代替 Logic 或 Rules 重新裁决领域业务。结果失效时，应返回明确结果，由 System 或 Processor 按既定契约决定是否重新读取、重新处理、拒绝或采用其他方案；不得由 Committer 自行重新计算或静默重试。
4. **必要的检查与写入应满足同一一致性契约。** 存在竞争时，仅在写入之前检查一次版本、余额或目标状态，不能自动保证安全；若检查和写入之间仍可能发生竞争修改，应使用实际能够覆盖该竞争的一致性机制。服务端权威业务必须由能够控制权威状态的一方落实必要保障，客户端检查或互斥不代替服务端校验及原子提交。
5. 优先沿用现有机制；从零设计时，若同步连续处理已经能够覆盖相关状态读写且不存在挂起、重入或其他竞争写入，则不需要额外并发框架。存在有序工作单元处理职责时，可以优先考虑 Processor；跨帧、多方写入或外部提交确有一致性需求时，再根据实际情况选择适用机制，不强制所有业务采用版本号、锁或事务。
6. 一致性机制只在实际需要的范围内生效，并明确正常完成、失败、取消及异常后的释放和清理责任。不得以阻塞引擎主线程或阻断异步续体继续执行的方式等待；在 Unity 项目中还须遵守 Unity 主线程及 PlayerLoop 执行约束。使用互斥机制时，应匹配其同步或异步语义，不得在不支持异步等待的临界区中跨越 `await`。
7. 结果有效性检查及并发保护必须遵守[校验与附加限制授权规范](../Governance/ValidationAuthorization.md)。不因采用状态一致性规范而获得新增业务规则、拒绝条件、自动重试、回滚或补偿的授权。

| 可选机制 | 适用语义及注意事项 |
|---|---|
| 同步连续处理 | 无相关竞争写入时，在明确执行边界内完成读取、判断及写入 |
| 顺序处理 | 同一冲突范围内按契约逐项处理，在实际执行时读取有效状态 |
| 互斥保护 | 保护明确的冲突范围，相关竞争写入必须遵守同一保护契约 |
| 版本或条件检查 | 根据实际相关状态判断旧结果是否仍可提交；检查与写入须满足一致性要求 |
| 原子条件更新 | 将必要条件检查和实际写入作为不可被相关竞争写入分割的操作 |
| 事务 | 在事务实际覆盖的权威状态范围内，按约定保证相关变更的整体提交 |

示例：余额为 100 时，WalletSpendLogic 计算消耗 80 后剩余 20；如果提交前其他合法操作已使余额变成 50，WalletSpendCommitter 不能直接写入旧结果 20。应按既定一致性契约确认结果是否仍可应用，并返回真实的提交情况。状态版本仅为候选机制，不要求项目为所有状态新增版本字段。

## 幂等性与重复请求

1. **幂等性表示同一次逻辑操作被重复执行时，不应额外产生该操作的业务效果。** 是否需要幂等保证、如何识别同一次逻辑操作及重复请求的返回语义，必须来自实际业务及权威来源契约。
2. 必须区分用户主动发起的多个独立操作、同一次逻辑请求的重复投递或重试、业务本身禁止重复发生的行为，以及同一异步结果被错误重复应用的实现缺陷。不得仅依据相同参数、同一商品、短时间点击间隔或请求到达顺序判定为同一次请求。
3. 确有幂等需求时，可以使用项目已有的请求 ID、交易 ID、业务唯一标识或权威状态约束。应明确标识的有效范围、重复判定、已处理结果及必要记录的生命周期；不得强制为所有 Request 增加 RequestID、持久化记录或全局去重机制。
4. 幂等保障应由能够控制实际业务效果的权威方落实，并覆盖需要防止重复的提交步骤。仅在客户端缓存请求 ID、限制按钮或进行队列处理，不能保证服务端不会重复执行；仅检查一次处理记录而未保证检查与实际效果之间的一致性，也不能推定幂等性成立。
5. 幂等性不等同于忙碌时拒绝、顺序处理、共享执行或批量合并。这些策略可以按实际契约组合，但不得互相代替。重试尚未确认的操作时，是否沿用原逻辑请求身份及如何查询结果，应遵循实际协议，未经确认不得自动重试。

例如，玩家主动购买两次相同商品可以是两个独立请求；同一次购买因网络响应丢失而再次发送，才可能属于需要幂等保障的重复投递。领取已经领取的任务奖励是否允许，仍由任务业务规则确定，不由通用请求去重机制重新定义。

## 异步取消与业务生命周期

1. **区分取消等待、取消执行与撤销已经发生的业务效果。** CancellationToken 表达相应范围内的取消请求，不能单凭令牌触发、等待中断或取消异常，认定底层执行已经停止，更不能认定业务状态已自动撤销。
2. 异步操作必须具有明确执行所有者。调用方的等待生命周期、实际业务执行生命周期、提交过程及前台展示生命周期应分别确定；取消令牌应与实际需要取消的执行范围一致，不得机械将最外层 View、页面或场景的生命周期传递为所有业务的取消条件。
3. 请求仍在待处理阶段时，是否移除、标记取消或继续处理，遵循请求契约；实际执行尚未产生业务效果时，可以在业务允许的边界停止；正在进行提交或外部操作时，必须根据底层实际取消能力确认执行情况，不得假定中断等待必然阻止写入。
4. 已经生效的业务效果应按真实结果表达。撤销、退款、回滚、补偿属于独立业务行为，必须具备明确需求和契约，不得作为普通 CancellationToken 的默认效果。
5. 当调用方取消等待但业务仍需继续执行时，应由明确的执行所有者继续管理任务、实际结果、异常及资源清理，按照原业务归属处理后续结果；不得因为调用方退出而形成无人管理的任务或丢失已发生的业务事实。
6. 同一执行过程存在多个等待者时，应明确各等待者取消与共享执行取消的关系；单个等待者的生命周期不自动等于整个共享任务的生命周期。Unity 项目的取消来源、令牌传递及 UniTask 等待约束遵循[Unity 异步与 UniTask 规范](Async.md)；其他引擎遵循对应技术契约。
7. 页面关闭、组件停用、场景卸载及对象回收时，按照实际职责停止不再适用的表现或局部执行，并保护业务数据及有效结果；是否取消关联业务须由其契约决定。本条不授权自动改变 UI 状态或交互行为。

| 所处阶段 | 取消处理参考 |
|---|---|
| 请求待处理 | 按已确认的取消契约处理待执行工作单元 |
| 尚未提交 | 在允许且能够安全停止的业务边界取消实际执行 |
| 正在提交 | 依据实际执行及底层取消能力判断结果，保证必要清理 |
| 已提交 | 保留已成立事实，不自动撤销或重复执行 |
| 外部结果尚未确认 | 如实表达未知结果，不推定未执行 |
| 独立展示执行中 | 根据展示生命周期停止或继续，不因此改变权威业务结果 |

## 过期请求及结果处理

1. **异步请求及结果应具有与实际业务相符的身份和有效范围。** 应根据需求明确账号、登录会话、存档、场景实例、角色、战斗、对象实例、对象池租用周期、页面生命周期或单次请求等归属，不得仅凭当前全局单例、同名对象或对象引用非空推定原请求仍然有效。
2. 账号、存档、场景、页面及对象切换后，旧请求或旧结果不得被错误应用到新的业务状态、对象实例或展示范围。同一账号重新登录、同一对象再次租用时，也应检查其原有效期是否仍成立，不能仅比较表面身份。
3. 请求的归属、处理期间的数据有效性及结果应用时机，应由 System、Processor、Committer 或对应的管理和表现职责所有者按各自边界保证。可以沿用显式对象引用、会话标识、生命周期令牌、版本号、租用标识或其他已有机制；不要求所有业务新增 SessionID、GenerationID 等统一字段。
4. 过期结果不适用于当前目标时，应按照既有契约处理其结果、异常和资源清理，不得写入错误的状态持有者，也不得借忽略旧展示结果而遗漏原业务已经产生的真实效果。需要为原有效范围处理或后续确认业务结果时，仍由相应所有者组织。 涉及池化对象、加载句柄及临时缓冲区时，须按实际所有权清理旧结果，保护新租用及仍被其他执行者使用的数据与资源，具体遵循[性能与内存管理规范](Performance.md)、[对象池规范](ObjectPooling.md)、[资源管理规范](ResourceManagement.md)。
5. 旧请求不再适用于当前页面或会话，不等于远端业务没有生效。已经发送的服务端请求，必须根据真实可确认的业务结果分别处理其权威效果和本地结果应用范围；不得自动取消、退款、补偿或重新提交。

例如，账号 A 发起背包加载后切换至账号 B，A 的加载响应不得覆盖 B 的 RuntimeData；若同样的场景是账号 A 发起的购买请求，则其结果不适用于 B，也不能据此宣称 A 的购买没有执行。

## 超时、失败与结果尚未确认

1. **区分等待失败与业务执行失败。** 网络断开、超时、取消等待、未收到成功响应或通信异常，不自动证明权威方没有执行操作。只能依据实际契约及可确认事实判断业务是否成功、失败、取消、部分完成或尚未确认。
2. RequestResult、CommitResult 等结果应在各自约定范围内如实表达执行情况，并保留已经发生的效果、未执行的步骤、已知失败及尚未确认的部分。无需执行的步骤不是失败；调用方等待取消也不应覆盖已知的提交事实。
3. 下表仅定义常用结果语义，不强制所有项目创建相同枚举、结果字段或状态机。必要时可分别表达执行进度、等待结果和提交事实，不以单一状态覆盖多个同时成立的事实。

   | 结果语义 | 含义 |
   |---|---|
   | Success | 对应范围内的成功条件已经确认 |
   | Failed | 对应范围内的失败已经确认，不据此抹除其他已发生的效果 |
   | Canceled | 对应等待或执行范围的取消已经确认，须区分具体取消对象 |
   | PartialSuccess | 已确认部分业务步骤或效果生效，其余步骤按实际情况表达 |
   | Unknown | 某项实际业务结果尚未确认 |
   | Pending | 相应请求仍待处理或等待确认，未达到对应完成边界 |

4. 对外部结果尚未确认的情况，应按照既有契约选择结果查询、状态同步、等待确认或具备相应幂等保障的重试等方案。不得擅自增加超时时间、自动重试、退款、回滚、补偿、静默恢复或其他可能产生额外业务效果的策略。
5. 业务条件不成立等可预期失败与异常诊断继续遵循既有日志与异常处理规范。不得吞掉异常、假装成功，也不得因日志、异常或取消而将已经确认的状态更新错误描述为未执行。 实际异常处理及日志记录由明确责任边界承担，正常业务拒绝、取消及技术故障须区分，不机械将所有异常转换为普通失败。

例如，服务端可能已经成功扣款和发货，但响应途中网络中断。客户端只能报告其可确认的状态；不能仅因等待超时就认定购买失败并以新请求再次购买。

## 跨 System 业务一致性

1. **由主导 System 组织跨系统业务的一致性契约。** 各 System 保持自身领域规则与权威状态边界，分别通过公开业务能力或已经明确的提交契约处理所属状态。不得由 Manager、UI、普通事件监听者或某一个 Committer 接管完整跨系统业务组织。
2. 必须先明确业务允许的实际结果、整体成功条件、各步骤事实成立条件，以及部分完成时需要表达或处理的结果。具体提交顺序及失败策略由既有业务或用户确认的契约决定，不通过通用规范统一选择一种机制。
3. **顺序处理不等于原子提交。** 依次调用多个 System 可以保证调用顺序，但不能自动保证全部成功或全部不生效。客户端队列、互斥或本地事务只能在实际覆盖的范围内提供保障，不得据此宣称跨服务、跨存储或跨权威来源的整体原子性。
4. 业务要求整体原子性时，应使用能够覆盖相关权威状态的明确机制，例如已有的统一权威提交接口或事务能力；若现有架构无法满足，则报告限制、风险和候选方案，不得以部分写入、普通事件或未经确认的回滚代替该保证。
5. 允许部分成功、补偿或最终一致性的业务，应具有明确业务依据、状态及结果契约。补偿是具有自身结果的业务操作，不等同于自动撤销原操作；最终一致性应具有明确的收敛条件及负责机制，不等同于允许无限期保留错误状态。不得为所有跨系统业务默认增加事务、补偿流程或全局协调框架。
6. 主导 System 必须综合各步骤已经确认的执行情况及尚未确认的部分，交付真实的整体结果。后续处理仍由主导 System 按契约组织，Committer 不自行定义跨系统重试、补偿、失败恢复及其他业务决策。

| 候选方案 | 含义 |
|---|---|
| 原子提交 | 在约定的权威状态范围内保证相关变更整体生效或整体不生效 |
| 顺序提交 | 按约定顺序执行各步骤，并分别保留实际结果 |
| 部分成功 | 按业务契约允许部分步骤生效，明确未完成及未知部分 |
| 补偿机制 | 对已发生的效果执行经确认的补偿操作，并处理补偿自身的结果 |
| 最终一致性 | 允许约定范围内暂时不一致，并通过明确机制使状态达到约定的一致结果 |

例如，任务领奖过程中背包奖励已经发放，但任务领取状态提交失败，主导 MissionSystem 必须保留两项实际结果，不能直接报告全部成功或假定奖励未发放。如何保证整体成功或处理部分完成，遵循该业务已经确认的一致性契约，不由本例决定。

## 异步持久化与状态同步

1. **状态生效与持久化完成必须区分。** System 决定业务保存策略及一致性要求，Committer 按提交契约组织保存，DataStorage 和 Service 等执行所属持久化与技术操作。不得统一假定状态更新后必须立即保存，也不得将保存请求已经发起当作保存已经成功。
2. 对同一存储目标或共享持久化状态存在多个异步写入时，应按照实际存储契约保证写入顺序、逻辑版本或更新语义正确，避免旧保存结果错误覆盖较新的有效数据。判断新旧依据的是对应业务及存储契约，不机械比较业务数值大小或请求完成时间。
3. 可以采用针对同一目标的顺序写入、权威方版本或条件写入、明确允许的保存合并等机制，优先沿用已有存储能力。不得仅在客户端按回调顺序更新显示，就推定外部实际写入顺序正确；不强制所有项目新增 SaveProcessor、存档队列、版本字段或统一保存系统。
4. 异步保存输入应具有明确的所有权、目标身份、内容语义及有效期。需要固定保存内容时，应使用符合既有契约的独立数据或稳定快照，不得在等待后无意读取已经变化的共享可变集合，导致保存内容与预期版本不一致。
5. 异步加载、服务端响应及其他状态同步结果应用到运行时状态前，同样应考虑目标身份、有效范围及相关状态是否已经变化，防止过期读取结果覆盖之后的合法更新。DataStorage 不因完成读取而自动取得权威状态提交权限。
6. 保存失败、取消、结果未知及部分完成时，应保留真实的运行状态与持久化结果，由 System 或其委托的 Committer 按契约组织后续处理。不得擅自增加自动保存、定时保存、写入合并、重试、回滚或状态恢复机制。

例如，任务进度先更新到 20，再更新到 30；若保存 30 的操作先实际写入，而较早的保存 20 后写入并覆盖它，就可能造成运行时与持久化状态不一致。需要按实际存储契约选择能够覆盖相应写入路径的保障，而不是仅凭保存发起顺序判断最终结果。

## EventSystem 与异步业务协作

1. **事实事件只在其对应事实按业务契约成立后发布。** 不得将尚未满足提交契约的中间状态报告为已完成事实。具体事实可以在整个业务或前台流程结束前独立成立，仍遵守已确定的事件发布时机，不统一推迟到全部异步操作结束。
2. 事件监听者发起的新业务，应经所属 System 的正常公开入口进入既有一致性及请求处理机制，不得绕过 Processor、Committer、状态持有者或相应业务规则直接修改权威状态。
3. 同步事件和其他外部回调可能在原业务尚未返回时再次进入业务入口；队列、异步互斥等实现必须考虑该实际重入关系。不得让当前请求等待一个只能在当前请求达到处理边界或释放相应保护后才能执行的请求，避免循环等待或死锁。
4. 默认避免在必要状态保护范围内执行与该保护无关的外部监听回调。确需在保护范围内发布事件或执行回调时，应明确其同步、重入及等待行为，确保既有业务一致性契约成立。不得擅自改变已有事件分发方式或事实发布时机来规避问题。
5. EventSystem 仍负责事实通知，不作为通用业务请求排队、去重、重试、合并、互斥或事务框架。普通事实事件不得承担主导 System 必须等待的必要业务执行步骤。
6. 事件分发结束、监听者异步响应完成、业务提交完成和最终业务结果交付必须分别表达。订阅者异常或取消不自动撤销已成立事实；异步监听的任务所有权、取消、异常、参数有效期及清理继续遵守[EventSystem 与事件协作规范](../Architecture/EventSystem.md)。Unity 项目的具体异步技术实现遵循[Unity 异步与 UniTask 规范](Async.md)。

例如，MissionProgressCommitter 提交任务进度后发布 MissionProgressChangedEvent；监听者若发起新的任务进度请求，该请求仍须按 MissionSystem 已有契约处理。如果当前 Processor 的完成条件包含等待同一队列中排在自己之后的请求，就可能产生循环等待；不得将此类等待关系隐藏在普通事件响应中。

## Agent 开发前检查与默认设计方案

1. 新增或修改存在异步、并发、重入或状态一致性风险的业务前，应根据实际任务检查下列事项，不要求对无关的同步操作机械执行全部检查：
   - 当前业务入口、权威状态来源、状态持有者以及相关读写路径和外部调用。
   - 项目已有请求处理、并发保护、状态提交、异步、持久化及事件契约。
   - 多个请求是否互相冲突，实际冲突范围以及是否允许顺序、并发、拒绝、取消、共享或合并。
   - 状态读取和计算依据的有效期，提交有效性检查及实际写入之间的一致性保障。
   - 实际执行所有者、各等待者和展示对象的生命周期，以及取消、过期结果和资源清理规则。
   - 同一次逻辑请求的身份及是否需要幂等保障；超时、异常、未知结果和部分完成的真实语义。
   - 跨 System、持久化、服务端提交、事件回调及其他可能造成重入或竞争写入的路径。
2. 任务方案应在与需求相关的范围内说明实际采用的业务处理策略、职责归属、有效作用域、完成边界及一致性保障。已有契约明确时优先遵守；发现实际缺陷、契约不明或需要新增机制时，应说明问题和候选方案，并按既有规则取得确认，不需要重复请示已经明确批准的内容。
3. 交付时应按实际任务说明所采用的处理策略及其依据、受影响的读写与提交路径、结果与取消语义，以及新增机制或限制的授权来源。列出需要用户手动验证的相关并发、重入、过期结果、取消或部分失败场景及尚无法静态确认的风险，不得宣称未经验证的运行结果，不得主动进行编译、编译错误检查或运行验证。

默认设计参考：

| 设计维度 | 默认推荐或约束 |
|---|---|
| 普通纯业务计算 | 无需等待时同步实现，保持纯处理边界 |
| 无状态冲突的请求 | 允许独立处理，遵循实际业务契约 |
| 有顺序依赖的工作单元 | 优先考虑已有处理机制或 Processor，按经确认的顺序策略组织 |
| 一致性保障 | 选择能够覆盖实际冲突范围及权威来源的适当机制 |
| 状态读取 | 使用与处理时机和计算契约相符的有效数据 |
| 过期提交 | 不直接应用已经失效的结果，按明确契约返回及处理 |
| 异步技术 | 遵循目标引擎的异步技术规范及已有稳定技术契约；Unity 项目遵循 Unity 异步与 UniTask 规范 |
| 一致性机制归属 | 优先由所属业务范围组织，不机械建立全局异步框架 |
| 已有实现 | 优先复用，实际冲突或缺陷按授权流程处理 |
| 内部职责拆分 | 鼓励建立稳定的职责边界，不因当前实现简单否定合理拆分 |
| 排队、拒绝、最新优先、共享、合并 | 按业务语义确定，不作为所有请求的默认策略 |
| 幂等记录、版本号、锁及事务 | 按实际需求和一致性契约选择，不强制引入 |
| 超时、重试、回滚及补偿 | 遵循已确认契约，不擅自增加 |
| UI 交互限制 | 不自动引入，须遵守 UI 与交互变更授权规范 |

本节不授权改变已有请求的执行顺序、并发范围、拒绝条件、取消语义、失败恢复、事件时机或 UI 行为。具体技术机制应服从已经确定的业务契约；架构可以提前建立，但不能为了所谓健壮性而擅自增加未确认的业务限制和运行机制。
