# Unity 性能与内存管理规范

## 规范定位与适用范围

定义性能目标、GC、数据结构、执行频率、缓存、渲染、物理及并行计算。

本规范是对应专业事项的规则主定义文档。规则适用范围、约束性质、优先关系及例外统一遵循 [规则优先级与冲突处理规范](../Governance/RulePriority.md)；项目修改、读取、实施及交付遵循 [AI 修改与交付规范](../Governance/AgentWorkflow.md)。

本节在既有架构先行、Manager 与 System 单向依赖、配置管理、数据所有权、事件协作及异步一致性约定的基础上，明确 Unity 性能设计、托管内存分配、对象复用、资源所有权及释放、执行频率和性能验证边界。性能优化不得破坏业务正确性、既有职责边界、玩法及表现契约。新项目默认规划 PoolManager、AssetManager 与 AssetSystem 的稳定基础架构，已有项目优先复用实际适用的机制。

## 适用范围与性能优化原则

1. **区分设计阶段的性能意识、实际瓶颈优化和架构级优化。** 新建代码应根据已知运行规模、执行频率、数据结构、资源生命周期及目标平台选择合理实现；存在实际性能问题时，依据静态分析及用户提供的运行数据提出针对性方案；涉及公共框架、执行模型或全局机制调整时，仍须按既有报备与确认规则处理。
2. **架构可以先行，具体优化机制应有依据。** 已明确存在大量敌人、弹幕、高频特效、列表条目或大型地图等运行需求时，可以在设计阶段规划适合的对象池、数据组织及算法，不要求等待实际卡顿后才设计。不得为假设性风险机械增加缓存、预热、队列、调度器、线程池、内存清理或其他运行机制。
3. 已有项目的资源加载框架、对象池、更新机制、数据结构、渲染管线及稳定性能方案优先复用。技术实现与本节默认方案不同不自动构成缺陷；发现实际职责冲突、资源泄漏、性能风险或能力不足时，应报告具体证据、受影响路径及候选方案，经用户确认后修改，不建立重复的平行框架。 已有稳定技术契约优先于通用默认方案，不自动优先于硬性架构、资源所有权、业务行为及授权约束；实际冲突遵循[规则优先级与冲突处理规范](../Governance/RulePriority.md)。
4. **性能优化必须保留实际业务及表现契约。** 不得以减少开销为由擅自改变业务规则、执行次数、处理顺序、随机语义、物理及网络模拟结果、配置来源、UI 交互、视觉品质或资源所有权。涉及改变现有契约的优化，应说明优化与行为变化的区别及实际影响，并取得确认。
5. 本节的新建默认方案不构成批量重构已有代码、修改资源或项目设置、安装工具或包、改变业务限制的授权。已确认任务所需的合理实现可以在授权范围内采用，不要求对每一项普通局部性能写法重复请示。

## 性能目标及瓶颈分类

| 性能维度 | 主要关注内容 |
|---|---|
| CPU | 脚本、算法、物理、动画、UI 重建、主线程及渲染线程等 |
| GPU | Shader、Overdraw、渲染批次、后处理、分辨率及带宽等 |
| 托管内存 | C# 对象、集合、字符串、临时分配及 GC |
| 原生及图形资源 | Unity 对象、Texture、Mesh、Material、RenderTexture、Native 容器及图形缓冲区等 |
| 加载及 I/O | 文件、配置、资源、网络、解压、反序列化及初始化等 |
| 帧时间稳定性 | 集中计算、加载峰值、GC、同步等待及长帧等 |

1. **性能目标根据实际项目确定。** 目标帧率、内存预算、加载时长及同时运行对象数量，应依据用户要求、目标平台、设备、画质、场景及玩法规模确定，不在通用规范中规定所有项目统一的帧率、内存上限或对象数量限制。
2. 帧率对应理论帧时间预算，例如 30 FPS 约为 33.33 ms、60 FPS 约为 16.67 ms、120 FPS 约为 8.33 ms；不能将 CPU 和 GPU 耗时简单相加推定实际帧时间。性能分析应区分平均表现、瞬时长帧及稳定性，不以单一 FPS 数值替代全部判断。
3. GC Alloc 表示相应采样范围内的托管分配，不等同于当前内存占用、内存泄漏或 GC 实际耗时；托管、原生、图形资源及平台内存指标应按各自统计口径理解。内存没有立即下降也不自动证明资源泄漏。
4. 优先识别实际高频路径、调用数量、数据规模、资源峰值及瓶颈类型，避免将所有问题归因于 GC、Update 数量、Draw Call 或某种 C# 写法。静态发现的风险与通过运行数据确认的瓶颈应分别表达。

## GC 与托管内存分配

1. **高频路径优先采用合理的低分配实现。** Update、FixedUpdate、LateUpdate、大量对象 Tick、战斗计算、高频查询和事件分发等稳定运行路径，应尽可能避免无必要的重复托管分配，以接近 0 B 的额外托管分配作为关键热点的优化目标，而非对所有方法及整款游戏强制零分配。
2. 项目启动、场景初始化、必要资源加载、低频业务请求、必要数据快照及编辑器工具，可以按职责、正确性和实际内存峰值采用合理分配，不为了形式上的零分配牺牲数据所有权、可读性、错误处理或业务结果完整性。
3. 根据当前 Unity 版本、脚本后端、实际类型和 API 评估高频分配来源，包括反复创建数组及集合、LINQ 中间结果、捕获变量的闭包、装箱、字符串拼接、ToList / ToArray、返回新数组的 API、重复创建短生命周期对象、集合扩容及异步状态相关分配。不得仅凭语法形式断言必然分配或没有分配。
4. 不全面禁止 `new`、LINQ、Lambda、`foreach`、委托或引用类型。普通泛型集合遍历并不必然产生托管分配；已有低频稳定代码不为形式批量改写。关键热点应选择经实际契约确认的低分配方式。
5. 可以复用稳定的职责实例、已装配的组件引用、符合有效期的配置及已有工作缓冲区；不得因此引入无所有权的全局可变对象或将独立业务状态合并。高频字符串及 UI 文本更新应减少无意义的格式化与赋值，但保留业务所需的精度、显示和诊断信息。
6. 普通托管对象由 GC 管理；应及时解除不再需要的长生命周期引用、订阅、缓存及任务关联。不得认为 `null` 赋值、对象池归还、集合 Clear 或触发 GC 必然立即降低实际进程内存。
7. 不默认手动调用 `GC.Collect()`、禁用 GC、修改增量 GC 设置或建立定时内存清理机制。确需在明确运行阶段进行特殊处理时，应结合目标平台、实测情况、停顿及内存风险提出方案并取得确认。

## 数据结构及临时集合复用

1. **数据结构与算法选择以实际访问模式、规模及语义为依据。** 应考虑查询、遍历、插入删除、排序、身份、空间范围、更新成本和内存占用；不机械将所有 List 替换为 Dictionary 或为每次查询建立索引。 主动识别成熟算法、数据结构及候选技术方案的设计和评估要求遵循[技术实现方案设计与评估规范](../Design/TechnicalDesign.md)，不改变本节实际运行成本、数据语义及验证权限约束。
2. 已明确存在大规模空间查询或高频批量计算时，可提前规划空间网格、其他空间索引或合适的算法实现。索引应与真实数据来源及更新时机一致，不能因候选过滤而遗漏原契约要求的对象，或擅自改变选择顺序、随机分布和计算结果。
3. 临时 List、数组、缓冲区及其他工作数据，在所有权、生命周期和并发契约允许时，可以复用已分配的容量，避免无必要的反复分配和扩容。初始容量及容量增长策略按实际需求确定，不凭空设置业务上限或默认无限扩张。
4. **复用前必须确认原使用者已经结束访问。** 不能清空、覆盖、归还或释放仍被异步任务、事件监听者、重入流程、Job 或其他调用方使用的数据。并行执行和同一线程上的重入均须保持各执行数据有效；不把可变静态集合当作所有调用的共享工作缓冲区。
5. `Clear()` 表示按容器契约清理元素或逻辑内容，并不等同于释放所有底层容量。大型临时集合长期保留过大容量时，应根据实际生命周期和已确认的回收方案处理，不默认每次调用 TrimExcess 或重新创建集合。
6. 低分配查询可使用明确只读视图、调用方提供的输出集合、独立工作缓冲区或其他适用接口。应保持数据所有权、完整性、借用范围及 Snapshot 的稳定语义，不通过性能优化泄漏可任意修改的权威数据。固定容量输出不足时，必须按真实契约保留完整结果或明确反映实际情况，不静默丢弃必要数据。
7. `class`、`struct`、`readonly struct`、`in`、`ref` 及其他传递形式，根据数据大小、复制成本、身份、可变性、装箱、序列化和调用契约选择。不得机械把所有 Config、Request、Result、Event 或 RuntimeData 改为结构体，也不得仅为避免复制而开放不应公开的修改权限。

| 数据结构 | 适用语义参考 |
|---|---|
| Array | 固定长度、连续索引或明确缓冲区 |
| List | 有序动态集合、顺序访问 |
| Dictionary | 按明确 Key 查询或映射 |
| HashSet | 成员判断及集合语义确实要求的去重 |
| Queue / Stack | 已明确的先进先出或后进先出处理语义 |
| 空间索引 | 大量空间对象的候选查询及明确索引维护 |
| Native 容器 | 符合 Native 内存、任务调度及平台契约的计算数据 |

上述仅为选型参考，不构成增加业务去重、排序、队列、对象上限或其他机制的授权。

## 性能优化与架构职责边界

1. **类型数量、文件数量和调用层级不直接等于运行时分配数量。** 应分别判断职责类型、实例创建频率、数据复制、算法复杂度及实际运行成本，不将细粒度架构本身判定为性能问题。
2. 不得仅以减少函数调用、类型数量、接口数量或潜在 GC 为由，擅自合并、删除或绕过已经建立的 System、Processor、Logic、Resolver、Calculator、Formula、Committer、Provider 等稳定职责边界。
3. 对具有稳定职责的普通 C# 类型，可由实际所有者在适当生命周期创建并复用，避免每次处理重复实例化；基础处理实现层继续优先采用其既有静态方案，并遵守显式输入、纯处理及无隐式共享可变状态约束。不得以减少实例数量为由将下属类型全部设为全局单例或可变静态类型。
4. 性能优化优先定位实际问题所在的职责：例如算法问题调整 Algorithm，公式问题调整 Formula，查询问题调整 Provider 或索引实现，执行频率问题调整合法调度所有者，资源问题调整相应资源所有者。不得以优化为由改变 System 的业务组织职责、Committer 的状态提交边界、权威状态所有权或 Manager 与 System 的单向依赖。
5. 确有证据表明现有数据传递、分层实现或执行路径存在无法在原边界内合理解决的开销时，应说明实际热点、候选方案、架构和行为影响，取得用户确认后再调整公开或内部稳定契约。不得以未经测量的性能收益作为擅自重构依据。

## Update、FixedUpdate 与执行频率

1. **执行方式由实际时间域和职责决定。** 连续移动、瞄准、动画、摄像机等持续性功能可以正常使用 Unity 生命周期；只在状态变化时需要执行的业务或表现，优先考虑明确方法调用或符合事件规范的事实响应；周期性业务按实际确认的时间间隔及执行契约组织。
2. 不新增没有实际执行内容的 Update 等生命周期方法，不在高频回调中无依据地重复查询、初始化、加载、扫描场景、装配引用或刷新不变的表现。不得以缓存为由增加未经授权的自动绑定或自动查找；已明确绑定的引用可以按所有权和有效期复用。
3. Update、FixedUpdate、LateUpdate、物理 Tick、网络 Tick 及项目自定义阶段具有不同语义，具体选择服从实际状态的时间域及已有运动、输入、动画和网络契约。不能因优化而擅自将物理逻辑改为渲染帧逻辑，或将所有普通业务改为固定 Tick。
4. **不全面推行事件驱动或集中更新。** 状态变化型 UI 可在初始化时获取当前状态，再按既有契约响应变化；持续逻辑仍可使用原生生命周期。不得为减少 Update 数量机械改为 UniTask 循环、协程、全局事件或定时轮询。
5. 大量对象的每帧回调存在明确调度需求时，可以规划或引入集中更新机制；UpdateManager 不作为所有新项目的默认基础架构。新建 UpdateManager 按 Manager 约定采用项目运行级 Unity 组件单例，负责自身管理范围内的更新注册、调度及生命周期协调，不承担领域规则、业务状态提交或通用业务请求调度职责。
6. 集中调度须明确更新阶段、时间步、注册与注销、遍历期间增删、对象失效、重入、异常及必要执行顺序。通过合法装配入口建立调度关系，System 不得反向查找或调用 UpdateManager，也不得通过回调、中转接口变相访问 Manager；上层按明确契约调用被调度能力，不改变其业务归属。
7. 降低更新频率、错帧执行、时间切片、预算调度、距离裁剪、暂停不可见对象或改变执行顺序，须具备实际业务及技术依据。不得为降低开销擅自跳过必要业务步骤、丢弃输入、改变物理或网络时间语义、降低 AI 响应或改变表现；涉及这些变化及全局设置的方案必须先取得确认。

| 执行场景 | 默认选择 |
|---|---|
| 持续渲染帧处理 | Update 或现有动态阶段 |
| 物理运动及模拟 | FixedUpdate 或现有物理 Tick |
| 依赖最终姿态的表现及相机 | LateUpdate 或现有表现阶段 |
| 状态变化响应 | 明确调用、局部事件或合法全局事实事件 |
| 周期业务 | 已确认的周期及时间域 |
| 大量对象集中更新 | 按实际需求设计，不机械建立 UpdateManager |

## 缓存管理及数据有效期

1. **缓存必须具有明确来源、所有者、有效期及清理责任。** 缓存用于减少符合契约的重复查询、计算或加载，不作为独立权威业务状态。应明确失效条件、更新及重新获取方式、内存规模和适用范围，按实际需求引入，不默认建立通用 CacheManager。
2. 合法组件引用及稳定配置引用可以在有效期内复用。数据发生变化、账号或场景切换、对象归还、资源重新加载或配置生效范围变化时，缓存必须按实际契约失效、更新或清理，不将历史数据误当作当前权威状态。
3. 业务查询缓存由所属 System 或符合契约的 Provider 等职责所有者组织，配置缓存由实际配置框架或使用方按契约维护，资源缓存由合法资源所有者按实际资源框架管理。纯处理层的中间计算及工作数据保持执行范围隔离，不通过可变静态集合建立隐式全局计算缓存。
4. **缓存空间及时间成本分别评估。** 长期存在的缓存应有明确生命周期及避免无意无限增长的策略；不默认给所有缓存增加 TTL、LRU、统一容量、定时清理或自动驱逐。确需新增策略时，明确过期语义、资源释放、缓存未命中及对业务行为的影响，并遵守授权规范。
5. 资源缓存应维持对应资源及加载句柄的合法所有权；删除字典条目不等于已正确释放底层资源，缓存失效也不自动取得销毁共享资产的权限。异步缓存加载结果、共享执行及失败处理遵循资源契约、配置规范和异步一致性规范。
6. 不得通过缓存减少必要的实时状态校验、改变查询语义、返回未经确认的旧值、重复持有权威配置或跳过既有业务处理。涉及公开查询由实时改为历史缓存、自动预取、自动合并或其他可观察行为变化时，须按实际调用契约报备并确认。

| 缓存内容 | 职责归属参考 |
|---|---|
| 已绑定组件引用 | 所属对象或组件 |
| 有效配置及引用 | ConfigSystem、合法 Provider 或明确使用方 |
| 业务查询及索引 | 所属 System 或合法 Provider |
| 临时工作数据 | 独立执行实例或合法缓冲区所有者 |
| 资源及加载结果 | 实际资源框架或明确资源所有者 |
| UI 条目及表现数据 | 所属 Controller 或表现职责类型 |
| 网络数据 | 所属业务或明确技术能力 |

## UI、渲染及物理性能

1. UI 显示优先根据真实状态变化及既有表现契约更新，避免不必要的重复赋值、布局重建及列表重建。大量列表条目可考虑复用、虚拟化或局部更新，但须保持实际排序、选择、滚动、绑定和交互契约，不擅自修改 Canvas 分组、层级、页面结构、显示规则及控件可用性。
2. 区分共享材质、共享 Mesh 与运行时独立实例。访问 Renderer.material、MeshFilter.mesh 等可能导致实例化的 API 时，应明确实际创建、缓存引用和释放责任；不得为降低分配机械替换成 sharedMaterial、sharedMesh 等共享访问，导致本应独立的修改影响所有使用方。
3. 根据实际渲染管线、平台及表现要求评估渲染批处理、GPU Instancing、SRP Batcher、MaterialPropertyBlock、图集、Overdraw、Shader、后处理、Texture、Mesh 和 RenderTexture 等成本。不同技术的兼容性和性能收益须按实际项目判断，不以单一指标或某种 API 宣称必然优化。
4. 动画、粒子及特效应按实际生命周期组织播放、停止、重复使用和清理，避免无依据的重复触发及无效更新。不得为降低开销改变动画时序、粒子数量、可见性、特效持续时间或其他既有表现；独立表现优化仍遵守 UI、资源及变更授权规范。
5. 高频物理查询可按实际碰撞契约选用合理 LayerMask、适用的低分配 API 或工作缓冲区。必须保持目标集合、过滤条件、触发器及碰撞语义；固定容量 NonAlloc 等查询结果可能不完整时，应按实际契约处理容量不足，不静默遗漏应命中的对象或擅自缩小查询范围。
6. 不得未经确认修改目标帧率、VSync、画质、分辨率、纹理及网格资源精度、渲染管线、物理时间步、碰撞层、Animator 更新模式、相机更新方式或其他公共项目设置。不得自动降低画质、调整玩法、减少敌人或粒子数量、降低 AI 更新频率或新增交互限制；实际需要这些取舍时，应先说明视觉、操作、业务及平台影响并取得用户确认。

| 领域 | 优先关注的技术风险 |
|---|---|
| UI | 不必要的重复刷新、布局及 Canvas 重建、列表实例创建 |
| Material / Mesh | 无意实例化、共享资产误修改、自有实例未清理 |
| 图形资源 | RenderTexture、Texture、Buffer 的所有权及有效期 |
| 动画和特效 | 重复触发、无意持续执行、池回收状态残留 |
| 物理查询 | 高频分配、过滤正确性、缓冲区结果完整性 |
| 渲染 | 结合实际渲染管线判断批处理、Overdraw、Shader 及带宽成本 |

## Jobs、Burst、ECS 与多线程

1. **异步等待与计算并行分别确定。** UniTask、Task、协程及回调不自动加速 CPU 密集计算；耗时算法应依据实际计算规模、平台及调度要求选择普通同步实现、分帧处理、Job System、Burst 或其他已有方案。
2. Jobs、Burst、Native Collections、ECS / DOTS 及其他多线程技术不作为所有新项目的默认基础架构。确有明确性能、计算规模或架构需求时，可以提前规划相应实现，检查当前 Unity 及包版本、平台、编译设置、数据布局、现有框架和实际收益风险，经确认后引入；不得擅自安装包或迁移至 ECS。
3. Unity 对象访问须遵守具体 API 的线程安全、主线程及执行阶段约束，不将所有 Unity API 假定为可在后台线程使用。WebGL 等平台继续遵守既有 UniTask 及目标平台约束，不借 Job、Task 或线程池绕开其实际平台限制。
4. NativeArray、其他 Native 容器及图形或计算缓冲区应明确分配器、内存所有权、数据有效范围、读写关系、任务依赖和清理责任，遵守实际包版本的分配器生命周期要求。容器结构体或句柄的复制不自动产生新的独立内存所有权，不以某个副本的状态推定全部别名都安全有效。
5. Job 尚在使用数据时不得提前访问不允许的读写区域、覆盖、归还或释放依赖内存。按明确 JobHandle 依赖和对应 Dispose 契约安排完成及清理；必要完成等待应考虑主线程阻塞及执行阶段，不能仅凭发起 Job 就宣称已经完成或获得性能收益。
6. 已有纯业务处理及基础处理实现边界应优先保留；合法上层负责任务调度、结果有效性及提交，独立算法或适用计算实现负责显式数据处理。可以在稳定计算契约下提供普通 C# 或经确认的 Jobs / Burst 等实现，不将网络、场景、全局配置查询或权威状态提交下沉到纯计算层。
7. 不为 Burst、并行化或数据布局调整擅自改变浮点精度、随机来源、选择顺序、数值结果、确定性、网络同步或录像回放契约。涉及计算结果、公开数据、执行模型及项目设置变化时，必须说明风险和替代方案，经用户确认后实施。

## 事件及异步执行性能

1. 高频事件应关注参数对象、监听委托、闭包、装箱、快照及诊断产生的实际分配，按已有事件机制和数据有效期选择适当实现，不机械将所有事件改成 struct 或对象池事件参数。
2. EventSystem 的监听者快照是分发语义，不强制每次创建新数组；低分配分发应继续满足现有订阅变化、重入、异常处理、监听生命周期及通知范围契约。不为减少分配擅自改为队列、批量合并、去重、异步分发或修改事件发布时机。
3. 长生命周期事件订阅、任务闭包及回调可能持有场景对象、业务数据和资源，应按实际所有权清理失效关系，避免无意累积或使已结束业务继续被引用；不改变合法的长期订阅语义，不因停用组件机械取消所有关联业务。
4. 池化事件参数、Request、Result、缓冲区及异步任务数据必须明确借用、转移和归还时机。事件分发返回不代表异步监听已经结束；需要跨越有效期使用数据时，应在有效期内取得符合实际契约的独立数据，或由合法所有者维持其有效性。不得将已归还的数据继续作为稳定结果或事实交付。
5. 高频异步调用应关注任务、闭包、令牌及临时数据开销，同时保留实际执行所有权、取消、异常、结果交付及 UniTask 多次等待等既有契约。不得仅为减少分配而删除必要令牌、忽略异常、重复等待不支持复用的任务或引入未经确认的共享执行机制。
6. 异步资源加载、对象租用及临时缓冲区复用，应确保正常完成、失败、取消、异常及过期结果的资源清理，不能把调用方停止等待等同于实际执行结束，也不能提前释放其他执行者仍需使用的资源。
7. 高频诊断及日志应避免无意义的重复记录、字符串构造和无界历史保存，保持既有必要诊断、失败返回及责任归属。不得以性能为由吞掉错误、擅自关闭必要日志、降低实际错误严重程度或新增静默丢弃规则。日志及异常的具体职责仍按专门规范处理。

## 性能分析及验证权限

1. **区分静态性能风险与实测性能瓶颈。** Agent 可以在授权范围内静态审查代码、数据结构、调用频率、分配路径、资源所有权及清理路径，分析用户提供的 Profiler 数据、内存快照、渲染记录及目标设备信息。未有足够运行数据时，应标明静态推断及待验证条件，不将风险描述为已实测瓶颈。
2. 实际性能目标及测量条件应根据项目明确，尽可能在同一场景、设备、平台、构建方式、画质、负载及采样条件下比较前后变化。Unity Editor、Development Build、Profiler 开销及实际发布环境可能不同，应结合目标设备结果判断，不能由单次 Editor 测量直接保证发布性能。
3. 用户可按实际问题选用 Unity Profiler、Memory Profiler、Frame Debugger、Profile Analyzer、Addressables 对应版本的诊断工具或平台性能工具。Agent 应提供需要用户采集的相关指标和操作场景，不默认安装分析包、加入运行监控、ProfilerMarker 或其他诊断框架；确有新增诊断需求时按变更授权处理。
4. **继续遵守禁止 Agent 主动编译及运行验证的规则。** Agent 不得自行编译、执行编译错误检查、启动 Play Mode、运行项目或进行性能测试、采集运行 Profiler 数据及内存快照。实际编译、运行和性能验证由用户手动完成；Agent 可以提供具体操作建议及分析用户提供的结果。
5. 不得虚构测试结果、性能提升比例、GC Alloc、FPS、内存释放量或其他测量结论。应区分方案预期收益、静态可确认事项、实际测量证据和仍需用户验证的风险，不能以完成代码修改代替性能验收。
6. 性能优化按明确问题、识别证据及影响、提出方案、用户确认、在授权范围内实施、用户手动验证的流程组织。发现额外瓶颈或其他缺陷时先报告，不擅自扩大任务范围；后续调整仍遵守[AI 修改与交付规范](../Governance/AgentWorkflow.md)中的授权及实施流程，并按[规则优先级与冲突处理规范](../Governance/RulePriority.md)处理适用规则及冲突。

| 工具 | 主要用途 |
|---|---|
| Unity Profiler | CPU、GPU、帧时间、托管分配及执行热点等 |
| Memory Profiler | 内存快照、对象引用、资源占用及前后差异 |
| Frame Debugger | 实际渲染事件及批次等 |
| Profile Analyzer | 多帧统计及采样数据对比 |
| Addressables 诊断工具 | 按实际包版本观察资源加载、依赖及引用情况 |
| 平台性能工具 | 目标设备 CPU、GPU、内存及平台指标 |

## Agent 开发前检查与默认设计方案

1. 新增或修改涉及高频处理、对象池、资源及性能相关代码前，应按实际任务范围识别：
   - 项目现有性能目标、目标平台、Unity 及相关包版本、实际执行规模与时间域。
   - 现有 PoolManager、PoolSystem、AssetManager、AssetSystem、资源加载框架、更新机制及数据结构，是否已经存在可复用的稳定能力。
   - 涉及 Resources 时，检查明确资源路径、资产类型及构建包含范围，区分固定绑定、正常主动加载和未经授权的引用兜底，以及实际加载与释放契约。
   - 关键高频路径的分配、重复计算、查询和资源峰值风险，以及实际性能瓶颈证据与静态推断的区别。
   - 资源创建、加载、所有权、借用、有效期及对应释放操作，池实例与每次租用的生命周期、容量及清理契约。
   - 缓存、临时集合、事件参数、异步任务及 Job 数据的有效范围、并发使用和释放责任。
   - 优化是否影响业务顺序、结果、状态提交、随机语义、表现、交互、配置、公共接口、资源及项目设置。
2. 方案应在任务相关范围内说明实际采用的优化方式、职责归属、资源所有权、预期收益及代价，明确静态可确认事项和需要用户验证的运行条件。新项目默认规划 PoolManager 及 AssetManager + AssetSystem；已有项目优先复用。涉及公共基础能力、已有契约、技术迁移、额外限制、运行调度或表现变化时，先报告方案与影响并取得确认，不要求已确认内容重复请示。
3. 交付时应说明实际修改的热点路径、资源取得与释放、池化及缓存机制、调用及生命周期变化、新增约束的授权依据，并列出需用户手动绑定、配置及性能验证的事项。涉及资源管理时，按实际任务提示验证重复创建或租用、归还、场景切换、共享资源、异常及取消、内存峰值和回收情况；涉及高频执行时提示对比帧时间及 GC Alloc 等相关数据。未测量的指标不得宣称已优化成功，不得主动编译、检查编译错误或运行验证。

默认设计参考：

| 设计维度 | 默认推荐或约束 |
|---|---|
| 性能目标 | 由具体项目、平台及实际需求确定，不统一规定 FPS 或内存上限 |
| 高频路径 | 尽量减少不必要分配，关键热点以接近 0 B 额外托管分配为目标 |
| 普通低频操作 | 保持职责及正确性，允许必要分配 |
| LINQ / Lambda / foreach / new | 按实际类型、频率及开销判断，不全面禁止 |
| 临时集合及工作数据 | 所有权允许时复用，防止重入、并发及释放后访问 |
| 数据结构及算法 | 按访问模式、运行规模及语义选择 |
| 细粒度架构 | 保持已建立的职责边界，不以潜在性能问题擅自合并 |
| Unity 生命周期 | 持续功能正常使用，按实际时间域执行 |
| UpdateManager | 存在集中调度需求时引入，不作为默认基础架构 |
| 对象池 | 高频重复创建对象优先考虑，不机械池化所有对象 |
| PoolManager | 新项目默认基础架构，项目运行级可挂载 Unity 组件单例 |
| PoolSystem | 按独立共享复用框架需求引入，不强制配套 |
| 对象池容量及预热 | 按实际需求和已确认契约决定，不擅自增加玩法限制 |
| 对象生命周期 | 区分实例与每次租用，按实际职责清理及重置 |
| AssetManager + AssetSystem | 新项目默认基础架构，纳入架构先行 |
| AssetManager | 可挂载项目运行级 Unity 组件单例，资源管理、来源装配及观察 |
| AssetSystem | 不可挂载项目运行级普通 C# 单例，统一资源访问及释放契约 |
| 公共动态加载资源 | 默认通过 AssetSystem 或合法访问边界取得 |
| 局部引用及已绑定资产 | 按所属对象及装配契约维护，不机械集中加载 |
| 资源技术选型 | 优先沿用已有框架，不强制 Addressables 或迁移 |
| Resources | 合法本地资源加载方式，默认经 AssetSystem 或合法底层实现；按实际需求选择同步或异步加载 |
| 本地配置资产 | SO、二进制及 JSON 默认归入 Assets/Resources/Configs/ 对应目录，已有及用户指定契约优先 |
| 固定引用及主动加载 | 固定依赖优先显式绑定；明确路径正常加载允许，未经授权的缺失引用兜底禁止 |
| 资源所有权 | 明确创建、借用、使用及释放责任，按实际 API 清理 |
| Manager 与 System | Manager 可以使用合法框架能力，System 不反向依赖 Manager |
| Config / Asset / Pool | 分别组织配置、资源及实例复用，不重复职责或形成循环依赖 |
| 缓存 | 按实际职责、所有权及有效期组织，不默认建立 CacheManager |
| 全局内存清理 | 不机械建立 MemoryManager 或定时 GC.Collect / UnloadUnusedAssets |
| UI、渲染、物理及画质 | 保留实际业务及表现契约，影响行为及全局设置须确认 |
| Jobs / Burst / ECS | 按实际架构、计算及平台需求引入 |
| 事件与异步 | 保留分发、完成、取消、数据有效期及清理契约 |
| 已有项目 | 优先复用稳定机制，实际缺陷按授权流程处理 |
| 性能验证 | Agent 静态分析及方案实施，用户手动运行及采集数据 |

上述默认方案不构成擅自新增机制、迁移已有资源框架、改动业务或表现、改变项目设置或运行验证的授权。架构先行允许提前确定稳定职责边界，性能优化应针对真实执行、内存和资源问题，始终保持此前确定的职责、访问权限、配置、状态提交、异步一致性及单向依赖约束。
