# 日志与异常处理规范

## 规范定位与适用范围

定义业务失败、运行错误、异常传播、诊断责任及 LogSystem。

本规范是对应专业事项的规则主定义文档。规则适用范围、约束性质、优先关系及例外统一遵循 [规则优先级与冲突处理规范](../Governance/RulePriority.md)；项目修改、读取、实施及交付遵循 [AI 修改与交付规范](../Governance/AgentWorkflow.md)。

本节在既有职责分层、Manager 与 System 单向依赖、纯处理、状态提交、事件协作、异步一致性及资源所有权约定的基础上，明确失败结果、异常传播、诊断责任和统一日志机制。问题发现、结果表达、异常处理及日志记录是不同职责，不要求由同一个类型承担。新项目默认建立 LogSystem 的稳定框架边界；已有项目优先复用实际适用的日志机制。

## 适用范围与已有实现保护

1. **统一诊断职责，不强制统一已有技术实现。** 本节的职责、依赖及真实结果约束适用于新增设计与业务开发；默认日志框架、接口及格式方案用于新建代码及经用户确认的相关重构。不得仅为统一形式主动批量修改现有代码。 已有技术差异、真实职责冲突及新旧规则的适用关系遵循[规则优先级与冲突处理规范](../Governance/RulePriority.md)。
2. 新增或修改日志、异常处理前，应识别项目已有日志入口、严重程度、输出格式、异常传播、过滤、生命周期及底层输出契约。已有适用的日志框架、Unity Debug 使用约定或第三方机制时，优先沿用，不擅自新增平行框架、替换全部 Debug 调用或调整公共接口。
3. 发现真实的诊断缺失、异常吞没、重复记录、错误等级、依赖冲突或不合理失败恢复时，应说明具体发生条件、影响范围及候选方案，取得用户确认后处理。诊断需求不构成改变已有业务行为、事件传播、取消契约、UI、校验限制或资源释放策略的授权。
4. 新增及修改公共日志能力、全局异常入口、输出过滤、日志保存或上报机制时，继续遵守公共基础模块报备及确认规则。已确认的局部实现无需重复请示；不得扩大授权范围。

## 正常结果、业务失败、运行错误与程序异常

| 运行情况 | 核心语义 | 默认处理 |
|---|---|---|
| 正常成功 | 实际达到对应操作的成功条件 | 正常返回；按实际诊断需要输出普通日志 |
| 正常业务失败 | 已确认的业务条件不满足或合法业务拒绝 | TryXxx、明确 Result 或状态返回；默认不输出错误日志 |
| 运行错误 | 真实技术故障、必要配置或依赖缺失等影响操作执行的问题 | 明确失败或实际结果，按严重程度记录必要诊断 |
| 程序异常 | 程序契约被破坏、内部不变量失效或运行时抛出的意外异常 | 由明确异常边界捕获、转换或传播，保留必要诊断及实际执行事实 |

1. **业务失败不等于程序错误。** 金币不足、背包已满、技能冷却、规则条件不满足、合法空值、查询无匹配对象等按业务契约返回结果，不将这些普通分支机械判定为 Error 或 Exception。确有诊断需要时，可按实际语义输出适当等级的日志，不为正常业务失败默认增加日志或异常。
2. 必需引用缺失、必要配置无法取得、资源加载失败、实际存储或通信故障等，应按真实运行影响表达结果并记录必要错误或警告。可选数据不存在、合法未就绪状态或既有默认值不自动构成错误。
3. **异常是执行机制，不是业务失败状态。** 第三方 API、C# 运行时、Unity API 或异步框架抛出的异常，可能对应可预期技术失败、正常取消或程序缺陷，应按真实原因及执行契约判断，不能只凭异常类型统一确定业务结果或日志等级。
4. 已经成立的业务事实、等待失败、实际执行失败、部分完成、取消和结果尚未确认应分别表达，具体遵循[异步业务与状态一致性规范](StateConsistency.md)。日志输出及异常捕获均不能代替真实结果交付。
5. 不得以增加日志、完善错误处理或增强健壮性为由新增没有依据的校验、拒绝条件、默认值、自动恢复或其他业务行为。继续遵守[校验与附加限制授权规范](../Governance/ValidationAuthorization.md)及[UI 与交互变更授权规范](../Governance/UIChangeAuthorization.md)。

例如，玩家金币不足时，返回所属购买业务的明确失败原因即可；商品所依赖的必需价格配置无法加载时，则应按实际配置契约返回失败并记录必要诊断。示例不规定购买规则、结果类型或额外业务限制。

## 各职责类型的日志权限

下表为缺少项目专用约定时的默认诊断归属。允许记录日志不代表该类型必须为每次调用、每个成功分支或每个失败结果输出日志，也不赋予额外业务执行、状态修改及全局访问权限。

| 职责类型 | 默认日志权限 | 诊断职责 |
|---|---|---|
| Manager | 允许 | 自身管理流程、实际运行状态及管理错误 |
| 业务 System | 允许 | 所属业务用例、系统运行错误及未由下层负责的最终诊断 |
| 框架 System | 允许 | 自身框架契约、技术执行及运行错误 |
| Controller / Presenter / View | 按自身职责允许 | 场景协调、交互及显示执行错误，不重复记录业务内部失败 |
| Module / 具有执行职责的对象 | 允许 | 本对象或能力的引用、局部行为、生命周期及执行错误 |
| Initializer | 允许 | 实际装配、依赖及初始化错误 |
| Factory | 允许 | 对象创建及初始化错误 |
| Processor | 允许 | 工作单元处理及执行生命周期错误 |
| Committer | 允许 | 实际提交范围内的状态写入、持久化及其他提交错误 |
| Provider | 有限允许 | 实际数据访问技术错误，普通未找到返回明确结果 |
| Registry | 有限允许 | 注册机制及内部状态错误，普通注册反馈按实际契约返回 |
| DataStorage | 允许 | 持久化读写、格式转换及存储技术错误 |
| Service / Adapter | 允许 | 底层技术操作、外部接口及适配错误 |
| Logic / Resolver | 默认不主动输出 | 返回纯处理或解析结果及必要诊断数据 |
| Rule / Rules / RuleSet | 默认不主动输出 | 返回规则判断结果 |
| Calculator / Evaluator | 默认不主动输出 | 返回计算及评估结果 |
| Matcher / Selector / Mapper / Normalizer | 默认不主动输出 | 返回匹配、选择、映射或规范化结果 |
| Operation / Formula / Algorithm | 默认不主动输出 | 返回基础处理结果及必要诊断数据 |
| Config / RuntimeData / Snapshot / Result 等数据承载类型 | 默认不主动输出 | 表达配置、状态、数据及结果，必要检查按原有契约返回 |
| Utility | 按具体技术职责确定 | 不借通用技术能力绕过调用方的纯处理约束 |

1. **纯处理层在正常运行过程中默认不得主动输出日志。** Logic、Resolver、具体职责能力及基础处理实现层应通过显式输入、输出及明确失败结果提供诊断所需信息，不直接或间接调用 Unity Debug、LogSystem、其他日志入口、全局诊断机制或具有日志副作用的回调。不因日志不修改权威业务状态而将其视为纯处理。
2. 纯处理层发现业务条件不成立、输入无法按实际契约处理或其他可预期失败时，按其既有返回契约提供结果，由合法上层负责判断实际运行影响和是否记录日志。不得因此为每个公式、规则或简单查询强制增加 Result 包装、异常字段或诊断类型。
3. 特殊算法调试及必要的专项诊断，可以按照用户明确要求或经确认的具体方案建立，明确适用范围、启用条件、输出成本及清理方式，尽量通过显式诊断数据和外部观察实现；确需在纯处理实现内部输出时，仅作为明确授权的特殊诊断例外，不改变正式纯处理职责及依赖约束，不默认保留为正常运行机制。 专项诊断的具体授权、范围、结束条件及其他保留约束应明确，遵循[规则优先级与冲突处理规范](../Governance/RulePriority.md)；不得将该专门许可推定为其他纯处理职责的例外。
4. 数据承载及状态对象默认不承担独立日志管理。具有明确执行职责的业务对象、Unity 对象或受控更新能力，仍按实际职责及必要运行契约处理诊断，不将所有对象机械视为纯数据类型。
5. 各非纯处理类型只能诊断自身实际职责及掌握的事实。Provider、Registry、DataStorage、Service、Adapter 等不得自行决定上层业务是否成功、是否恢复或如何继续执行；LogSystem 也不接管这些决定。所有日志权限仍受既有依赖方向、访问权限和实际线程约束。

## 失败结果与诊断信息传递

1. **可预期失败必须具有明确返回契约。** 使用 TryXxx、明确 Result 或状态返回，让调用方能够判断对应操作实际结果。已有简单 bool、枚举、查询或其他明确契约能够准确表达结果时，可以继续沿用；不为统一日志引入全局 Result 基类或强制改造全部返回签名。
2. Result 优先表达所属业务语义。程序需要据以分支处理的失败原因，使用稳定枚举、状态或其他明确契约表达，不依赖解析日志正文或异常 Message 判断业务条件。简单规则返回 bool 等已有方式仍然有效。
3. 诊断数据按实际需要传递，可以包括失败原因、相关对象或配置标识、操作阶段、实际提交状态、技术错误信息及必要的原始异常。公开结果不机械暴露内部异常对象、调用堆栈、敏感数据或无关技术实现，原始技术诊断应限制在合法处理和记录边界。
4. 下层按自身职责返回真实结果，上层按职责组织或转换结果，转换时不得丢失调用方必须知道的失败语义、已完成步骤及尚未确认的事实。无需重复返回整套内部技术细节，也不要求所有层分别构造新的 Result。
5. Logic 的业务处理结果、Committer 的实际 CommitResult、Processor 的 RequestResult 及 System 的用例结果继续遵守各自约定。日志是否成功输出、是否过滤以及日志中使用的严重程度，不决定实际业务结果。

| 信息内容 | 用途 |
|---|---|
| 操作状态 | 表达实际成功、失败、取消、部分完成或其他真实状态 |
| 失败原因 | 供合法调用方判断后续处理，例如 InsufficientCapacity |
| 必要诊断信息 | 供开发人员定位真实运行问题 |
| 关联对象、配置或请求标识 | 在实际需要时关联相应操作及有效范围 |
| 提交事实 | 表达已经执行、未执行及尚未确认的实际效果 |
| 原始异常 | 在确有技术诊断需要的边界保留异常类型和堆栈 |

上述信息仅为选型参考，不强制每个 Result 都包含全部字段，不为日志引入没有实际语义的请求 ID、错误码体系或额外状态。

## 日志记录责任与重复诊断

1. **同一错误事实应具有一个明确的主要记录负责人。** 根据谁实际处理错误、能够确认其运行影响并具有足够诊断上下文确定记录边界，不统一规定所有错误都由最先发现问题的类型或最终业务 System 输出。
2. 底层只负责返回或转换错误且由上层统一记录时，应提供足够的错误原因及必要异常信息，不重复输出相同诊断。底层已经按明确契约完成主要记录时，上层继续处理真实结果，不沿调用链机械追加同一错误的重复日志。
3. 上层发现新的独立错误事实、实际业务影响或提交结果时，可以按真实诊断需求独立记录。例如底层记录文件写入失败后，提交层确认已经更新运行时状态但保存失败，可以记录具有独立意义的部分提交诊断。不得将同一异常简单更换类型前缀后层层输出。
4. 禁止把 throw 当作日志使用，也不得对同一个错误先重复记录日志再抛出异常。捕获后重新传播、日志记录及异常最终处理应由实际边界协调，避免遗漏必要诊断或重复打印相同堆栈。不强制引入全局去重、异常已记录标记、日志 ID 或调用栈分析机制。
5. **局部错误仅影响直接依赖范围。** 局部错误导致当前操作无法安全完成时，由实际诊断责任边界输出能定位业务对象、操作及失败原因的 Error 级别日志，并按既有契约停止直接受影响的操作；其他不依赖该错误且能够安全执行的独立流程继续运行。不得把无法安全继续的内部状态强行作为普通失败后继续执行，也不得无依据终止整个页面、场景或全局业务。
6. 必需 Inspector、Prefab、场景及配置表引用的运行时显式空值检查和错误记录仍为必要要求。缺失后不得主动寻找替代引用或抛出普通业务异常；可由发现问题的合法非纯处理边界直接记录，或按明确诊断契约由上层记录。不使用纯处理层的日志限制规避原有必要检查及错误诊断。

职责示例（不是固定捕获、转换或日志调用顺序）：

```text
InventorySystem
    → InventoryTransferCommitter
        → InventoryDataStorage
            → FileStorageService：执行实际文件写入
            ← 返回技术失败及必要诊断，或按技术契约传播异常
        ← 返回明确保存结果
    ← 返回实际提交结果（保留状态是否已经生效）
InventorySystem：按所属业务契约交付实际用例结果
```

上述示例中，文件写入异常可以由能够确认失败且具备必要上下文的存储或提交边界统一记录，其他层返回真实结果。若上层发现独立的部分提交问题，可以记录新的诊断；不要求每层分别捕获、记录和重新抛出相同异常。

## throw 的使用边界与异常传播

1. **严格限制主动创建并抛出异常。** throw 仅允许用于边界明确、封装完善的底层框架、基础设施层或插件适配层，并且只用于程序契约被破坏、内部不变量失效等无法作为正常运行结果处理的问题，以及必须遵循的明确底层技术异常契约。能够通过正常返回值表达的可预期失败不得主动抛出异常。
2. 业务 System、Manager、Processor、Committer、Logic、Resolver、具体职责能力、基础处理实现、Controller、Module、普通 MonoBehaviour 及其他普通游戏逻辑，不得使用主动 throw 表达配置缺失、引用缺失、业务条件不满足、用户输入无效、普通查询失败或其他可预期失败。不得借框架 System、Service、Adapter 或纯处理实现的技术名称扩大主动抛出异常的权限。
3. 底层确需主动抛出异常时，应使用能够准确表达实际技术问题的异常类型，并在稳定公开契约中说明触发条件、传播范围及实际处理责任。不得为普通参数或配置问题机械新增自定义异常类型、Assert 或额外运行限制；实际校验依据继续遵守原有授权规范。
4. **禁止主动抛出普通业务异常，不等于禁止异常传播。** C# 运行时、Unity API、第三方插件及异步框架可能在未编写主动 throw 的情况下产生异常。无需在每个方法内捕获；异常可以按正常调用链传播到具有真实处理职责的边界。
5. 已经发生的异常在当前层不能安全处理时，可以按实际契约继续传播；确需捕获后重新传播原异常时使用保留原堆栈的 `throw;` 或符合实际技术契约的等价方式，不使用 `throw ex;` 破坏原始堆栈。重新传播既有异常、遵循既有取消传播契约，与主动创建普通业务失败异常是不同情形，不因此放宽主动 throw 限制。
6. 底层允许传播的异常及无法在当前层处理的意外异常，由明确的上层所有者或框架终止边界处理，必要时转换为可如实表达执行情况的结果、保留异常传播或终止受影响执行范围。不得为了保证表面继续运行，将所有异常无条件转换为普通 Failed 或成功结果。

## try-catch、异常捕获及清理边界

| 职责类型 | 默认异常处理边界 |
|---|---|
| Manager | 自身管理流程及实际执行边界 |
| System | 所属业务用例或框架执行中具有处理责任的边界 |
| Processor | 单个工作单元的执行、结果交付及必要生命周期清理 |
| Committer | 自身实际提交、持久化协作及相关执行边界 |
| Initializer / Factory | 装配、创建及其拥有的临时资源清理边界 |
| DataStorage / Service / Adapter | 实际存储、文件、网络、序列化、第三方调用及已知技术异常转换边界 |
| Provider / Registry | 自身明确的数据访问或注册技术契约，不接管上层业务恢复 |
| EventSystem / 实际事件分发实现 | 按分发契约承担监听调用异常隔离和诊断 |
| Controller / Presenter / View / Module / 执行对象 | 自身交互、表现、局部生命周期及任务所有权边界 |
| Logic / Resolver / 具体职责能力 / 基础处理实现 | 默认不承担通用异常捕获；仅按明确纯处理契约处理可转换为纯结果的问题 |

1. **try-catch 必须具有明确处理目的。** 可以用于已知技术异常转换、独立执行隔离、真实结果交付、最终诊断、必要上下文保留或符合契约的继续传播。不要求每层、每个 public 方法或每个 Unity 生命周期方法机械包裹 try-catch。
2. 应尽量在能够准确识别和处理相应问题的范围捕获。能够明确识别异常类别时优先采用适当的具体异常类型；确有独立操作隔离或最终执行边界需要时，可以捕获较宽的异常范围，但必须按真实契约区分正常取消、已知故障和无法安全处理的程序错误。
3. **禁止吞掉异常及虚假成功。** 不得使用空 catch、只打印日志后返回成功、忽略未知提交情况或将无法继续的异常状态当作正常状态。只有具备明确技术契约、真实可忽略语义及必要结果处理时，才按该契约处理相应异常，不以通用 catch 掩盖程序问题。
4. 捕获异常后能否继续处理下一工作单元、其他监听者或其他独立操作，应以实际隔离范围、状态完整性和已有失败处理契约为依据。默认保护不受影响且能够安全继续的独立流程，不自动重启、跳过本应执行的业务、清空队列或修改全局运行状态。
5. **资源清理与异常记录分别归属。** 实际资源或执行所有者按既有契约使用 using、try/finally 或明确的生命周期清理方式，保证成功、失败、取消及异常路径上的必要释放。只有清理需求时不强制增加 catch；捕获异常也不代表拥有其他资源的释放权限，不得重复释放、掩盖原始异常或将清理完成等同于业务成功。具体遵循[性能与内存管理规范](Performance.md)、[对象池规范](ObjectPooling.md)、[资源管理规范](ResourceManagement.md)。
6. 不得通过日志、异常捕获、自动重试或未经确认的恢复掩盖需要修复的程序缺陷。调整已有异常传播、终止范围、结果转换或失败处理机制属于实际行为契约变更，应按原有授权规则处理。

## 状态提交、跨 System 与失败处理

1. **错误诊断不决定业务提交事实。** Logic 处理完成、实际权威状态更新、持久化完成、外部提交确认、事件分发及整个用例完成，按照实际契约分别表达，不因为某个步骤抛出异常或输出 Error 就否定已经成立的其他事实。
2. Committer 负责如实表达自身提交范围内实际完成、未执行、失败、取消及结果尚未确认的情况，记录或传递相应诊断。Processor 负责工作单元最终交付，System 负责用例及跨 System 结果组织。不得将诊断责任转移给 LogSystem 代替业务处理。
3. 远端通信超时、等待中断和未知提交结果，不得根据异常或错误日志直接推断权威方没有执行。部分提交、结果未知及必要一致性处理继续遵循[异步业务与状态一致性规范](StateConsistency.md)。
4. **日志与异常处理不构成业务恢复授权。** 不默认新增重试、回滚、补偿、重复提交、默认数据恢复、自动修复、状态重置、禁用 UI 或提示界面。需要改变已有失败处理及恢复契约时，应说明具体条件、执行效果及影响，经用户确认后实施。

例如，物品转移已经更新运行时状态，而其后存档写入失败时，Committer 应如实表达状态已更新、保存未完成以及可确认的失败原因；System 按既有业务契约处理整体结果，不自动回滚或重新发起物品转移。该示例不规定具体提交顺序、整体成功条件或保存策略。

## EventSystem 的异常与日志归属

1. 已有事件框架优先遵循其稳定异常传播及分发中断契约。新建普通事实事件分发机制默认隔离单个监听者的异常，并明确记录必要的事件类型、监听者、失败操作及异常信息，使其他相互独立且能够安全执行的监听者继续接收通知。
2. 监听者已经按照自身契约处理并记录的错误，不由事件框架重复记录。监听调用中未处理且到达实际分发边界的异常，由 EventSystem 或其具体分发实现负责隔离和诊断；不要求发布方额外捕获每个监听者异常或修改已有发布结果类型。
3. 监听者启动的独立异步任务，其后续失败、取消、资源清理和异常记录由该任务的实际所有者或明确异步分发边界负责。同步分发中的 catch 不覆盖已经脱离同步调用链的异步异常。
4. 监听者异常及分发结束不自动改变已经成立的业务事实、实际状态提交结果或整体业务完成条件。具体分发顺序、异常隔离、监听者有效期及重入处理继续遵循[EventSystem 与事件协作规范](../Architecture/EventSystem.md)，不以统一日志为由改变事件运行语义。

## Unity 异步与 UniTask 的异常归属

1. 每个异步操作都必须具有明确的执行所有者及异常观察责任。返回的 UniTask 应按既有规范 await、明确 Forget 或通过既有方式转交所有权，不因引入 LogSystem 而取消实际任务管理、等待及结果交付要求。
2. await 的异常由实际等待调用链中具有处理职责的边界捕获或按明确契约继续传播，不要求每个 await 都设置独立 try-catch。共享执行应区分执行所有者、各等待者的失败及取消语义，避免多个等待者无意重复记录同一次执行异常。
3. 使用 `.Forget()`、Unity 或第三方必须为 void 的入口、事件触发的独立任务等情况时，必须明确异常处理入口或任务所有者，遵循当前 UniTask 版本及项目现有机制，不产生无人观察的异步异常。同步调用入口的异常捕获不得被当作后续异步任务异常处理的替代品。
4. **按实际取消契约处理预期取消。** 正常页面关闭、组件销毁、生命周期结束及用户主动取消等合法取消，不机械输出 Error 或 Exception 级日志。需要检查实际取消范围、令牌及执行契约，不能仅凭 OperationCanceledException 类型将全部情况认定为无害取消或业务未执行；必要的异常诊断及提交事实仍须保留。
5. 已经取消等待但仍在执行的任务，继续由实际执行所有者观察异常、交付可确认结果并完成清理。异步错误不得通过停止等待、返回默认成功或静默丢弃旧任务结果掩盖。具体遵循[Unity 异步与 UniTask 规范](Async.md)及[异步业务与状态一致性规范](StateConsistency.md)。
6. 全局异常回调或未观察异常诊断可以按项目已有或经确认的契约提供最后诊断保障，不替代实际任务所有者的异常处理；不默认新增全局异常订阅、自动线程切换、异常队列或统一恢复框架。输出须遵守实际平台、线程及 Unity API 契约。

## LogSystem 默认架构及职责边界

1. **日志基础架构先行。** 从零设计项目时，默认提前规划并建立 LogSystem 的稳定职责边界，作为项目公共日志框架；不以当前日志数量、调用方数量、复杂度或复用规模作为必要条件。具体新建工作仍须遵守公共基础能力报备及确认规则。已有项目优先复用实际适用的日志机制，不自动补建 LogSystem 或迁移已有 Debug 调用。
2. **LogSystem 属于框架 System。** 新建 LogSystem 统一采用不可挂载的项目运行级普通 C# 单例，遵循已有 System 单例、可见性及生命周期约定；不继承 MonoBehaviour，不依赖 Unity 组件单例机制。作为统一日志记录入口，负责日志严重程度及必要分类、格式组织和底层输出机制，不持有具体游戏业务权威状态。
3. 默认底层输出使用 Unity Debug API，提供与普通信息、警告、错误及异常记录相符的输出能力；已有项目使用其他稳定日志框架时继续沿用。明确的统一日志入口可以替代本文件原有对 Debug API 的直接调用要求，但必须保留相应严重程度、异常堆栈及必要定位信息，不因此放宽必需引用检查和真实失败返回要求。
4. **日志机制不接管异常处理及业务裁决。** LogSystem 接收合法调用方提供的诊断信息并组织输出，不负责捕获所有业务异常、判断业务条件、回滚状态、执行重试、调度任务或自动修复问题。诊断是否成功输出不作为业务成功或失败的判断条件。
5. Manager、System、Controller、Processor、Committer、DataStorage、Service、Adapter 及其他符合日志权限的类型可以按实际职责使用统一日志入口。LogSystem 不依赖具体游戏业务 System、其内部实现或任何 Manager；纯处理层不得因 LogSystem 属于框架 System 而直接或间接调用它。LogSystem 也不得被借作全局业务事件、状态提交或服务定位入口。
6. **基本日志能力应能覆盖早期初始化错误。** 新建 LogSystem 的基础输出不应依赖 ConfigSystem、AssetSystem、EventSystem、PoolManager 或可视化管理对象已经初始化成功，避免日志初始化与其他框架的循环依赖。额外日志配置可由明确装配入口提供，在合法范围内选择输出及诊断能力；不因此强制建立全局初始化状态机、缓存队列或重复日志后端。基础输出及故障处理应按技术契约避免因诊断本身失败而递归记录或掩盖原始错误。
7. 可以按照稳定职责边界进一步拆分日志数据、格式组织和具体输出实现，即使目前仅委托 Unity Debug 输出也允许保持明确的独立框架入口。内部类型不继承 LogSystem 的强制单例约定，访问范围按实际调用契约确定；不机械增加接口、类别枚举、记录容器或全部输出实现。
8. 分类过滤、运行观察、历史、文件写入、远端上报及其他扩展能力按实际需求和已确认契约引入，不因建立默认 LogSystem 而自动实现。新增公共日志能力或改变已有输出及诊断契约时，须说明具体使用方、运行影响和风险并取得确认。

默认内部组织参考（按实际职责及稳定契约引入）：

```text
Assets/Scripts/Framework/Log/
├─ LogSystem.cs
├─ LogLevel.cs
├─ LogCategory.cs
├─ LogEntry.cs
├─ LogFormatter.cs
└─ Output/
   ├─ ILogOutput.cs
   └─ UnityLogOutput.cs
```

| 类型 | 推荐职责 |
|---|---|
| LogSystem | 统一日志入口及日志能力组织 |
| LogLevel | 具有实际统一等级契约时，表达日志严重程度 |
| LogCategory | 按实际分类需求表达日志类别 |
| LogEntry | 具有明确记录及输出契约时承载日志数据 |
| LogFormatter | 组织稳定的日志格式 |
| ILogOutput | 存在明确输出能力边界时表达其契约 |

以上为候选内部职责和文件归属，不强制所有类型同时存在，不确立 Formatter、Output 等新的通用职责后缀，也不统一规定具体接口签名或固定日志数据结构。目录组织继续遵循[代码目录组织与文件归属规范](../Code/DirectoryStructure.md)。

## LogManager 的引入及依赖关系

1. **LogManager 不作为 LogSystem 的默认配套类型。** 存在独立项目级日志管理职责时，例如日志类别及级别的可视化配置、运行日志面板、历史查看或日志文件管理，可以按明确方案引入 LogManager。仅因 LogSystem 有配置、状态或输出功能，不要求增加 LogManager。
2. 新建 LogManager 属于项目级 Manager，采用可挂载的项目运行级 Unity 组件单例，负责自身日志管理、配置装配、必要运行观察及相关管理流程，可以主动调用 LogSystem。不接管 LogSystem 已有的统一记录及输出机制，不另行维护能够独立裁决相同日志配置或输出的权威状态。
3. **禁止 LogSystem 及其他 System 反向依赖 LogManager。** LogManager 或合法装配入口可以显式提供已确认的日志配置和合法技术依赖；不得将指向 Manager 的执行接口、委托或隐式查询作为 System 的底层日志输出依赖。可视化工具主动读取日志框架提供的必要只读信息，不改变日志框架职责。
4. 管理及调试功能须按实际数据所有权、历史容量、清理范围和生命周期组织，不为查看日志而无界持有业务对象、Unity 对象、异常对象或资源。需要新增运行 UI、Inspector 配置、调试组件、文件保存、上传及相关公共能力时，继续遵守各自既有授权和技术规范。

职责协作参考（箭头表示合法调用方向）：

```text
合法非纯处理职责类型 → LogSystem → Unity Debug 或既有合法底层输出
LogManager（按需）    → LogSystem：配置装配、管理调用及运行观察
纯处理层             → 返回处理结果及必要诊断数据 → 合法上层判断及记录

System 不反向依赖 LogManager；
LogSystem 不接管业务错误处理，不依赖具体 Game 业务；
日志记录路径不是固定业务处理阶段。
```

## 日志等级与输出语义

以下为新建日志机制或缺少专用约定时的默认映射。直接使用 Unity Debug 的合法既有项目与统一日志框架保持相同的严重程度语义，不因包装接口名称不同而改变实际诊断等级。

| 日志用途 | Unity 默认底层 API | 使用边界 |
|---|---|---|
| 普通信息（Log） | `Debug.Log` | 必要运行信息、重要初始化结果及明确调试信息 |
| 警告（Warning） | `Debug.LogWarning` | 真实风险、非关键问题或符合契约的效果退化，按实际影响判断 |
| 错误（Error） | `Debug.LogError` | 真实运行错误、必要依赖缺失或相关操作无法安全完成 |
| 异常记录（Exception） | `Debug.LogException` | 已捕获且需要保留原始异常类型及堆栈的诊断 |

1. 日志等级根据真实问题严重程度及影响范围确定，而不是根据调用层级、是否使用 Result、是否捕获异常或开发者是否希望减少 Console 中的红色提示决定。
2. 可恢复或非关键问题使用适当警告；普通成功与调试信息按需输出；必要运行错误不得使用普通信息或警告掩盖。正常业务拒绝、合法未找到和正常取消默认不作为 Error 或 Exception 输出。
3. 已经捕获且确实需要保留原始异常类型和堆栈时，使用 Debug.LogException 或统一框架的等价异常记录能力。不只输出异常 Message 而丢失必要堆栈；需要补充业务上下文时，按真实记录契约组织，避免重复打印同一异常。异常记录方式不必对应独立自定义 LogLevel。
4. 已有框架使用 Trace、Debug、Info、Fatal、Assert 等其他等级及技术契约时可以继续沿用；缺少实际需求时不为统一形式额外建立等级、断言、全局停机或运行限制。

## 日志格式、语言及诊断内容

1. **新建日志默认使用中文正文与明确的英文职责类型、技术标识。** 基础格式为 `[职责类型] 操作及结果；必要诊断信息`。已有稳定日志格式、第三方原始错误信息、异常类型、堆栈及技术协议保留实际表达，不为统一语言擅自翻译或破坏原始诊断。
2. 默认提供真实所属职责类型及具体操作，错误日志必须尽可能明确失败原因及实际影响。能够定位相应对象、字段、配置、资源路径或工作单元时，提供任务所需的标识及上下文，避免只写“失败”“有错误”“请检查”等无定位价值的内容。
3. 类型及业务术语应与项目现有代码、配置及文件归属一致，不伪造错误来源。记录方可以按契约组织上层业务上下文，但不掩盖真实技术来源。异常类型及堆栈按实际诊断需要保留。
4. 请求 ID、会话范围、对象 ID、资源标识、时间戳及其他结构化信息按已有契约和实际定位需要提供，不强制每条日志带全部字段，不为格式创建新的全局追踪、业务 ID 或时间系统。已有输出机制提供时间等信息时不机械重复添加。
5. Unity 对象 Context 在能够帮助定位对象且满足 API、所有权及有效期约束时使用；普通 C# System 不为提供 Context 而查找场景对象或改变可挂载性。不为日志历史长期持有失效对象、资源引用或池化数据。
6. 不得记录或泄露密码、AccessToken、完整认证凭据及其他不应公开的敏感数据。异常消息、网络响应、配置内容、用户数据及路径等应按实际诊断范围控制输出，不机械打印完整请求、响应、存档及对象内容；既有外部输出需符合真实数据保护及权限契约。

格式示例：

```text
[InventorySystem] 背包初始化完成。
[CombatSystem] 战斗配置加载失败；ConfigID=1001。
[MissionDataStorage] 任务存档写入失败；原因=文件访问异常。
[InventoryPanelController] 无法刷新道具列表；缺少 itemListRoot 引用。
[AssetSystem] 资源加载失败；Path=Configs/Binary/Item。
```

示例不规定所有初始化、业务失败及资源访问都必须输出日志，不强制项目使用示例配置 ID、资源路径、字段或数据结构。

## 高频日志、分类及输出控制

1. **日志应服务于真实诊断，而非记录全部执行步骤。** Update、FixedUpdate、高频战斗计算、公式、算法、对象池租用、事件分发等路径，应避免无意义的普通日志、重复错误文本构造及无界历史保存。纯处理层默认不主动输出日志，专项诊断按已确认方案处理。
2. 日志过滤、等级开关、类别开关及重复日志限流按实际诊断需求引入。存在高频重复诊断时，应先识别其真实触发原因、业务结果及记录责任，再提出合适的日志策略；不默认使用全局去重、固定输出次数、自动静默丢弃或其他过滤机制。
3. 有过滤机制时，应按实际技术实现避免为不会输出的高频日志无依据地构造昂贵字符串或诊断数据；不强制所有日志采用委托、结构化记录、字符串池、后台写入或其他包装。具体性能约束遵循[性能与内存管理规范](Performance.md)、[对象池规范](ObjectPooling.md)、[资源管理规范](ResourceManagement.md)。
4. 不得以性能、包体或发布环境为由擅自关闭必要诊断、降低真实错误等级、删除必要异常信息或隐藏失败，不默认关闭发布版本的全部日志。确需调整开发及发布环境的输出策略时，应明确类别、等级、影响、保留诊断和具体授权。
5. 日志开关、限流或输出方式变化不得影响业务规则、实际返回结果、失败处理、事件时机或资源清理。不为防止重复输出擅自停用组件、禁止重复业务调用、改变交互或增加运行限制。
6. 日志历史、文件持久化、远端上报及额外输出目标不作为默认运行机制。确有需求时，应明确输出范围、真实所有者、启用条件、写入时机、容量及清理、平台路径、异常处理、敏感信息及访问权限，遵守已有配置、资源、异步及变更授权规范；不默认将运行日志写入 Resources 或 Unity 项目资产。
7. 多线程、Job、异步任务及外部回调中的日志输出应按实际 API、平台和框架线程契约组织；不因统一日志入口推定所有输出实现均线程安全，不为日志擅自引入线程池、全局锁、后台写入或主线程调度机制。

| 功能或行为 | 默认方案 |
|---|---|
| 普通日志 | 根据实际诊断需要使用，不每帧机械输出 |
| 高频重复错误 | 保留必要诊断；确需过滤或限流时按确认方案处理 |
| 日志等级及类别过滤 | 按实际需求引入 |
| 运行时调试观察 | 按明确管理或诊断需求建立 |
| 日志历史 | 按需引入，明确容量、有效期及清理 |
| 文件持久化 | 按实际需求及平台契约引入 |
| 远端日志上报 | 按明确需求、数据范围及授权引入 |
| 发布环境输出 | 遵守实际确认策略，不默认关闭全部日志 |

## Agent 开发前检查与默认设计方案

1. 新增或修改日志、异常及失败处理前，应按当前任务相关范围识别：
   - 项目已有日志框架、Unity Debug 使用方式、严重程度、输出格式及实际异常契约。
   - 当前运行结果属于正常成功、普通业务失败、真实运行错误、程序异常、取消还是结果尚未确认。
   - 问题发现者、结果表达者、异常处理边界和主要日志记录负责人，以及是否涉及纯处理层。
   - 实际执行、状态提交、任务和资源所有权；是否存在部分完成、外部结果未知或其他独立操作。
   - 日志所需上下文、真实错误来源、异常堆栈、重复记录风险、输出频率及敏感信息范围。
   - 是否涉及改变已有异常传播、日志输出、公共接口、UI、校验、资源清理、业务恢复或新增公共日志能力。
2. 任务方案应在与需求相关的范围内说明真实失败处理及日志责任、采用的日志入口、异常捕获范围及新增机制的依据。新项目默认规划 LogSystem；已有项目优先沿用稳定机制。需要改变已有契约或新增公共诊断能力时，应说明原因、影响及候选方案，经用户确认后实施，不要求无关任务输出完整审计报告。
3. 交付时应说明实际新增或修改的失败返回、异常捕获、日志等级、主要诊断责任及相关行为变化，列出必要引用、配置、运行错误、正常业务失败、事件监听、异步取消及异常路径等需要用户手动验证的相关场景。仅进行符合既有协作规范的静态审查，不主动编译、检查编译错误、运行项目或验证实际日志输出，不宣称未经验证的运行结果。

默认设计参考：

| 设计维度 | 默认推荐或约束 |
|---|---|
| 普通业务失败 | TryXxx、明确 Result 或状态返回，默认不输出错误日志 |
| 真实运行错误 | 真实结果及必要 Error / Warning 级别诊断 |
| 纯处理层 | 正常运行时默认不主动输出日志，提供结果及必要诊断数据 |
| 专项纯处理诊断 | 明确授权后按具体范围引入 |
| 非纯处理类型 | 在自身职责内允许输出，不机械层层记录 |
| 日志负责人 | 由实际诊断责任边界承担，避免重复记录同一错误事实 |
| Result | 以业务语义及真实结果为主，不强制统一基类及全部诊断字段 |
| 主动 throw | 严格限制于明确底层程序契约，不表达普通业务失败 |
| 已发生异常传播 | 按实际契约到明确处理边界，保留必要原始异常信息 |
| try-catch | 按真实处理职责设置，不机械包裹所有方法 |
| 局部错误 | 停止直接受影响且无法安全执行的操作，保留独立安全流程 |
| 异常及取消清理 | 按实际资源及执行所有权处理 |
| 正常取消 | 按取消契约表达，不机械输出 Error 或 Exception |
| 自动重试、回滚、补偿 | 不默认引入，遵循已确认业务契约 |
| EventSystem | 保持既有分发契约；新建普通事实事件默认隔离监听者异常并记录 |
| UniTask | 明确执行、等待及异常观察责任，避免无人观察的任务异常 |
| LogSystem | 新项目默认基础架构，项目运行级不可挂载普通 C# 单例 |
| LogManager | 按独立管理需求引入，不强制配套 |
| LogSystem 的职责 | 统一日志记录、格式及输出，不接管异常处理或业务裁决 |
| 默认底层输出 | Unity Debug API，已有稳定机制优先 |
| 默认代码目录 | Assets/Scripts/Framework/Log/ |
| 日志正文 | 中文正文，英文职责类型及技术标识，保留原始异常信息 |
| 日志等级 | 按真实严重程度及异常诊断需求选择 |
| 日志开关、分类、限流 | 按真实需求及确认契约引入 |
| 日志历史、持久化及远端上报 | 按需建立，不默认引入 |
| 已有项目 | 优先复用稳定框架，不批量替换或重构 |

上述默认方案不构成新增校验、改变业务及 UI、调整异常传播、批量迁移已有日志框架或修改全局诊断策略的授权。日志记录机制与失败结果、异常处理及业务裁决分别归属，始终保持原有 Manager 与 System 单向依赖、纯处理、权威状态提交、事件及异步一致性边界。
