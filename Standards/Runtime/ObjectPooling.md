## 对象池的引入及职责归属

1. **对象池用于具有重复创建与回收需求的对象复用。** 应根据创建销毁频率、并发需求、对象初始化成本、资源占用、可重置性及实际生命周期确定是否采用对象池，不将对象池作为所有对象的唯一创建方式。
2. 子弹、弹幕、频繁生成的敌人、高频战斗特效、伤害飘字及重复列表条目等，属于设计阶段可以优先考虑对象池的典型场景；音频播放实例、页面及其他低频对象按实际收益和常驻内存成本决定。Manager、System 等具有独立有效单例生命周期的类型不作为普通业务对象池的租用对象；配置等稳定数据默认不使用池。
3. 普通 C# 对象、临时集合、事件参数、Request 和 Result 等确有高频复用需求时，可使用现有适用对象池或明确装配的独立池实例。不得为形式统一而要求所有数据对象入池，不得因回收破坏稳定结果、不可变事实或异步数据有效期。
4. 已有 UnityEngine.Pool、第三方对象池或项目自定义池时，优先沿用实际租用、归还、创建、重置及清理契约；不机械包装所有已有对象池，也不擅自修改对象创建方式或迁移现有对象。
5. 对象池的职责是管理复用对象的可用状态及资源生命周期，不承担敌人生成数量、子弹伤害、技能执行、奖励发放或其他领域业务规则。业务 System 继续组织业务使用，具体创建、初始化及复用由具有合法职责的类型按契约承担。

## PoolManager 与 PoolSystem

1. **PoolManager 纳入新项目基础架构先行。** 从零设计项目时，默认提前规划并建立 PoolManager 的稳定管理职责，不以当前对象池数量、逻辑复杂度或复用规模为必要条件。具体创建工作仍须遵守既有公共基础能力报备及确认规则；不因此自动为全部对象开启池化、预热或容量限制。
2. 新建 PoolManager 属于项目级 Manager，采用可挂载的项目运行级 Unity 组件单例，负责全局 GameObject / Prefab 对象池的组织、池实例管理、租用与归还、空闲实例维护、明确的容量及清理契约，以及必要的 Hierarchy、Inspector 运行观察。局部场景或对象所属的独立池仍可按实际生命周期使用，不强制全项目所有池归入一个物理容器。
3. PoolManager 可以按照实际职责建立或复用 PoolRegistry、普通对象池实例及其他细粒度实现。PoolRegistry 只维护明确的池实例注册关系及查询，不替代对象创建、池容量规则或资源加载。可使用通用池类型创建多个不同对象池实例，不强制每种 Prefab 配套独立 Pool 类；下属类型不继承 Manager 单例约束。
4. **PoolSystem 按实际框架需求引入，不与 PoolManager 强制配套。** 存在多个合法 System 共享通用对象租用、归还、池实例组织等框架职责时，可以建立不可挂载的项目运行级普通 C# 单例 PoolSystem。普通 C# 对象的局部复用可先使用符合所有权及依赖规范的独立池实例，不因单项需求机械创建全局 System。
5. PoolSystem 可以提供普通 C# 对象复用，以及确有需求时可由合法 System 使用的 Unity 对象复用底层机制；必须明确线程、执行阶段、创建与归还、资源和实例所有权，不反向依赖 PoolManager。纯处理层不得借 PoolSystem、PoolManager 或其包装获取隐式全局可变工作数据。
6. PoolManager 可以调用 AssetSystem 取得池所需资源；存在 PoolSystem 时，可以调用其合法框架能力承担上层管理、来源装配和运行观察。二者不得分别维护同一个池的独立权威租用状态或重复执行回收、销毁；没有 PoolSystem 时，PoolManager 可以独立完整承担自身管理职责。
7. **禁止 System 反向调用 PoolManager。** System 不得通过 Factory、Provider、Service、能力接口、委托或其他方式间接调用 PoolManager。业务确需使用池化对象时，可以由合法上层管理或装配实际对象，或者使用与 Manager 无反向依赖的明确执行能力、独立池实例及已确认的 PoolSystem 等框架机制；不得让普通事实事件承担业务必须等待的对象创建或复用结果。
8. 池化对象创建、租用初始化和业务使用分别遵守 Factory、Module、System 等既有职责。Factory 可以负责真正创建及初始化对象；复用对象时按照已明确的租用初始化契约处理，不把每次租用都视为新建实例，不无意重复初始化或提交业务。
9. 已有对象池机制、PoolManager 或 PoolSystem 优先复用，不仅因名称不同而迁移。已有项目缺少默认 PoolManager 或已有另一方时，不自动补建或重构；真实职责冲突、公共能力不足及需迁移的对象按既有确认流程处理。

推荐内部职责参考：

```text
PoolManager：项目级 Unity 对象池管理入口
    ├─ PoolRegistry（按独立注册职责引入）：已建立池实例的注册及查询
    ├─ 多个普通池实例：按 Prefab 或明确池身份提供租用与归还
    └─ 资源及诊断协作：按实际契约使用 AssetSystem、观察池状态

确有公共复用框架需求时：
    PoolManager → PoolSystem
    合法业务或框架 System → PoolSystem
    PoolSystem 不反向依赖 PoolManager
```

上述为职责组织参考，不要求所有对象池使用同一容器、固定接口、固定节点层级或同时建立上述全部类型。

## 对象池生命周期及容量管理

1. **区分对象实例生命周期与每次租用生命周期。** 对象从创建到最终销毁可以跨越多次租用；每次租用具有独立的有效身份、运行状态及归还边界。不能仅凭对象实例引用、名称或 active 状态推定它仍代表原业务对象。
2. 池必须明确新建、首次装配、租用、归还、重新租用和最终清理的实际契约。需要重置的状态应在对应阶段完成初始化或清理，避免 OnEnable / OnDisable 等 Unity 回调在身份或数据尚未装配、已经失效时访问错误状态；不统一规定所有池必须采用同一回调及激活顺序。
3. **按实际租用职责清理。** 本次租用建立的事件订阅、异步任务、回调、业务身份、临时引用、运行状态（如生命、速度、动画、粒子）及独占资源，应按契约停止、清除或重置；属于整个实例生命周期的稳定依赖及合法共享资源可以保留。不要求每次归还机械清空所有字段或释放全部共享资源。
4. 对象归还不自动表示相关异步业务已经取消或所有回调已经结束。实际执行所有者仍应处理已发生的业务效果、异常、取消及资源清理，并确保旧租用的结果不能应用到新租用的业务对象；根据实际契约使用生命周期令牌、租用身份、引用、版本或其他机制，不强制所有池对象增加 GenerationID 等字段。
5. 池应具有明确的对象归属和可租用状态契约，防止同一有效租用被重复归还、同一实例同时被多个不兼容使用者租用、向错误的池归还或在归还后继续使用。具体校验及反馈根据已有池契约和实际技术依赖确定，不借此增加无依据的业务拦截或自动修复。
6. **容量与预热须有依据。** 初始数量、预热时机、空闲容量、活跃实例峰值、扩容、缩容、资源清理和不足时处理，应根据实际运行需求及已确认的资源策略确定。对象池以常驻资源换取部分创建销毁开销，容量越大不一定越好，不默认无限保留已创建对象，也不机械定期清空。
7. 对象池的最大空闲保留数量、资源容量与游戏允许同时存在的对象数量是不同概念。资源不足时是否创建、等待、拒绝或采取其他措施，应遵循已有或已确认契约；不得因资源优化擅自限制敌人数量、跳过子弹或特效、销毁正在被使用的对象，或将未执行操作报告为成功。
8. 清理池时，应明确空闲与租用中实例的处理方式、持有资源及其释放时机；不能仅清除容器就推定所有对象及其依赖资源已经释放。场景切换及项目结束按实际池所有权处理，不因 PoolManager 跨场景存续而永久保留全部池和资源。
9. 池的诊断可按实际需要展示空闲数、租用数、容量和加载状态，区分实际采样数据与配置目标；不得为观察目的无限保留对象历史、重复维护权威租用状态或擅自增加运行调试功能。

例如，一个 Enemy 实例先用于敌人 A，归还后再用于敌人 B。A 的延迟表现或伤害相关回调不得仅因对象引用仍有效就直接应用到 B；如果 A 的业务已经实际生效，则仍由原业务所有者按契约处理其真实结果。本例不规定所有池对象必须支持同一种异步取消或租用标识机制。
