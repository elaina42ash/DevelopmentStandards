## Unity 资源所有权及释放

1. **每项具有独立生命周期的资源必须明确所有权。** 区分资源创建者或加载者、负责维持资源有效性的所有者、在约定范围内使用资源的使用者，以及实际执行清理的释放者。上述职责可以由同一类型承担，也可明确分工；持有资源引用、加载句柄副本或使用资源，不自动取得资源释放权。
2. 应按取得方式确定资源的创建、借用、共享、所有权转移、有效期及对应释放操作，保证正常完成、失败、取消、异常、对象回收和场景切换等实际路径的资源清理。不得由多个职责类型分别释放同一份所有权，也不得在其他合法使用者仍需资源时提前释放；存在延迟销毁、异步任务或 Job 使用时，应保证相关依赖在实际使用结束前有效。
3. **托管对象、Unity 原生对象及 GPU / Native 资源分别管理。** 普通 C# 对象由 GC 回收，Unity 对象及 Native 资源按具体 API、实际创建方式和生命周期显式管理。解除托管引用、销毁场景对象或结束异步等待不自动等于底层资源已经释放。
4. Inspector 已绑定资源、共享资产、从其他所有者借用的资源及独立运行时创建的资源，应区分其释放权限。不得将项目共享 Material、Mesh、Texture、Sprite、Prefab、配置资产或其他借用资源作为调用方自有运行时对象任意 Destroy；也不能因为资源由 SO 引用，就推定它与配置具有完全相同的生命周期。
5. 单例、跨场景对象及静态引用应按实际生命周期清理失效的场景、账号、对象和资源关联。DontDestroyOnLoad、全局池、缓存及单例存续不代表所有被引用资源都必须常驻；不得使用全局存续方式规避实际资源装配及清理问题。
6. 使用 IDisposable、文件流、Native 容器、图形缓冲区及其他需显式清理的资源时，应采用符合实际契约的 using、try / finally、明确生命周期释放入口或其他等价方式。按真实取得的所有权配对清理，避免重复释放、异常路径遗漏、释放后访问及未完成任务使用已释放内存；不得假定所有 API 的 Release 或 Dispose 均可安全重复执行。
7. 不默认引入通用 MemoryManager、自动资源扫描回收、定时 GC.Collect 或频繁 Resources.UnloadUnusedAssets 等全局机制。确有明确需求时，说明真实资源依赖、释放范围、阻塞或长帧风险及调用时机，经确认后实施；不以立刻降低内存数字作为无依据的强制清理理由。

| 资源及取得方式 | 生命周期处理参考 |
|---|---|
| 普通 C# 对象及集合 | 解除不再需要的引用，按 GC 及容器契约管理 |
| 自有 GameObject 实例 | Destroy 或按已确定的对象池契约归还，区分归还与最终销毁 |
| 自有运行时 Material / Mesh / Texture 等 Unity 对象 | 在实际使用结束后按 API 销毁，保留共享及借用资产 |
| RenderTexture.GetTemporary | 配对 ReleaseTemporary，不将借用的临时资源作为自有永久资源 |
| 自行创建的 RenderTexture | 按实际生命周期 Release 图形资源，不再使用对象时按契约销毁 |
| ComputeBuffer / GraphicsBuffer | 按相应 API 使用 Release 或 Dispose，不机械重复调用 |
| 自有 NativeArray 及其他 Native 容器 | 按分配器、所有权及 Job 依赖契约 Dispose |
| Resources 加载的资源 | 按实际资产引用、使用范围及所有权契约管理；不任意卸载共享资产，不机械触发全局回收 |
| Addressables 资源及实例 | 按加载、实例化及持有句柄方式使用对应释放契约 |
| 文件流等 IDisposable 资源 | 使用对应 Dispose 或确定性的清理方式 |

上述表格用于判断责任及 API 配对，不代替项目当前 Unity 及包版本的实际 API 契约。通过其他框架、渲染流程或对象池借用的资源，按其实际释放方式处理，不将某种 API 机械用于全部资源。

## Resources 资源管理

1. **Resources 属于合法的本地资源加载机制。** 对于随游戏发布、具有明确资源标识或路径且需要主动加载的本地资产，可以采用 Resources.Load、Resources.LoadAsync 或项目已有等价加载契约。缺少专用目录约定时，SO、二进制及 JSON 配置资产默认归入 Assets/Resources/Configs/ 的相应载体目录，原始 Excel 配置表保留在项目根目录 Excel/；具体文件归属遵循[代码目录组织与文件归属规范](../Code/DirectoryStructure.md)。
2. **固定依赖优先使用 Inspector 显式引用或明确装配。** 编辑阶段已确定的场景对象、Prefab 内部组件、固定资源引用及已明确持有的合法资源，应沿用实际绑定、装配和使用契约，不因资产存放在 Resources 下而强制重新加载。运行时选择资源也可以使用已明确绑定的资源集合，不机械采用动态加载。
3. **主动加载与缺失引用后的自动查找必须区分。** 根据用户指定、既有资源契约或明确配置中的路径及标识取得本地资源，属于正常资源访问。不得未经授权使用 Resources.Load、Resources.LoadAsync、Resources.LoadAll 或其他加载、查找方式代替 Inspector 手动拖拽、自动修复缺失引用或寻找替代资源。Resources 用于取得资源资产，不用于查找场景实例或 Prefab 实例中的子对象；资源加载与 GameObject 实例创建、池化及使用应分别按实际职责组织。
4. **公共动态资源默认经 AssetSystem 或合法访问边界取得。** Resources.Load、Resources.LoadAsync 等默认由 AssetSystem 或其合法底层资源实现使用，ConfigSystem 可以按契约通过 AssetSystem 取得配置资产，业务 System、Manager、Controller、Factory 等合法资源使用职责类型通过适用的资源入口协作，不分别建立重复的通用加载机制。已有稳定专用加载及装配契约继续沿用；不要求为每个 Resources 接口额外建立 Adapter，也不因使用 Resources 改变 Manager 与 System 的单向依赖。
5. 纯业务处理类型及基础处理实现层不得直接或间接调用 Resources.Load、Resources.LoadAsync、AssetSystem 或其他全局资源机制，自行取得未显式提供的资源。其处理输入由合法上层明确提供，不借资源访问绕过既有纯处理、显式依赖和外部副作用约束。
6. **加载路径应具有明确来源及稳定技术契约。** 路径可以来自用户指定、已有配置、资源标识映射或具有明确程序语义的固定资源路径，不属于无依据的业务硬编码。Resources 的加载路径相对于 Resources 目录，不包含文件扩展名，使用 `/` 分隔目录；实际文件位置、类型及加载路径必须相符。项目存在多个 Resources 目录时，应避免重复或存在歧义的加载路径，不仅凭文件名推断资产位置。
7. 禁止通过无依据的名称猜测、全目录扫描或批量加载资源寻找替代对象。确有明确批量加载需求时，可以按已确定的资源范围及既有契约使用相应加载能力，不将合法批量加载与缺失引用兜底混为一谈。资源不存在、类型不匹配、加载失败或尚未就绪时，应按现有加载及业务契约返回明确结果，执行必要诊断，不擅自生成默认资源、选择其他资产、自动重试或改变 UI 交互。
8. **同步和异步加载按实际成本及执行时机选择。** 少量、低频或初始化阶段的小型配置资源可以使用 Resources.Load；游戏运行中可能造成明显等待的资源加载，可以按已有异步及资源契约使用 Resources.LoadAsync。异步加载应明确完成、取消等待、过期结果及实际资源清理责任，遵守 UniTask 及异步一致性规范；不机械将全部加载改为异步，不因加载未结束自动改变业务或 UI 行为。
9. **资源访问及释放必须具有实际所有权和有效期。** Resources.Load 返回资源引用，不自动产生可独立释放的加载句柄或调用方任意卸载资源的权限。应区分共享资产引用、资源使用范围及自有运行时实例。按实际 Unity API 及资源框架契约管理引用、允许的资产卸载及实例清理，避免高频重复加载已有有效资源、提前卸载其他使用者仍需的资源或直接销毁共享资产。不得将 Addressables 句柄引用计数或 ReleaseInstance 等契约机械用于 Resources；不默认引入额外引用计数、缓存、预加载或自动清理机制，不为单项业务清理频繁调用 Resources.UnloadUnusedAssets 或 GC.Collect。
10. **区分构建包含范围与运行时内存驻留。** Resources 目录中的资产及其必要依赖会进入相应构建，即使没有直接场景引用；这不意味着所有资源均在游戏启动时加载到内存。应根据资源规模、构建体积、初始化及加载成本和平台约束判断适用性。随游戏发布的小型配置适合本地 Resources 机制，不要求大量美术、模型、音视频或大型地图等资源一并存入 Resources。
11. Resources 本身不提供远端内容下载及独立热更新机制。存在远端更新、大型资源分发或专用资源管理需求时，应优先沿用已有适用框架，或按确认方案选择 Addressables 等资源技术。不因 Resources 与 Addressables 可以共存就默认同时引入两套加载后端，不擅自迁移既有技术、资源目录、地址或公开同步及异步契约。
12. 资源放入、移动或移出 Resources 目录前，须确认真实维护来源、资源加载路径、序列化引用、构建包含范围及已有框架契约；文件迁移遵守[代码目录组织与文件归属规范](../Code/DirectoryStructure.md)，保留原 .meta、GUID 及合法引用，不自动更改现有 Inspector 装配、加载方式或生成工具输出位置。

Resources 选型参考：

| 实际需求 | 默认处理 |
|---|---|
| 编辑期确定的场景对象、Prefab 内部组件或固定资源 | Inspector 显式引用或合法装配 |
| 已取得且仍然有效的资源引用 | 直接使用或按实际借用契约复用 |
| 少量随游戏发布的 SO、二进制及 JSON 配置 | 明确引用；需要主动加载时可使用 Resources |
| 根据道具、敌人或关卡配置标识主动取得本地资产 | 通过合法资源入口使用已有适用后端 |
| 高频使用同一资源 | 按实际所有权及有效期复用，不在每帧无依据地重复加载 |
| 可能造成明显等待的运行时加载 | 按实际资源及异步契约选择 LoadAsync 等方式 |
| 大型资源、独立资源更新及远端内容 | 根据实际项目选择已有适用框架或经确认的方案 |
| 缺失必需 Inspector 引用 | 按引用检查及日志规范处理，不擅自加载替代资源 |
| 玩家存档及运行时下载数据 | 既有持久化及下载契约，不作为 Resources 资产写入 |

| 配置资产位置 | Resources 加载路径 | 加载类型 |
|---|---|---|
| Assets/Resources/Configs/ScriptableObjects/Combat/CombatConfig.asset | Configs/ScriptableObjects/Combat/CombatConfig | 对应的 CombatConfig 类型 |
| Assets/Resources/Configs/Binary/Inventory/Item.bytes | Configs/Binary/Inventory/Item | TextAsset |
| Assets/Resources/Configs/Json/Mission/Mission.json | Configs/Json/Mission/Mission | TextAsset |

上述路径仅用于说明默认配置位置及合法加载方式。对于按 TextAsset 导入的二进制配置，可以按契约读取 bytes；JSON 可以按契约读取 text，再由实际配置解析职责处理。具体资源加载由 AssetSystem 或合法底层实现组织，不代表业务 System 应直接调用 Resources.Load，也不规定固定 API 签名、配置格式、加载顺序、缓存或释放策略。

## Addressables 资源管理

1. 已有 Addressables 资源框架时，优先沿用项目实际包版本、加载接口、资源地址、分组、依赖及句柄所有权契约。未使用 Addressables 的项目不因本节自动安装包、迁移资源或建立平行加载框架；需要切换技术时须提出方案并取得确认。
2. **加载、实例化及释放方式必须对应。** 使用 LoadAssetAsync 取得资源时，由实际所有者管理该次取得的加载句柄或框架等价所有权；使用 InstantiateAsync 创建实例时，按相应实例、跟踪方式及句柄契约使用 ReleaseInstance 等对应操作。不得仅凭地址、资源类型或 C# 引用推断已经取得或释放独立所有权。
3. 使用 LoadAssetAsync 加载 Prefab 后自行 Instantiate 时，应按实际契约管理实例及源资源的有效性；普通 Instantiate 不自动为每个实例建立对应 Addressables 加载引用计数。源资源及其依赖应在仍有合法实例使用期间保持有效，包括对象池中的空闲实例；最终销毁普通实例和释放相应加载所有权是不同操作。
4. 复制 AsyncOperationHandle 或将句柄传给其他调用方不自动产生新的独立加载所有权。多个使用者共享资源时，按已有 Addressables 引用计数和项目实际共享契约管理，不默认在外层重建一套重复引用计数，也不得因单个使用方结束就释放其他使用方仍依赖的所有权。确需额外的借用或引用管理时，应明确与底层引用计数的对应关系并经确认。
5. 加载失败、异常、取消等待、页面切换或过期结果，均应按实际取得的句柄、自动释放约定及底层是否仍在执行处理资源清理。取消等待不保证加载已经停止；迟到的加载结果仍由明确所有者处理，不能将其应用到已失效的对象，也不得遗漏应释放的资源或重复释放已由框架清理的句柄。
6. 对象归还对象池不自动释放其依赖资源。池的资源所有者应保证空闲及租用中实例所需资源仍然有效，按池最终清理、实例实际销毁及资源所有权契约进行释放；场景卸载与共享资源释放分别处理，Addressables 场景等专门加载方式遵循对应卸载接口和所有权约定。
7. **Release 不等同于实际内存立即下降。** 资源引用计数、AssetBundle 依赖、共享资源及 Unity 内存回收时机都会影响实际驻留状态。不得仅依据调用 Release、引用计数变化或内存暂未下降，宣称内存已完全释放或存在泄漏；应结合实际诊断及引用关系判断。
8. Addressables 的加载方式、资源地址及依赖契约仍遵守既有配置、资源命名、Prefab、手动绑定及变更授权规范。明确资源地址的正常加载不等同于未经授权的自动查找缺失 Inspector 引用；不得借资源管理新增默认回退资源、自动查找、自动预加载、重试或其他未经确认的运行机制。

## AssetManager 与 AssetSystem

1. **资源基础架构先行。** 从零设计项目时，默认规划并建立 AssetManager 与 AssetSystem 的稳定职责边界，不以当前资源数量、复杂度或复用程度为建立边界的必要条件。两者具有独立管理职责和框架职责；具体建立工作按公共基础能力报备及确认规则执行，不改变其他 Manager 与 System 不强制配套的原则。
2. AssetManager 属于项目级 Manager，采用可挂载的项目运行级 Unity 组件单例，负责资源来源及管理配置、资产与来源装配、项目级资源管理流程及可视化运行观察。可以维护自身管理职责内的配置及状态，并主动调用 AssetSystem；不重复实现 AssetSystem 已经提供的资源机制，不为展示另行维护一份独立裁决资源加载或有效性的状态。
3. AssetSystem 属于框架 System，采用不可挂载的项目运行级普通 C# 单例，负责统一资源加载、访问、取得及释放契约、资源生命周期组织及必要的加载结果和诊断信息。可以按稳定职责进一步拆分具体加载、资源持有、查询及释放实现；下属类型不继承单例要求，不强制采用固定类名或全部实现同一套机制。
4. **需要主动加载、具有独立资源生命周期的公共资源，默认通过 AssetSystem 或其合法访问边界取得。** 业务 System、Manager、合法装配及执行类型按照各自职责使用相应能力，不为每个业务分别建立重复的通用资源加载、缓存及释放机制。已明确绑定的 Inspector、Prefab 内部组件引用、局部场景对象及有效借用资源，不强制通过 AssetSystem 重新加载或包装；特殊专用加载契约按现有实现或经确认的方案处理。
5. AssetSystem 可以依赖项目已有资源框架、底层 Service、明确的数据访问及 Adapter 等符合职责的能力。AddressablesAssetAdapter 等只有在确有实际适配契约或稳定框架边界时才引入；不强制所有项目使用 Addressables、某个插件、固定泛型接口、资源 Key、缓存或自定义句柄封装。 Resources 是合法的本地资源加载机制，可以直接作为 AssetSystem 的底层实现，也可以根据真实适配职责及稳定边界建立独立实现。不强制建立 ResourcesAssetAdapter 或同时引入 Resources 与 Addressables，不为统一资源访问擅自迁移已有框架。
6. **AssetSystem 不反向依赖 AssetManager 或其他 Manager。** AssetManager、Initializer 等合法装配入口显式提供配置、资源来源描述及合法技术依赖，不向 System 传入指向 Manager 的执行接口、委托或隐式查找能力。AssetManager 可主动读取 AssetSystem 提供的诊断信息，不改变二者所有权及依赖方向。
7. AssetSystem 不接管业务资源使用决策、领域规则、玩家存档、有效业务配置选择、对象池的租用状态或完整业务流程。统一入口不等于所有资源由 AssetSystem 永久持有；应明确每次资源取得的所有权、使用范围及清理责任，遵循实际底层资源契约。
8. 具有明确领域或用途的资源访问职责时，可以建立 AssetProvider 或其他具有具体语义的 `XxxAssetProvider`，属于既有 Provider 的具体应用，不强制每种资源配套 Provider。Provider 可以按合法契约提供已有资源及只读资源信息，并使用 AssetSystem 的相应访问能力；涉及产生加载任务、句柄所有权或释放责任的操作，必须按明确的资源执行契约由合法职责所有者组织，不借 Provider 隐藏加载、缓存及释放副作用，不向纯处理层开放全局资源访问。
9. 预加载、按需加载、共享加载、缓存、资源更新、远端下载、自动释放、容量策略和其他运行机制，按实际需求及既有契约建立，不因资源基础架构先行自动实现。新增公共资源能力、改变加载接口、资源生命周期或全局管理策略时，应说明调用、资源、平台及运行影响并取得确认。
10. 已有适用资源框架优先复用，已有类型的实际职责与默认名称不同不构成重命名依据。不得为符合 AssetManager + AssetSystem 的默认结构新增平行框架或机械补建缺少的一方；发现真实职责冲突、缺陷或能力不足时按既有确认流程处理。

职责协作参考（箭头表示合法调用或装配方向）：

```text
AssetManager：项目运行级 Unity 组件单例
    → AssetSystem：资源来源装配、管理调用、只读诊断查询
合法业务 System / 其他资源使用职责类型
    → AssetSystem：按实际资源契约取得、使用及释放资源所有权
    或 → 合法 AssetProvider：取得适用资源或明确资源信息
AssetSystem：项目运行级普通 C# 单例
    → 已有资源框架 / 合法底层 Service / Adapter：执行实际资源操作
```

上述协作不规定固定的技术后端、加载顺序、内部类型及资源缓存机制。AssetProvider 不替代真实资源所有者；纯处理类型仍不得自行加载或释放 Unity 资源。
