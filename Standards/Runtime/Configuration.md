# 配置数据管理规范

## 规范定位与适用范围

定义配置分类、载体、ConfigManager、ConfigSystem、配置来源、读取及生命周期。

本规范是对应专业事项的规则主定义文档。规则适用范围、约束性质、优先关系及例外统一遵循 [规则优先级与冲突处理规范](../Governance/RulePriority.md)；项目修改、读取、实施及交付遵循 [AI 修改与交付规范](../Governance/AgentWorkflow.md)。

本节在既有架构先行、Manager 与 System 单向依赖、Provider 数据访问、状态所有权、访问权限及异步一致性约定的基础上，明确配置数据语义、承载形式、配置管理架构、有效配置来源及使用边界。配置载体由用户决定，配置来源由具有管理职责的 ConfigManager 组织，统一配置机制由 ConfigSystem 提供，各业务 System 组织所属业务的配置使用，纯处理层通过显式输入使用配置。已有项目按实际配置契约及下述保护规则执行。

## 适用范围与规则优先级

1. **用户明确指定的合法配置方案优先。** 用户明确指定某项配置的承载形式、存放位置、编辑入口或组织方式时，必须按照其合法要求设计和实现，例如指定 Inspector 字段、特定场景对象或 Prefab、ScriptableObject（SO）资产、Excel 配置表或其他配置来源。不得因 Agent 偏好其他方式而擅自替换或迁移。
2. 用户未明确指定的部分，优先遵循有效项目及局部专用约定与已有稳定配置契约，包括配置来源、承载形式、读取接口、加载机制、资源组织及导表流程；缺少适用约定时，再采用本节默认方案。
3. **配置载体与职责边界分别确定。** 用户指定配置存放方式，不自动改变配置的架构归属、读取权限、状态所有权、有效范围及 Manager 与 System 的单向依赖。不得为了统一配置获取而擅自移动用户指定的字段或资产，也不得因为配置位于 Manager 的 Inspector 中就允许 System 反向访问 Manager。 配置方案选择的优先关系不得解释为解除硬性架构约束、状态所有权及专项授权；规则裁决与历史实现保护遵循[规则优先级与冲突处理规范](../Governance/RulePriority.md)。
4. 用户要求与已有配置契约、实际技术条件或架构约束存在冲突时，Agent 必须说明具体冲突、影响及候选解决方案，按照用户确认的方案处理，不得自行更换配置载体或扩大修改范围。
5. 本节的职责、依赖及数据语义约束适用于新增设计与业务开发；默认技术方案适用于从零设计及经用户确认的配置架构调整。本节不构成主动批量迁移、重构、修改无关配置、增加校验限制或改变 UI 行为的授权。

## 已有配置框架的识别与保护

1. 新增或修改配置相关功能前，必须根据任务识别已有配置机制，包括真正的维护来源、配置类型及标识、Inspector 或资产绑定、配置表及生成工具、加载与查询入口、配置就绪及资源生命周期、有效配置选择与覆盖关系、配置更新契约及实际调用方，不得只凭类型名称、当前文件格式或目录位置推断配置来源。
2. **已有适用配置框架优先复用。** 项目已有稳定的 ConfigManager、ConfigSystem、配置 Provider、导表框架或其他配置机制时，沿用其实际技术契约，不为套用本节默认名称、接口或实现结构而重命名、拆分、合并或替换。
3. 已有名为 ConfigManager 的普通 C# 配置框架，应按其真实框架职责理解，保留稳定名称与接口；若其实际为 Unity 挂载管理器且业务 System 反向依赖它，则属于需要报告的实际架构冲突。技术名称不同不自动构成职责违规，发现冲突也不构成自动重构授权。
4. **禁止擅自建立平行配置框架。** 已有机制能满足当前需求时，不得新增另一套承担相同职责的 ConfigManager、ConfigSystem、加载器、缓存或查询包装层。已有一方而缺少另一方时，按照独立管理或框架职责评估是否需要扩展，不得仅为配齐默认双层架构自动补建。
5. 现有机制存在实际职责冲突、配置来源不明、功能缺失或运行缺陷时，应先说明具体问题、相关调用方、数据及资源影响和候选方案，经用户确认后修改。新增或修改公共配置基础能力仍须遵守[AI 修改与交付规范](../Governance/AgentWorkflow.md)中的公共基础模块报备及确认要求，并按[规则优先级与冲突处理规范](../Governance/RulePriority.md)处理适用规则及冲突。
6. 上述检查按实际任务范围执行，不要求每次输出完整配置框架审计报告；发现真实冲突、契约不明、生成流程变更或需要调整公共机制时，必须明确报告。

## 配置数据的分类

| 数据类别 | 核心语义 | 典型示例及归属 |
|---|---|---|
| 程序常量 | 固定程序、数学或协议语义 | 数学常量、固定协议标识、明确技术常量 |
| 局部组件配置 | 服务于具体组件、对象、Prefab 或场景的可调整参数 | 局部移动参数、UI 动画时长、相机参数 |
| 业务设计配置 | 表达玩法规则及数值设计所需的参数 | 技能消耗、敌人基础属性、任务奖励、背包容量 |
| 项目及环境配置 | 表达项目运行环境及全局配置选择 | API 地址、服务环境、已确认的功能开关 |
| 用户设置 | 用户主动选择及调整的偏好 | 音量、画质、输入设置 |
| 运行时状态 | 当前实际有效的业务或管理状态 | 当前生命值、金币、任务进度、实际播放状态 |
| 持久化数据 | 用于保存、恢复或传输的数据 | 玩家存档、账号数据、用户设置记录 |

1. 上述分类表达数据语义及用途，不规定数据必须分别使用不同的存储技术或独立类型。用户设置可以持久化，但用户设置的当前有效值、设计默认值及持久化表示仍具有不同语义。
2. 不得因多个数据具有相同名称或数值，就将它们视为同一份数据。例如设计默认背景音乐音量、玩家选择的音量以及音源实际播放音量，应按照各自职责及有效范围管理。
3. 业务设计配置可以用于建立初始运行状态，但当前业务状态、请求执行状态及表现状态不应被当作设计配置维护。用户设置和存档业务仍由所属业务或管理职责类型处理。

## Config 的职责与命名

1. **Config 表示具有明确用途的配置数据，不表示特定技术实现。** 独立配置类型默认采用“业务领域、对象或具体配置主题 + Config”命名，例如 `EnemyConfig`、`SkillConfig`、`CombatConfig`、`CharacterMovementConfig`、`DamageFormulaConfig`、`BiomeGenerationConfig`。
2. Config 可以采用普通 C# 类或结构体、`[Serializable]` 数据结构、ScriptableObject、配置表生成类型、JSON 或其他外部数据契约对应的结构。既有生成类型、外部接口及第三方框架命名继续沿用；不得仅因类型继承 ScriptableObject 就将其命名为 Config。
3. Config 默认承担配置内容的表达及承载职责，不组织完整业务流程，不执行网络请求、存档、权威状态提交、业务事件发布或表现更新。具有独立转换、解析、规则判断或计算职责的能力，按 Mapper、Resolver、Rules、Calculator 等既有职责边界组织。
4. **允许提前建立稳定的配置数据边界。** 一组数据具有明确配置语义或稳定数据契约时，即使当前字段较少、只有一个使用方，也允许建立独立 Config。普通局部参数仍可以直接使用所属类型的序列化字段，不机械为每个字段或组件建立独立 Config。
5. 配置类型和成员的有效可见性、字段封装及数据访问权限按真实使用契约和[类的访问权限与公开接口规范](../Code/AccessControl.md)确定，不因统一配置框架而默认公开所有配置实现及可变成员。

## 配置承载形式与选型

以下选型仅适用于用户未指定且缺少项目专用约定的情况。配置承载形式、编辑来源及运行时读取格式可以不同，同一项目可以合法共存多种配置方式。

| 实际需求 | 默认推荐方式 | 注意事项 |
|---|---|---|
| 单个组件、Prefab 或场景对象的局部参数 | Inspector 私有序列化字段 | 归属对应对象或能力，不强制独立资产 |
| 具有独立语义的一组局部参数 | Serializable Config | 可在所属对象中序列化并组织，不强制 ScriptableObject |
| 多个对象共享设计配置或独立可编辑资产 | ScriptableObject 或已有配置框架 | 运行时按只读配置契约使用 |
| 包含 Prefab、Sprite 等 Unity 资源引用的配置 | ScriptableObject 或已有资源配置机制 | 明确资源引用、装配与释放责任 |
| 大量同结构的设计数据及批量数值调整 | Excel、CSV 等配置表及已有导表机制 | 区分原始表、Schema、生成代码与运行时数据 |
| 外部工具生成、跨平台交换或远端下发 | JSON、二进制或既有协议 | 数据格式不等同于独立配置架构，也可能是导表产物 |
| 项目及运行环境参数 | 项目已有环境配置机制 | 明确有效环境，不混用不同来源 |
| 玩家主动调整的设置 | 用户设置及既有持久化机制 | 不将用户当前设置写回共享设计配置 |
| 固定程序语义 | const 或符合契约的 readonly | 遵循既有常量及访问权限规范 |

1. **集中管理不等于集中存放。** 业务配置资产、配置表、序列化字段及其他来源可以继续按业务归属独立组织，不要求统一迁移至单一目录、单一 ScriptableObject 或单一配置文件。统一配置机制应按契约提供有效配置，而非决定所有数据必须存放在哪里。 缺少项目专用目录约定时，随游戏发布的 SO、二进制及 JSON 配置资产默认存放于 Assets/Resources/Configs/ 下的对应载体目录；原始 Excel 配置表默认存放于项目根目录 Excel/。具体文件归属遵循[代码目录组织与文件归属规范](../Code/DirectoryStructure.md)，不因此强制采用 Resources 加载、集中所有配置或迁移已有资源。 数据驱动与参数化方案的技术设计遵循[技术实现方案设计与评估规范](../Design/TechnicalDesign.md)，本节继续决定配置载体、维护来源、访问及所有权等实际契约。
2. 用户明确指定 Inspector、SO、Excel 或其他配置形式时，应保持指定编辑入口；不得为符合默认选型、统一查询方式或减少实现成本而擅自改变其存放位置。
3. 项目已有 Luban 或其他导表、配置加载框架时，沿用其实际维护及运行契约，不擅自引入新的工具、包、解析框架或与之并行的配置系统。
4. 使用 ScriptableObject 并不自动保证数据不可变；资源引用、运行时配置保护和生命周期仍须由实际设计保证。不得把共享配置资产直接当作玩家存档、运行时可写状态或自动持久化机制。

## 硬编码、常量与配置的区别

1. **禁止无依据的业务参数硬编码及不合理的魔法数字，不禁止具有明确数学或程序语义的字面量。** 是否配置化应由实际语义、设计调整需求、作用范围及已有契约决定，不以是否出现数字作为唯一标准。
2. 伤害倍率、技能消耗、冷却时间、敌人基础属性、奖励数量及其他可调整玩法参数，应使用用户指定或项目已有的配置来源；不得仅因当前值固定而将其写成 Formula 内部的硬编码数值或全局常量。
3. 数学公式固有系数、循环起始值及语义明确的程序字面量，可以按实际表达直接使用，不强制为每个数字建立配置字段或命名常量。例如三角形面积公式中的除数 `2f` 属于公式数学关系，不应作为玩法配置。
4. 固定程序常量按实际职责及作用范围组织，继续使用代码命名规范中的 `UPPER_SNAKE_CASE` 约定；不为形式建立集中保存全部游戏参数的巨大 GameConstants 类型。环境地址等实际可切换参数遵循环境配置契约。
5. 具有明确设计依据的初始值、默认配置值或可选参数默认值可以按已经确认的契约使用，不得将其与配置缺失后擅自添加的兜底值混淆。

| 内容 | 推荐归属 |
|---|---|
| 暴击倍率、基础生命、技能冷却 | 对应业务设计配置 |
| UI 淡入时间、局部特效持续时间 | 所属对象的表现配置 |
| 公式固有数学系数、循环起始值 | 公式或程序语义本身 |
| 固定协议标识 | 明确归属的程序常量 |
| API 地址、服务环境 | 环境配置 |
| 玩家当前金币及实际属性 | 当前有效运行时状态 |

## ConfigManager 与 ConfigSystem 默认架构

1. **配置基础架构先行。** 从零设计项目时，默认规划并建立 ConfigManager 与 ConfigSystem 的稳定职责边界，作为项目的基础配置架构，不以当前配置数量、实现复杂度、调用方数量或复用程度作为建立该边界的必要条件。具体新建工作仍须遵守公共基础能力报备及用户确认规则。
2. ConfigManager 属于项目级 Manager，负责配置管理、来源装配及可视化观察；ConfigSystem 属于框架 System，负责统一配置机制、有效配置组织及查询入口。两者具有独立职责，不是单纯为了名称配对而创建的转发类型。
3. **业务 System 所依赖的设计配置，默认通过 ConfigSystem 统一提供。** 各业务 System 按自身职责独立组织配置的使用，不分别建立重复的通用配置加载、缓存、查询和生命周期管理机制。允许直接使用 ConfigSystem 的合法查询入口，也允许通过具有独立领域配置访问职责的 Provider 获取。
4. 统一配置获取不要求所有配置字段集中存放，也不要求所有局部组件参数、Prefab 内部引用、表现参数、固定常量、用户设置、运行时状态及存档进入 ConfigSystem。局部数据按照真实归属及作用范围维护。
5. **鼓励明确的内部职责拆分。** ConfigManager 可以组织资产绑定、来源装配和运行观察；ConfigSystem 可以组织配置加载、有效配置容器、配置查询和初始化等能力，按稳定职责边界进一步独立拆分。即使当前仅有简单实现或委托关系，也可以保留已成立的架构边界；下属类型不自动继承 Manager 或 System 的单例约束。本节不强制内部类型名称或新增通用职责后缀。
6. 架构先行不等同于提前实现所有配置功能。热更新、版本管理、自动缓存、远端下载、自动重试、自动合并及其他运行机制，必须具有实际需求及明确契约，不为充实基础框架擅自增加。
7. **已有项目优先复用。** 新项目的默认双层架构不构成已有项目的强制改造要求；已有适用配置框架应按实际职责继续使用，缺少 ConfigManager 或 ConfigSystem 时不自动补建。实际需要扩展、迁移或重构时，按本节已有实现保护及既有变更授权规则执行。
8. ConfigManager 与 ConfigSystem 的默认配套，是针对配置领域两个独立职责的架构先行约定，不改变其他 Manager 与 System 不强制配套的通用原则，也不要求每个业务 Config 都具有相应的 Manager、System 或 Provider。

职责协作参考（箭头表示合法调用或显式装配方向）：

```text
ConfigManager：项目运行级 Unity 组件单例
    → ConfigSystem：提供已确定的配置来源、资产或数据，组织管理职责内的装配
    → ConfigSystem：查询配置框架提供的就绪、加载及诊断信息

业务 System
    → ConfigSystem：按统一配置契约获取业务所需配置
    或 → 所属领域 ConfigProvider → ConfigSystem：按独立配置访问契约查询
    → 将所需有效配置显式提供给 Logic / Calculator / Rules / Formula 等

ConfigSystem
    → 按契约使用配置来源、已有加载框架或底层技术能力
    → 提供统一有效配置访问，不反向调用 ConfigManager
```

上述结构不规定固定初始化顺序、接口命名、加载算法或必须建立的内部类型。用户指定的配置位置保持不变；已有或经确认的专用直接装配契约继续遵循其实际范围。

## ConfigManager 的职责与边界

1. **ConfigManager 属于项目级 Manager。** 新建 ConfigManager 采用继承 `MonoBehaviour` 的可挂载项目运行级 Unity 组件单例，通常跨场景存续，遵循既有 Manager 单例、访问权限及生命周期约定。
2. 负责项目级配置来源管理、配置资产引用、配置方案选择、配置装配及可视化运行观察。可以持有自身管理职责内的配置来源选择、装配状态及必要资源引用，不接管具体业务规则、业务用例或运行时业务状态。
3. 可以通过 Inspector 显式配置各业务的 SO 资产、配置表来源、环境配置及其他已经确定的配置入口；默认集中管理配置来源及引用，不将所有具体业务配置字段集中写入 ConfigManager，也不要求将配置表中每一条记录分别拖入 Inspector。用户指定的字段或资产位置仍须保留。
4. ConfigManager 可以主动调用 ConfigSystem，提供已经确定的配置来源、资产引用或配置数据，并在自身管理职责范围内组织装配、配置选择及初始化。实际加载机制由 ConfigSystem 或现有合法加载能力承担，不重复实现同一套配置框架。
5. ConfigManager 可以主动读取 ConfigSystem 的只读配置就绪、加载及诊断信息，用于 Hierarchy、Inspector 或 Odin 观察。不得为可视化另行维护一份独立裁决有效配置的状态、配置数据或加载结果。诊断字段及调试能力按实际需求引入。
6. **不得作为 System 的反向配置入口。** 业务 System、ConfigSystem 及为其提供配置的 Provider 不得主动查找或调用 ConfigManager，也不得通过接口、委托、闭包或其他间接方式取得 Manager 的执行能力。需要传递配置时，由 ConfigManager、Initializer 或合法装配入口显式提供数据及合法资源依赖。
7. 配置资产的引用、实际加载、使用和释放责任须分别明确。ConfigManager 的单例生命周期不代表所有配置资源必须永久持有，也不自动获得释放其他所有者资源或修改配置框架生命周期的权限。
8. Inspector 字段、配置来源分组、必需引用、只读观察及资源绑定继续遵守 Odin Inspector、访问权限及 Unity 项目约束；本节不授权擅自创建场景对象、自动绑定资产或增加调试 UI。

推荐管理形式示例：

| Inspector 区域 | 可以组织的配置入口 |
|---|---|
| 战斗配置 | CombatConfig.asset、DamageFormulaConfig.asset |
| 世界生成配置 | BiomeGenerationConfig.asset、WorldGenerationConfig.asset |
| 配置表来源 | 已有配置表加载配置或生成数据来源 |
| 运行状态观察 | ConfigSystem 提供的实际配置就绪、加载及诊断信息 |

上述为可能的管理组织形式，不要求项目建立对应配置资产、字段、环境选择或调试功能，也不授权自动迁移已有字段。

## ConfigSystem 的职责与边界

1. **ConfigSystem 属于框架 System。** 新建 ConfigSystem 采用不可挂载的项目运行级普通 C# 单例，不继承 MonoBehaviour，不使用 Unity 组件单例机制，遵循既有 System 单例、公开入口及依赖规范。
2. 负责统一配置加载组织、有效配置数据持有及组织、确定性索引、配置查询、配置就绪和配置框架自身的生命周期管理。可以将具体加载、数据容器、查询和初始化委托给职责更细粒度的类型。
3. ConfigSystem 可以持有当前有效配置、配置来源映射、查询索引及必要的框架运行状态；其持有及组织方式必须遵循真实配置权威来源及生效契约，不因建立统一入口而要求复制全部配置数据，也不接管原始配置的设计维护权。
4. 合法的业务 System 可以直接使用 ConfigSystem 的公开配置查询能力，或通过合法 ConfigProvider 获取所需有效配置。查询应具有明确类型、身份、作用范围、有效期及失败语义，优先沿用现有稳定契约，不强制统一泛型查询、字符串 Key 或某种数据容器实现。
5. ConfigSystem 可以调用符合既有依赖规范的加载框架、Service、DataStorage 或 Adapter 等底层能力完成配置加载、解析及技术转换，不强制自行实现每种数据格式、下载或资源加载机制。具体业务配置选择、领域规则及业务用例仍由相应职责类型组织。 需要主动加载配置资产或运行时配置资源时，可以按合法契约调用 AssetSystem；ConfigSystem 负责有效配置，AssetSystem 负责资源取得及释放机制，避免相互等待及初始化循环，具体遵循[性能与内存管理规范](Performance.md)、[对象池规范](ObjectPooling.md)、[资源管理规范](ResourceManagement.md)。
6. **禁止反向依赖 ConfigManager。** ConfigSystem 通过明确装配的配置数据、来源描述及合法底层依赖取得所需配置，不得持有 ConfigManager 实例、指向 Manager 的执行接口或委托，也不得隐式查找场景中的配置管理对象。
7. ConfigSystem 不负责具体游戏业务规则、权威业务状态、用户设置业务、玩家存档、完整业务用例、UI 更新或具体表现，不作为通用业务数据中心、任意对象注册表或全局服务定位器。
8. 可以按已确认的配置更新契约维护配置缓存、版本、远端更新及有效配置切换等框架能力；没有对应需求时不机械建立这些机制。涉及配置变化通知时，由合法职责承担者按[EventSystem 与事件协作规范](../Architecture/EventSystem.md)发布已经成立的事实，不默认增加热更新事件。
9. 可以向合法的 ConfigManager、调试工具及其他明确调用方提供必要的只读就绪、加载及诊断信息，不因可视化需求而继承 MonoBehaviour。配置修改、注册、装配、初始化和释放等入口，按实际所有权及调用范围确定，不作为所有业务的任意写入能力。
10. 内部实现的细粒度拆分遵循架构先行及访问权限规范；不强制增加 ConfigLoader、ConfigContainer、ConfigRegistry、ConfigValidator 等通用职责后缀。静态配置查询不默认使用具有运行时对象注册语义的 Registry，已有框架存在相应固定命名或明确注册契约时按其实际职责使用。

## ConfigProvider 与配置访问

1. **ConfigProvider 是 Provider 在配置领域的具体应用。** 采用“业务领域或对象 + 配置主题 + Provider”命名，例如 `SkillConfigProvider`、`EnemyConfigProvider`、`MissionConfigProvider`。负责提供明确配置查询契约、确定性读取、索引访问及符合所有权约定的只读配置，不承担完整业务裁决。
2. 具有统一配置架构时，ConfigProvider 可以按合法契约使用 ConfigSystem 的只读查询能力，优先通过明确装配或项目已有稳定访问方式取得所需依赖。该约定只针对明确配置访问职责，不自动允许其他 Provider 任意访问 System 或反向依赖 Manager。
3. ConfigProvider 不重复承担通用加载、配置更新、版本发布、框架生命周期管理或独立权威配置维护；复杂的配置选择、条件匹配或组合问题按照既有职责由 Resolver、Rules、Calculator 等纯处理能力处理，所需数据显式提供。
4. 具有明确且稳定的配置访问职责时，即使当前仅转发一次 ConfigSystem 查询，也允许提前建立独立 ConfigProvider。已有稳定配置访问边界不得为减少调用层级擅自绕过或删除；不要求每个 Config 或每个配置字段机械配套 Provider。
5. 业务 System 可以直接使用 ConfigSystem 的合法查询能力，也可以通过所属领域 ConfigProvider 获取所需配置。初始化时取得配置后，可以按照其实际有效期及所有权持有只读配置引用或必要数据，不要求每次业务计算都重新查询 ConfigSystem。
6. 特殊业务需要独立配置来源或直接装配时，遵循已有稳定契约或经确认的专用方案。用户指定某个 Inspector 字段作为业务设计配置来源时，默认保持该字段位置并通过合法装配将其纳入统一配置机制；存在明确直接装配契约时也可以直接提供给对应 System，不因此建立另一套通用配置框架。
7. Provider 的具体返回值、缺失处理、只读边界、集合所有权及数据有效期继续遵循原有 Provider、访问权限和异步一致性规范。不得为查询便利向调用方开放可任意修改的共享配置数据。
8. 纯业务处理及基础处理实现层不得借 ConfigProvider 间接访问 ConfigSystem、Manager 或其他上层系统能力；其配置应由合法上层显式提供，具体遵循“配置传递与纯业务处理约束”。

## 配置传递与纯业务处理约束

1. **业务 System 负责组织所属业务的配置使用。** 根据实际业务输入、目标对象及有效配置契约，通过 ConfigSystem、合法 Provider 或已确认的装配方式取得所需配置，并将其与必要业务数据提供给对应处理类型。具有工作单元处理职责时，Processor 可按照明确的数据访问和处理时机契约获取所需输入，不依赖具体业务 System，也不自行定义配置生效策略。
2. Logic、Resolver、Rules、Calculator、Evaluator、Matcher、Selector、Mapper、Normalizer、Operation、Formula、Algorithm 等纯处理类型，所需配置、参数、随机来源及其他依赖必须通过显式输入或明确装配的只读配置依赖提供，不直接或间接通过 ConfigSystem、ConfigManager、其他全局单例、Provider、静态配置访问入口或回调隐式获取配置系统能力。
3. 不强制所有配置字段都逐层作为独立方法参数传递；可以传递具有明确语义的只读 Config、InputData、具体参数集合，或在普通实例中持有明确装配且符合纯处理契约的配置。需要跨调用持有配置时，应明确引用所有权、有效范围及变化语义；不得通过可变静态字段保存隐式全局配置。
4. 纯处理类型可以按照自身职责组合已提供的数据，例如通过 DifficultyConfigResolver 解析已经提供的候选配置，或通过 Calculator、Formula 计算配置参数组合结果，但不得自行加载文件、访问远端、查询全局系统、应用配置更新或修改权威配置。
5. Committer 可以接收或使用提交契约需要的明确配置及必要技术依赖，保证实际提交仍符合约定有效性要求；不重新制定玩法配置、重复领域规则或自行改变业务配置生效策略。

例如，CriticalDamageFormula 应接收攻击力及已确定的暴击倍率，由合法上层提供该倍率，而非在公式内部访问 `ConfigSystem.Instance`。以下仅用于说明配置输入方式，不规定具体暴击公式及游戏数值：

```csharp
/// <summary>按照显式提供的倍率计算暴击伤害。</summary>
/// <param name="attack">本次计算使用的攻击力。</param>
/// <param name="criticalDamageMultiplier">本次计算使用的暴击倍率。</param>
/// <returns>计算得到的暴击伤害。</returns>
public static float Calculate(float attack, float criticalDamageMultiplier)
{
    return attack * criticalDamageMultiplier;
}
```

上述调用方式继续遵守各纯处理类型的职责、默认静态实现、显式依赖及无外部副作用约束。

## 配置与运行时状态的关系

1. **Config 与 RuntimeData 必须具有独立的数据语义。** Config 表达设计参数及已确定的配置内容；业务对象或 RuntimeData 表达当前实际有效的业务状态；SaveData 或既有持久化结构表达保存、恢复及传输所需的数据。Snapshot、DisplayData、InputData、Result 等仍遵循各自专门约定，不接管权威配置或权威状态所有权。
2. 多个业务对象可以共享同一份设计配置，但各自需要独立变化的运行时状态，应按照真实业务身份、所有权和生命周期分别维护。不得把共享配置对象中的基础属性、默认参数直接作为各对象可以独立修改的权威状态。
3. RuntimeData 可以在初始化时读取 Config 的参数，建立初始状态，也可以持有具有明确有效期的只读配置引用。不要求每个运行时对象完整复制所有配置；需要独立变化的字段、派生状态和必要的稳定输入，按实际业务契约组织，避免无依据的数据复制及重复权威来源。
4. 普通业务运行期间，默认不得直接修改共享设计配置。伤害、属性加成、玩家进度及其他业务效果由所属 System 组织，通过业务对象、RuntimeData 和符合职责的提交能力落实；不得将这些效果写回 SO 资产、配置表或其他共享设计来源。
5. **区分配置编辑与运行时状态变更。** 编辑器中的配置编辑、经确认的运行时配置调试、配置方案切换及服务端配置更新，可以按照明确的所有权、权限和生效契约修改或替换配置；不因普通业务默认只读而禁止合法配置编辑与更新。已有运行时可变配置机制继续遵守实际契约，不擅自收紧或改为不可变实现。
6. 配置字段、属性和集合应按照实际读取及编辑契约提供访问能力。运行时默认只读并保护共享数据及其内部元素，不得仅因引用为 readonly、属性无 setter 或接口为 IReadOnlyList 就宣称配置对象不可变；不强制所有读取创建完整副本，确需独立修改、稳定输入或隔离时按契约提供对应数据。
7. ScriptableObject 是可用于承载配置的 Unity 对象，不自动隔离共享资产的运行时修改；在编辑器中无意修改共享资产可能影响其他使用方及后续运行。构建后的游戏不得将修改 ScriptableObject 资产当作可靠的持久化存档机制，实际存档仍由既有持久化能力承担。

| 数据示例 | EnemyConfig（设计配置） | EnemyRuntimeData（运行时状态） |
|---|---|---|
| 生命 | 基础生命值 | 当前生命值、当前最大生命值（按玩法契约） |
| 攻击 | 基础攻击力 | 当前有效攻击力或实际属性计算所需状态 |
| 移动 | 基础移动参数 | 当前运行的运动状态或实际变化参数 |
| 奖励 | 设计奖励配置 | 本次业务的实际奖励处理结果（按相应职责归属） |

例如，多个敌人共享 EnemyConfig 时，某个敌人受到伤害应通过其所属状态提交契约改变该敌人的当前生命值，不修改共享基础生命值。上述数据示例不要求每个敌人都独立创建 RuntimeData 类型或保存全部列出的字段。

## 配置权威来源及覆盖关系

1. **同一配置含义在同一有效范围内必须具有明确权威来源。** 应区分设计期原始维护来源、生成产物、加载后的当前有效配置、只读引用及派生数据；允许合法的数据转换、缓存和不同用途的表示，不允许多个来源分别独立裁决同一配置含义。
2. 存在多个配置来源、难度配置、场景或对象覆盖、环境差异及远端下发时，应按已有或经确认的契约明确选择、覆盖、组合的条件、优先级、作用范围与生效时机。不得统一假定远端优先、Inspector 优先或配置表优先，也不得自行以最后加载结果或非空值决定覆盖关系。
3. ConfigManager 组织已经确定的配置来源及配置方案，ConfigSystem 按框架契约提供当前有效配置，各业务 System 按自身职责使用配置。Provider、业务 System、UI 或其他调用方不得分别维护另一份能够独立决定相同配置含义的数据，不得为修复显示或业务差异而重复硬编码配置。
4. 基础值、倍率、难度修正、活动修正及其他具有不同设计语义的配置可以同时存在。只有在明确选择及组合契约下才进行组合；涉及实际领域计算或业务裁决时，由所属 System 组织相应 Resolver、Rules、Calculator、Formula 等处理类型，不将业务规则转移给通用配置框架。
5. 对环境配置及服务端权威业务，应明确真实的有效来源、运行环境和客户端与服务端的数据契约。客户端配置不得替代服务端的权威业务规则及安全校验。

例如，基础攻击力与困难难度倍率是具有不同语义的配置，可以按已确认规则参与计算；同一基础攻击力分别在 Excel、SO、Prefab 和代码中独立维护不同值，则必须先确定实际来源及覆盖契约，不能由调用方随意选择。此例不授权新增任何难度、活动或覆盖机制。

## 配置加载、初始化与生命周期

1. **配置就绪与实例创建分别确定。** Manager、ConfigSystem 或业务 System 的单例存在，不自动代表相应配置已经装配、加载成功或具备执行所有业务的条件。具有独立加载生命周期时，应明确配置就绪、业务初始化及可访问的有效范围。
2. ConfigManager 可以组织配置来源装配，ConfigSystem 负责统一框架加载及有效配置组织，Initializer 根据其装配职责协调依赖准备、接收加载结果及提供业务初始化所需配置，业务 System 按所属业务契约使用配置。已有专门装配入口继续沿用，不重复实现加载或初始化流程。
3. 具体加载方式根据配置载体、实际使用时机及资源生命周期确定。可以使用 Inspector 显式引用、项目启动时加载、场景初始化时加载、按需加载或远端异步加载等方式，不强制所有配置异步加载，不强制所有项目配置在同一时刻一次性加载。
4. 有异步加载需求时，应明确任务所有者、配置来源、完成条件、失败、取消、结果有效范围及资源清理，遵守[Unity 异步与 UniTask 规范](Async.md)及[异步业务与状态一致性规范](StateConsistency.md)。需要使用配置的业务流程应按真实前置条件处理未就绪情况，不将单例存在当作加载完成，也不擅自增加全局初始化屏障。
5. **明确配置及资源所有权。** 配置资产提供者、加载资源的所有者、ConfigSystem 中有效数据的持有者及业务使用方可以不同。应明确配置引用、资源句柄、加载结果、缓存及其有效范围、借用或转移契约、释放责任。使用方持有只读配置不自动取得释放共享资源的权限；跨场景单例不代表全部配置必须永久驻留。 配置资产及其依赖资源按实际资源框架的加载、借用及释放契约管理，具体遵循[性能与内存管理规范](Performance.md)、[对象池规范](ObjectPooling.md)、[资源管理规范](ResourceManagement.md)。
6. 配置加载、选取和资源装配应使用已明确的来源与合法依赖，继续遵守 Unity 项目中禁止未经授权的自动查找、自动绑定和静默创建规则。项目已有的正常数据加载及资源地址契约，不因本节而改成手动逐项拖拽；不得把正常配置加载扩大为替代缺失 Inspector 引用的自动查找。 明确资源路径的 Resources 正常加载属于合法本地资源访问，默认由 AssetSystem 或其合法底层实现组织；已明确绑定的配置资产可直接装配，具体遵循[性能与内存管理规范](Performance.md)、[对象池规范](ObjectPooling.md)、[资源管理规范](ResourceManagement.md)。
7. 不得为了统一加载生命周期或防范假设性问题，机械增加加载状态机、延迟加载、预加载、共享任务、缓存、自动重试、全局依赖容器或其他未确认的运行机制。配置未就绪也不自动授权禁用按钮、增加 Loading 或改变其他 UI 交互。

| 加载方式 | 适用情形 |
|---|---|
| Inspector 显式引用或直接装配 | 局部配置、已有资产及已确定的配置入口 |
| 启动时统一加载 | 业务启动前必须准备好的配置 |
| 场景初始化时加载 | 场景专属配置或资源 |
| 按需加载 | 大型、低频或具有明确独立有效期的配置 |
| 远端异步加载 | 确有服务端配置来源及对应加载契约 |
| 运行时热更新 | 项目已明确支持运行时配置更新 |

上述方式可以组合使用，具体顺序不作统一规定。

## 配置热更新及版本一致性

1. **运行时配置更新按需引入。** 默认设计配置由正常业务只读使用，不要求所有项目具备热更新、版本号、配置快照、远端下发或配置变化通知。存在实际需求时，必须明确来源、更新权限、配置生效范围、失败及清理契约，并按照既有授权流程实施。
2. 已有热更新及配置选择机制时，优先沿用实际配置加载、校验、版本、生效及通知约定。配置下载完成、数据解析成功和新配置正式生效应根据真实契约分别表达，不能把尚未应用的配置称为当前有效配置。
3. **业务计算及提交所依据的配置必须满足实际一致性契约。** 当配置可能在异步等待、工作单元处理或提交期间发生变化时，应明确本次业务所需的配置有效期及生效策略。不能无意混用不兼容的配置版本，不能仅通过只读引用推定配置内容始终稳定。结果失效时由具有合法业务及提交职责的类型按既有契约组织处理，不由纯处理层自行加载或重新决定配置。
4. 具体生效策略由业务需求决定，可以固定本次操作配置、在提交时重新确认、下一次业务或下一局游戏生效，或按明确规则立即应用。不统一规定始终使用最新配置，也不强制永久保留旧配置；确需同时使用多套配置时，明确身份、版本或其他有效范围及资源清理责任。
5. 涉及一组相互依赖的配置时，应按实际契约保证使用方取得满足对应业务一致性条件的有效配置组合。不得仅因采用版本号、配置缓存或更新通知，就宣称已经保证配置切换一致性；具体保护机制按实际需求确定。
6. ConfigSystem 按明确框架职责组织有效配置更新，ConfigManager 按管理职责选择及装配来源，业务 System 负责决定对应业务如何使用已经生效的配置。配置更新通知属于实际成立的事实，按事件规范及已有技术契约处理，不以事件替代必要的配置装配、业务确认或状态提交步骤。
7. 更新失败、取消或结果尚未确认时，遵循已有配置及异步一致性契约，不擅自新增自动回退旧版本、重试、修复、覆盖或恢复行为。服务端权威业务中的配置版本及生效时机继续服从实际协议，客户端配置不取得服务端裁决权。

| 生效策略参考 | 核心语义 |
|---|---|
| 固定本次操作配置 | 本次操作在约定有效范围内继续使用原配置 |
| 提交时重新确认 | 根据实际提交契约确认计算依据是否仍可应用 |
| 下一次操作生效 | 当前操作按原契约完成，之后使用新配置 |
| 下一局游戏生效 | 同一局或战斗使用约定的稳定配置 |
| 立即生效 | 已运行的对象按已确认规则使用新配置 |

例如，一次技能释放尚未结束时技能消耗配置发生变化，应按照已确认的技能业务契约决定本次使用何种配置，不擅自重新扣除资源或更改已成立事实。此例不规定固定的热更新策略。

## 配置缺失与错误处理

1. **配置缺失、尚未就绪、合法可选值不存在、解析失败和不符合实际配置契约是不同情形。** 配置访问及加载应根据现有契约返回明确结果，区分查询不到配置、依赖缺失、数据无效、加载失败及其他实际状态；不将未找到、未加载或失败描述为成功。
2. 必需的 Inspector、Prefab、场景或配置表引用缺失时，继续遵守 Odin Inspector、Unity 项目约束及日志规范，进行必要的显式检查，记录能够定位对象、配置项及失败操作的错误，并只跳过直接依赖该配置而无法安全执行的操作；不得因此终止无关流程或自动创建替代资源。
3. 配置 ID 或查询数据可能不存在时，优先按 Provider 规范使用 TryGet 或明确结果类型。可选配置、明确允许为空的字段、已经定义的默认配置及可选参数默认值，按照真实业务语义处理，不将合法空值机械判定为错误。
4. **禁止无依据的配置兜底。** 未定义默认值或替代来源时，不得自动生成默认配置、选择第一条记录、补齐字段、静默返回无依据的数值或查找替代资产。用户明确指定的默认值及已有合法默认语义可以正常使用；不得把配置缺失后擅自生成的数值当作已确认默认值。
5. 配置校验必须基于明确业务要求、已确认配置契约或实际技术运行依赖。不得擅自加入范围限制、Clamp、负数修正、去重、自动填充、自动修复、名称或层级限制、拒绝条件及其他附加行为，具体遵循[校验与附加限制授权规范](../Governance/ValidationAuthorization.md)。
6. 配置编辑期校验可以使用项目已有 Odin 或导表校验能力，按实际严重程度区分错误、警告及说明；校验方法保持无副作用，不自动绑定、修改配置或执行业务。运行时必要检查、日志责任及可预期失败返回继续遵循既有规范，不通过 throw 处理普通配置缺失或业务失败。 具体记录边界及统一日志入口按[Unity 日志与异常处理规范](Logging.md)处理，不因缺失或查询结果而机械重复输出错误。
7. 配置加载及使用失败不得成为改变 UI 交互、创建提示界面或禁用按钮的默认授权，也不得以增强健壮性为由扩大任务范围。需要新增限制、恢复或提示策略时，应先说明触发条件、依据、后果及影响并取得确认。

| 情形 | 处理参考 |
|---|---|
| 必需配置未绑定 | 按真实依赖记录错误，停止直接依赖的操作 |
| 查询的配置 ID 不存在 | 返回明确的查询结果 |
| 配置格式无法解析 | 按实际加载契约返回失败 |
| 配置尚未加载 | 按已有就绪和生命周期契约处理 |
| 可选配置不存在 | 遵循已确认的可选语义 |
| 已定义合法默认值 | 按明确契约使用 |
| 未定义默认值或替代来源 | 不擅自生成、查找或补齐 |
| 可疑配置数值 | 按真实风险及已确认校验依据处理 |

## 配置字段、标识、单位及引用

1. 配置类型、字段及表列名称应体现所属领域和实际用途，沿用项目已有稳定术语、序列化及生成契约。不得为统一命名主动迁移既有字段或外部协议。
2. **数值单位和表达方式必须明确。** 根据实际需要明确秒、米、角度、数量、倍率、百分比、概率及其他单位，特别是比例使用 0 至 1 还是 0 至 100 等数据语义。不能仅从当前数值猜测单位，不得在没有确认的情况下改变既有单位、精度或换算方式。
3. 配置需要独立身份、跨表关联、存档引用或确定性查询时，使用项目已有的稳定标识及其实际唯一性范围。不得默认将易随编辑、插入、排序发生变化的配置表行号或集合索引当作稳定业务身份；已有明确且稳定的索引契约继续遵循。不强制所有局部 Config 都增加 ID。
4. 涉及配置标识、配置间关联及资源地址时，应保持已有引用关系、真实数据源和序列化契约。新增标识、改变类型或删除已有配置前，按实际影响检查引用方、生成代码、运行时查询及相关存档兼容，不擅自重新编号或补齐缺失引用。
5. Inspector 配置字段默认采用 `[SerializeField] private`，遵循中文 LabelText、完整 Tooltip、Odin 分组及 Required 等既有规范。Tooltip 应根据实际需要说明业务用途、单位、默认含义及有效条件；不得为形式增加未经确认的范围限制或校验 Attribute。 配置字段的源码中文注释和 Inspector 的 LabelText、Tooltip 分别保留，单位及生效语义须与真实配置契约一致。
6. SO、Prefab、Sprite、Addressables 等配置资产及引用应使用明确的绑定、资源地址和既有加载契约。不得擅自扫描场景、按名称匹配、自动创建或修改资产引用；不因配置管理需要而扩大资源编辑、字段重命名、目录迁移及 UI 修改授权。
7. 配置公开读取与编辑权限、序列化字段及内部可写状态分别确定，按[类的访问权限与公开接口规范](../Code/AccessControl.md)保护共享配置及其所有权。不得为 Inspector 可编辑而机械公开所有字段，亦不得为使用 readonly 等修饰符破坏既有序列化契约。

## 配置表及生成产物保护

1. **区分配置源、结构定义、生成过程与运行时产物。** 项目采用 Excel、CSV、外部工具或自动生成框架时，Agent 必须先查明实际维护来源（如原始表或 Schema）、所用生成工具、生成代码及运行时数据，确认应修改的真实来源，不以扩展名推断某个文件是否为生成产物。 缺少项目专用约定时，原始 Excel、运行时生成的二进制及 JSON 配置、自动生成的业务配置代码分别按[代码目录组织与文件归属规范](../Code/DirectoryStructure.md)存放。
2. 优先修改已经确认的原始配置数据或结构定义，并按照项目已有生成流程更新相应产物；自动生成代码、JSON、二进制数据及其他生成产物默认不直接手工修改。确有经确认的临时处理或专用维护流程时，应说明覆盖风险、实际范围及后续恢复方式；不得用修改生成产物掩盖原始来源未修改的问题。
3. 项目已有 Luban 或其他生成工具时，应沿用其数据定义、生成代码、访问接口及资源发布契约。不得擅自新增导表工具、并行解析框架或替换已有生成流程；工具版本、生成配置及公共类型变更仍须遵守公共基础模块报备及确认规则。 生成代码及数据的实际输出与清理范围须与人工维护文件明确隔离，不得覆盖或删除非所属的手写代码、SO 或手工维护的 JSON、二进制配置；不擅自迁移已有生成目标和原始配置位置。
4. 修改配置字段名、数据类型、单位、默认语义、配置 ID 或 Schema 时，应检查关联表、代码调用方、生成类型、序列化、存档、网络协议及运行时兼容性；不得仅修改当前可见的字段或产物而遗漏实际维护来源及相关依赖。
5. 删除或调整配置 ID、迁移配置资源及修改配置资产引用时，须遵守已有资源和变更授权规则，检查真实引用及持久化兼容，保留需要保持的 Unity .meta 与 GUID；不得擅自重建资产、修改路径约定或重新绑定引用。
6. 涉及重新导表、生成数据、Unity 资源导入或其他验证流程时，应使用项目已有工具及用户已经确认的执行范围。需要用户手动进行导表、生成、绑定及 Unity 验证的事项，必须在交付时明确列出。本节不改变 Agent 不得主动编译、检查编译错误或运行验证的既有要求。

配置维护数据流参考：

```text
原始配置表 / Schema / 其他明确的维护来源
    → 项目已有生成工具
    → 生成代码及 JSON / 二进制等运行时配置数据
    → 已有配置加载机制 / ConfigSystem
    → 业务 System 或合法 ConfigProvider
```

例如，原始 Excel 中某项属性为 20，生成 JSON 中同样为 20。需要调整该属性时，应在授权范围内修改真实维护来源，再依照已有流程生成；不应只修改会被下一次导表覆盖的生成 JSON。直接维护的 JSON 并非必然属于生成产物，仍按实际项目契约处理。

## Agent 开发前检查与默认设计方案

1. 新增或修改配置相关功能前，应按任务相关范围检查以下事项：
   - 用户是否明确指定配置的承载形式、存放位置、编辑入口及组织方式。
   - 配置属于程序常量、局部参数、业务设计、项目环境、用户设置还是运行时及持久化数据。
   - 项目现有配置框架、实际维护来源、生成流程、配置身份、字段单位及资源引用契约。
   - ConfigManager、ConfigSystem、ConfigProvider、Initializer 及各业务 System 的真实职责、调用边界及合法装配方式。
   - 当前有效配置的来源、覆盖关系、配置只读性、所有权、加载和就绪条件、有效范围及释放责任。
   - 配置可能变化时的生效契约、异步计算及提交依据、配置缺失和可选默认值语义。
   - 涉及配置结构、生成产物、序列化、资源和跨业务调用的实际变更影响。
2. 方案中应说明实际采用的配置来源、职责归属、配置访问及传递方式，并在有相关风险时说明配置就绪、有效期、错误处理及一致性保障。新项目默认规划 ConfigManager + ConfigSystem；已有项目优先沿用实际稳定配置框架。需新建或改变公共配置能力、调整用户指定位置、迁移数据或增加校验、热更新等机制时，须报告原因、范围及方案并取得确认，不要求对已经确认的同一具体内容重复请示。
3. 交付时应列出实际修改的配置源、配置字段、资源引用、公开接口及生成产物，说明新增机制、限制及其授权依据。需要用户手动完成的 Inspector 拖拽、配置表导出、代码或数据生成、资源导入、Unity 配置及运行验证，应按任务列出对应入口和必要检查；无法静态确认的依赖和风险须明确标记，不得宣称未经验证的运行结果或主动编译、检查编译错误及运行验证。

完整配置协作示例：

```text
ConfigManager：按照用户指定的编辑入口及已有来源完成配置装配
    → ConfigSystem：组织有效配置及统一查询

WorldGenerationSystem
    → BiomeConfigProvider → ConfigSystem：取得有效 BiomeGenerationConfig
    → BiomeGenerationLogic：传入明确配置、地图输入和随机来源
        ├─ BiomeWeightCalculator：按配置计算权重
        ├─ BiomeGrowthAlgorithm：执行约定的生态扩张算法
        └─ BiomeDistanceDecayFormula：按显式参数执行距离衰减计算
    ← 返回 BiomeGenerationResult
    → BiomeGenerationCommitter：按契约应用结果到 WorldRuntimeData
    ← 返回实际提交结果
```

上述示例展示配置、纯处理、状态提交及运行状态的职责分离，不要求项目采用示例中的玩法规则、算法、配置字段或类型，也不要求每次业务经过所有列出的职责层级。Logic 不直接调用 Committer；实际业务衔接由 System 或符合职责的 Processor 组织。

默认设计参考：

| 设计维度 | 默认推荐或约束 |
|---|---|
| 配置载体及存放位置 | 用户明确指定优先，其次已有项目契约，缺少约定时采用默认推荐 |
| 已有配置框架 | 优先复用，不擅自迁移、重构或建立平行机制 |
| 从零开发配置架构 | ConfigManager + ConfigSystem，纳入架构先行，按确认方案建立 |
| 引入时机 | 不以当前配置数量、复杂度或复用程度为必要条件 |
| ConfigManager | 项目运行级可挂载 Unity 组件单例，管理配置来源、资产装配及运行观察 |
| ConfigSystem | 项目运行级不可挂载普通 C# 单例，提供统一配置机制及有效配置访问 |
| 依赖方向 | ConfigManager 可以调用 ConfigSystem；System 不反向依赖 ConfigManager |
| 业务设计配置 | 默认通过统一 ConfigSystem 或合法 ConfigProvider 获取 |
| 配置管理与存放 | 集中管理来源，按业务归属分散维护，不堆积全部配置字段 |
| 默认 SO 配置资产目录 | Assets/Resources/Configs/ScriptableObjects/，按领域归类 |

| 手写及生成配置代码 | 手写类型归属领域 Data/Configs/；生成代码默认 Assets/Scripts/Game/Generated/Configs/，沿用实际工具契约 |
| 局部组件配置 | 所属对象或组件维护，不强制纳入统一配置机制 |
| ConfigProvider | 具有独立稳定访问职责时鼓励拆分，不机械配套 |
| 业务配置使用 | 各业务 System 独立组织，允许持有符合有效期的只读配置 |
| 纯处理层 | 显式参数、输入数据或明确装配的只读配置，不访问全局配置系统 |
| 独立配置类型 | XxxConfig，具体实现按配置载体确定 |
| Inspector / Serializable | 局部参数或明确指定的配置 |
| ScriptableObject | 独立共享配置资产及 Unity 对象引用 |
| Excel / CSV | 大量同结构配置及批量编辑，沿用已有导表机制 |
| JSON / 二进制 | 外部交换、远端来源或生成数据，按实际契约使用 |
| 固定程序语义 | const 或符合实际契约的 readonly，允许正常数学及程序字面量 |
| 设计配置运行时访问 | 默认只读，合法编辑及更新按明确契约处理 |
| 运行时状态 / 用户设置 / 存档 | 按各自职责及所有权管理，不作为通用设计配置 |
| 权威来源及覆盖 | 来源和生效关系必须明确，不擅自合并或覆盖 |
| 加载、缓存及资源生命周期 | 按实际需求和既有契约确定，不默认增加机制 |
| 配置热更新及版本一致性 | 按需求引入，明确本次业务的有效配置契约 |
| 缺失及错误处理 | 明确结果，不擅自兜底、修正或替代 |
| 配置表与生成产物 | 优先维护真实来源，保护生成及序列化契约 |
