## Committer 职责后缀定义

`Committer` 用于承担明确的应用层状态提交职责，负责按照已确认的提交契约，将已经确定的业务处理结果应用到对应状态持有者，并返回实际提交结果。Committer 可以组织与状态提交直接相关的状态写入、持久化、服务端提交及业务事实事件发布，可以将具体提交操作委托给职责更加细粒度的类型。Committer 不承担纯业务计算、领域规则裁决或完整跨系统业务用例编排，不接管所属业务系统的权威状态所有权。默认采用不可挂载的普通 C# 实例，不强制单例。具体职责、依赖方向、状态约束及实例方式遵循本规范的专门约定。

## 业务数据与状态层

1. **业务数据与状态层负责承载当前有效业务状态，并提供受控更新能力。** 它应明确保存哪些业务身份、数值、集合及关联信息，使业务处理具有明确的数据来源。

2. **状态唯一性按照业务身份和有效范围确定。** 同一业务对象在同一有效范围内，应具有明确的状态持有者。不同账号、角色、存档或业务对象可以分别拥有数据实例；不得仅因类型相同就将它们合并为同一份全局数据。

3. **状态读取与状态修改必须具有明确边界。** 外部调用方通过公开查询、只读访问或 Snapshot 获取状态；状态修改由所属 System 组织，通过明确的受控提交入口应用；可以由所属 System 直接组织，也可以委托 Committer 按照提交契约执行。Committer 的写入权限不等于状态所有权。不得向 UI 或无关模块暴露能够任意修改权威状态的字段、成员或集合。 读取权限与写入权限应分别通过字段、属性、查询及受控更新入口表达；仅限制引用赋值或返回只读接口不能代替实际权威状态保护，具体遵循[类的访问权限与公开接口规范](../Code/AccessControl.md)。

4. **业务判断与状态维护分离。** 业务条件、资格判断、数值计算等由所属 System 组织，可通过 Logic、Rules、Calculator 及基础处理实现层等职责明确的类型完成。具有独立语义或稳定架构边界的处理职责优先考虑独立表达；仅属于系统内部的局部处理也可由职责明确的方法承担，不得将业务判断转移到运行时数据的状态维护职责中。运行时数据对象负责保存状态、接受已确定的更新结果，不重复实现同一套领域规则。必要的数据有效性检查仍须遵守既有契约及[校验与附加限制授权规范](../Governance/ValidationAuthorization.md)。

5. **数据对象不主动组织外部业务流程。** 不直接执行网络请求、存档、UI 更新、动画、音效或全局业务事件发布，也不通过反向调用 System 组织业务。这些操作由 System 或其明确委托的提交、执行实现协调。Committer 只组织与状态提交直接相关的操作，不因本条取得通用表现管理职责。

6. **允许具有不同用途的数据副本。** Snapshot、SaveData、DisplayData、编辑草稿等可以包含相同业务数值，但必须明确用途、有效范围和更新方式，不得分别成为能够独立决定同一业务事实的数据来源。Controller、Presenter 和 View 可以维护自身的展示及交互状态。

7. **配置、运行时状态和持久化数据分别表达。** Config 表达设计配置；运行时状态表达当前有效业务信息；SaveData 或既有持久化结构表达保存、传输所需的数据。不得将玩家进度写回设计配置，也不得将尚未应用的读取结果或编辑草稿直接视为当前有效业务状态。 RuntimeData 可以根据 Config 建立初始状态，也可以按照明确契约持有配置的只读引用，但普通运行时业务效果不得直接写回共享设计配置。用户设置、编辑草稿、持久化数据及合法运行时配置更新，按照各自语义、所有权和生命周期管理，具体遵循[配置数据管理规范](../Runtime/Configuration.md)。

8. **权威来源遵循业务既有契约。** 本地业务可以由运行时数据持有权威状态；服务端权威业务中，客户端运行时数据保存已确认状态或按既有同步契约维护的状态，不因增加数据层而接管服务端裁决。

9. **数据必须具有明确所有者和生命周期。** System 可以持有或显式关联数据对象；具体方案应说明创建或接收、初始化、加载、更新、保存和清理责任，以及账号、存档、场景或对象切换时的处理方式。System 采用单例，不代表其管理的数据对象也必须采用单例。 异步读取、计算及提交必须遵守实际数据归属和有效范围，不得将旧业务实例的结果错误写入新的状态持有者；相关一致性边界遵循[异步业务与状态一致性规范](../Runtime/StateConsistency.md)。

10. **数据类型按用途和稳定契约确定。** 已有业务对象能够完整承载状态时，可以继续沿用。需要独立拆出运行时数据时，使用 RuntimeData。Provider、Snapshot、SaveData 等具有明确数据用途、所有权或稳定架构契约时，可以提前建立独立类型，不以当前字段数量或复杂度为限制；不得为了形式配齐一套类、复制权威状态，也不据此自动重构现有代码或修改稳定序列化、网络和数据库契约。

## `Committer` 与状态提交层

### 职责定位与引入原则

1. **Committer 表示应用层状态提交者。** 负责将已经确定的业务处理结果按照已确认的提交契约应用到对应的状态持有者，并返回实际提交结果。采用“业务对象或领域 + 提交主题 + Committer”命名，例如 `MissionProgressCommitter`、`InventoryTransferCommitter`。

2. **默认采用综合提交职责。** Committer 不仅可以组织权威状态写入，还可以组织与该次提交直接相关的持久化、服务端提交及业务事实事件发布。具体提交范围、步骤顺序、业务事实成立条件及完成边界，必须遵循所属业务已经确认的契约，不强制所有提交都包含上述步骤。

3. **允许提交组织与具体实现分离。** Committer 可以将具体状态写入、持久化及事件发布委托给职责更加细粒度的类型。综合 Committer 即使当前仅承担提交过程的组织与委托职责，也可以作为稳定的架构入口独立存在。

4. **允许提前建立稳定的提交边界。** 不以代码行数、调用数量、当前实现复杂度或复用需求作为 Committer 独立存在的必要条件。即使当前只需要修改一个字段，也可以建立具有明确职责的 Committer。不得为了充实其实现而擅自增加保存、事务、事件、重试、回滚或其他未经确认的机制。

5. **Committer 不属于固定必经层级。** System 可以按照既有契约直接组织状态提交，也可以委托 Committer。普通查询、纯计算及不涉及状态变更的操作，不需要经过状态提交层。已经建立稳定提交边界的业务，不得为了减少调用层级而擅自绕过或删除 Committer。

### 状态归属、提交契约与副作用

1. **状态所有权与提交权限必须分离。** 权威状态仍由所属业务对象、RuntimeData 或既有业务契约确定的权威来源持有。Committer 可以持有明确装配的受控提交依赖，并在授权范围内调用状态更新入口，但不得另外维护一份能够独立裁决同一业务事实的权威状态，也不得向外部暴露可任意修改的权威数据。

2. **提交已经确定的业务结论，不重新进行领域裁决。** Committer 接收明确的业务处理结果、目标身份及提交所需信息，按照契约使结果生效。不得重新实现所属 System、Logic、Rules、Calculator 等类型已经承担的领域规则及计算，不得擅自改变业务处理结果或补充业务决策。

3. **允许进行必要的提交有效性检查。** Committer 可以按照已确认的提交契约检查提交目标是否仍然有效、结果所依据的状态是否仍然适用，以及必要的提交依赖是否就绪。此类检查用于保证提交契约成立，不等同于重新执行完整业务规则。存在并发状态变更风险时，检查与实际写入必须满足对应的一致性契约，不得将一次独立的前置检查视为已经保证提交安全。结果不再适用时，应返回明确结果，由上层组织后续处理。新增校验及一致性机制仍须遵守既有授权规范。 读取、计算和提交之间的竞争状态变化，以及必要检查与写入的一致性保障，具体遵循[异步业务与状态一致性规范](../Runtime/StateConsistency.md)。

4. **持久化由专门的持久化能力承担。** Committer 可以按照所属业务已经确定的保存时机及持久化策略，通过 DataStorage、Service 等职责明确的能力完成所需操作。不得接管通用存储实现、序列化框架或擅自制定保存策略。DataStorage 不负责组织权威状态提交及业务事实事件发布。

5. **业务事实事件必须在对应事实成立后发布。** Committer 可以通过 EventSystem 等既有事件机制发布按照业务契约已经成立的事实。不得将纯计算成功、尚未执行的提交或结果尚未确认的操作当作已生效事实。不得通过事件要求 Manager 完成所属 System 的必要业务步骤，也不得通过事件变相组织其他业务 System 的必要提交。 同一业务事实应明确由 System 或其委托的 Committer 负责发布，不得无意重复发布同一次事实。具体发布权限、事实成立条件和事件数据契约遵循[EventSystem 与事件协作规范](EventSystem.md)。

6. **提交副作用限定在自身职责范围内。** Committer 可以组织使业务结果实际生效所需的状态写入、持久化、服务端操作及事实事件发布，但不作为通用 UI、动画、音效、场景操作或表现流程的执行入口。业务提交与前台展示流程分别遵守各自既有契约，不得以提交为由扩大 UI 修改授权或破坏 Manager 与 System 的单向依赖。

7. **提交必须尊重权威来源及一致性契约。** 本地业务与服务端权威业务应按照各自实际权威来源提交结果，不得因引入 Committer 而使客户端接管服务端裁决权。涉及多个状态持有者时，应遵守已经确认的整体成功、部分成功或其他一致性契约。不得在没有需求依据的情况下统一引入事务、锁、版本号、自动回滚或补偿机制。 多状态持有者、服务端权威提交及异步持久化的相关边界，遵循[异步业务与状态一致性规范](../Runtime/StateConsistency.md)。

### 调用关系、实例方式与生命周期

1. **System 可以调用所属 Committer，Processor 通过明确的提交接口调用。** System 负责组织整个业务用例，按照已确认的业务契约确定提交范围及提交时机。Processor 通过显式提供的 Committer 接口或项目已有的明确提交契约委托实际提交，不直接承担应用层提交副作用。System 直接使用所属 Committer 时，不强制额外建立接口。

2. **Committer 是所属业务系统的内部提交能力。** Manager、Controller、Presenter、View、Module 及其他外部业务调用方，应通过所属 System 的公开业务入口提交请求，不得直接调用其内部 Committer 绕过业务处理流程。Committer 采用静态实现，也不改变该访问边界。 新建内部 Committer 默认采用 internal 类型，正式调用入口可使用 public；同程序集可访问或因框架契约而公开，均不解除内部提交能力的架构访问边界。

3. **Committer 可以使用与提交职责直接相关的下属能力。** 包括业务状态持有者、细粒度提交实现、DataStorage、底层 Service 及符合依赖规范的框架 System 能力，例如通过 EventSystem 发布业务事实。相关依赖应通过显式装配、明确参数或项目既有框架契约提供，不得通过场景扫描、服务定位或其他隐式方式获取提交目标及所属业务 System。

4. **禁止反向依赖和接管跨 System 业务协调。** Committer 不得反向调用所属业务 System、Processor 或纯业务流程入口以重新发起业务处理，不得直接或间接依赖 Manager。默认不得调用其他业务 System。具有业务前后依赖的跨系统用例，由主导 System 组织，各业务 System 分别通过自身提交契约更新所属状态。不得通过接口、委托、事件或框架能力变相绕过该边界。确有特殊跨系统提交机制时，必须先说明方案并取得用户确认。

5. **纯业务处理层不得依赖状态提交层。** Logic、Resolver、Rules、Calculator、Evaluator、其他具体职责能力及基础处理实现类型，不得直接或间接调用 Committer，不得通过提交接口、委托或其他类型修改权威业务状态。纯业务处理结果必须返回给 System 或 Processor，再由符合职责的提交实现应用。

6. **默认采用不可挂载的普通 C# 实例。** Committer 不得继承 `MonoBehaviour`，不强制单例。由所属 System 或明确的装配所有者提供依赖，根据提交职责确定实例数量、复用范围和生命周期。当不需要持有实例依赖，且提交目标、参数及执行能力均可显式提供时，允许采用静态实现。静态形式不改变其在提交职责范围内允许产生副作用的性质。

7. **提交依赖与执行生命周期必须明确。** 应区分 Committer 实例、业务状态持有者、持久化资源及单次提交过程的所有权和有效范围。异步提交的等待、取消、异常、完成及资源清理，应遵守所属业务契约和 Unity 异步规范。不得因调用方取消等待而自动认定已经发生的提交被撤销，也不得自行增加重试、回滚或补偿策略。 取消等待、实际取消执行及撤销已发生业务效果必须分别表达，具体遵循[异步业务与状态一致性规范](../Runtime/StateConsistency.md)。

8. **统一 Committer 的接口及实现命名。** 新增 Committer 接口默认采用 `I` + 对应 Committer 类型名称，例如 `IMissionProgressCommitter` 与 `MissionProgressCommitter`。已经形成稳定调用契约的现有接口继续沿用，不得仅为统一命名而擅自修改。 仅供系统内部协作的提交接口优先使用 internal，具体可见性及成员约定遵循[类的访问权限与公开接口规范](../Code/AccessControl.md)。

### 业务处理结果、提交结果与最终请求结果

1. **业务计算完成不等于业务状态已经提交。** 在业务处理流程中，`XxxResult` 可以表达纯业务处理得出的结论；`XxxCommitResult` 表达状态提交范围内的实际执行情况；`XxxRequestResult` 表达整个工作单元或请求的最终处理结果。名称应与实际业务阶段及交付契约一致。

2. **Committer 必须如实返回实际提交结果。** 根据提交契约保留已完成、未执行、失败、取消、部分完成及结果尚未确认等必要事实，明确实际状态是否更新、持久化是否完成，以及其他提交步骤是否达到约定完成边界。不得将已经发生的状态变更描述为未发生，也不得将部分完成或尚未确认的结果报告为全部成功。无需执行的步骤不应被描述为失败。 超时、通信中断或取消等待不自动证明业务没有生效；未知结果及部分完成的表达遵循[异步业务与状态一致性规范](../Runtime/StateConsistency.md)。

3. **事件发布与监听者执行结果必须区分。** Committer 负责反映业务事实是否已经成立，以及事件发布是否达到既有契约规定的完成边界。Manager、Controller 或其他监听者随后执行的表现、管理及异步操作，不自动成为状态提交成功的必要条件。监听者执行失败，不得直接推导为已经生效的业务状态未发生。 事件分发、监听者异常及异步响应按项目既有事件框架契约和[EventSystem 与事件协作规范](EventSystem.md)处理。事件分发失败与已生效的状态应分别表达；不得因监听者失败而自动撤销已经成立的业务事实，也不得在无法确认监听结果时报告全部监听成功。

4. **提交结果与后续业务处理分别归属。** Committer 负责返回实际提交事实；Processor 按工作单元处理契约生成最终请求结果；System 负责整个业务用例的结果及跨系统后续协作。保存失败是否影响整体业务成功、是否需要重新提交、回滚或补偿，由已经确认的业务契约决定，不由 Committer 自行创造策略。 提交错误的日志记录、异常转换及实际处理责任遵循[Unity 日志与异常处理规范](../Runtime/Logging.md)；不得以日志或异常替代真实提交事实。

5. **数据结构按照实际阶段与稳定契约建立。** 允许为稳定的提交结果建立独立 CommitResult 类型，即使当前字段较少。已有简单返回契约能够准确表达结果时，也可以继续沿用。不要求每个业务同时存在 Result、CommitResult 和 RequestResult，不得为了配齐结果类型而虚构请求生命周期、提交步骤或失败状态。

| System | 组织整个业务用例及跨 System 协作 | 不绕过所属系统直接修改其他领域的权威状态 |
| Processor | 工作单元处理生命周期、委托提交及结果交付 | 不直接执行应用层提交副作用 |
| Logic 及下层纯处理类型 | 确定应当发生的业务结果 | 不提交权威状态、不调用 Committer |
| Committer | 按契约组织已经确定结果的实际提交 | 不重复领域裁决、不接管完整业务用例 |
| 业务对象 / RuntimeData | 持有所属状态并提供受控更新能力 | 不主动组织外部业务流程 |
| DataStorage | 数据的持久化读取、保存及转换 | 不决定业务提交及事实事件发布 |

例如，物品转移由 InventorySystem 组织用例，InventoryTransferLogic 根据输入确定转移结果，InventoryTransferCommitter 按契约将结果应用到对应 Inventory 对象，并按需要组织持久化或事实事件发布。如果任务领奖涉及背包和任务两个业务领域，则由 MissionSystem 作为主导 System 组织跨系统步骤，InventorySystem 与 MissionSystem 分别按各自提交契约落实所属状态，不由 MissionRewardCommitter 自行发起背包业务。上述示例不规定固定执行顺序，也不授权自动增加事务、重试、回滚、事件或其他业务机制。
