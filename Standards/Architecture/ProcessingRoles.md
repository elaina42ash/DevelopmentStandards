## Operation、Formula 与 Algorithm

`Operation`、`Formula`、`Algorithm` 属于基础处理实现层，负责具体基础操作、数值公式及算法实现。

## `Rule`、`Rules` 与 `RuleSet`

1. `Rule` 表示一条可以独立判断的业务规则，采用“业务对象 + 具体条件 + Rule”命名，例如 `MissionLevelRequirementRule`。
2. `Rules` 表示围绕一个业务主题固定存在的一组规则，例如 `MissionUnlockRules`、`InventoryStackRules`。
3. `RuleSet` 表示由多条独立规则动态组合而成的规则集合，适用于规则可注册、替换、扩展或根据配置组合的情况。
4. `Rule`、`Rules` 和 `RuleSet` 接收显式业务数据或只读状态，返回布尔值或明确规则判断结果，不直接修改权威状态、保存数据或刷新 UI，不得直接或间接依赖或调用 Committer。 不得发布全局业务事实事件，不作为独立的全局业务事件监听者，也不得通过局部事件、回调或其他机制间接执行外部业务副作用。
5. `Rules` 可以组织多个 `Rule`，也可以在自身职责内直接完成判断；`RuleSet` 负责按已确认的组合契约组织相应规则。Rule、Rules、RuleSet 可以使用符合依赖规范的基础处理实现或其他具体职责能力完成判断所需的计算、转换及匹配，不得将领域规则的决策职责转移给无明确规则语义的通用工具。
6. 具有明确业务语义的单条规则可以独立命名为 Rule；即使规则较少或当前仅委托一个下层能力，也允许建立稳定的 Rules 入口。不要求将所有具体判断机械拆成 Rule，也不要求 Rule、Rules、RuleSet 成对或成套出现。

## `Logic`

1. `Logic` 表示领域层中一次边界明确的纯业务流程编排者，采用“业务对象 + 业务流程主题 + Logic”命名，例如 `MissionProgressLogic`、`InventoryTransferLogic`。
2. `Logic` 接收显式传入的只读输入数据、状态快照或操作数据，按照领域规则组织处理步骤，可以调用 `Rules`、`Calculator`、`Evaluator`、`Resolver` 等细粒度业务能力，也可以直接调用符合依赖规范的基础处理实现，并汇总为明确业务结果。Logic 可以作为稳定的纯业务流程入口，即使当前只有一个处理步骤或全部具体处理委托给下层类型，也允许独立存在。 业务计算依据的有效性由合法上层及提交实现按[异步业务与状态一致性规范](../Runtime/StateConsistency.md)组织；Logic 不因此取得读取全局状态、组织外部异步等待或重新发起业务的职责。
3. `Logic` 可以控制领域处理步骤、业务分支和中间结果组合，但不得直接修改权威状态，不得依赖或调用 Committer，也不得通过提交接口、委托或其他类型间接提交状态。Logic 不得执行存档、网络、UI、动画、音效、全局事件发布、场景操作或跨模块调用等外部副作用。 Logic 不作为独立的全局业务事件监听者；需要处理事件数据时，由具有相应职责的上层类型接收并显式传入。不得通过局部事件或回调绕过纯处理约束。
4. `Logic` 不作为业务状态的长期权威持有者。当前状态由调用方提供，处理结果通过独立 Result 类型返回。
5. `Logic` 返回的结果应包含上层提交状态和执行副作用所需的完整业务结论；调用方不得在 `Logic` 外部重复实现同一套领域判断。
6. 推荐依赖方向为 `System → Processor → Logic → Resolver / 具体职责能力 → 基础处理实现`。该方向约束职责及依赖，不是固定必经调用链；符合职责及依赖规则时，上层可以直接调用适用的下层能力。下层不得反向依赖上层处理类型或完整业务 System，也不得直接或间接调用 Manager。 纯业务处理类型及基础处理实现层所需配置，由合法上层通过显式参数、输入数据或明确装配的只读配置依赖提供，不得直接或间接通过 ConfigSystem、ConfigManager、全局单例、Provider 或其他机制自行获取未显式提供的配置；具体遵循[配置数据管理规范](../Runtime/Configuration.md)。 纯处理层在正常运行过程中默认不主动输出日志，处理失败通过明确结果提供必要诊断信息，由合法上层按[Unity 日志与异常处理规范](../Runtime/Logging.md)处理；不直接或间接访问 LogSystem 等全局日志入口。

## `Processor`

1. `Processor` 用于持续、顺序或分批消费一组明确工作单元，并管理这些工作单元从待处理到最终完成的处理生命周期。
2. `Processor` 采用“业务对象 + 工作单元 + Processor”命名，例如 `MissionProgressRequestProcessor`、`DamageActionProcessor`。
3. `Processor` 可以负责工作单元入队和出队、处理顺序、重入保护、当前处理状态、获取处理时所需的最新有效状态、调用 `Logic`、通过显式提交接口委托领域结果的提交、生成最终请求结果并继续处理下一项。
4. `Processor` 的输入和输出应具有清晰对应关系，例如输入 `MissionProgressRequest`、输出 `MissionProgressRequestResult`、处理者 `MissionProgressRequestProcessor`。
5. `Processor` 不定义具体领域规则，不直接承担应用层副作用，也不依赖具体业务 `System`；领域处理委托给 `Logic`，状态提交委托给显式提供的 Committer 接口或项目已有的明确提交契约。Processor 不直接更新权威状态、不自行执行持久化或业务事实事件发布；接收实际提交结果后，按已确认的工作单元处理契约生成并交付最终请求结果，不将业务计算成功直接视为提交成功。 状态提交及相关业务事实事件发布由符合职责的 System 或提交实现负责；Processor 不作为独立的全局业务事件调度入口。需要处理由事件触发的工作单元时，由所属 System 等合法业务入口组织提交。
6. 重试、跳过、合并、去重、过期和失败恢复策略必须来自明确需求或配置，不得添加静默默认策略。 多请求的处理策略、实际冲突范围、有效状态读取、执行与等待取消及请求结果交付，均遵循[异步业务与状态一致性规范](../Runtime/StateConsistency.md)；不得因使用 Processor 而默认增加请求拦截或串行化限制。
7. Processor 当前仅有一个工作单元待处理，或处理顺序及生命周期实现较简单，并不影响其已成立的工作单元处理职责及稳定架构边界。若类型实际只负责一次局部执行、不承担工作单元处理生命周期，或只保存队列、只负责路由或只负责调度，则应按照实际职责命名，不得仅为统一层级滥用 Processor。
8. 队列管理、单次执行、结果交付等具有独立职责或稳定架构边界时，可以提前建立相应处理类型，不以代码复杂度或当前工作单元数量作为唯一拆分依据。没有相应处理需求时，不得仅为了充实 Processor 的实现而新增队列、异步等待、重入限制、取消、重试或其他未经确认的处理机制。

## `Resolver`

1. `Resolver` 表示围绕一个明确解析问题的综合解析组件，负责组织所需的细粒度解析能力，消除输入中的歧义、引用、候选冲突或业务分支，并形成最终明确结果。当前只有一个解析步骤时，仍可以作为具有明确职责的稳定解析入口。
2. `Resolver` 可以调用 `Matcher`、`Rules`、`Evaluator`、`Calculator`、`Selector`、`Normalizer`、`Mapper` 等具体职责能力，也可以直接调用符合职责边界的 Operation、Formula、Algorithm 等基础处理实现，负责解析子流程编排和最终结果汇总。
3. `Resolver` 的编排范围必须限制在一个明确解析问题内，不得扩张为完整领域业务流程；独立的纯领域业务流程由 Logic 编排，System 负责整个业务用例的组织及结果提交。
4. 推荐依赖方向为 `System → Processor → Logic → Resolver → 具体职责能力 → 基础处理实现`。符合职责及依赖规则时，上层可以直接调用 Resolver，Resolver 也可以直接使用基础处理实现；不强制增加只为补齐调用链而存在的中间类型。
5. `Resolver` 接收显式解析输入数据，返回明确 ResolveResult。解析失败、无候选项或存在无法解决的冲突时，必须返回明确状态和原因。
6. `Resolver` 的下属依赖必须显式提供，不得通过场景扫描、全局单例、服务定位、反射或自动创建等方式隐式获取。
7. 解析子职责具有明确语义或稳定架构定位时，优先考虑独立拆分，即使当前实现简单、只有一个调用方或仅委托下层执行。复用、替换和独立验证是进一步拆分的依据，但不是必需前提；不要求每个局部实现步骤都建立独立类型。
8. `Resolver` 不持有权威业务状态，不执行存档、事件发布、UI 更新或其他外部副作用，不得直接或间接依赖或调用 Committer。 不作为独立的全局业务事件监听者，不得通过局部事件或回调间接执行外部业务副作用。

## `Calculator`

1. `Calculator` 表示围绕明确业务或技术主题提供的计算能力，负责计算过程组织、计算方式选择及计算结果汇总，采用“计算主题 + Calculator”命名，例如 `DamageCalculator`、`MissionProgressCalculator`。
2. Calculator 可以直接执行计算，也可以调用 Formula、Operation、Algorithm 或具有更细粒度计算职责的 Calculator 完成具体计算。计算能力的组织与具体公式、算法及操作实现可以分别建立稳定的类型边界。
3. Calculator 可以作为稳定的综合计算入口，即使当前只调用一个下层计算类型，也允许独立存在，不需要为了证明其独立价值而增加额外计算步骤。
4. Calculator 接收显式输入数据及配置，返回明确的计算结果，不持有或直接修改权威业务状态。
5. Calculator 不承担完整业务流程编排，不执行存档、网络请求、UI 更新、事件发布等外部副作用，不得反向依赖 Manager、System、Processor、Logic、Resolver 等上层职责类型，也不得直接或间接依赖或调用 Committer。 不作为独立的全局业务事件监听者，不得通过局部事件或回调间接执行外部业务副作用。

## `Evaluator`

1. `Evaluator` 表示围绕明确对象、候选项或业务状态提供的评估能力，负责评估条件组织、评价过程及评估结果汇总，例如 `CombatTargetThreatEvaluator`、`RewardValueEvaluator`。
2. Evaluator 可以返回评分、等级、权重、优先级、适合程度或明确的条件评估结果。Calculator 侧重计算数值或其他确定计算结果；Evaluator 侧重依据评价标准形成对对象或候选项的评价结果。
3. Evaluator 可以调用 Rules、Calculator、Formula、Operation、Algorithm 等符合依赖规则的处理能力完成具体评估，也可以将全部具体评估委托给下层实现。
4. Evaluator 不承担完整业务流程，不自行提交业务状态，也不将评价结果等同于最终候选选择或完整业务裁决；后续选择和处理由具有对应职责的类型组织。
5. Evaluator 接收显式输入并返回明确结果，不持有或直接修改权威业务状态，不执行外部副作用，不反向依赖上层业务处理类型，不得直接或间接依赖或调用 Committer。 不得发布全局业务事实事件，不作为独立的全局业务事件监听者，也不得通过局部事件、回调或其他机制间接执行外部业务副作用。

## `Matcher`、`Selector`、`Mapper` 与 `Normalizer`

1. `Matcher` 表示依据明确匹配条件识别对应对象或候选项的能力，例如 `MissionTargetMatcher`。返回匹配结果，不负责整个解析流程或后续业务状态提交。
2. `Selector` 表示依据明确的选择条件、评价结果或选择策略从候选项中确定所需对象的能力，例如 `CombatTargetSelector`。不擅自新增候选来源、默认候选或选择策略。
3. `Mapper` 表示在明确的源数据与目标数据契约之间组织映射和转换的能力，例如 `MissionDisplayDataMapper`。不修改源权威状态，不通过映射过程自行决定领域规则或获取未提供的业务数据。
4. `Normalizer` 表示按照明确契约将输入规范化为统一表达形式的能力，例如 `GridCoordinateNormalizer`。不借规范化擅自修复、限制或替换原本允许的业务输入。
5. 上述类型接收显式输入并返回明确结果，可以直接实现对应处理，也可以委托 Operation、Formula、Algorithm 等基础处理实现。不得反向依赖 Manager、System、Processor、Logic、Resolver 等上层类型，不持有或直接修改权威业务状态，不执行外部副作用。不得直接或间接依赖或调用 Committer。具体职责能力之间可以按明确职责组合调用，不得形成循环依赖。 不得发布全局业务事实事件，不作为独立的全局业务事件监听者，也不得通过局部事件、回调或其他机制间接执行外部业务副作用。

具体职责能力的判定参考：

| 类型 | 核心问题 |
|---|---|
| `Rule` / `Rules` / `RuleSet` | 是否符合明确的规则或规则组合？ |
| `Calculator` | 计算结果是什么？ |
| `Evaluator` | 对象或候选项的评价结果是什么？ |
| `Matcher` | 哪些对象与输入及匹配条件对应？ |
| `Selector` | 根据既定条件应选择哪些候选项？ |
| `Mapper` | 如何将源数据映射为目标数据结构？ |
| `Normalizer` | 如何按既定契约统一输入表达？ |
| `Resolver` | 如何综合组织解析步骤，确定明确的解析结果？ |
| `Logic` | 如何组织完整的纯领域业务处理流程？ |

上述具体职责能力可以具有稳定的独立入口，即使当前只有一个处理步骤，也不要求合并到上层类型中。选择名称应以该类型负责的问题和输出语义为依据，不以方法数量、代码行数或是否使用多个下属类型为依据。

## 基础处理实现层

1. **基础处理实现层承载具体的细粒度处理实现。** 该层主要包含 Operation、Formula、Algorithm，将具体职责能力的组织与基础操作、数学公式和算法实现分离。上层类型确定处理目标、处理条件、所需步骤及结果组织方式；基础处理实现按照明确的输入和处理契约完成具体处理。
2. **基础处理实现层可以被符合依赖规则的上层类型使用。** Calculator、Rules、Rule、RuleSet、Evaluator、Matcher、Selector、Mapper、Normalizer、Resolver、Logic 等可以根据自身职责调用基础处理实现；Manager、System 等合法上层类型也可以在自身职责范围内使用适用的基础处理能力，但不得因此绕过已确立的系统入口、稳定能力边界或状态提交契约。
3. **允许简单、独立的基础实现。** 具有明确处理语义的单步操作、单个公式或简单算法可以独立成类，不以代码量、调用数量、复用需求或当前复杂度作为引入的必要条件。上层类型当前可以仅委托一个基础实现，而不需要增加其他处理步骤。
4. **允许按职责组合基础处理能力。** Operation、Formula、Algorithm 之间没有固定的调用顺序，可以使用职责更细粒度的同层能力及符合本层约束的通用技术能力，但必须保持清晰的依赖关系，不得形成循环依赖。
5. **本层不是固定必经层级。** 可以根据职责及稳定架构边界直接处理局部实现或建立独立基础处理类型。不得为了引入该层而擅自增加业务规则、处理步骤、全局状态或额外运行机制。

### `Operation`

1. `Operation` 表示一项具有明确处理语义、输入及输出边界的基础处理操作，例如数据转换、拆分、组合、范围处理或映射等具体处理实现，不承担完整业务流程编排。
2. Operation 可以包含业务相关的具体处理逻辑，但不得自行决定所属业务系统的完整业务规则、权威状态更新或业务用例的后续执行方式。
3. Operation 根据显式输入计算并返回处理结果，不直接修改权威业务状态。对集合、缓冲区或其他数据的处理，应遵守明确的输入输出及所有权契约，不得隐式修改调用方的权威数据或其他共享状态。
4. 名称必须体现具体处理对象或动作，不使用含义宽泛的 Helper、Utility 代替明确的处理职责。

典型示例：

| 类型 | 职责 |
|---|---|
| `InventoryStackSplitOperation` | 根据明确输入计算物品堆叠拆分结果 |
| `InventoryStackMergeOperation` | 根据给定容量和数量计算堆叠合并结果 |
| `MissionProgressClampOperation` | 根据已经确定的上下限处理任务进度 |
| `GridCoordinateConvertOperation` | 按明确规则转换网格坐标 |

### `Formula`

1. `Formula` 表示具有明确数学关系或数值设计语义的具体计算公式，负责公式本身的实现，不承担多个公式之间的完整计算流程组织。
2. 公式所需参数、倍率、配置和随机输入必须显式提供，不得隐式获取 System 状态、项目级配置或全局随机数状态。
3. Formula 返回明确的计算结果，不持有或直接修改权威业务状态。即使只包含一行计算代码，也允许独立成类。
4. 名称应体现具体公式的业务或数学语义，例如 `DefenseReductionFormula`，而不是笼统使用 Helper、Utility 或缺乏职责区分的计算名称。

典型示例：

| 类型 | 职责 |
|---|---|
| `BaseDamageFormula` | 基础伤害公式 |
| `DefenseReductionFormula` | 防御减伤公式 |
| `CriticalDamageFormula` | 暴击伤害公式 |
| `CharacterExperienceFormula` | 角色升级经验公式 |
| `EnemyHealthGrowthFormula` | 敌人生命值成长公式 |
| `BiomeDistanceWeightFormula` | 生态区域距离权重衰减公式 |

### `Algorithm`

1. `Algorithm` 表示用于解决明确处理问题的具体算法实现，负责算法内部步骤、中间结果及最终算法结果，不承担完整业务流程组织。
2. Algorithm 可以组合 Operation、Formula、其他 Algorithm 等基础处理能力；算法内部步骤属于其算法职责，不等同于所属系统的完整业务流程。
3. 算法所需配置、执行环境信息、随机来源及其他依赖必须显式提供，不得通过全局单例或场景扫描隐式获取。
4. 存在明确的分步执行、算法替换、多态、独立配置或执行状态需求时，可以采用普通实例实现，并明确执行状态、所有权及生命周期。不得为了统一静态形式而使用全局可变字段保存执行状态。

典型示例：

| 类型 | 职责 |
|---|---|
| `AStarPathfindingAlgorithm` | A* 寻路算法 |
| `RegionGrowthAlgorithm` | 区域生长算法 |
| `WeightedRandomAlgorithm` | 加权随机选择算法 |
| `FloodFillAlgorithm` | 洪水填充算法 |
| `PoissonDiskSamplingAlgorithm` | 泊松圆盘采样算法 |

### 基础处理实现层的实现形式与状态约束

1. **实现形式。** 基础处理实现层统一采用不可挂载的普通 C# 类型，不得继承 MonoBehaviour，不采用上层 Manager、System、Controller 的强制单例约定。
2. **默认静态实现。** Operation、Formula、Algorithm 默认优先采用静态类及静态方法。无独立实例职责时，不得仅为了调用处理能力而创建对象或引入单例。
3. **普通实例实现的适用条件。** 存在明确的算法或处理实现替换、多态、独立配置、跨调用执行状态或符合本层职责的技术依赖需求时，可以采用普通实例实现。不为假设性的替换需求强制引入接口、实例化机制或依赖注入容器。 具体算法替换、多态及稳定能力契约按[技术实现方案设计与评估规范](../Design/TechnicalDesign.md)进行选型；具有明确设计价值的替换契约可以架构先行，不以已有多个实现为必要条件，仍遵守本层默认静态、纯处理及状态隔离约束。
4. **显式输入与输出。** 处理所需数据、配置、依赖及随机来源必须通过调用参数或明确装配的实例依赖提供，返回与处理契约对应的结果。随机处理应使用显式随机样本、种子或明确传入且具有独立所有权的随机来源；不得隐式读取或修改全局随机数状态。可预期失败的返回及诊断方式仍遵守本文件既有规范。 配置输入继续遵循[配置数据管理规范](../Runtime/Configuration.md)，不得通过全局配置入口、ConfigSystem 或 ConfigProvider 间接访问上层配置系统能力。
5. **权威状态隔离。** 本层不得持有或直接修改权威业务状态，不得通过可变成员、集合、引用或委托间接写入权威状态。业务状态更新由所属 System 组织，或由其明确委托的 Committer 等状态提交实现负责；Manager 自身管理状态的更新仍由具有该管理职责的所有者负责。
6. **禁止隐式可变状态。** 禁止使用可变静态字段或共享可变对象保存业务状态、执行进度、计算中间结果或全局计算结果缓存。允许使用常量、真正不可变的静态数据、方法局部变量及相互隔离的实例执行状态。`static readonly` 引用不等同于引用对象本身不可变；不得借其保存全局可变集合等共享状态。
7. **禁止外部副作用。** 本层仅承担纯处理职责，不得直接或间接执行存档、网络请求、UI 更新、动画、音效、业务事件发布、Unity 对象生命周期管理或其他与基础处理无关的外部操作。不得借技术依赖或通用辅助能力绕过本条。正常运行过程中默认不主动输出日志，不直接或间接调用 Unity Debug、LogSystem 等日志入口；必要诊断通过明确处理结果及诊断数据交由合法上层处理。特殊诊断仅按明确授权的方案执行，具体遵循[Unity 日志与异常处理规范](../Runtime/Logging.md)，不得以诊断为名引入业务副作用。 本层不作为独立的全局业务事件监听者，不得通过局部事件或回调间接执行外部业务副作用；事件所表达的数据应由符合职责的上层类型接收并显式提供。
8. **单向依赖。** 不得直接或间接依赖或调用 Manager、System、Processor、Logic、Resolver、具体职责能力等上层处理类型，也不得依赖或调用 Committer 等状态提交能力；不得通过接口、委托、单例或其他类型变相建立反向依赖。允许按明确职责组合其他基础处理能力、使用显式传入的只读数据及符合本层要求的通用技术能力，不得形成循环依赖。
9. **独立执行状态。** 算法或基础处理确实需要保存跨调用的执行进度、中间结果或独立配置时，应通过普通实例或显式执行数据进行隔离，明确其所有权、有效范围和清理责任。允许算法维护自身执行所需的局部工作数据，但不得将不同执行过程的状态合并为全局共享状态，也不得将局部执行状态当作权威业务状态。需要跨帧调度、等待或外部执行时，由符合职责的上层按照项目既有异步和生命周期约定组织。 允许按实际契约使用独立实例或调用方明确提供的临时集合及缓冲区，复用时须保护所有权、并发及有效期；不得为降低 GC 引入全局可变工作数据或借 PoolSystem 隐式获取资源。具体遵循[性能与内存管理规范](../Runtime/Performance.md)、[对象池规范](../Runtime/ObjectPooling.md)、[资源管理规范](../Runtime/ResourceManagement.md)。
10. **静态形式不得凌驾于职责边界。** 静态是默认实现选择，纯处理、显式依赖、无隐式可变状态、无业务副作用及单向依赖是职责约束。不得将静态实现等同于无状态或纯逻辑实现，也不得为了统一静态形式而破坏算法可替换性、执行状态隔离及实际职责。

上述示例仅用于说明职责命名和处理边界，不代表已经确认这些业务规则、数学公式、算法、限制或功能，不要求项目实现所有示例类型。
