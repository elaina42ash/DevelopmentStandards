## Request、Command、Action 与 Event 的语义

| 语义 | 定义 | 关注重点 |
|---|---|---|
| `Request` | 调用方提出的一次业务请求，表达希望所属系统处理的业务用例及其输入，并遵循相应的受理、处理和结果返回契约。 | 调用方请求什么、输入是什么、如何表达处理结果；请求本身不代表已经受理或成功。 |
| `Command` | 一项明确的命令意图，表达要求指定职责承担者执行的具体操作。 | 要执行什么操作、由谁按契约负责处理；命令本身不代表操作已经执行或成功。 |
| `Action` | 项目现有 Action 对象模型中可以被调度或执行的一次具体业务动作。 | 继续遵循项目已有 Action 类型、调度及执行契约，不强制替换为 Request 或 Command。 |
| `Event` | 已经发生、并可通知其他职责类型的事实。 | 事实何时成立、由谁发布，以及订阅者如何按自身职责响应。 |

`Request` 与 `Command` 的语义侧重点不同，但在具体业务中可能重叠；项目可以根据既有术语及调用契约选择其中一种表达，不要求为同一操作机械建立两套类型。若二者都存在，应明确各自的业务含义，不把名称当作可互换的同义词。`Request`、`Command` 和 `Action` 表达请求或执行意图，不得作为已经成立的业务事实发布；`Event` 不用于表达要求其他对象完成必要业务步骤的指令。

1. **Event 只表达已经成立的事实。** 事件用于通知其他职责类型某个业务事实、运行状态变化、用户交互或技术过程已经发生。发布方负责准确表达事实，订阅者根据自身职责和已经确认的业务契约决定如何响应。
2. 禁止通过事件名称、事件参数、目标对象或回调机制，变相指定 Manager 或其他职责类型完成发布方所属业务的必要步骤。
3. 事件名称必须反映实际发生的事实。表示开始、失败、取消的事件同样属于事实事件，但不得将开始或计算完成错误描述为整个业务已经成功。

## EventSystem 与事件协作规范

### 适用范围与规则优先级

1. **区分架构职责与技术实现。** 本规范统一约束 EventSystem 的架构定位、事件语义、职责归属、依赖关系及事件协作边界。上述架构与职责约束适用于所有项目的新增设计与业务开发，不要求不同项目采用完全相同的事件系统技术实现。
2. **已有事件框架优先复用。** 项目已经存在能够满足当前需求的事件系统时，必须优先沿用其稳定接口、事件标识、事件参数、分发机制、监听管理和生命周期约定。具体技术契约优先于本节针对新建框架给出的默认技术方案，但不得据此在新增业务中违反架构与职责约束。 该技术优先关系仅覆盖默认技术方案，规则适用、历史实现保护及真实冲突处理遵循[规则优先级与冲突处理规范](../Governance/RulePriority.md)。
3. **默认方案适用于新建及经确认的重构。** 项目缺少适用的事件系统且存在建立该系统的实际需求，或者用户已经明确批准事件框架重构时，优先采用本节规定的默认设计方案；具体创建、扩展或重构方案仍须遵守公共基础模块的报备与确认规则。
4. **技术实现差异不构成架构违规。** 不得仅因现有事件系统的名称、接口、事件标识、分发方式或内部结构与默认方案不同，就判定其需要重构。
5. **实际职责冲突必须明确报告。** 已有框架存在架构职责冲突、功能缺失或实际运行缺陷时，Agent 必须说明具体问题、影响范围和候选解决方案，经用户确认后才能修改；不得将发现问题视为自动修复或迁移的授权。
6. **本规范不构成重构授权。** 不得以落实事件规范为由，自动修改已有事件框架、迁移全部事件类型或改变稳定事件的运行行为。

### 已有事件框架的识别与保护

1. 新增事件、实现事件订阅或修改事件相关业务之前，必须先识别项目现有事件机制及实际调用契约，不得仅根据类型名称或方法名称推断其行为。
2. 根据当前任务需要，检查以下内容：

   | 检查对象 | 检查内容 |
   |---|---|
   | 框架入口 | EventSystem、EventCenter、EventBus 或其他现有机制 |
   | 实例方式 | 单例、静态入口或其他既有方式 |
   | 事件标识 | 字符串、枚举、类型或其他标识 |
   | 事件数据 | 构造、传递、读取、所有权及有效范围 |
   | 订阅管理 | 注册、解除及重复订阅处理 |
   | 分发机制 | 同步、异步、队列、线程及更新阶段约定 |
   | 异常处理 | 监听者异常是否影响后续分发 |
   | 重入行为 | 分发过程中再次发布事件以及监听关系变化的处理方式 |
   | 生命周期 | 订阅生效、失效及清理时机 |
   | 已有事件 | 是否已经存在表达相同事实的事件 |

3. **禁止擅自建立平行事件系统。** 已有适用事件框架时，不得为了符合默认命名、接口或技术方案而新增另一套承担相同职责的事件系统。
4. 不得仅为了统一接口名称，在已有事件框架外部机械增加新的 EventSystem、Adapter 或转发层。存在明确适配、迁移或独立作用域需求时，必须先说明方案并取得确认。
5. 已有事件框架无法满足需求时，应优先评估扩展现有框架的可行性，再考虑替换或新增独立机制。新增和修改公共事件能力仍须遵守公共基础模块的报备及确认规则。
6. 上述检查应根据实际任务执行，不要求每次向用户输出完整检查报告；但发现契约不明确、存在冲突或需要修改公共框架时，必须明确报告。

### EventSystem 的架构定位

1. **EventSystem 属于框架 System。** 负责提供统一的事件订阅、取消订阅、事件发布和事件分发能力，不属于业务 System，也不属于 Manager。
2. 新建 EventSystem 统一采用不可挂载的项目运行级普通 C# 单例，遵循核心职责规范中已经确定的 System 单例约定。已有事件框架继续遵循其稳定实现；存在实际职责或作用域冲突时，按照本节的识别与保护规则报告并提出方案。
3. EventSystem 可以持有自身职责范围内的订阅关系、监听者集合、分发状态及必要的诊断信息，但不得持有其他业务系统的权威状态。
4. EventSystem 不感知具体业务规则，不负责业务用例组织、状态提交、UI 更新、动画、音效或其他订阅者的具体响应行为。
5. **通用事件分发不构成 System 对 Manager 的反向依赖。** EventSystem 可以执行订阅者主动注册的通用监听回调，但不得依赖具体 Manager 类型，不得主动查找 Manager，也不得针对具体 Manager 组织特殊执行逻辑。发布方不得利用通用分发机制变相指定 Manager 完成自身业务的必要步骤。
6. 已有 `EventCenter`、`EventBus` 等具有相同框架职责的稳定类型可以继续沿用原有名称，不强制重命名为 EventSystem。
7. 项目自定义 EventSystem 与 Unity uGUI 自带的 `UnityEngine.EventSystems.EventSystem` 必须明确区分。出现类型名称冲突时，优先遵循项目已有命名空间及类型引用约定，不据此擅自修改普通业务代码的命名空间。

典型命名参考：

| 不推荐的指令式事件 | 推荐的事实式事件 |
|---|---|
| `RefreshInventoryEvent` | `InventoryChangedEvent` |
| `PlayDeathSoundEvent` | `CharacterDiedEvent` |
| `ShowRedDotEvent` | `MissionRewardAvailableEvent` |
| `UpdateMissionProgressEvent` | `MissionProgressChangedEvent` |
| `SavePlayerDataEvent` | `PlayerDataSavedEvent` |

上述名称不是机械替换关系。需要执行具体操作时，应使用明确的业务调用、Request 或 Command；已有稳定事件名称不因本表而自动获得改名授权。

### 事件与直接调用的选择

1. **具有明确业务执行目标、结果依赖或前后顺序要求的操作，优先使用明确的方法调用、Request 或 Command。**
2. EventSystem 用于事实通知及相互独立的职责响应，不作为所有业务操作的统一转发入口。
3. 发布方需要取得其他 System 的执行结果，或者后续业务必须等待某项操作完成时，应由主导 System 显式组织调用及结果处理。需要等待具体表现或局部执行操作时，由该流程的明确所有者在合法依赖范围内组织，不以普通事实事件替代必要的执行契约。
4. 允许业务 System 订阅其他 System 发布的事实事件，并根据自身职责组织独立的后续业务。
5. 不得将具有必要业务前后依赖的多个步骤拆散到普通事件监听者中，使完整业务的正确执行依赖监听者是否存在、注册顺序或执行结果。
6. 普通事实事件允许没有监听者。不得将监听者不存在统一判定为业务执行失败。
7. 查询当前有效业务状态时，应通过所属 System 的公开查询能力获取，不得将事件系统当作权威状态查询中心或通用服务定位器。

职责协作示例：

```text
直接业务调用：
MissionSystem → InventorySystem：明确请求发放奖励并取得实际结果
MissionSystem 按领奖契约组织后续提交，不依赖事件监听者完成必要发放步骤。

独立事实响应：
CombatSystem → EventSystem：发布 EnemyKilledEvent
EventSystem → MissionSystem：通知已经发生的击杀事实
MissionSystem 根据自身职责处理独立的任务进度业务。

不符合规范：
MissionSystem → 发布 GiveRewardEvent
              → 假设 InventorySystem 已经发放奖励
              → 直接将任务标记为领奖成功
```

上述示例不规定具体领奖提交顺序或一致性机制。事件用于降低通知关系的耦合，不用于隐藏必要的业务执行依赖。

### 全局事件与局部事件

1. **全局事件用于跨独立职责边界的事实通知。** 具有明确跨系统、跨场景或跨独立功能通知意义的事件，可以通过项目统一 EventSystem 发布。
2. **局部事件用于明确对象及所有者范围内的协作。** 对象内部交互、View 与 Controller 的通信、局部动画完成、组件状态变化等，可以使用 C# `event`、UnityEvent 或明确的局部回调。 新建明确的 C# 局部事件通知契约时，优先采用 event 而非可任意赋值、覆盖及触发的公共委托字段；已有稳定机制保持不变，具体遵循[类的访问权限与公开接口规范](../Code/AccessControl.md)。
3. 不得将所有局部事件机械迁移到全局 EventSystem。事件作用范围应根据实际职责及生命周期确定，而不是根据监听者数量决定。
4. 全局 EventSystem 的项目运行级作用域，不代表通过它发布的每个事件都具有全项目业务作用域。涉及账号、存档、场景、角色、战斗或其他独立业务实例时，必须明确事件适用范围，避免其他实例错误响应。
5. 局部事件同样不得绕过既有业务规则、权威状态提交边界和 Manager 与 System 的依赖关系。事件响应涉及 UI、交互或附加限制的变更时，仍须遵守UI 变更授权规范及校验与附加限制授权规范。

典型示例：

| 事件 | 推荐归属 |
|---|---|
| 任务完成 | 全局事件 |
| 背包状态变化 | 全局事件 |
| 账号切换 | 全局事件 |
| 场景切换完成 | 全局事件 |
| 商品条目按钮点击 | 局部事件 |
| 卡片拖拽结束 | 局部事件 |
| View 上报交互操作 | 局部事件 |
| 对象内部动画播放完成 | 局部事件 |

上述示例作为默认判断参考，实际使用仍需根据事件的通知范围确定。

### 事件定义、命名及数据约束

#### 事件标识与接口命名

1. 从零设计 EventSystem 时，默认优先采用强类型事件，使事件身份与事件数据契约具有明确的类型边界。
2. 已有项目使用字符串、枚举、EventArg 或其他事件标识及参数机制时，继续沿用其稳定契约，不得擅自迁移。
3. 具有独立数据契约的事件类型，默认采用“业务领域或对象 + 已发生事实 + Event”的命名形式。
4. 不要求每个事件都创建独立数据类、枚举成员、标记接口或配套类型，应根据实际事件契约确定；强类型事件方案也不要求同时增加独立事件标识枚举。

| 用途 | 默认命名 | 示例 |
|---|---|---|
| 事件数据类型 | `XxxEvent` | `MissionCompletedEvent` |
| 事件名称 | 已发生事实 | `MissionCompleted` |
| 事件响应方法 | `HandleXxx` | `HandleMissionCompleted` |
| 订阅方法 | `Subscribe` | `Subscribe` |
| 取消订阅方法 | `Unsubscribe` | `Unsubscribe` |
| 发布方法 | `Publish` | `Publish` |
| 内部分发方法 | `Dispatch` | `Dispatch` |

已有 `AddListener`、`RemoveListener`、`TriggerEvent`、`Broadcast` 等稳定接口继续保留。`OnXxx` 的使用仍遵循 C# 基础命名格式中的既有约定。

#### 事件数据

1. **事件数据默认在创建后保持只读。** 发布方和订阅者不得擅自修改已经发布的事件数据，使不同监听者收到不一致的业务事实。只读要求应覆盖实际传递的数据内容，不仅是引用自身不可重新赋值。
2. 事件参数必须具有明确业务语义，仅包含表达事件事实和必要作用域所需的数据。
3. 事件数据不得暴露能够任意修改权威业务状态的 RuntimeData、集合、状态提交接口或执行委托。
4. 事件数据可以包含明确的业务对象标识、变化前后的数值、只读快照及必要的作用域信息。
5. 时间戳、请求 ID、事件 ID、版本号等信息根据实际需求提供，不强制为所有事件建立统一的附加字段。
6. **区分事件发生时的事实与当前有效状态。** 订阅者需要处理事件当时的变化时，应使用事件数据；需要当前最新状态时，应通过所属 System 查询。不得将查询到的新状态替代已经发生的历史事实。
7. 已有事件框架使用可变参数对象、对象池参数或其他具有特定有效期的数据时，必须遵守其既有所有权和有效期契约。不得擅自修改其他监听者需要的数据，也不得在参数已经失效或回收后继续持有和访问。异步监听者需要跨越原参数有效期使用数据时，应在有效期内提取必要的独立数据或按现有契约转移其所有权。 高频事件分配及对象池参数复用按[性能与内存管理规范](../Runtime/Performance.md)、[对象池规范](../Runtime/ObjectPooling.md)、[资源管理规范](../Runtime/ResourceManagement.md)组织，不为降低 GC 提前回收仍被合法使用的数据或改变事件事实。

例如，`MissionProgressChangedEvent` 可以记录任务标识、原进度 30 和变化后进度 50；若监听者处理时实际任务进度已经变为 60，事件中的 50 仍表示对应变化发生时的事实，System 的公开查询提供当前有效进度。该示例不要求实际项目增加这些字段或独立事件类型。

### 事件发布权限与发布时机

发布权限参考：

| 职责类型 | 全局业务事实事件发布权限 |
|---|---|
| Manager | 允许发布自身管理职责范围内的事实 |
| System | 允许发布自身系统确认成立的事实 |
| Committer | 允许发布自身提交契约内已成立的事实 |
| Controller | 允许发布具有全局通知意义的场景或流程事实 |
| Module | 默认局部事件，存在明确全局通知职责时允许 |
| Processor | 不直接承担业务事实事件发布 |
| Provider | 不承担业务事件发布 |
| Registry | 不承担所属业务事实发布 |
| DataStorage | 不承担领域业务事件发布 |
| Logic | 禁止 |
| Resolver | 禁止 |
| Rule / Rules / RuleSet / Calculator / Evaluator | 禁止 |
| Matcher / Selector / Mapper / Normalizer | 禁止 |
| Operation / Formula / Algorithm | 禁止 |
| Utility | 不承担业务事件发布 |

底层框架可以拥有自身明确的技术通知契约，但不得借此绕过业务事件的发布权限、纯处理约束或既有依赖边界。

1. **事件发布权属于能够确认对应事实成立的职责承担者。** EventSystem 发布入口的技术可访问性不自动赋予调用方任意业务事实的发布权限。
2. System 可以直接发布自身已经确认的业务事实，也可以明确委托 Committer 在状态提交过程中发布相关事件。
3. 同一个业务事实应具有明确的发布负责人，不得由 System、Committer 或其他职责类型无意重复发布同一次事实；不同语义、不同成立条件的事实应分别按照各自契约表达。
4. 不得将纯业务计算成功、尚未提交的业务结果、未执行的操作或尚未确认的服务端结果描述为已经生效的事实。
5. 事件发布时机按照具体业务事实成立的条件确定，不统一要求所有事件都在持久化成功后发布，也不统一延迟到全部前台展示流程结束后发布。
6. 事件发布完成、状态提交完成、业务用例完成及前台展示完成，应按照各自契约分别表达，不得相互混淆。事件发布可以发生在 Committer 的提交过程内，或在 System 已确认相应事实成立之后，不强制等待全部 CommitResult 返回。

事件发布方示例：

| 事件 | 推荐发布方 |
|---|---|
| `MissionProgressChangedEvent` | MissionProgressCommitter 或直接组织提交的 MissionSystem |
| `InventoryChangedEvent` | 对应 InventoryCommitter 或 InventorySystem |
| `MissionRewardClaimedEvent` | 能够确认完整领奖事实成立的 System 或其明确委托的提交实现 |
| `BattleStartedEvent` | 负责确认战斗开始的 CombatSystem |
| `SceneLoadStartedEvent` / `SceneLoadCompletedEvent` | 负责确认相应事实的 SceneFlowManager |
| `PanelOpenedEvent` | 实际负责确认面板打开的 UIManager 或相应职责所有者 |

### 事件订阅与生命周期管理

1. **订阅关系必须具有明确所有者。** 谁建立订阅关系，谁负责按照约定的有效范围管理和解除订阅；由装配入口代为建立时，必须明确实际清理责任。
2. 订阅关系的生命周期应与订阅者的实际职责、对象生命周期及业务状态有效范围一致，不得因 EventSystem 跨场景存续而使所有监听关系永久有效。
3. Unity 组件可以根据实际需求，在 `OnEnable`、`OnDisable`、初始化、销毁、页面打开与关闭、对象池租用与回收等明确的生命周期入口管理订阅。
4. 不强制所有 Unity 组件采用 `OnEnable` 注册、`OnDisable` 解除的方式。订阅有效期应以实际职责为依据，不得擅自改变页面隐藏或组件停用后的既有响应行为。
5. 普通 C# 实例的订阅关系应由明确的实例所有者管理，不得依赖对象被垃圾回收后自动解除仍被事件系统持有的订阅。
6. 应防止无意重复建立相同订阅关系。重复订阅的拒绝、覆盖、允许或反馈方式遵循项目现有契约；新建框架默认避免同一有效订阅关系被无意重复注册，并提供明确反馈。确有多个独立订阅关系时，按照实际契约分别管理。
7. 取消订阅时只解除自身拥有的订阅关系，不得随意清空其他对象的监听关系或整个事件系统。
8. 账号、存档、场景及对象切换时，必须根据订阅作用域正确处理旧订阅，避免旧业务实例继续响应不属于自身的事件。
9. 取消订阅不代表已经启动的异步任务被自动取消。监听者仍须按照异步生命周期规范管理自身启动的异步操作。
10. 新建框架中的普通事实事件默认不提供历史重放；已有框架具备重放能力时按其明确契约使用。后续才建立订阅的对象，需要当前状态时，应从明确的状态来源进行初始化，不得假设此前发生的事件会自动重新分发。

| 订阅者 | 推荐订阅范围 |
|---|---|
| Manager | 自身有效生命周期或业务会话范围 |
| System | 所属系统及业务状态有效范围 |
| Controller | 所属场景或实际流程范围 |
| View | 页面需要接收通知的有效期间 |
| Module | 自身能力有效期间 |
| 对象池对象 | 每次租用或激活期间 |
| 普通 C# 实例 | 实例所有者规定的有效范围 |

Logic、Resolver、具体职责能力及基础处理实现层不作为独立的全局业务事件监听者，不承担事件驱动的业务调度。需要处理事件所表达的数据时，由具有相应业务职责的上层接收事件并显式提供处理输入。纯处理类型不得通过局部事件、回调或其他方式间接执行外部业务副作用；本条不限制符合纯处理契约的数据传递或计算委托。

### 同步与异步事件分发

1. **已有事件系统优先沿用现有分发机制。** 不得擅自改变同步、异步、延迟、队列或特定更新阶段的分发语义。
2. 从零设计 EventSystem 时，默认采用同步事件分发。普通同步 Publish 在当前分发契约所要求的同步监听方法处理结束后返回；返回本身不证明所有监听者均成功。
3. 允许同步监听方法根据自身职责启动独立异步操作，但同步事件分发结束不代表监听者启动的异步操作已经结束。
4. 异步监听者必须明确任务所有者、取消时机、异常处理及完成边界。Unity 项目的具体异步技术实现遵循[Unity 异步与 UniTask 规范](../Runtime/Async.md)；其他引擎遵循对应技术契约。
5. 不得默认使用 `async void` 规避异步任务管理，不得产生无人观察的异步异常。
6. 存在等待全部异步监听者完成的明确需求时，可以按照已确认方案建立独立的异步分发契约，并明确等待范围、执行方式、失败处理及取消规则。
7. 业务流程必须等待某项具体操作完成时，应优先使用明确的异步业务调用，不得依赖普通事实事件隐式承担等待职责。
8. EventSystem 不默认承担线程切换和 PlayerLoop 调度。涉及 Unity API 的监听者必须按照实际分发线程及更新阶段，在正确的主线程和执行阶段操作 Unity 对象；不得仅凭事件接口名称假定回调一定在主线程执行。 异步监听者启动的新业务须进入所属 System 的正常请求入口，并遵守[异步业务与状态一致性规范](../Runtime/StateConsistency.md)中的实际并发、重入及结果应用边界。

同步分发与异步监听示例（新建框架的默认语义）：

```text
Publish
    → 同步监听 A：启动由其自身管理的异步表现任务
    → 同步监听 B：完成同步响应
    ← Publish 返回

监听 A 启动的异步任务可能仍在执行，
其完成、失败及取消由相应任务所有者负责。
```

### 事件分发顺序、异常与重入

#### 事件分发顺序

1. 普通事实事件的业务正确性不得依赖监听者注册顺序、遍历顺序或未明确保证的优先级。
2. EventSystem 可以按照稳定的注册顺序分发事件，以便运行观察和问题定位，但该顺序不自动成为业务执行契约。
3. 确有明确顺序依赖的业务步骤，由主导 System 或相应流程所有者显式组织。具有专门顺序保证的框架分发机制，按照已确认的契约使用，不得借顺序保证将普通事件变为隐式的必要业务执行链。

#### 监听者异常

1. 已有事件框架的异常传播及分发中断方式应保持原有契约，不得未经确认修改。
2. 从零设计普通事实事件分发机制时，默认隔离单个监听者的异常，使其他相互独立的监听者能够继续接收通知。
3. 异常隔离不得等同于吞掉错误。应按照既有日志规范保留必要的事件类型、监听者、失败原因及异常信息，避免重复记录同一错误。 由实际分发边界承担到达该边界的未处理监听者异常的诊断责任；监听者已处理并记录的错误不重复输出，具体遵循[Unity 日志与异常处理规范](../Runtime/Logging.md)。
4. 监听者异常不得直接推导为已经成立的业务事实无效，也不得由 EventSystem 自动撤销已经提交的业务状态。
5. 事件分发结果与业务提交结果应分别表达。部分监听者失败时，不得将实际分发情况虚假报告为全部成功；已有接口不提供逐监听者结果时，不得据其正常返回推断全部监听者成功，也不据此擅自修改公共返回类型。
6. 监听者启动的异步操作发生异常时，由对应任务所有者或明确的异步分发边界负责处理，不能假设同步分发阶段的异常捕获能够覆盖后续异步异常。

#### 事件重入与监听关系变化

1. 允许订阅者在处理事件过程中，根据自身职责发布新的已成立事实事件，具体嵌套行为遵循框架实际分发契约。
2. 不得形成缺少明确结束条件的事件循环、重复业务提交或无限递归分发。
3. 同步事件嵌套可能使内部事件先于外部事件剩余监听者完成。不得在不了解现有分发契约的情况下，假设所有事件都按全局先进先出顺序处理。
4. 分发期间发生订阅、取消订阅或监听对象失效时，必须遵循明确的监听关系生效契约，避免集合遍历异常和错误调用。
5. **新建 EventSystem 默认采用本轮分发的监听者快照，并明确订阅变化的生效时机。** 每轮分发开始时确定本轮待处理的订阅关系；分发期间新增的订阅不参与当前轮次，但如果在后续嵌套分发开始前已经建立，可以参与该嵌套分发。分发期间取消订阅应立即使对应订阅关系失效：尚未开始执行的监听回调在当前轮次及后续分发中均跳过；已经开始执行的回调不能通过取消订阅强行中断。取消后重新订阅应形成新的订阅关系，不重新激活旧快照中的订阅项。实现应在执行每个回调前确认该订阅关系仍有效，并避免集合遍历异常、已失效对象调用及重复执行。低分配监听快照实现须保留上述分发及重入语义，不能将共享可变工作集合无条件用于不同分发过程。
6. 不得为了防止潜在事件循环而擅自增加全局事件队列、自动去重、事件合并、重入锁、触发次数限制或静默丢弃策略。 事件系统不承担通用业务并发控制；业务请求与事件回调之间的循环等待及状态保护问题，按[异步业务与状态一致性规范](../Runtime/StateConsistency.md)组织。

事件链示例：

```text
正常事件链：
EnemyKilledEvent
    → MissionSystem：按职责处理任务进度
    → MissionProgressChangedEvent
    → RedDotManager：按自身职责刷新红点

错误事件循环：
InventoryChangedEvent
    → MissionSystem
    → MissionProgressChangedEvent
    → InventorySystem
    → InventoryChangedEvent
    → 无明确结束条件地继续触发相同业务
```

### EventSystem 内部职责拆分

1. 新建或经确认重构 EventSystem 时，优先按照明确的职责边界组织统一事件入口、订阅关系维护、事件分发及订阅记录等内部能力。
2. 具有明确职责语义和稳定架构边界的内部类型，可以提前独立建立，不要求等到 EventSystem 内部代码复杂后才进行拆分。
3. EventSystem 可以将具体订阅管理和分发操作全部委托给下属职责类型，自身负责统一框架入口及能力组织。
4. 下属类型不自动继承 EventSystem 的项目运行级单例约束，应按照实际所有权、依赖及生命周期确定实例方式。
5. 既有事件系统内部结构保持稳定，不得仅为了符合推荐职责结构而擅自拆分、合并或重构。

推荐职责结构：

```text
EventSystem：统一框架入口，项目运行级普通 C# 单例
    ├─ EventSubscriptionRegistry：订阅关系维护及确定性查询
    ├─ EventDispatcher：按契约执行事件分发及监听回调
    └─ EventSubscription：单项订阅记录的身份及必要信息
```

上述结构用于说明职责归属，不代表三个内部类型必须是平行的直接依赖。EventSubscription 可以由 EventSubscriptionRegistry 按实际所有权管理；其余依赖及装配方式按明确的框架契约确定。上述类型属于推荐框架结构，不要求所有项目全部创建，也不将 Dispatcher 确立为通用职责后缀。

### 事件可视化与调试

1. EventSystem 可以按照实际开发和调试需求提供只读的订阅关系、事件发布及分发状态观察能力。
2. 可视化需求不得成为将 EventSystem 改为 EventManager、继承 MonoBehaviour 或改变其框架系统职责的理由。
3. 可以通过独立的 EditorWindow、Odin 调试组件或项目已有的调试管理能力观察 EventSystem 的运行状态。
4. 调试工具可以主动读取 EventSystem 提供的诊断信息，EventSystem 不得反向依赖具体调试 Manager 或 Unity 可视化组件。
5. 事件历史、发布计数、监听者异常记录、分发耗时等诊断功能应按实际需求引入，明确启用范围、记录容量及清理时机。
6. 调试功能不得默认无限制保存事件数据、监听者对象或高频分发记录，不得改变正常事件的运行语义。
7. 新增可视化调试能力仍属于公共基础能力或相关工程功能的修改，必须按照既有授权规范取得确认。
