# 技术实现方案设计与评估规范

## 规范定位与适用范围

定义软件设计原则、设计模式、算法、数据结构、技术研究、选型与方案评估。

本规范是对应专业事项的规则主定义文档。规则适用范围、约束性质、优先关系及例外统一遵循 [规则优先级与冲突处理规范](../Governance/RulePriority.md)；项目修改、读取、实施及交付遵循 [AI 修改与交付规范](../Governance/AgentWorkflow.md)。

本节规定 Agent 在技术实现方案设计与评估阶段如何主动识别、研究、比较和选择实现方式。默认采用架构先行型设计、职责命名优先、组合优先与合理继承、主动外部技术研究以及主动方案对比的设计倾向。技术设计解决具体功能如何实现得更加合理的问题；架构设计确定职责、依赖、归属和状态边界；具体修改方案负责将推荐技术方案落实到当前项目。三者共同遵循[AI 修改与交付规范](../Governance/AgentWorkflow.md)的七阶段开发流程，不新增独立的审批或实施阶段。

## 适用范围与基本原则

1. **主动进行技术设计。** 在项目调查后、确定具体修改方案前，应根据实际任务考虑适用的设计模式、软件设计原则、算法、数据结构、抽象方式、执行机制、原生能力、已有实现及外部成熟方案。不得仅以能够实现功能、快速生成代码或减少代码量作为技术设计目标。
2. **延续架构先行原则。** 优先建立具有明确语义、稳定契约及独立职责的技术设计边界，积极采用具有实际设计价值的设计模式。不能仅因当前实现简单、调用者较少、尚无多个实现或实际复用而否定合理的设计。
3. **技术设计必须服从已经确认的职责及业务契约。** 保持 Manager 与 System 的单向依赖、单例作用域、纯处理层的显式输入输出、权威状态所有权、状态提交、事件、配置、资源及表现等既有边界；不得以技术先进性、性能或设计模式为由擅自改变这些约束。
4. **技术设计以真实项目证据为依据。** 用户明确要求、实际运行条件、已有稳定框架及对应专门规范应共同作为设计依据。缺少适用实现时，主动评估新的实现方式；发现真实技术或架构冲突时，应说明具体原因及候选方案，不自行突破原有规则。 有效规则、项目专用约定、已有技术契约和用户决策的适用关系及真实冲突，统一遵循[规则优先级与冲突处理规范](../Governance/RulePriority.md)。
5. 设计模式、抽象、算法、数据结构及技术选型均应具有明确价值，不为满足模式形式、配齐类型、追求更多抽象或假设性需求而新增运行机制。提前建立稳定边界不等于提前实现未确认的功能。
6. 本节适用于新建功能、系统设计、公共框架设计、问题修复及经确认的技术重构。已有稳定实现优先复用和保护，发现缺陷或更优方案可以主动提出建议，不构成主动重构授权。按任务规模、实际影响及技术不确定性调整设计深度，简单明确的修改不要求机械展开全部设计维度。
7. 技术设计及研究属于实施前分析工作，相关项目修改、源码引入、依赖安装、外部操作和专项变更仍须按原有授权规则执行。技术分析、静态审查及用户手动验证的边界不因本节而改变。

## 技术设计目标及评估优先级

1. **先满足硬性约束，再评估技术设计质量。** 已确定的业务规则、架构职责、合法依赖、数据所有权、真实引擎及平台能力、项目明确的性能预算和使用授权，均是方案成立的前置条件。不能满足这些条件的方案不得直接作为现有架构下的可实施推荐方案；确有调整价值时，作为独立变更提案说明并确认。 先按[规则优先级与冲突处理规范](../Governance/RulePriority.md)核对相关约束的真实适用范围及有效决策，不将偏好、示例、默认覆盖或尚未批准的例外视为已满足硬性条件。
2. 对满足硬性约束的候选方案，默认结合以下设计目标进行评估。表中顺序是一般设计关注顺序，不是所有项目固定的权重或优先级裁决公式。

| 设计目标 | 主要评估内容 |
|---|---|
| 功能正确性 | 是否准确满足已确认需求、输入输出、结果及行为契约 |
| 架构一致性 | 职责归属、依赖方向、稳定边界及项目已有框架 |
| 技术实现合理性 | 设计模式、算法、数据结构、抽象及执行机制是否适合实际问题 |
| 扩展性与维护性 | 独立变化方向、实现替换、修改影响范围、职责可定位性及阅读维护成本 |
| 运行性能 | 执行频率、时间及空间复杂度、分配、资源和实际平台成本 |
| 实现经济性 | 开发、接入、装配、迁移及长期维护成本，是否存在无实际价值的复杂度 |

3. **职责语义及长期架构价值优先于机械减少代码。** 不以文件、类型、接口、代码行数或调用层级的多少直接判定方案优劣；也不以使用更多模式或抽象作为设计质量的证明。应分别评估代码组织、实际依赖复杂度及真实运行成本。
4. AI 辅助开发可以降低部分编码、注释和多文件修改成本，但不消除错误架构决策、复杂装配、运行开销、长期维护及迁移成本。应将具有真实职责价值的细粒度设计与没有明确收益的额外复杂度区分开。
5. 根据当前项目及任务确定评估重点。例如高频战斗计算重点关注正确性、执行成本及规则扩展，任务系统重点关注状态一致性和扩展边界，公共资源框架重点关注生命周期、兼容性和可靠性。明确的性能预算仍为硬性约束，不被一般维护性偏好覆盖。

## 软件设计原则

1. **主动考虑成熟的软件设计原则。** SOLID、高内聚低耦合、关注点分离、信息隐藏、契约式设计、组合优于继承等用于指导技术设计和判断实际职责，不是要求每个类型配齐接口、基类、派生类或中间层的固定结构。

| SOLID 原则 | 在本项目职责体系中的应用 |
|---|---|
| SRP（单一职责原则） | 围绕明确职责及主要变化原因组织类型，例如业务用例、纯计算和状态提交分别归属 |
| OCP（开闭原则） | 通过具有实际价值的稳定能力契约和扩展边界，减少新增独立实现时对已有稳定逻辑的修改 |
| LSP（里氏替换原则） | 实现或派生类型应满足共同的行为契约，不能仅凭相同签名或继承关系认定可替换 |
| ISP（接口隔离原则） | 按实际调用能力表达接口，不让调用方依赖与其职责无关的能力 |
| DIP（依赖倒置原则） | 需要隔离不稳定实现时，使合法协作方依赖稳定抽象，具体实现按契约装配；不改变既有架构依赖方向 |

2. 依赖倒置不等于必须使用 Interface、依赖注入容器或服务定位器。已有 System 单例公开入口、明确的普通类型协作及显式参数传递均按实际职责正常使用。Processor 通过明确提交契约调用 Committer 等既有规则保持不变。
3. **高内聚、低耦合及关注点分离。** 将具有相同实际职责、共同变化原因的能力合理组织在所属范围内，将独立变化的职责、技术实现及业务状态明确隔离。不能仅凭调用关系、相似代码或目录归属认定不同职责应合并。
4. **DRY（避免重复）关注相同语义及规则的重复实现。** 相同业务规则应具有明确所有者，不在多个业务或表现层重复裁决。同样的公式或代码片段可能具有不同业务含义及变化方向，不因当前写法相同就强制抽象成一个通用类型；确有独立共享技术语义时可提取对应能力。例如角色经验成长公式和敌人生命成长公式当前可能采用相同计算表达，但仍可以独立维护其设计语义。
5. **KISS（保持简单）在已确定职责边界内应用。** 优先采用清晰、可理解、无非必要复杂度的实现，不以简化为由合并或绕过稳定的 System、Logic、Calculator、Formula、Committer 等职责类型。具有明确价值的细粒度委托层仍可保留。
6. **YAGNI（不提前实现尚未需要的功能）限制无依据的功能和运行机制，而不否定稳定架构先行。** 已经明确的职责、能力契约及独立变化方向可以提前建立边界，不为未来假设性场景实现额外策略、队列、缓存、重试、状态机或其他未经确认的功能。
7. 信息隐藏、最少知识原则及契约式设计应服务于清晰的公开能力和合法依赖。调用方不应依赖无关内部结构、可变权威数据及具体存储实现；输入、输出、真实前置条件、行为、副作用和生命周期按实际契约表达。不得以契约式设计为由擅自增加校验、限制、异常或运行时调用者检查。
8. 各设计原则是相互协作的设计依据，不机械执行单个原则而破坏其他已经确定的职责、性能、资源及业务约束。存在取舍时应说明实际问题、采用方式及理由。

## 设计模式主动识别与选型

1. **采用架构先行型设计模式引入策略。** Agent 必须主动识别适用的成熟设计模式，积极考虑能够改善职责边界、实现替换、对象创建、行为扩展、技术隔离及长期维护性的方案。不将设计模式仅作为代码已经复杂之后的重构手段。
2. 设计模式应根据实际设计问题、稳定能力契约、独立变化方向和引入成本选择，不为套用模式机械建立全部参与类型，也不将模式名称当作实际技术价值的证明。多个模式具有明确协作依据时，可以合理组合使用。
3. 以下为常见 GoF 设计模式的选型参考。模式应用应结合项目实际职责、运行条件和已有框架；示例不代表必须采用相应模式、创建对应类型或新增业务机制。

| 创建型模式 | 主要设计问题 | 游戏开发应用参考 |
|---|---|---|
| Singleton（单例） | 在明确作用域内组织唯一有效实例 | 已确定的 Manager、System、Controller 单例机制 |
| Factory Method（工厂方法） | 通过明确创建契约隔离具体创建实现 | 敌人或道具的创建扩展 |
| Abstract Factory（抽象工厂） | 创建具有配套关系的对象族 | 同类生态资源对象族的创建 |
| Builder（建造者） | 分步骤构建复杂对象或数据 | 关卡、技能、对话结构的数据构建 |
| Prototype（原型） | 根据已有原型创建对象 | Prefab 实例化、模板对象复制等原型式创建思路 |

| 结构型模式 | 主要设计问题 | 游戏开发应用参考 |
|---|---|---|
| Adapter（适配器） | 适配不同接口契约 | 第三方输入、存储、资源访问适配 |
| Bridge（桥接） | 隔离可以独立变化的抽象与实现 | 武器能力与对应执行或表现实现的独立变化 |
| Composite（组合） | 统一组织树形对象及递归组合 | 红点树、任务条件树 |
| Decorator（装饰器） | 在保持能力契约的前提下组合附加行为 | 已确认的能力修饰、属性处理或技术诊断 |
| Facade（外观） | 提供对内部复杂能力的统一入口 | System 或已有框架公开能力 |
| Flyweight（享元） | 共享无需独立变化的内部数据 | 多个敌人共享设计配置，独立维护运行时状态 |
| Proxy（代理） | 隔离或控制对目标能力的访问 | 具有明确契约的远端资源访问、延迟加载 |

| 行为型模式 | 主要设计问题 | 游戏开发应用参考 |
|---|---|---|
| Strategy（策略） | 隔离可替换的处理实现 | 目标选择、伤害计算、寻路算法 |
| State（状态） | 组织对象不同状态下的行为 | 角色状态、敌人 AI |
| Observer（观察者） | 解耦事实通知及独立响应 | EventSystem、局部事件 |
| Command（命令） | 将明确的执行指令表达为对象 | 回合指令、已确认的技能指令处理 |
| Chain of Responsibility（责任链） | 按确定契约将请求交由一系列处理者 | 输入处理及具有明确处理顺序的规则或请求 |
| Template Method（模板方法） | 定义稳定流程骨架及合法继承扩展步骤 | 具有相同执行骨架的技术实现 |
| Iterator（迭代器） | 通过明确契约遍历集合或对象结构 | 地图节点及业务集合遍历 |
| Mediator（中介者） | 组织多个参与者之间的协调关系 | 具有明确场景或业务归属的协调流程 |
| Memento（备忘录） | 保存并按契约恢复对象状态 | 编辑器撤销、已确认的回溯玩法 |
| Visitor（访问者） | 将操作与稳定对象结构的类型分派分离 | 节点结构分析及导出 |
| Interpreter（解释器） | 解释具有明确语法及语义的规则表达 | 已确认的条件表达式或技能规则语言 |

4. **不局限于 GoF 模式。** 对象池、有限状态机、行为树、组件化、数据驱动、空间分区等游戏开发常见技术模式及设计机制，也应根据实际问题主动考虑。已有 EventSystem、对象池、单例、配置、资源、异步及 UI 分层等专门设计约束继续生效。
5. 区分改善代码结构的模式与可能改变运行行为的机制。策略契约、工厂创建边界、外观入口、适配边界等可以按稳定职责设计；状态转换、命令调度、事件传播、责任链中止、代理延迟加载、装饰器附加行为、备忘录恢复及对象池复用等，应按实际需要明确行为及生命周期，不自动取得新增机制的授权。
6. 使用 Command 不代表需要命令队列、历史或撤销；使用 Observer 不代表所有必要业务步骤改为事件；使用 Proxy 不代表自动加载、缓存或访问限制；使用 State 不代表可以自行增加状态或转换条件。其他模式同样不自动带入其可能使用的运行机制，具体行为仍遵守对应专项规范。
7. 项目已具有适用模式、框架或语言原生能力时优先复用，不机械重复实现。例如 Unity Prefab 的原型式创建、现有集合迭代契约及项目统一单例机制，不要求另行实现一套同名模式。重要模式选型须说明实际问题、参与类型、职责分工、引入依据、代价及适用条件。

## 设计模式与现有架构协作

1. **职责命名优先，设计模式辅助表达。** 设计模式描述类型之间的实现结构及协作关系，职责命名表达类型实际承担的业务或技术职责。采用模式不自动改变类型名称、所属层级、访问权限、依赖方向或目录归属。
2. 已有职责语义能够准确表达类型时，优先使用代码命名规范确立的业务对象名称及职责后缀。不因使用 Strategy、Facade、Mediator 等模式而机械采用模式名作为类型后缀，也不为表示模式角色而新增独立职责层。

| 设计模式 | 可以承担相应模式角色的既有职责类型 |
|---|---|
| Strategy | Selector、Calculator、Evaluator、Algorithm 等具有独立处理契约的类型 |
| Factory Method / Abstract Factory | 具有相应创建职责及扩展契约的 Factory |
| Adapter | Adapter 或符合真实适配职责的已有类型 |
| Observer | EventSystem、Event、合法订阅者及局部通知契约 |
| Composite | RuleSet、树形业务对象等具有组合语义的类型 |
| Facade | System 或其他明确统一能力入口 |
| Command | Command、明确的 Request 及工作单元处理协作 |
| State | State 与实际状态所有者及行为处理实现 |
| Template Method / Bridge | 按实际公共流程、扩展契约及独立能力职责命名 |
| Mediator | Controller 或具有明确合法协调职责的流程组织者 |
| Flyweight / Memento | 具有明确共享数据或状态保存恢复语义的对象和数据类型 |

3. 上述为可能的应用关系，不是一一对应的固定命名。普通 Factory 不一定采用 GoF 工厂方法；System 的统一入口不一定实现外观模式；Snapshot 表示只读快照，不自动具有备忘录模式的恢复能力。具体业务对象、Config、Command、State、Factory、Adapter 等继续按其既有定义命名。
4. **允许有依据地扩展职责命名体系。** 某个模式参与类型确实具有独立职责，而已有职责名称无法准确表达时，Agent 可以提出新的职责名称及后缀。应说明职责定义、适用边界、与现有类型的区别、依赖方向、实例方式、访问范围和文件目录归属，经用户确认后采用；新增通用职责后缀须经用户确认后纳入命名及目录规范。
5. Builder、Decorator、Proxy、Visitor、Iterator 等可以作为未来独立职责命名的候选，而不是本节直接新增的通用职责后缀。Builder 侧重复杂对象的分步骤构建；Decorator 侧重在稳定契约外组合附加行为；Proxy 侧重目标访问的间接控制；Visitor 侧重对象结构上的独立访问操作；Iterator 侧重明确的遍历契约。实际采用时须判断既有命名是否已能准确表达对应职责。
6. **不默认建立以设计模式分类的平行目录体系。** 采用策略模式的 Selector 仍归入实际所有者的 Selector 职责目录，不自动建立全局 Strategies、Decorators、Proxies 等目录。新增独立职责目录与类型后缀应共同说明并确认；已有稳定框架和第三方代码保留其真实命名与目录契约。
7. 重要模式的采用理由、参与类型及模式角色应在修改前技术方案中明确，并按[代码注释规范](../Code/Comments.md)在合适的源码位置保留必要的中文设计说明，在最终交付中说明实际采用情况。不得仅为标识设计模式增加 Attribute、空接口、运行时标记或无独立职责的类型，也不为套用模式重命名已有稳定实现。

策略模式与职责命名协作示例：

```text
SkillSystem：组织技能业务用例
    → SkillCastLogic：组织纯技能处理流程
        → SkillTargetResolver：组织目标解析
            → ISkillTargetSelector：明确的目标选择能力契约
                ├─ NearestTargetSelector：最近目标选择
                ├─ LowestHealthTargetSelector：最低生命值目标选择
                └─ RandomTargetSelector：随机目标选择
```

假设上述选择方式均已明确，Selector 的实际处理职责仍然属于纯处理层，模式契约和策略装配由合法所有者按已确认方案组织。Resolver 接收显式解析输入及已经明确装配或选定的合法能力；随机来源按既有纯处理规范显式提供，不自行访问全局配置、状态或随机数。逻辑结果返回 System，由合法提交实现落实状态。示例不要求为此新增固定调用链、反射扫描、策略注册中心或配置驱动机制。

## 设计模式与架构先行

1. **允许提前建立具有稳定价值的模式边界。** 不以当前代码量、复杂度、具体实现数量、调用方数量或实际复用次数作为采用设计模式的必要条件。存在明确的稳定能力契约、独立变化方向、职责隔离、技术隔离、实现替换价值或降低修改影响范围的设计依据时，积极考虑相应模式。
2. 当前只有一种处理方式，也可以先建立合法的策略契约；当前只有一个具体派生类型，也可以建立具有明确公共职责和扩展契约的基类；只有一个调用方时，仍允许建立有独立职责价值的创建、适配及处理边界。具体形式仍遵守接口、实例、继承及各职责类型的专门规范。
3. **提前设计边界，按需实现功能。** 例如当前仅需最近目标选择，可以根据稳定的目标选择能力契约定义 ISkillTargetSelector 并实现 NearestTargetSelector；不需要创建尚未确认的最低生命值选择、随机选择、默认策略、策略注册中心或运行时动态切换机制。
4. 已有适用实现时优先复用；具有稳定边界价值的委托层可以保留，不以当前只转发一次调用为由否定已确定的模式。不得为满足模式形式增加无明确职责的类型、虚构业务需求或为未知功能预先生成占位实现。
5. 采用可替换接口、普通实例或多态时，应明确实际装配、所有权、有效期和运行开销；基础处理实现层继续默认优先静态，具有明确替换、多态、独立执行状态或其他既有适用条件时才采用对应实例形式。稳定的替换契约可以构成设计依据，不要求已经出现多个实现；不得为此引入隐式可变状态。
6. 架构先行属于积极的设计倾向，不是强制使用某一模式。无法说明模式解决的实际设计问题，或者其引入会破坏已确定契约、增加无依据的运行机制时，应选择更适合实际职责的方案，并按需要说明取舍。

## 继承与组合

1. **组合优于继承作为默认设计倾向。** 对独立功能能力、可替换实现、处理策略及多个独立变化维度，优先考虑对象组合、明确能力契约及委托实现。组合是广义能力组织方式，并非要求使用 GoF Composite 模式，也不是新增固定职责层。
2. **保留具有明确语义的继承。** 存在真实稳定的类型关系、公共实现、明确继承扩展契约或已有框架要求时，可以采用继承、抽象基类及模板方法。派生实现应满足共同的行为契约，包括真实前置条件、返回结果、副作用及生命周期，不仅满足类型名称或 Is-a 关系。
3. 仅为复用相似代码、增加某个独立能力或预测未知需求，不机械建立 Base 类型、深层继承结构及大量 virtual 方法。基类应具有明确公共职责和合法扩展语义，不维护另一份重复权威状态。继承深度不规定固定层数，以真实职责、可替换性和维护成本判断。
4. **继承与组合允许共同使用。** 项目已有单例基类、Unity MonoBehaviour、框架规定的基类或其他合法继承关系继续沿用；可以通过继承复用稳定框架，通过组合组织具体业务能力。不因组合优先擅自改变 Manager、System、Controller 的实现约束或原有继承体系。
5. 组合可以使用普通 C# 实例、合法 Unity Module、稳定接口实现、显式数据及委托等不同方式，不机械将独立能力设计成 MonoBehaviour 或 Module。Module 仍须符合所属对象、可独立拆卸或替换、挂载与生命周期等既有职责定义。
6. 组合设计应明确各能力的真实所有者、装配入口、依赖方向、实例范围、状态归属及清理责任。替换实例、运行时重新装配或动态组合按实际已确认契约引入，不因采用组合而默认增加动态切换、自动绑定、场景扫描、服务定位器或 DI 容器。
7. 继承、接口、组合、委托及依赖注入均不得绕过 Manager 与 System 的单向依赖、纯处理边界、状态所有权及实际访问权限。不能通过父类实现、被装配接口、委托或组合对象间接执行不允许的操作。公开和受保护成员的访问范围按[类的访问权限与公开接口规范](../Code/AccessControl.md)确定。
8. **继承和组合均遵循架构先行。** 可以提前建立具有独立能力语义、明确变化方向、稳定类型关系或技术隔离价值的结构，不要求先积累多个实现、子类或调用方。调整已有继承、装配、序列化及公开契约时，仍须按实际影响取得确认。

| 实际需求 | 默认选型倾向 |
|---|---|
| 多种可独立变化的能力 | 优先组合 |
| 能力需要独立拆卸、替换或复用 | 组合及明确能力契约 |
| 多种实现需要按共同契约替换 | Interface、组合或其他适用多态机制 |
| 稳定的类型关系及公共实现 | 合理继承 |
| 公共流程骨架及明确的派生扩展 | 抽象基类、模板方法或组合式策略，按实际契约选择 |
| Unity 组件及既有单例框架 | 遵循引擎技术契约和已有合法继承方式 |
| 相似代码或局部公共算法 | 判断相同语义及独立职责，再选择复用方式 |
| 无独立实例需求的纯基础处理 | 优先静态实现，遵循基础处理实现层规范 |

例如 Character 可以由明确的合法所有者装配移动 Module、设计 Config 和运行时状态；CombatSystem 可以沿用现有 C# 单例继承机制并组合所属 Logic、Calculator、Committer 等能力。示例不确立新的组件、基类、状态持有方式或单例实现。

## 抽象、接口及语言特性选型

1. **抽象应表达稳定契约或隔离真实变化。** 不将抽象等同于 Interface 或继承，也不要求为每个类型配套接口、抽象基类和泛型。具有明确稳定能力或独立职责边界时，即使当前只有一个实现，也可选择适合的抽象形式。
2. 根据实际职责、依赖、对象身份、调用方式、配置和执行生命周期选择普通方法、静态类型、普通实例、接口、抽象类、泛型、委托、事件及数据结构等方式。基础处理层默认静态、Committer 默认普通实例等既有专门约定继续生效。

| 实现形式 | 适用语义参考 |
|---|---|
| 普通方法 | 所属类型内明确的局部实现细节 |
| 静态类及方法 | 无独立实例需求、符合职责约束的基础处理及通用技术能力 |
| 普通实例类 | 独立依赖、执行状态、实例身份、所有权或替换职责 |
| Interface | 稳定能力契约、实现隔离、合法替换及独立验证 |
| 抽象类 | 真实的公共实现及明确继承扩展契约 |
| 泛型 | 具有相同处理语义并适用于不同数据类型的能力 |
| 委托 | 具有明确调用、输入输出及生命周期契约的行为传递 |
| C# event | 明确范围内的事实通知及合法订阅契约 |
| 枚举 | 有限且明确的类型、状态或策略标识 |
| 配置数据 | 参数化及具有明确解释契约的行为组合 |

3. 接口按实际能力及稳定契约引入，遵循接口隔离和现有访问范围规则；不机械为所有 System、普通计算类型或组成对象增加同名接口。通过构造函数、初始化参数、合法装配或明确方法参数传递依赖，可以作为普通设计方式，不默认引入 DI 容器。
4. 泛型用于相同技术或业务处理语义在不同类型间复用，明确类型参数、约束和返回契约，不为当前具体业务任意增加类型参数或建立过宽泛的公共基础框架。涉及 Unity 序列化、Inspector、IL2CPP/AOT、反射及泛型实例化时，按真实版本与目标平台核实技术适用性。
5. 委托和回调可以用于边界明确的策略传递、合法装配和协作，但应明确被调用行为、持有关系、有效期及副作用，不通过委托间接调用禁止依赖的类型。事件通知、纯计算委托及必要业务调用的语义不能混用，继续遵守事件和提交规范。
6. 抽象类、virtual、abstract、protected、sealed、readonly 等根据实际扩展和语言契约选择，遵守既有访问权限规范。无明确继承扩展职责的普通具体实现默认优先 sealed；不得因增加抽象而破坏已有 Unity 序列化、Inspector、单例基类及资源契约。
7. **不机械抽象相似代码。** 应判断是否确实具有共同语义、共同变化方向和稳定共享契约。属于不同领域或不同设计含义的处理，即使当前算法相同，也可保留独立职责；真正通用的算法、操作或技术能力按其实际归属复用。
8. class、struct、readonly struct、in、ref、集合及其他语言特性，根据数据身份、可变性、复制成本、可访问性、分配、序列化和目标平台决定。不默认批量转换数据类型，不以抽象或性能为由暴露可写权威数据、复制多份权威状态或新增隐式全局依赖。

## 算法选型

1. **主动识别具有明确算法性质的问题。** 对寻路、地图生成、排序、采样、搜索、图关系、空间查询、批量计算等需求，应根据实际问题主动考虑成熟算法，而不只采用最先想到的写法。普通明确且低成本的实现仍然可以作为推荐方案。
2. 选型前应明确输入输出、问题规模、调用频率、数据变化方式、结果语义及必要约束，例如最短路径条件、坐标与距离定义、权重和随机分布、顺序、稳定性、确定性、连通性及精度。用户未确认的玩法规则、随机策略、边界限制和失败处理不得自行确定。
3. 存在多个有意义的候选算法时，比较正确性及成立条件、时间与空间复杂度、预处理成本、动态更新成本、典型与最坏情况、实际数据特征和运行开销。近似算法、启发式裁剪及其他改变结果的优化，不自动与原算法等价；需要改变业务结果时按授权规则处理。

| 处理问题 | 候选算法或技术方向 |
|---|---|
| 地图寻路 | BFS（无权或等代价）、Dijkstra（非负权重）、A*（根据启发式及最优性要求选择） |
| 区域连通性 | Flood Fill、BFS、DFS、并查集（适合其支持的连通关系更新方式） |
| 随机地图及生态生成 | 区域生长、Voronoi、噪声及符合需求的组合算法 |
| 资源散布及间距约束 | Poisson Disk Sampling、分层随机采样等 |
| 加权随机选择 | 累计权重遍历、前缀和二分查找、Alias Method 等 |
| 大量对象范围查询 | 线性扫描、空间网格、空间哈希、四叉树等 |
| 技能目标选择 | 线性筛选、评价及空间索引辅助查询 |
| 属性、技能及任务依赖关系 | 图搜索、拓扑排序（依赖关系满足相应条件时）、明确分阶段计算 |

4. 上述候选不构成固定算法选型或业务规则。例如低频且权重经常变化的随机抽取可以采用简单累计权重，而需要大量重复抽样且权重相对稳定时可以评估前缀索引或 Alias Method；应比较预处理及权重更新成本，而非仅比较单次抽样复杂度。
5. **算法实现归入既有职责体系。** 领域规则及流程由合法上层组织，具体算法、数值公式和基础操作按 Algorithm、Formula、Operation 等定义承接。算法所需数据、参数、配置、随机来源及技术依赖按实际契约显式提供，不自行访问上层单例、权威状态或 Unity 外部副作用。
6. 具有复杂执行状态、分步计算、算法替换或平台相关调度需求时，应按实际职责及生命周期设计；纯算法可以维护隔离的局部工作数据，跨帧、线程、Job 调度和资源所有权由合法层组织。不默认引入后台线程、全局缓存、队列、固定处理上限或未经确认的随机行为。
7. 复杂算法或关键技术前提不明确时，应开展必要外部研究，核实成熟实现及适用条件。算法理论收益、静态代码推断和实际运行性能分别表达，遵守[性能与内存管理规范](../Runtime/Performance.md)、[对象池规范](../Runtime/ObjectPooling.md)、[资源管理规范](../Runtime/ResourceManagement.md)；未测量不得宣称已达到实际性能目标。

## 数据结构选型

1. **数据结构根据真实语义和访问模式选择。** 应识别数据身份、顺序、是否允许重复、查询方式、遍历、插入删除、排序、优先级、空间关系、变化频率及数据规模。不能仅凭个人习惯默认使用 List、Dictionary 或其他容器，也不机械替换已有稳定结构。

| 数据结构 | 主要适用语义及选型关注点 |
|---|---|
| Array | 固定长度、连续索引或明确工作缓冲区 |
| List | 有序动态集合、遍历及索引访问 |
| Dictionary | 明确 Key 的确定性映射和查询，考虑索引维护及 Key 契约 |
| HashSet | 成员判断及确实要求集合去重的语义 |
| Queue / Stack | 明确的先进先出 / 后进先出处理顺序 |
| Heap / 优先队列 | 动态优先级查询及处理，明确相同优先级语义 |
| Tree | 明确层级、父子节点及树形关系 |
| Graph | 多节点间关系及图算法处理 |
| BitSet / BitMask | 有限标识范围内的集合或状态表达 |
| Spatial Hash / 空间网格 | 大量空间对象的候选查询及索引更新 |
| Quadtree 等空间树 | 具有空间层级或区域划分需要的查询 |
| Native 容器 | 符合 Native 内存、Job、Burst 和平台契约的计算数据 |

2. **比较完整成本而非单次查询。** 除查询复杂度外，还应考虑构建索引、更新、删除、遍历、扩容、内存占用、数据局部性及真实访问频率。空间索引等结构可以在已明确的大规模高频需求下提前规划；无需为没有实际价值的查询机械维护额外索引。
3. 数据结构改变不得擅自改变业务顺序、随机分布、重复项语义、身份、优先级、有效候选集合或实际结果。索引应与真实权威来源及变化时机一致；不把派生索引、缓存或查询结果变成另一份独立权威状态。
4. 明确集合的所有权、读取及写入权限、快照语义、有效范围及复用方式。临时集合、缓冲区、池化容器及 Native 内存按[性能与内存管理规范](../Runtime/Performance.md)、[对象池规范](../Runtime/ObjectPooling.md)、[资源管理规范](../Runtime/ResourceManagement.md)管理，不为降低分配引入共享可变静态工作数据、无依据的容量上限或静默截断。
5. 数据结构及算法的技术选型不自动授权新增排序、去重、队列、缓存、回收、拒绝或其他运行行为。确有新增行为时须说明必要性及影响并取得确认。

选型简例：对于大量敌人的范围查询，全量遍历单次检查 O(n) 个对象，维护简单；空间网格先取得相交网格的候选对象再进行精确范围判断，其查询成本取决于访问网格数量和候选数量，并有索引维护和内存开销。已知需要大量高频查询时可积极评估空间索引；小规模低频查询可以选择直接遍历。两者均须保留已确认的范围条件、选择顺序、结果完整性及数据一致性。以上为理论及设计分析，不代表 Unity 实测收益或固定性能结论。

## 数据驱动与配置化设计

1. **主动考虑数据驱动设计。** 对技能、道具、装备、Buff、敌人、任务、属性和地图生成等可通过参数化或已定义能力组合表达的业务，应评估使用稳定配置契约及可复用处理能力的价值，不机械为每项配置创建一套独立重复逻辑。
2. 明确哪些变化是设计数值、同一规则的不同数据、处理策略、独立业务行为或运行时状态。配置用于表达已确定的设计内容，运行时数据承载实际状态，所属 System 组织行为及提交；不得将权威状态写回共享设计配置，也不得让通用配置框架接管业务规则。

| 变化方向 | 推荐考虑的实现方式 |
|---|---|
| 数值、持续时间、权重等设计参数变化 | 配置化及明确输入 |
| 相同规则用于不同对象 | 通用处理能力与所属配置组合 |
| 处理方式或算法独立变化 | 策略契约、独立能力或算法实现 |
| 多个已经定义的效果需要组合 | 具有明确执行及组合语义的能力结构 |
| 独立特殊业务行为 | 职责明确的业务实现，不强行塞入通用解释器 |
| 对象随状态产生不同行为 | 合适的状态模式或已确认的状态机 |

3. 配置化、策略模式及代码驱动实现可以共同使用。业务 System 通过合法配置入口取得有效配置，并按已确认的映射及装配契约提供处理能力和显式数据；纯处理层不自行读取配置系统，不借数据驱动引入隐藏的上层依赖或外部副作用。
4. 具体配置载体、维护来源、编辑入口、目录、权威来源、就绪时机及读取方式继续遵循[配置数据管理规范](../Runtime/Configuration.md)，用户指定的位置和形式不因数据驱动方案而改变。参数化不要求所有数据都集中进入 ConfigSystem，也不将普通局部配置和固定程序常量机械配置化。
5. 数据驱动只表达已经确定的配置字段、能力、组合规则及执行契约。不得为追求通用性自动增加配置映射机制、可视化技能编辑器、节点图、规则解释器、脚本语言、反射发现、热更新、策略注册中心或未经确认的默认行为。存在相应需求时按具体方案评估并取得确认。
6. 数据驱动方案应评估配置维护、引用和标识、规则组合、可读性、错误定位、技术兼容性、运行成本及新增内容的实际修改范围。不能仅凭配置项多或代码量少判定方案更优；特殊行为继续允许独立实现。

## 技术研究与开源实现参考

1. **采用主动研究型技术调查。** Agent 在技术设计阶段应主动考虑成熟设计模式、算法、官方技术能力、开源实现及行业工程实践，不仅依靠已有知识或等到实现受阻才进行调查。根据任务性质、真实技术不确定性和研究价值决定外部研究范围，不要求每个简单修改都检索外部资料。
2. 技术研究按以下等级组织。等级表达研究深度和核实要求，不构成新的任务管理机制，也不要求额外审批阶段。

| 研究等级 | 适用场景 | 研究要求 |
|---|---|---|
| 一级：按需研究 | 明确的公式调整、简单查询、普通显示更新、沿用已有稳定框架的常规功能 | 根据实际问题及技术不确定性调查，不机械搜索 |
| 二级：主动研究 | 完整业务系统、技能或装备等复杂功能、地图生成、寻路、敌人 AI、复杂交互及大规模处理 | 主动调查具有实际参考价值的成熟设计及实现，结合当前项目评估 |
| 三级：必须研究或核实 | 新建或替换公共基础框架、明显不确定的复杂算法、陌生或版本敏感 API、第三方依赖选型、关键平台兼容问题、用户明确要求研究 | 核实相关重要技术依据、适用条件及风险；不能核实的前提明确标记，不将其当作已确认事实 |

3. **根据研究问题选择合适的资料来源。** 不规定统一的绝对来源排序；当前项目源码用于确认实际契约，官方文档用于核实真实技术能力，源码和算法原始资料用于分析具体机制，实践及社区资料用于参考工程经验和识别潜在风险。

| 资料来源 | 主要研究用途 |
|---|---|
| 当前项目源码、配置及真实维护契约 | 识别可复用能力、实际接口、架构、版本及项目限制 |
| C#、Unity 和第三方官方文档 | 核实当前版本 API、技术契约、平台及使用条件 |
| 官方源码及公开开源项目源码（如 GitHub） | 研究实际设计模式、算法、数据结构、关键代码及协作机制 |
| 算法论文、数学资料及原始技术资料 | 核实算法原理、正确性依据、复杂度及成立条件 |
| GDC、开发者技术分享及工程案例 | 研究行业实际解决思路和工程权衡 |
| 技术文章及教程 | 获取候选思路，必要时核实原始技术依据 |
| Issue、发布记录及社区讨论 | 调查已知缺陷、版本变化、维护及兼容风险 |
| Agent 已有知识 | 提供候选方案，不代替必要的事实核实 |

4. 研究重要开源实现时，应尽可能查看与实际问题相关的源码、文档、版本、示例及必要 Issue，理解其真实职责和技术机制，不仅根据项目简介、Stars 数量、名称或知名度判断能力及适用性。若仅阅读文档、摘要或部分源码，应如实说明实际阅读范围。
5. **区分研究成熟实现与引入外部依赖。** 应按实际采用方式确定调查深度、许可证核实、维护范围、项目适配及实施授权。

| 使用方式 | 核心语义及实施边界 |
|---|---|
| 设计思想参考 | 借鉴架构、职责、设计模式、数据组织及协作思想，不直接引入外部代码或依赖 |
| 技术实现参考 | 研究算法和实现机制，按当前项目契约设计自己的实现；不能将直接复制或改编源码伪装为独立设计 |
| 部分源码复用 | 明确来源、适用版本或提交、许可证、署名及其他义务、维护和适配范围，取得实施授权 |
| 完整依赖引入 | 将第三方库或插件作为正式项目依赖，评估版本、平台、依赖、许可证、安全、接入及替换成本，取得实施授权 |

6. **外部方案须适配现有架构。** 可以仅吸收适合当前项目的算法、数据结构或设计模式，不照搬与既有职责体系冲突的完整架构。外部 Manager / System、事件、配置、资源、DI、服务定位器、ECS、自动绑定及其他实现方式，不自动取得改变当前项目架构的权限。确有架构调整价值时，应单独说明问题、收益、迁移影响及替代方案并取得确认。
7. 允许符合既有操作权限的只读公开资料搜索、文档阅读及源码调查，不要求为每次普通研究分别申请授权。将外部源码引入项目、安装或升级依赖、执行具有副作用的外部脚本、修改工程、向外部服务传输私有项目数据等，须按[AI 修改与交付规范](../Governance/AgentWorkflow.md)取得对应授权。不得以研究为由主动编译、执行编译错误检查、运行项目、外部示例或测试代码进行验证。
8. 外部资料不可访问、版本不明确或无法确认关键前提时，应如实说明实际调查范围、限制、假设和待核实事项。不得虚构引用、开源项目能力、API、源码阅读经历、版本兼容性、性能数据或研究结果；研究工具及资料数量不作为设计质量的直接指标。
9. 重要研究结果纳入修改前技术方案，说明研究问题、实际查阅的资料及链接、关键发现、项目适配差异、建议采用及不采用的部分，以及未核实的风险。按需要记录版本、源码位置、提交或发布信息，不强制创建独立研究报告文件或规定检索项目数量。

研究示例：设计红点管理能力时，可以调查树形节点、字典索引、Composite、Observer、局部更新及父节点汇总等成熟思路，再按当前架构确定 RedDotManager、节点对象及适用的内部处理能力。上述仅为研究方向示例，不表示已研究某个具体开源项目，也不确立红点数值、节点路径、状态汇总或 UI 绑定规则。

## 原生能力、第三方库与自研选型

1. **先调查已有能力，再评估候选实现。** 项目已有适用且稳定的公共框架、接口或处理能力时优先复用，不机械新增平行框架。存在真实不足时，先评估扩展现有实现，再比较 C# 原生能力、Unity 原生能力、官方扩展包、成熟开源实现、部分源码复用及自研方案的适用性。
2. 不规定自研优先或开源优先的绝对顺序，也不因为现有实现勉强可用就禁止提出更优方案。应按照实际职责、目标平台、实现质量、运行成本、维护及迁移成本确定推荐方式，已有稳定实现的改造仍须取得确认。

| 实现方式 | 主要优势及评估重点 |
|---|---|
| 项目已有能力 | 架构及契约一致，减少重复开发；需判断能否真正满足需求 |
| 扩展现有实现 | 保持稳定入口及已有使用方；评估扩展边界、公共影响和兼容成本 |
| C# 原生能力 | 外部依赖较少；核实实际语言、运行时及目标平台支持 |
| Unity 原生能力 | 与引擎集成；核实版本、资源、生命周期及平台契约 |
| 官方扩展包 | 可复用专项能力；评估包版本、依赖、平台及接入成本 |
| 第三方开源库或插件 | 可复用成熟实现；评估适配、维护、安全、许可证及替换风险 |
| 部分源码复用 | 可以按独立技术边界引入；明确来源、许可证义务、自身维护及后续更新方式 |
| 自研实现 | 按当前职责及业务契约设计；承担实现正确性、验证、优化及长期维护成本 |

3. **正式引入第三方依赖前应核实真实技术条件。** 根据实际用途调查下列相关事项；仅参考设计思想或研究算法时不机械进行完整依赖引入审计。

| 评估维度 | 调查要求 |
|---|---|
| 功能及架构适配 | 解决的实际问题、支持范围及与既有职责体系的兼容性 |
| 实现质量及成熟度 | 关键实现、可核实的文档、真实使用或验证依据及已知限制 |
| 维护情况 | 版本发布、维护活动、问题修复、重要未解决缺陷及未来维护风险 |
| Unity 与平台兼容 | 当前引擎版本、渲染管线（相关时）、目标平台、脚本后端、AOT/IL2CPP 及程序集条件 |
| 依赖及工程影响 | 直接和传递依赖、包版本冲突、项目设置、资源导入和装配影响 |
| 运行性能 | 执行规模、CPU、内存、GC、资源及实际测量条件 |
| 许可证 | 所需的使用、修改、分发和商业发布权限及署名、通知、源码公开等适用义务 |
| 安全与外部行为 | 已知安全风险、安装脚本、网络访问、数据处理及不必要的外部权限 |
| 接入、维护及替换 | API 隔离、适配、版本升级、项目自行维护、替换和数据迁移成本 |

4. 无明确许可证、许可范围不明或无法确认拟采用的版本及源码来源时，不得默认允许复制、修改及商业分发；应报告限制，必要时选择合法替代方案。公开可访问、免费或具有 GitHub 仓库不等于允许任意复用。已有第三方代码的许可证和维护契约仍须保留。
5. 需要隔离第三方接口差异、版本依赖及具体存储或平台实现时，可以通过职责明确的 Adapter、Service 或其他既有合法能力边界组织。不强制为所有原生 API、简单调用或第三方类型建立包装；适配层不承接额外业务规则、隐藏运行机制或绕过既有依赖方向。
6. 技术选型须明确实际采用方式、必要依赖、版本及来源、需要的适配与维护责任、项目及平台影响、未能确认的风险和用户手动验证事项。新增、升级、替换依赖、修改 Packages、asmdef、工程设置或引入外部源码，须按具体方案确认，不默认执行安装、迁移、下载执行脚本或修改插件源码。
7. 已有适用的 UniTask、Odin、事件、配置、资源、对象池及其他框架继续遵守其专门规范；候选库评价不改变已确认的技术默认方案。确需调整这些技术时，应先说明实际问题、候选方案、兼容性及迁移影响，取得具体授权后实施。

## 技术方案对比与评估

1. **采用主动对比型技术决策。** Agent 应主动识别和评估具有实际价值的候选实现，包括现有实现及其扩展、设计模式、抽象方式、算法、数据结构、原生能力、第三方库与自研方案。关键技术决策存在多个合理方案时，应主动展示关键差异、适用条件、优势、缺点及推荐依据，不仅罗列方案让用户自行承担全部技术分析责任。
2. 方案评估默认按设计目标及实际约束识别候选、检查硬性条件、进行多维度质量评估、形成推荐及待验证事项的顺序开展。项目调查与设计可以迭代；具体修改方案、用户确认、代码实施及交付仍属于原七阶段开发流程，不新增审批或写入阶段。
3. **先检查硬性约束。** 按实际需求检查业务正确性、架构职责、单向依赖、权威状态所有权、纯处理边界、技术可行性、目标平台、明确性能预算、授权范围、许可证及安全条件。存在实质冲突或尚未核实的关键前提时，应明确标记，不能把未经确认的架构调整或假设当作已符合要求的默认方案。
4. 对能够满足硬性约束的方案，选择与实际问题相关的质量指标进行评估，不要求所有任务机械填写完整评价表。

| 评估维度 | 主要判断依据 |
|---|---|
| 职责清晰度及架构一致性 | 职责归属、稳定契约、依赖方向及定位修改的便利性 |
| 内聚与耦合 | 共同变化的职责是否集中，独立变化的能力是否隔离，依赖是否可预测 |
| 扩展性 | 已知独立变化方向、增加功能时的实际修改范围及接口稳定性 |
| 可维护性 | 阅读、理解、修改、排查问题及长期维护的成本 |
| 可替换性 | 算法、策略、技术实现及第三方能力能否在稳定契约下替换 |
| 可验证性 | 能否独立理解、静态分析及由用户验证重要行为和异常情况 |
| 运行性能 | 时间和空间复杂度、执行频率、CPU/GPU、内存、GC、帧时间及资源开销 |
| 运行可靠性 | 生命周期、清理、失败结果、异常、重入及状态一致性 |
| 兼容与迁移 | 现有调用方、接口、配置、存档、序列化、资源及目标平台的影响 |
| 实现与维护成本 | 开发、装配、学习、引入依赖及长期维护成本 |

5. **不默认采用统一权重或固定评分体系。** 以定性评估及有依据的定量分析表达关键取舍；确有评价需求时，可以使用评分矩阵，并说明评分、指标和权重依据。不得凭空构造性能收益、评分或量化权重来证明预设方案更优，也不以代码量、文件数量、类型数量、调用层级及当前实现数量直接判定设计质量。
6. 方案比较的深度根据任务复杂度、技术风险和实际价值确定，不强制每次提供两种或三种候选方案，不为满足格式虚构不合理的方案。

| 任务类型 | 默认评估要求 |
|---|---|
| 明确局部修改、公式调整 | 直接说明实现及必要理由，按需调查或比较 |
| 普通功能开发 | 主动评估适用模式及实现，存在有意义的替代方案时展示 |
| 具有独立变化方向的功能 | 比较适合的模式、稳定抽象及职责边界 |
| 完整业务系统 | 对比关键实现方式、架构协作及技术取舍 |
| 公共框架或重要技术调整 | 重点对比已有、扩展及替代方案，说明调用方及长期影响 |
| 算法、数据结构和高风险性能选型 | 比较成立条件、复杂度、运行成本及实际结果语义 |
| 第三方依赖引入 | 评估已有能力、适用自研和外部实现以及相关风险 |
| 用户明确要求比较 | 按用户要求展开有实际依据的方案比较 |

7. **必须给出具有明确依据的推荐方案。** Agent 应说明当前推荐的实现、解决的问题、适用条件、实际取舍、为何不采用其他重要候选、扩展方向及潜在风险。若只有一种满足约束的方案，说明原因即可；关键前提无法确认时，应说明有条件的推荐或暂不能确定最终选择的原因，不虚构确定性。
8. **技术评估必须区分证据性质。** 项目当前事实、官方技术契约、实际外部研究、理论分析、静态推断、用户提供的测量结果及待验证假设，应按真实依据分别表达。理论复杂度改善不等于实际帧时间或 GC 收益，未经测量不得宣称性能提升比例、实测指标或已经达到预算。

| 证据类型 | 表达参考 |
|---|---|
| 已确认的项目事实 | 通过源码或实际配置确认项目已有适用的 EventSystem |
| 官方技术依据 | 对应版本的官方文档明确给出的 API 或平台契约 |
| 外部研究结果 | 实际查阅的源码、文档、论文或工程案例所支持的发现 |
| 理论分析 | 全量线性遍历需要检查 O(n) 个对象 |
| 静态代码分析 | 实际代码中存在重复查询、遍历或分配路径 |
| 设计推断 | 稳定策略契约有望降低新增实现的修改影响 |
| 用户提供的实测 | 明确测量条件下用户提供的 Profiler 等数据 |
| 待验证假设 | 新的索引或缓冲区方案可能降低实际帧时间或 GC Alloc，尚需用户测量 |

9. 重要技术选型、核心设计模式、算法、公共抽象及实际行为机制应在修改前可审查，并纳入具体方案授权。已确认范围内的普通变量、私有方法及不改变原方案和行为契约的局部实现细节，由 Agent 自主完成；关键选型、技术前提、实际行为及公共影响发生变化时，应按[AI 修改与交付规范](../Governance/AgentWorkflow.md)说明差异并取得补充确认。
10. 技术评估可以采用源码审查、文档核实、理论分析、调用关系图、示例代码及用户提供的实际运行数据；不得主动编译、检查编译错误、运行代码、执行自动化测试或性能验证来取得评估结果。未核实的风险和用户手动验证条件应明确说明，不宣称未经验证的结果。

技术方案对比示例：假设技能目标选择已确定支持最近目标、最低生命值目标和随机目标，各选择方式均有明确职责及结果语义。

| 设计方案 | 实现思路 | 主要优势 | 主要代价及适用条件 |
|---|---|---|---|
| A：职责拆分 + 枚举分支 | Resolver 根据已明确的 TargetType 分支调用独立 Selector | 组织直接，装配较少 | 新增选择方式通常需调整分支；适合选择集合稳定的情况 |
| B：职责拆分 + 策略模式 | Resolver 通过 ISkillTargetSelector 使用已选定或装配的具体 Selector | 稳定能力契约、独立实现及替换边界 | 需要明确策略选择和装配；新增策略仍可能需调整装配关系 |
| C：策略模式 + 配置驱动映射 | System 根据明确 SkillConfig 及映射契约提供 Selector | 支持已确认的不同技能配置选择需求 | 增加配置、映射和装配维护成本，须有对应需求及授权 |

若目标选择具有明确独立变化方向，且当前没有通过配置选择策略的需求，可以推荐 B。若已经要求策划通过配置决定各技能的目标选择方式，则应重点评估 C；若分支集合稳定且没有适合的替换边界，则 A 也可以合理采用。上述示例不设定策略注册、反射扫描、配置字段、默认选择方式、选择顺序或随机规则，不代表任何实际性能测量结果。

## 技术债务识别与重构建议

1. **主动识别实际技术债务及优化机会。** 在项目调查和技术设计过程中，Agent 应关注职责冲突、重复规则、过度耦合、无依据的继承层级、状态重复、隐式依赖、实现替换困难、不合理算法及真实运行成本。不能仅凭现有代码未采用某种设计模式、与推荐示例不同或文件较多，就判定存在技术债务。
2. 发现设计问题时应根据实际代码说明问题发生位置、语义、触发条件或变化影响，区分已确认缺陷、静态风险、潜在维护问题及可选改进机会。没有证据的未来假设不作为擅自整改依据。

| 实际问题或设计机会 | 可评估的优化方向 |
|---|---|
| 同一类型分支不断扩展且变化方向独立 | 评估稳定策略契约、独立处理能力及装配方式 |
| 继承层级因独立能力组合不断增长 | 评估组合式能力组织及真实类型关系 |
| System 堆积具有独立语义的计算 | 按职责拆分 Logic、Calculator、Formula、Algorithm 等 |
| 多个模块重复实现同一第三方接口访问 | 评估独立技术能力、Service 或 Adapter |
| 多个类型分别裁决同一权威状态 | 明确状态持有者、读取和提交边界 |
| 高频重复查询或无效遍历 | 比较算法、数据结构及索引维护成本 |
| 必要业务步骤依赖隐式事实事件 | 按所属业务及完成契约评估显式调用方式 |
| 多处实现相同业务规则 | 明确自然规则所有者及合法共享契约 |

3. 重构应以实际改善职责、依赖、技术质量、维护成本或真实运行问题为目标，说明目标、候选方案、预期收益、迁移风险及现有行为保护。不因代码相似、模式名称、风格差异或 AI 编写速度擅自合并、替换、重命名及拆分已有稳定类型。
4. **主动提出优化不等于获得修改权限。** 与当前任务直接相关的设计优化应纳入修改前方案；实施中出现的超范围调整须补充确认。与当前任务无关的技术债务可单独报告，不顺手修复；阻塞当前任务的实际问题按[AI 修改与交付规范](../Governance/AgentWorkflow.md)暂停受影响部分并提出方案。
5. 已有稳定框架、公开接口、序列化、资源、配置、用户及其他 Agent 的修改均须保护。任何重构仍遵守具体授权、目录、命名、访问权限、业务规则、UI 及技术契约，不通过架构整改扩大任务范围。实际性能和运行结果由用户手动验证，不为验证重构主动编译或运行。

## Agent 技术设计检查与交付要求

1. 开发前，Agent 应按任务实际相关范围完成以下设计检查，不要求每次输出全部维度的长篇报告，也不将每项检查变成独立审批步骤：
   - 已确认的业务目标、实际规模、硬性架构及技术约束、目标平台和需要保持的行为契约。
   - 已有框架、接口、代码、真实依赖及可复用能力，明确职责、所有者和独立变化方向。
   - 适用的设计模式、软件设计原则、继承或组合关系、抽象、接口及语言特性，是否具有稳定架构价值。
   - 算法及数据结构的实际语义、成立条件、复杂度、更新成本、分配、数据有效范围及运行成本。
   - 数据驱动、配置化、原生技术能力、第三方库及自研方案的适用性和实际引入影响。
   - 对应研究等级所需的技术依据、实际查阅资料及源码、版本、兼容性、许可证和无法核实的前提。
   - 候选方案的硬性约束、主要质量差异、推荐理由、取舍、扩展方向及待用户验证事项。
   - 是否存在需要专项授权的运行机制、公共能力、接口、资源、UI、校验、项目配置或外部操作，是否保持原有职责及授权边界。
2. **技术设计说明纳入修改前方案。** 按任务规模选择下列相关内容组织表达，重要技术决策应在用户确认前说明。可以使用文字、职责表、调用关系图、目录树及关键代码示例，不强制独立设计文档、固定候选数量或展示全部最终代码。

| 技术设计说明内容 | 具体要求 |
|---|---|
| 01. 设计目标 | 实际技术问题、业务目标、运行条件及约束 |
| 02. 现有实现及研究依据 | 真实项目能力、实际外部资料、版本及重要研究发现；未开展研究时不虚构结果 |
| 03. 候选技术方案 | 具有实际价值的模式、算法、数据结构、抽象和技术实现方式 |
| 04. 方案结构 | 核心职责、参与类型、模式角色、依赖方向、输入输出、数据流及相关装配和生命周期 |
| 05. 方案对比 | 优势、缺点、成立条件、实际成本、影响及风险 |
| 06. 推荐方案 | 明确选择、采用理由、关键取舍及不采用其他重要方案的原因 |
| 07. 扩展性说明 | 已知变化方向、扩展及替换路径、预计修改范围，不承诺实现未经确认的功能 |
| 08. 不采用的机制 | 本次明确不增加的额外业务、框架、依赖、运行机制及相关边界 |
| 09. 待验证事项 | 未核实的技术前提、兼容性、真实运行性能及用户手动验证条件 |

3. 技术设计、候选比较和研究说明可合并到同一份修改方案中，不重复输出已经明确的内容。具体修改清单、实际行为及影响范围、授权及手动操作等仍遵循[AI 修改与交付规范](../Governance/AgentWorkflow.md)，不以技术设计报告替代实施方案或用户确认。
4. 实施及交付时应核对实际代码与已确认技术方案是否一致，说明真正采用的设计模式、算法、数据结构、职责组织、关键实现及其扩展方式；重要设计意图、模式角色、算法、数据结构及实际技术契约按[代码注释规范](../Code/Comments.md)在相关代码中表达，并同步维护受影响的说明。对实际采用的外部资料、源码及依赖说明来源和必要维护契约，对重要局部取舍、原方案差异和未完成部分如实报告。
5. **严格区分静态分析及运行验证。** 仅在允许范围内开展静态文本与代码审查，说明实际核实结果和剩余风险；提供由用户手动执行的编译、功能及性能验证步骤和预期结果。不主动编译、检查编译错误、运行项目、执行自动化测试、外部代码验证或采集运行测量数据，不虚构运行结果。关键技术方案变化及后续修复继续遵守既有授权流程。

默认设计参考：

| 设计维度 | 默认推荐或约束 |
|---|---|
| 技术设计阶段 | 必须主动开展，按任务规模调整深度，不额外增加开发阶段 |
| 设计模式倾向 | 主动识别、积极采用、架构先行、按需实现 |
| 模式引入依据 | 稳定契约、职责边界、独立变化方向、实现隔离及实际设计价值 |
| 当前实现及调用方数量 | 不作为引入稳定模式或抽象边界的必要条件 |
| 软件设计原则 | SOLID、高内聚低耦合、关注点分离、信息隐藏及契约式设计等，按实际问题应用 |
| DRY / KISS / YAGNI | 避免同语义重复及无实际价值的复杂度，不否定稳定架构先行，不提前实现未经确认的功能 |
| 职责命名 | 职责命名优先，设计模式辅助表达 |
| 新增通用职责后缀 | 有明确独立职责且现有名称不适合时提出，确认后纳入规范 |
| 设计模式目录 | 不默认建立独立平行分类体系 |
| 继承与组合 | 组合优先、合理继承、契约驱动、架构先行 |
| 接口、泛型及委托 | 按实际能力、处理语义、依赖和稳定契约选型，不机械配对或引入框架 |
| 基础处理实现 | 默认静态，实例及多态按既有职责条件确定 |
| 算法与数据结构 | 主动评估成熟方案，按实际语义、成立条件、访问模式、运行规模及完整成本选择 |
| 数据驱动 | 主动考虑明确参数化及能力组合需求，保持配置及权威状态边界 |
| 外部技术研究 | 主动研究型，简单任务按需、复杂功能主动、关键技术必须研究或核实 |
| 参考成熟实现 | 鼓励借鉴设计思想及算法，适配已有项目架构 |
| 部分源码及第三方依赖 | 核实来源、许可、兼容、维护及风险，取得具体授权后引入 |
| 原生能力与自研选型 | 先调查已有能力，不规定自研与开源的绝对优先级 |
| 方案评估 | 主动对比、多维评估、明确推荐、用户决策 |
| 硬性约束 | 先满足业务、架构、技术、平台及授权等实际约束 |
| 候选数量及评分 | 按实际价值比较，不固定方案数量或评分权重 |
| 评估证据 | 区分项目事实、技术依据、研究、理论、静态推断、用户实测及待验证假设 |
| 技术债务 | 主动识别并提出建议，不擅自实施重构 |
| 技术方案说明 | 纳入修改前方案，重要选型、结构及取舍可审查 |
| 已确认技术方案变化 | 关键变化须补充确认，授权内正常实现细节自主完成 |
| 验证权限 | Agent 静态分析及审查；实际编译、运行、测试及测量由用户手动完成 |

本节确立技术设计及评估的默认思考方式，不规定每个业务必须采用的具体模式、算法、结构或第三方库。设计模式和技术研究不改变已有架构、命名、目录、访问权限、状态、配置、资源及事件等专门规范，不授权提前实现额外功能、自动安装依赖、增加未经确认的运行机制或重构已有项目。技术选型及具体实施仍按[AI 修改与交付规范](../Governance/AgentWorkflow.md)完成用户确认、代码实施、静态审查及真实交付。
